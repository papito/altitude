# Altitude DAM – Agent Guide

## Do

These apply to every change, server or frontend.

* Avoid documentation drift. When code is added, changed, or removed, update the guide that describes it in the same change: this document for the architecture, design patterns, or anything else future developers should know, [views/AGENTS.md](views/AGENTS.md) for the frontend, [docs/faces.md](../docs/faces.md) for faces, the glossary in the root [CONTEXT.md](../CONTEXT.md) for domain terms, and [docs/READINESS.md](../docs/READINESS.md) when a change closes or opens one of its security, data safety or operational readiness items. Guidance goes in the guide that owns the area, never in the root `AGENTS.md`, which only routes to the guides.
* When adding features or modifying existing behavior, review nearby code comments and docstrings, update them where needed, and warn about discrepancies in comments vs code.
* Always add comments for less than trivial logic, unless the comment is redundant with the code, and it's a simple getter/setter or similar. If you find yourself writing a comment that starts with "This is needed because..." or "This exists to work around...", consider whether the code can be refactored to eliminate the need for the comment.
* Always log on INFO important events and log on DEBUG events that may be useful for debugging. Avoid logging on DEBUG events that are too noisy to be useful (use TRACE if available).
* Extract shared logic into functions when the same or similar logic appears more than once.

### Server-side

* Use test-driven Development with strict red-green-refactor cycle using integration tests. Do not trigger TDD for documentation-only, configuration-only changes, or front-end-facing code.
* Write the minimal amount of code that preserves clarity, readability, and maintainability. "Minimal" does NOT mean that you should leave dead or redundant code after changes and refactoring.
* DO NOT add new migrations or bump the schema version: see **Schema migrations**.

### Tests

* Every test opens with a Scaladoc comment, the first thing in its body, in this format, with these section names in this order and a blank ` *` line after each name and between sections:

  ```scala
  test("Folder tree JSON carries recursive asset counts") {

    /**
     * Setup:
     *
     * A logged-in user's repository with folder1 and its child folder1_1: two imported assets in folder1_1, one in folder1, and
     * one triaged asset outside any folder.
     *
     * Mocks:
     * External service is mocked to avoid outside HTTP calls
     * 
     * Assertions:
     *
     * The folder tree API nests folder1_1 under folder1 under the root, and gives each folder its number of children and an asset
     * count that includes the assets of every folder below it.
     *
     * Edge cases:
     *
     * The triaged asset is counted nowhere, not even in the root.
     */
  ```
  
The Mocks and Edge Cases should be added only when applicable and otherwise are optional.

* `Setup:` is the state the test starts from, and `Assertions:` the behavior it proves; both are required. `Edge cases:` is the boundary or exclusion the test also proves, and is left out when there is none. There are no other sections.
* Write the sections as plain sentences about behavior, not a retelling of the code line by line. A `//` comment inside the body still explains one specific line.
* When a test changes, its comment changes with it.

## Architecture Overview

Altitude is a Scala 3 application built with Mill: Cask serves HTTP, Twirl renders the templates, Pekko Streams runs the import and purge pipelines, ScalaSql and JDBC reach SQLite or PostgreSQL, OpenCV and FFmpeg (through Bytedeco) decode media, and ONNX Runtime runs the Scene models. The versions are in `build.mill`.

`App.scala` is the single entrypoint (extends `cask.Main`). It registers all routes and wires the app via `new Altitude()`, whose constructor migrates the database and loads the Settings before it builds the actor system (see **Settings** and **Schema migrations**); `App` then fails the Imports a stop interrupted and prunes the Import history, prunes the unfinished imports, requeues and reconciles (see **Library stats and purging**), and starts the Watch folder scans (see **Watch folders**).

The frontend is organized around a thin composition root in `static/js/frontend-app.js`.
Feature logic is split into focused ES module folders instead of accumulating in one large file:

`frontend-app.js` should stay the composition root: it initializes context stores, creates the

fragments. Avoid moving feature logic back into that file when adding new behavior.

`Altitude.scala` is the central dependency-injection object. It creates every DAO, service, and the Pekko `ActorSystem` inline, in a fixed startup order: the settings service (empty) → the transaction manager → the DAOs → `migrationService.migrate()` → `settings.load()` → `importParallelism` → the actor system → the Scene embedder (`sceneEmbedder`, built by the constructor's `newSceneEmbedder`; see **Sequences and Image quality**) → the services. `migrationService` and `settings` sit on `Altitude` itself, above `service`, because they run before any service exists. The `DAO` inner object and the `service` inner object both use `dataSourceType match` blocks to mix in the correct DB-specific trait:

```scala
val asset: dao.AssetDao = dataSourceType match {
  case Const.DbEngineName.POSTGRES => new dao.postgres.AssetDao(app.config)
  case Const.DbEngineName.SQLITE   => new dao.jdbc.AssetDao(app.config) with dao.sqlite.SqliteOverrides
}
```

Never instantiate services or DAOs elsewhere — always inject `app: Altitude` and use `app.service.*` / `app.DAO.*`.

## Request Lifecycle

Every request gets its authenticated user, repository and the user's Permissions there injected into **thread-local** `DynamicVariable`s in `RequestContext` (account, repository, permissions). These are set by:

- `decorators.repoContext()` — clears them (request threads are pooled, so a value would otherwise outlive its request), then parses `/r/:repoId` from the URL and calls `repository.setContextFromRequest`
- `decorators.requireLogin` — authenticates the request (`decorators.authenticate`: the dev user, or the PASETO token of a Bearer header or the cookie; see **Login and the token**), populates `account`, `permissions` (the token's Permissions in the path's Library: every one for an Admin; none for anyone else when the path names no Library) `grants` (the token's grants in every Library, none for an Admin, which `RequestContext.holdsAnywhere` and `createsAccounts` read) and `sessionExpiresAt` (the token's expiry, which the account info dialog shows), and answers a repository in the path that the token gives no access to (an Admin sees every one, anyone else one its token carries a grant in; see **Accounts and access**), or one that does not exist, with the same 404 (JSON for an API request, else the plain text `Const.Msg.Err.LIBRARY_NOT_FOUND`), as for any foreign entity. The gate reads no database. A token rebuilt because its account changed is set as the answer's cookie, unless the answer sets the session cookie itself (a password change mints a token after the rebuild, which the change revoked), and a refused cookie's token is cleared by the 302 or 401 that refuses it when it will never be good again: one that does not decrypt or has expired, or whose account is gone or deactivated (`TokenCheck.Refused(clearsCookie)`); a token refused only for being revoked or stale leaves the cookie, which the browser may have replaced meanwhile (a password change in another request). A request with no login is a 302 to the login carrying its own URL as `redirect`, or a JSON 401 for an API request; an htmx request (`HX-Request`) is a 401 with `HX-Redirect` to the login carrying the page it was sent from (`HX-Current-URL`, its path and query), since htmx's fetch would follow a redirect and swap the login page in as the partial, and the client sends the window to the login on every 401 (`js/common/session.js`, **Requests and a refused session** in `views/AGENTS.md`)
- `decorators.requireLoginOrSignature` — the content route's: a request with both `exp` and `sig` query parameters is answered by `ContentSigner.verify` over the request path alone, with no account in the context (a plain-text 403 when the signature is invalid or expired, no redirect; a 404 for a repository that does not exist, as `requireLogin` answers it); any other request is `requireLogin`'s

All three global decorators are applied in `App.mainDecorators`: `compress → requestResponseLogger → repoContext`; they run on a WebSocket handshake too, whose result is a `WsHandler` or a `WebsocketResult.Response` rather than a `Raw`, which `requestResponseLogger` logs as such. Per-route authentication uses `@requireLogin` (`@requireLoginOrSignature` on the content route); a WebSocket endpoint, which a `RawDecorator` cannot wrap, refuses a handshake from another origin with 403 (`decorators.isSameOriginOrNone`: an Origin header, when there is one, must be an http or https URL whose host and port, as written, are the Host header's; a client that is no browser sends none) and calls `decorators.authenticate` itself, answering a handshake with no login 401, one for a Library the account cannot see, or that does not exist, 404 as `requireLogin` does, and a Guest's, or that of an account without Import in the Library, 403 (`ImportController.pipelineStatus`, the socket of `/import/r/:repoId/status`); a route that not every account with access may call adds one gate after `@requireLogin` (see **Permissions on routes**): `@requirePermission(...)`, `@requireMember`, `@requireLibraryCreator` or `@requireAdmin`, each answering an account it refuses with 403 (JSON for an API request, plain text otherwise, no redirect) and throwing if no account is in the context. A full page of a Library adds `@rememberRepository` last, after the authentication: once the page answers 200, it records the request's repository as the account's last active one (see **Libraries**); a failure to record is logged at WARN and the page is served. `compress` gzips for a client that accepts it (never a 304, which has no body), and marks every response it may gzip with `Vary: Accept-Encoding`. `@cachedForever` is for a file under a content-hashed name (the stylesheet bundle's route): it adds `Cache-Control: public, max-age=31536000, immutable` to a 200 only, so a miss is never cached. `@revalidated` is for files whose names stay when their content changes (everything under `/static/`: the vendored libraries, the fonts, the JS modules): a 200 gets `Cache-Control: no-cache` and a weak `ETag` hashed from the bytes on every request, and a request whose `If-None-Match` holds it is answered 304 with no body, so a reload costs a round trip per file rather than its bytes, and a file refreshed under a running dev server is never answered as unchanged.

The DB connection is `RequestContext.conn`, a `ThreadVariable`: the thread's own value, which a thread started meanwhile does not inherit (a `DynamicVariable` is inherited). Only `TransactionManager` binds it, for as long as the outermost transaction of the thread lasts.

## DAO / Service Layer

- `BaseService` wraps every DAO call in `txManager.withTransaction{}` (writes) or `txManager.asReadOnly{}` (reads). Controllers call services; services call DAOs — never skip a layer.
- `BaseDao` (JDBC) has abstract methods (`jsonFunc`, `jsonText(column, key)`: the text of a JSON object column's top-level key, spelled as an index on it is, `(column->>'key')` on PostgreSQL and `json_extract(column, '$.key')` on SQLite, `nativeBool`, `nativeLocalDateTime`, `nativeUtcTimestamp`, `getBooleanField`, `getDateTimeField`, `getDateField`, `getSortValueField`, `forUpdate`, `instantOf` (public: the instant a model's `LocalDateTime` of an instant column stands for, the inverse of `toLocalDateTime`, which reads one in the JVM zone on PostgreSQL and as UTC on SQLite; what a moment needs before the browser shows it in the viewer's zone, `UserService.accountTimes`), `forKeyShare` (`FOR KEY SHARE` on PostgreSQL, the lock a foreign key's check takes, which a delete or a `FOR UPDATE` of the row waits for; nothing on SQLite; `UserDao.lockAsImporter` is its use), `advisoryLock(key)`: transactions taking one key take turns until they end where row locks cannot serialize them, a row one will insert being in no row the other can lock (`pg_advisory_xact_lock` on PostgreSQL, nothing on SQLite, whose one write connection serializes the writers; `AssetDao.lockSequences`, `PersonDao.lockName`, `FolderDao.lockName`, `FolderDao.lockTree` and `WatchFolderDao.lockPaths`, the one key that is the instance's rather than a Library's, are its uses), `nativeLocalDate`, `dayOf`: the engine's capture-day expression, the one spelling of `SearchDialect.dayWrapper`; `vectorPlaceholder`, `vectorBind` and `getVectorField`: a Scene embedding's placeholder in a hand-written statement, its bind value and its read from a result row, `?::vector`, the pgvector literal of `PostgresOverrides.vectorLiteral` (shared with `postgres.FaceDao`) and a `PGobject`'s text on PostgreSQL, `?`, the raw little-endian float32 bytes and a `byte[]` on SQLite) filled in by `PostgresOverrides` or `SqliteOverrides` traits. `rowProcessor` is how result rows become maps: `PostgresOverrides` reads `timestamp`, `timestamptz` and `date` columns as `java.time` values so a wall-clock timestamp never round-trips through an instant in the JVM zone. A hand-written read goes through `manyBySqlQuery(sql, values)`, which materializes its rows, or through `collectBySqlQuery(sql, values)(f)`, which streams them: each row is mapped as it is fetched, through the same row processor, kept when `f` returns a value and dropped otherwise, with a fetch size (`STREAMING_FETCH_SIZE`, 256) so the PostgreSQL driver does not buffer the whole result (SQLite's reads row by row whatever the size), and it answers `BaseDao.Collected(kept, scanned)`: the kept rows in the result's order and how many rows were scanned, so a caller reading up to a limit can tell when the limit was reached. `BaseDaoTests` (both engines) covers it: a mapper keeping every other row gets those rows alone, in order, with the full count, and one keeping nothing gets the count alone.
- DB-specific DAO overrides live in `dao/postgres/` and `dao/sqlite/`. The JDBC base lives in `dao/jdbc/`.
- Face vector search requires `txManager.withFaceVector{}`: the outermost `withFaceVector` of a thread sets the transaction up for it before running its block (the calls nested in it do not set it up again). On SQLite there is nothing to set up per transaction: every connection, as it is opened, loads the vector extension and registers `face.features` with it (`vector_init`) when the `face` table exists. A database being created has no tables when its first connections are opened, so once `MigrationService` has created the schema it calls `txManager.schemaCreated()`, which replaces the pooled SQLite connections (a no-op on PostgreSQL). On PostgreSQL the setup is `SET LOCAL hnsw.ef_search` (the PostgreSQL-only `face.recognition.hnsw_ef_search` Setting, 100, read from the current snapshot when the outermost `withFaceVector` runs; nothing is set before the Settings are first loaded) and `SET LOCAL hnsw.iterative_scan = relaxed_order`, so a search of the vector index goes on until its limit is met by rows that pass the repository and bad-match filters. `txManager.withFaceVectorReadOnly{}` is the same setup over `asReadOnly{}`, for a search that stores nothing (`PersonService.suggestedPeople` and `assignablePeople`, the Change combobox's options): `SET LOCAL` is allowed in a read-only transaction, so the search reads one snapshot on PostgreSQL, and on SQLite it leaves the one write connection alone.
- A DAO never manages a transaction of its own (`BaseDao` has no transaction manager): the service around it does.
- **Repository scoping.** A DAO is scoped to the context repository by default (`BaseDao.repositoryScoped`): `getById`, `getByIds`, `getOneByQuery`, `query`, `updateById`, `updateByQuery`, `deleteById`, `deleteByQuery` and `increment` add `repository_id` from `RequestContext.getRepository`, which throws when the context has no repository, so another repository's row is out of reach exactly as a row that does not exist. Six DAOs opt out (`repositoryScoped = false`): those of the four tables with no `repository_id` (`RepositoryDao`, `UserDao`, `SettingDao` and `SystemMetadataDao`), and `RepositoryGrantDao` and `AuditEventDao`, whose rows are read and written with no Library in the context (a login, an account's grants across Libraries, an event of an account). An `updateByQuery` or `deleteByQuery` with an empty query is refused (`IllegalArgumentException`), scoped or not, since it would change every row. Hand-written SQL on a scoped table carries `repository_id = ?` itself (in both arms of a recursive statement, as `FolderDao`'s are), and so does a statement that selects the rows it writes (`AlbumDao.addAssets` takes only the context repository's assets). Six statements are the only ones on a Library's table that carry no Library. Three reach `asset` by an account's ID in every Library (**Account management**): `AssetDao.countOwnedBy`, a read of its own for the Delete dialog (the assets that would move), and two writes run in the transaction of the account write they serve, `reassignOwner` (a delete gives the account's assets to the deleting Admin) and `rewriteImporterRecords` (an update rewrites the importer record of the assets the account imported). Three reach `watch_folder` (**Watch folders**): `WatchFolderDao.everywhere`, a read of every Watch folder of the instance with its Library, since no two may overlap in any Library, and two writes by an account's ID in the transaction of the account write they serve, `pauseOwnedBy` (a deactivation or a demotion) and `reassignOwner` (a delete). No other statement may reach a Library's table without its Library. A `BaseDao` write returns the number of rows it changed; `BaseService.updateById`, `deleteById` and `increment` turn 0 into `NotFoundException`, so a write by an unknown ID, or another repository's, is never a silent no-op (a service calling the DAO directly reads the count itself through `BaseService.requireFound`, as `UserMetadataService` does for an asset's metadata and a field's delete). An ID a request names as a reference is read through `getById`, scoped as every read is, in the transaction of the write (`LibraryService.moveAssetsToFolder` and `FolderService.add` read the destination or parent folder; `PersonService.setFaceAsCover` reads the Face and checks it is the Person's). At the route, `NotFoundException` is a 404 through `BaseController.answering` (plain text) or `answeringJson` (JSON): another repository's ID gets the answer an unknown one does, and names nothing of it. Both answer `ForbiddenException`, an asset the account's Permissions do not reach (`AssetRules`, **Permissions on routes**), with the 403 of `decorators.forbidden`; a service checks a Permission only over rows it has read scoped, so another repository's ID is a 404, never a 403. `RouteTableTests` (controller suite) holds every route of `App.allRoutes` in one table, which also says who may call each (**Permissions on routes**): a route missing from it, an ID parameter of a route that no probe sends, or a body ID field that no probe sends, fails the test, and each probe asserts that another repository's IDs and unknown ones get the same answer, that the answer names nothing of the other repository and that no row of either changes; the few routes that answer otherwise by design (a dialog's field error, an empty map, a batch operation that leaves out IDs that are not the repository's, the advanced search panel's form, which drops them, a filtered search, whose title names no chip for them) say why in the table. A route's body ID fields are read off the controllers' sources with Scalameta (`RouteTableTests.idFieldsOf`, through `ALTITUDE_SOURCE_DIR` as `TransactionBoundaryTests` reads them): every ID-shaped value (`id`, `...Id`, `...Ids`) of `Api.Field` that the route's method names, or a member of its controller, of `BaseController` or of an object under `routes/` that it reaches by name, less the endpoint's own parameters. Reaching by name over-approximates, so a row lists a field its route names without acting on it (`ignoring`, with why), and a member of an object under `routes/` named as a common method is reached by every route that calls one (a `read` by every `ujson.read`), so such a member takes a name of its own (`AccountForm.submittedIn`); a body field read by a string literal rather than through `Api.Field` is not seen, so a body field is always named through `Api.Field`. `RepositoryIsolationTests` (both engines) covers the DAOs and services, and `TestContext.rowsOf(repository)` reads every row of a repository's scoped tables (`TestContext.SCOPED_TABLES`) by hand-written SQL, so two reads compare whole repositories.
- **Schema guards.** The database holds every reference in one repository (`all.sql`, both engines): `repository_id` is `NOT NULL` on every scoped table, each table a reference names has `UNIQUE (id, repository_id)` (led by the ID, so it never competes with the indexes that lead with the repository), and each reference is a foreign key over `(repository_id, <ref>_id)`: a Face's asset and Person, an album's and a Location's memberships, a metadata value's asset and field, a Search document's asset, an Import file's Import and a Watch folder file's Watch folder (all `ON DELETE CASCADE`), a Location's category, a folder's parent, an asset's folder, and an Import's and a Watch folder's destination folder (no delete action; the root folder is its own parent, which its insert satisfies). A NULL reference is not checked: an asset in no folder (a triaged one) is stored with `folder_id` NULL, which `AssetDao` writes for the model's empty folder ID and reads back as one, so the model and every caller see `""` as before, and the folder counts (`SearchQueries.folderCounts`) count it under no folder. `person.cover_face_id` is a single-column key onto `face (id)`, `ON DELETE SET NULL` (a composite key's SET NULL would clear `repository_id` too; on PostgreSQL it is declared after `face` with `ALTER TABLE`, the two tables naming each other); every path that deletes a cover Face picks another cover first, so the delete action only backs that up, and the cover's repository is checked in code. `import_file.asset_id`, onto `asset (id)`, and `import.watch_folder_id`, onto `watch_folder (id)`, are the other two single-column keys, `ON DELETE SET NULL` for the same reason: an Import file outlives its asset and an Import its Watch folder, and `ImportService.settle` reads the asset, and `open` the Watch folder, in the context repository before it writes the reference (`import_file_02` and `import_02` index them for the delete action). `person_04` indexes every cover, a merged-away Person's included, for that delete action. `repository.root_folder_id` has no key: the repository row is written before its root folder. A hand-written write that breaks one is refused (`RepositoryIsolationTests`); on SQLite every constraint violation has error code 19, which `Util.newDuplicateExceptionOrRethrow` reads as a duplicate, so a write is checked in code before the database would refuse it.
- **Transaction boundaries.** A public service method that reaches a DAO opens or joins a transaction itself (`withTransaction`, or `asReadOnly` when it only reads), even when every current caller already has one: joining costs one check. An operation that must be atomic is one service method under one wrapper, never a loop of wrapped calls, which commits each call on its own (`LibraryService.restoreRecycledAssets` restores a whole batch in one transaction, skipping and reporting an asset whose content was imported again after it was recycled, so any other failure restores nothing). Pipeline flows, controllers and DAOs never open a transaction or reach a DAO. `TransactionBoundaryTests` (unit suite) parses the sources with Scalameta and enforces the syntactic part: a DAO reference in a non-`private` service method must sit inside a wrapper (a `private` helper is covered by its caller's), and nothing under `dao/`, `pipeline/` or `routes/` names the transaction manager. It cannot see the loop of wrapped calls. Mill runs tests in a sandbox, so `build.mill` hands it the source directory as `ALTITUDE_SOURCE_DIR`.

**Connections and transactions** (`transactions/TransactionManager.scala`). Every transaction borrows a connection from a HikariCP pool, opened on first use and closed at `Altitude.cleanup` (`TransactionManager.shutdown`); `connection(readOnly)` borrows one with its transaction begun, so the suites' setup code takes one as before, and a transaction started inside another on the same thread joins it through `RequestContext.conn`, which is bound for exactly as long as the outermost one runs. A write commits, then runs the actions `afterCommit` registered in it (outside a transaction an action runs at once; one that throws is logged at WARN); a read, and any transaction that failed, ends with a rollback, which drops them, and a rollback that fails is logged at WARN and never thrown, so a failed transaction fails with its own exception. Neither wrapper logs the exception it rethrows. A pool logs, with the borrower's stack trace, a connection held longer than `db.pool.leak_detection_threshold` (60 s; 0 turns it off).

- PostgreSQL has one pool, of `db.postgres.pool_size` connections; left unset, a connection per core for requests running at once plus six for the import pipeline (a transaction at most per database stage of a repository's import: the duplicate check, indexing, face recognition, completion, the discard of a dropped asset and the settling of its Import file), never below 10. Every connection opens with `db.postgres.options` (`-c jit=off -c plan_cache_mode=force_custom_plan -c work_mem=64MB`, reasons in `reference.conf`). A read transaction is `REPEATABLE READ, READ ONLY`, so all of its statements see one snapshot, and begins with `SET LOCAL statement_timeout` (the PostgreSQL-only `db.postgres.read_statement_timeout` Setting, 30 s, read from the current snapshot as the transaction begins; a read before the Settings are first loaded, the migration of a fresh database, has no limit; the tests of the limit save 1 s through `withSetting`). `Db.read` turns a statement cancelled by it (SQLSTATE `57014`) into `QueryTimeoutException`, which `SearchResultsController` answers with a plain-text 503 and `MapController` with a JSON 503 (`Const.Msg.Err.SEARCH_TIMED_OUT`).
- SQLite has a read pool (`db.sqlite.read_pool_size`, 4) and a write pool of one connection over the same file, opened through `SQLiteConfig` with `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=10000`, `temp_store=MEMORY`, a 64 MiB cache and a 1 GiB mmap. When opened, each connection loads the vector extension and runs `PRAGMA optimize=0x10002`; the write connection checkpoints the WAL every 500 pages, and a read connection is `query_only`, so a write nested in a read transaction fails instead of vanishing in the closing rollback. A write transaction begins `IMMEDIATE`, taking the write lock when it starts, and the single write connection queues writers in the process instead of failing them with `SQLITE_BUSY`; a read transaction reads one WAL snapshot. `PRAGMA optimize` runs hourly on the write connection, scheduled on the actor system, and once more at cleanup.

## Libraries

A **Library** (`CONTEXT.md`) is a `Repository` in the code: the UI says "library", and the code, the tables and the URLs keep `repository`. A Library has no owner: it belongs to the server, an Admin reaches every Library by its account type and anyone else a Library it holds a grant in (**Accounts and access**), so deleting an account never deletes a Library. The nav's Library menu lists the Libraries the account can see and switches between them (`views/AGENTS.md`, **Nav**).

**The name rule.** `Repository.validName(name)` is the one rule for a Library name, which setup and the New library dialog share through `RepositoryService.addRepository`. It normalizes the name (`Repository.normalizedName`: trimmed, each run of Unicode whitespace one space, then NFC through `NameKey.normalized`), and throws a `ValidationException` giving `FieldConst.Repository.NAME` the first error of: required, no control characters, 2 to 80 code points (`Api.Constraints.MIN_`/`MAX_REPOSITORY_NAME_LENGTH`), a name key within `NameKey.MAX_KEY_BYTES` (see **Names**); the texts are `Const.Msg.Err.LIBRARY_NAME_*`, and `NAME_KEY_TOO_LONG` for the key. A control character, to the rule, is an ISO control character, an invisible format character (Unicode `Cf`: a zero-width space, a bidirectional override or isolate, a byte order mark, a soft hyphen, a tag), which would let two names that look alike differ or reorder the text around a name, or an unpaired surrogate; the two join controls are allowed, ZERO WIDTH JOINER for emoji sequences and ZERO WIDTH NON-JOINER for Persian and the Indic scripts. Neither the setup form's Library name field nor the New library dialog's sets `minlength` or `maxlength`, since the rule counts the name normalized, which the browser cannot. The name is stored normalized. It is unique instance-wide under its name key (see **Names**): `repository.name_key` carries `Repository.nameKey`, `NameKey.of` of the normalized name, under the unique index `repository_01`, so a name that differs from a held one only in case, in any script, or in Unicode form ("WEISS" for "Weiß", a full-width letter) is taken. `addRepository` turns its unique violation into a `DuplicateException` saying the name, as normalized, is taken (`LIBRARY_NAME_TAKEN`, through `Util.newDuplicateExceptionOrRethrow`), so of two adds racing on one name, the database leaves one. `SetupFormController` runs the rule beside its request validator, which does not check or trim the name (a trim would drop the control characters at its ends that the rule refuses), and puts its error under the Library name field.

**Listing and landing.** `RepositoryService.getAccessibleTo(account)` reads the Libraries the account can see (every one for an Admin, `RepositoryDao.getAll`; those it holds a grant in for anyone else, `RepositoryDao.getGrantedTo`) and sorts them in Scala by `util.NaturalOrder`: each run of ASCII digits compared as a number ("Client 2" before "Client 10"), the text between by the root locale's collation (`java.text.Collator`, secondary strength, one per thread since a collator is not thread-safe): case-insensitive, an accented letter beside its base letter ("Émile" before "Zoo"); numbers sort among the text where "0" does, and names equal to the collation fall back to their plain order, so the order is total. `landingRepositoryOf(user)` is the Library login and `/` open: the account's `last_active_repo_id`, read from the database, while the account can see it; otherwise the first it can see by name, which is recorded; `None` when it can see none. `IndexController` (`/`, the dev user's path included) redirects to it, or answers a plain-text 404, `Const.Msg.Err.NO_LIBRARY`, when there is none; the login redirect (`SessionController`) goes to it when the request carries no valid `redirect`, and to `/` when there is none. The login token (`PasetoService.createToken`, **Login and the token**) never carries the last active Library, which every switch would make stale: a `User` rebuilt from the token has no `lastActiveRepoId`.

**Recording the last active Library.** `decorators.rememberRepository`, on the full pages of a Library (`IndexController.repositoryView` and `assetView`, `ImportController.pipeline`, `SettingsController.page`, `UsersController.page`, `StyleGuideController.styleGuide`), calls `UserService.rememberLastActiveRepository(user, repoId)` once the page answers 200. It reads the account's recorded Library in a read-only transaction and opens a write transaction only when that differs, so a load of the Library recorded already takes no write lock (on SQLite, the one write connection); the write is one conditional statement, `UserDao.rememberLastActiveRepository`: `UPDATE account … WHERE id = ? AND last_active_repo_id IS DISTINCT FROM ?` on both engines, so of two loads racing, the second writes nothing, and it reports whether it wrote. The page is rendered by then, so the decorator logs a failure to record at WARN and serves the page. Partials and API routes do not carry the decorator, so a nav reload or a search never moves where the user lands, and neither does a page that is not found. Setup records nothing itself: the redirect's load of the new Library does. Each page's URL names its Library, so tabs are independent, and the tab loaded last decides where the next login lands.

**The New library dialog.** `LibraryActionController` (`routes/web/partial/`), both routes `@requireLogin() @requireLibraryCreator()` (an Admin, or an account whose token carries the Create Libraries flag) and scoped to the Library the dialog is opened from: `GET /htmx/library/r/:repoId/dialogs/new` renders `htmx/new_library_dialog`, and `POST /htmx/library/r/:repoId/new` reads `Api.Field.Library.NAME` from the unscrubbed JSON body and calls `addRepository` with the file-system store and the request's account as the creator; the Library has no owner, an Admin reaches it by type and a creator who is no Admin by the grant of every Permission it is given (**New-Library grants**). A refused name (the rule's `ValidationException` or the `DuplicateException`), or a creator already at its bound of grants (`IllegalOperationException`, `TOO_MANY_GRANTS`), re-renders the form through `dialogFormValidationResponse` with the typed name and the error under the field; a created Library is logged at INFO and answered with `HX-Redirect` to its Import page, `/pipeline/r/<id>`, whose load records it. The front end is in `views/AGENTS.md` (**Nav**, **Context menus**). The repository cache (`RepositoryService.getById`, `Altitude.repositoriesById`) is never invalidated: nothing changes a Library once it is created.

## Accounts and access

An **Account** (`CONTEXT.md`) is a `User` in the code, a row of `account`: its email address and its `username` (each unique under its name key, see below), `name`, `account_type` (Admin, User or Guest), `password_hash`, `is_active`, the Create Libraries flag (`can_create_libraries`), the new-Library grant (`grants_new_libraries` and its `new_library_permissions` bitmask), `created_by_account_id` (`ON DELETE SET NULL`), `last_login_at` and `last_active_repo_id`. `User` derives `emailKey` and `usernameKey` with `NameKey.of`; `UserDao.addUser` writes both beside what they key, under `account_01` (`email_key`) and `account_02` (`username_key`), so an address or a username that differs from a held one only in case or Unicode form (a full-width letter) is a `DuplicateException`, and a login's lookup (`UserDao.getWithPasswordHash`) compares the key column, so the lookup and the index cannot differ. A username keeps to `User.validUsername`, which `UserService.add` applies: 3 to 32 ASCII letters, digits, `.`, `_` and `-` (`Api.Constraints.MIN_`/`MAX_USERNAME_LENGTH`; `USERNAME_RULE`, or `VALUE_REQUIRED` when empty, under `FieldConst.User.USERNAME`), so a username never holds an "@" nor a character whose case or form folds. The setup form takes the setup Admin's username (`Api.Field.Setup.ADMIN_USERNAME`, trimmed), with the rule's error under the field beside the request validator's.

**Permissions and grants.** A `Permission` (`models/Permission.scala`) is one of the nine, each on a stable bit (`Permission.bit`, 0 to 8 in the order the UI lists them), never renumbered, since the bitmask is stored and carried in tokens; `Permissions` is a set of them as that mask, refusing a bit no Permission has, written to JSON as the bare number. A `repository_grant` row (`RepositoryGrant`: account, Library, `Permissions`; unique per pair, cascading from both) gives a User or a Guest access to a Library; a Guest's holds no Permission, and an Admin needs none, reaching every Library by type. `RepositoryService.setGrant(accountId, repositoryId, permissions)` writes one (an upsert, `RepositoryGrantDao.setGrant`, replacing the Permissions held there), locking the account's row (`UserDao.lockById`) and reading the Library in its transaction, so an unknown one is `NotFoundException` and the account type checked is the stored one: it refuses a grant to an Admin and a Permission to a Guest (`IllegalOperationException`), and a grant in one Library more than `RepositoryService.MAX_GRANTS_PER_ACCOUNT` (35, `TOO_MANY_GRANTS`), the bound of what a login token fits (**Login and the token**), while a grant set again where one is held still changes; the row lock makes two grants racing past the bound take turns on PostgreSQL. Once committed it bumps the account's version, so its sessions see the grant at their next request. `replaceGrants(accountId, grants)` replaces an account's every grant at once under the same rules (the grants it held elsewhere go, an Admin's all), bumping once: account management's write of the grants. `getGrants` reads an account's grants; `getAccessibleTo` lists the Libraries an account can see (**Libraries**). `requireLogin`'s gate is the token's grants, never the table. A grant goes with its account, so deleting an account deletes its grants and never a Library, and the database refuses to delete an account that owns an asset (`RepositoryServiceTests`).

**Permissions on routes.** Every route declares who may call it, by its decorators (`routes/decorators.scala`), and `RouteTableTests` holds that declaration for every route: anyone (no decorator), any account with access to the Library of its path (`@requireLogin()` alone), or `@requireLogin()` followed by one gate: `@requirePermission(p, ...)`, the holder of any one of the Permissions in the path's Library (`RequestContext.permissions`, the token's; every one for an Admin, none for a Guest), its `anyOf` read by the table; `@requireMember()`, an account that is no Guest (the Triage partials); `@requireAccountCreator()`, an Admin or the holder of Create Users or Create Guests in any Library, read from the token's grants (`RequestContext.createsAccounts`), not only the path's; `@requireLibraryCreator()`, an Admin or the Create Libraries flag (`decorators.mayCreateLibraries`); `@requireAdmin()`. Each gate is `decorators.allowedOnly`, logging a refusal at WARN with no database read and answering it with `decorators.forbidden(why, json)`, the one 403 of every refusal for lack of a Permission, from a gate, a route or a service: `{"error": why}` in JSON (the shape of `BaseController.jsonError`) and "Forbidden: why" in plain text; a gate's `why` is a `Const.Msg.Err.FORBIDDEN_*` (`FORBIDDEN_ADMIN` for `requireAdmin`). A full page's gate comes before `@rememberRepository`, so a refused page records nothing. The mapping: Import the Import page, the upload routes (opening an Import with a destination folder takes Organize as well, which `ImportService.openUpload` checks once the folder is read: **Uploads**), the Import history's partials, the Watch folders' cards and, checked in the route, the import status WebSocket (**Import history and the status feed**); Organize every move of assets, every write and dialog of folders, albums, Locations and their members, the geocoder (the Add location dialog's), and People's merges (the Merge people modal and its merge, and a Face's Person merged into a named one), cover, hide, show and delete; Edit Metadata a Face's Person (change, name, remove) with the Change combobox's options, and a Person's rename and name edit with their editors; Recycle or a Curate Permission the asset API's recycle and restore; a Curate Permission all of Curation (its count, shell, queue, sets, selection, resolve and reopen); Purge both purges; a member the Triage partials; a create Permission in any Library the Users page, its cards and the Add User modal and its create; the Create Libraries flag the New library dialog and its save; an Admin the Settings page and its save, an account's edit, password, deactivation, reactivation and delete, and every write and dialog of a Watch folder (**Watch folders**). Every other route is any account's with access: those that only read, and the change of the account's own password (`PUT /htmx/account/password`, whose path names no Library). `RouteTableTests` fails a route that changes a Library (any method under `/r/:repoId` but GET and a WebSocket's handshake) and declares no gate past the login; the import status WebSocket's row says who its handshake lets through (`Access.HolderInRoute`), which the table's 403 test holds it to as it holds a decorated route.

A rule a decorator cannot decide is checked where its input is. A Guest sees Browse alone. A route that takes the view as a parameter (the main page, the search results, the map's cells and bounds, the People list's `triaged`) refuses it Triage, the Trash and `triaged=true` (`decorators.maySeeView`, `refusedView`); a route that takes an asset's ID (the Detail panel, the asset-detail modal and its JSON, the asset's page, its Preview and its original under `/content`) answers it a triaged asset or one in the trash as an unknown one, a 404, after the scoped read (`decorators.maySeeAsset`, `visibleOnly`; a Face's crop stays served, as it may be the cover of a Person the Guest sees, and a signed URL, with no account, is not a Guest's); and the import status WebSocket refuses its handshake with a 403, as it does that of any account without Import in the Library. A rule that depends on the asset is `AssetRules`, called by the service in the transaction of its write, over the assets it has read scoped to the Library: `requireRecycle` (`Permissions.mayRecycle`: a triaged asset, as one recycled from Triage still is, takes a Curate Permission, a sorted one Recycle) in `LibraryService.recycleAssets` (so a folder's delete too), `restoreRecycledAssets` and, for the assets it takes out of the trash, `moveAssetsToFolder`; `requireCurate` (`Permissions.mayCurate`: Curate all, or Curate own on an asset whose `owner_user_id` is the account, the one rule that reads the owner) over the triaged live Picks of `CurationService.resolve` and over every triaged Pick of `reopen`, in the trash or not, as `setSequence` writes each; both read every ID they are sent (the Picks and the frames to recycle or restore) scoped to the Library first (`requireKnown`), so an unknown or foreign ID is a 404 even beside a frame the account may not curate. One refused asset throws `ForbiddenException`, so the whole operation rolls back. Curation shows an account holding Curate own without Curate all its own frames alone (`AssetRules.curatedOwner`, the `owner` of `AssetDao`'s Curation statements: the queue, its count, a Sequence's window and size, a selection), so a set never holds a frame its outcome would be refused for, and `resolve` judges a Sequence complete over the frames the account is shown, so another account's frames neither keep its Picks in the queue nor are touched; the grouped grid's Curate button on a Sequence counts them too (`CurationService.curatableFrameCounts`). The rules read `RequestContext.permissions` and `account`: a request's, or a pipeline stage's as `PipelineUtils.withContext` binds them; no pipeline, startup task or purge reaches them. A template renders an action control only where the account may use it, by the same bitmask (`RequestContext.holds(p, ...)`, `isMember`, `recyclesIn(view)`, `restores`), and the main page puts what the scripts need on its body (`views/AGENTS.md`, **Controls follow Permissions**).

**Assets.** `asset.owner_user_id` (`Asset.ownerUserId`, `NOT NULL REFERENCES account (id)` on both engines, with no delete action, so an account with assets cannot be deleted without moving them first) is the account that owns an asset, and `asset.original_owner` (`Asset.originalOwner`, an `AccountSnapshot`: the importer's ID, name, username and email as JSON, `STORAGE MAIN` on PostgreSQL so the general reads that select it find it in the heap row) is the importer record, which outlives the account. `LibraryService.stagedFileToAsset` writes both from the context account at upload, and `persistAndIndex`, the import's insert, builds the importer record again from the account as stored then (`UserService.lockImporter`, which share-locks the row through `UserDao.lockAsImporter`, so a delete or an update of the account waits for the insert and then sees its asset): an account deleted or deactivated while the file waited in the pipeline fails the file with `ImporterUnavailableException` (`IMPORTER_GONE`, `IMPORTER_DEACTIVATED`), which the Import history shows as the file's reason, never a foreign key's error; an update of the account rewrites its records in every Library, and a delete gives its assets to the deleting Admin (**Account management**). Neither reaches the browser: `Asset.toBrowserJson`, the asset JSON a route answers (the asset-detail modal's), leaves both out, since they name an account to anyone who can see the Library.

**Login and the token.** `UserService.loginAndSetUser(login, password, clientIp)` folds the login with `NameKey.of` and looks it up by `email_key` when the folded login holds an "@" and by `username_key` otherwise, whatever the case it is typed in (a login with a control character is not looked up, since no username or address holds one and PostgreSQL refuses a NUL in a text parameter); it checks a dummy hash for a login that names no account, and refuses a wrong password, an unknown login and a deactivated account alike, so `SessionController` answers each the same 401. The lookup and the bcrypt check run in a read-only transaction, so on SQLite they hold no write connection; then it reads the account's version (the account named, the version is read before anything else of it), and a short write transaction of its own locks the account (`UserDao.lockWithPasswordHash`), refuses the login when the hash is no longer the one checked (a password changed meanwhile, whose revocation the version may predate), reads the claims, and records `last_login_at` (`UserDao.recordLogin`, which leaves `updated_at`, the stamp of an account change) and a login event, or a failed login's event (no actor, the account named if any as target, the login as typed in `detail`, its control characters escaped and cut to 64 characters by `Util.printable`, which the failure's WARN uses too), both with the client IP the controller reads off the exchange. The login form's field is "Email or username".

The token is PASETO v2.local (`PasetoService`), its key random per process. Its claims (`TokenClaims`) are the account's ID, email, username, name, account type and Create Libraries flag, its grants as a JSON object of Library ID to Permission bitmask (none for an Admin, who holds every Permission by type), the account's version and the expiry, 7 days after the login. `PasetoService.readToken` is the one place a token's claims are read, with no database query; `TokenClaims.permissionsIn(repositoryId)` is every Permission for an Admin, the grant's for anyone else, and None without one. A grant costs about 57 bytes of token, and the longest account (an 80-character name of four-byte characters, which the token's JSON escapes to 12 bytes each) about 1820 bytes with none, so the session cookie holds 37 grants at most within the 4096 bytes a browser keeps; `MAX_GRANTS_PER_ACCOUNT` is 35 (`LoginTokenTests` builds that token and asserts the cookie fits). The bound rests on the account rules `UserService.add` applies (`User.valid`: the username rule, a name of 2 to 80 characters once normalized, an email address of 3 to 80 ASCII characters), and `createToken` logs at ERROR a token past `PasetoService.MAX_TOKEN_BYTES` (3950), which a browser may drop. Every expiry is `UserService.tokenExpiry` (7 days, to the second), and the login's cookie lives as long as its token (`SessionController.authCookie(token, expiresAt)`).

**Account versions.** `AccountVersions` (`app.service.accountVersions`, one map of the process, `AccountVersions.processWide`, which every `Altitude` of the process shares as they share a database) holds per account a current version and a revoked-below version, both 0 for an account never changed; nothing persists it, since the token key does not outlive the process either. A token carries the version it was minted at, read before the transaction that reads the account, so a change committed meanwhile leaves it stale rather than wrong. `UserService.checkToken(token, renewable)` reads one `AccountVersions.Snapshot` of the account and judges the token against it: `Current` for a token at the current version; for one below it, `Renewed`: the claims rebuilt from the database (`claimsAt`: the account, when it still exists and is active, and its grants) with the old expiry, minted at the snapshot's current version (`renew`), so a revocation that lands meanwhile leaves the rebuilt token below it, and the token that replaces it, which `requireLogin` and `/` set as the cookie; and `Refused` for a stale token that cannot be replaced (a Bearer header's), for an account deactivated or deleted since, and for a token below the revoked-below version; `Refused(clearsCookie)` says whether the answer clears the cookie: for a token that does not decrypt or has expired, or whose account is gone or deactivated (a revoked token's account read once to tell), and never for one refused only for being revoked or stale. `bump(accountId)` makes an account's tokens stale and `revoke(accountId)` (a password change, and a deactivation, so a reactivated account logs in again) refuses them, a token minted after it holding; an account write calls one in `TransactionManager.afterCommit`, so a rebuild reads the change (`setGrant`, `replaceGrants` and every write of **Account management**). `onChange` tells listeners of each change: `Altitude` closes the account's import status sockets, in every Library (`ImportStatusWsActor.CloseAllFor`), a bump with 1013, which the page's client reconnects on, its handshake checking the login and Import in the Library again (refused for an account deactivated or deleted, or one whose grant no longer holds Import, a grant's change being a bump), and a revocation with 1008, which `hx-ws` does not (the page connects its sockets again after its own password change, `js/listeners/account.js`). The dev user (`UserService.getDevUser`) has its claims built from the database on every request.

**Account management.** `UserService` holds the writes of the Users page, each in one transaction that records its audit event and reads the acting account from the database, never from the token. `create(creatorId, model, password, grants)` adds an account (`createdByAccountId` the creator), `update(actorId, model, grants, openedState)` changes its name, username, email address, type, grants, Create Libraries flag and new-Library grant, and `deactivate`, `reactivate`, `delete`, `setPassword` and `changeOwnPassword(accountId, current, new, ...)` do what they say; every write but a password's and a deactivation's bumps the account's version once it commits (an update through `replaceGrants`), and a password or a deactivation `revoke`s its tokens, the session that changed its own being given a new one (`OwnPasswordController.renewedSession`: `claimsOf`, `paseto.createToken`, `SessionController.authCookie`). The rules: `User.valid`, a password of `Api.Constraints.MIN_`/`MAX_PASSWORD_LENGTH`, and at least one Library and at most `MAX_GRANTS_PER_ACCOUNT` for a User or a Guest, a refusal a `ValidationException` naming its field (`FieldConst.User.*`, `GRANTS` for the Libraries), as is an email address or username another account holds (the unique violation of `account_01` or `account_02`, read off the driver's message); the account held to its type (`shapedByType`: an Admin keeps no grant, flag or new-Library grant, a Guest no Permission, so a type change to Guest keeps the Libraries and clears the Permissions, and one to Admin drops the grants). With the new-Library switch off, the grant's Permissions are cleared. A creator's row is locked and an inactive creator refused (`FORBIDDEN_INACTIVE`); one who is no Admin creates within its ceiling (`withinCeiling`, over its grants read in the transaction, and over what was asked, before the shaping): a User only where it holds Create Users, a Guest only where it holds Create Guests, with Permissions it holds there, never an Admin, the Create Libraries flag or the new-Library grant (its switch or its Permissions), anything else a `ForbiddenException`; a Library it holds nothing in is refused as above its ceiling whether or not it exists. Every other write is an Admin's: it first locks the active Admins' rows in ID order (`UserDao.lockActiveAdmins`, `FOR UPDATE` on PostgreSQL) and the actor must be one of them (`ForbiddenException` otherwise), so two Admins' writes take turns, and an Admin deactivated or demoted by the first can do nothing in the second. That check, made under the lock, is what keeps an active Admin, with the refusal of the actor's own account (`OWN_ACCOUNT`: a `ValidationException` on the type for an update that demotes it, an `IllegalOperationException` for a deactivation or a delete): the actor is an active Admin and never the one it removes. An update is checked against the state the Admin's form was opened over (`openForEdit` reads the account, its grants and `UserService.editState`, a SHA-256 of the name, username, email address, type, flag, new-Library grant and grants, which the form carries back as `Api.Field.User.OPENED_STATE`): compared in the write's transaction, under the account's row lock, which every write of the account and its grants takes (a new Library's grant included), a save over a change made since is a `ValidationException` on `FieldConst.User.OPENED_STATE` (`ACCOUNT_CHANGED`) that writes nothing. A write that changes none of those fields (a login, the last active Library) does not change the state. A wrong current password in `changeOwnPassword` is logged at WARN and recorded (`PasswordChangeFailed`, with the client IP). An update whose name, username or email address changed rewrites the importer records of the account's assets (`AssetDao.rewriteImporterRecords`, through the `asset_importer` index on the record's ID); a delete gives the account's assets to the Admin (`AssetDao.reassignOwner`), and its Watch folders with them (`WatchFolderService.passOn`), and deletes the row, whose grants cascade and whose created accounts lose their creator (`ON DELETE SET NULL`), leaving the importer records. A deactivation, and an update that takes the Admin type from an account, pauses the Watch folders the account owns, in every Library, in the same transaction (`WatchFolderService.pauseOwnedBy`): a Watch folder's owner owns the assets it imports, so it is an active Admin (**Watch folders**). `accountsVisibleTo(viewer)` lists what the Users page shows: every account for an Admin, for anyone else the accounts it created that are no Admins, with their grants in the Libraries it holds one in itself.

**New-Library grants.** `RepositoryService.addRepository(name, fileStoreType, creatorId)` grants, in the add's transaction, every account whose new-Library switch is on (an Admin aside) its new-Library Permissions through `setGrant`, having locked the active Admins' rows first (`UserDao.lockActiveAdmins`, as every Admin's account write takes them first), then every account it grants, those and the creator, in one pass in ID order (`UserDao.lockGrantees`): one order everywhere, so an Admin's create cannot hold a grantee's row while it waits on its own, which an Admin's edit of that grantee holds, and two creates at once, each granting the other's creator, cannot deadlock (both `RepositoryServiceTests`, on PostgreSQL); recording each grant as a change of Permissions (`PermissionsChanged`, the Library and its Permissions, acted by the creator, or by no one for a Library added with none); skipping with a WARN an account `setGrant` refuses (one at its bound), so another account's bound never fails a create; then a creator who is no Admin, by its stored type, every Permission, a refusal of which (the creator at its bound, `TOO_MANY_GRANTS`) fails the whole add, so no Library is left that its creator cannot open. The add switches the request's Library to the new one; a refused add puts the caller's back, so the dialog answering the refusal still names the Library it was opened from.

**The Users page.** `GET /users/r/:repoId` (`routes/web/UsersController`, a full page) and its partials (`routes/web/partial/UserActionController`, under `/htmx/users/r/:repoId`): the account cards (`/accounts`, which the page reloads after a change) and the Add User modal (`/dialogs/add`) and its create (`POST /add`), each `@requireAccountCreator()`: an Admin, or the holder of Create Users or Create Guests in any Library, so the page opens from any Library the account sees; the edit form (`/dialogs/edit`) and its save (`PUT /edit`), the Set password dialog and its save (`PUT /password`), Deactivate and Reactivate (`PUT /deactivate`, `/reactivate`), the Delete dialog (`/dialogs/delete`, naming the assets that move) and the delete (`DELETE /account`), each `@requireAdmin()`. The account's ID (`Api.Field.User.ACCOUNT_ID`) is a query parameter of a dialog and of the delete, and a body field of the other writes, the form's fields are `Api.Field.User`'s (`libraryIds`, and `permissions` as "<Library ID>:<Permission>"), read by `AccountForm.submittedIn`; a Permission given in a Library gives access to it too. Every account and Library ID a request names is held to `Validators.isUuid` (`UserActionController.uuid`), anything else a 400 before it reaches a statement or a log line. The edit form carries the state it was opened over, and its title names the account as stored (`AccountForm.storedName`), whatever name a refused save typed. The form renders the creator's ceiling (`UserActionController.ceilingOf`) and nothing above it; a refusal of a field comes back as the form (`dialogFormValidationResponse`), an unchosen type with every other field's error (`UserService.fieldErrors`), and a refusal above the ceiling as a 403 through `answering`. The cards open on the first tab that holds one (`UserActionController.startTab`). Every account's own password is `routes/web/partial/OwnPasswordController` (`GET /htmx/account/dialogs/password`, `PUT /htmx/account/password`), whose paths name no Library, so any account logged in reaches them. Every account's info dialog is `routes/web/partial/AccountInfoController` (`GET /htmx/account/r/:repoId/dialogs/info`, any account with access to the Library, whose Permissions it shows): the account, its type, its Permissions in the Library and its Libraries, from the token's claims and grants (the Libraries' names from `getAccessibleTo`), and its times, when it was added and last logged in (`UserService.accountTimes`, read from the database as instants) and when the session's token expires (`RequestContext.sessionExpiresAt`). The front end is in `views/AGENTS.md` (**Users page**).

**Audit log.** `audit_event` is append-only: `AuditService.record(event, actor, target, detail, clientIp)` writes an `AuditEvent` (its type an `AuditEventType`, stored by `dbValue`; the actor and the target as `AccountSnapshot`s, since accounts change and are deleted; the actor is None for a failed login) in the caller's transaction when there is one, so the event commits or rolls back with the change it records, and logs it at INFO once the outermost transaction has committed (`TransactionManager.afterCommit`), so a rolled-back event is never logged. `AuditService` has no generic writes and reads no event; there is no screen. The events recorded are the logins (`loginAndSetUser`), the account writes of **Account management**, each with the client IP of its request (`BaseController.clientIpOf`), the setup Admin's creation (`SystemService.initializeSystem`, acted by the Admin itself, `"setup": true` in its detail), and each grant a new Library gives (**New-Library grants**).

## Import Pipeline

Pekko Streams pipeline in `service/ImportPipelineService.scala` and `pipeline/flows/`: one flow for both engines, a substream per repository. A stage's work runs in a future on the import dispatcher (`Altitude.importDispatcher`, `altitude.import-dispatcher`: a `thread-pool-executor` with a fixed pool of `Altitude.importParallelism` threads: the `import.parallelism` Setting as it was saved when the server started, a Restart setting, where 0, the default, means half the cores or what half the machine's memory (a container's limit in a container) affords beside the shared net and the two Scene models (`ImportParallelism.FIXED_COST`: `POOL_COST`, 384 MB, and `SCENE_MODELS_COST`, 1152 MB), whichever is fewer, and never fewer than 2 (`util/ImportParallelism`), and `import.parallelism.max` in the server config caps it whatever the Setting says, 0 being no cap and any other value under 2 stopping startup; added to the app's config when `Altitude` creates the actor system), never on the default dispatcher, which the stream actors, the import status feed, the SQLite optimize schedule and the Import history prune share: a stream actor only routes, so the stages of every repository's import work at once without asynchronous boundaries, and the dispatcher's threads bound the work of all of them. Per repository, in order:

| Stage | Operator | Touches |
|---|---|---|
| `CheckMediaTypeFlow` | `map` | nothing |
| `CheckDuplicateFlow` | `mapAsync(1)` | database read |
| `AssignIdFlow` | `map` | nothing |
| `ExtractMetadataFlow` (metadata, dimensions) | `mapAsync(importParallelism)` | file |
| `IndexFlow` | `mapAsync(1)` | database write |
| `DetectFacesFlow` | `mapAsync(importParallelism)` | file |
| `MeasureImageFlow` (Image quality, perceptual hash, Face sharpness, Scene embeddings) | `mapAsync(importParallelism)` | file |
| `RecognizeFacesFlow` | `mapAsync(1)` | database write, face files |
| `FileStoreFlow` | `mapAsync(1)` | rename |
| `AddPreviewFlow` | `mapAsync(importParallelism)` | stored file, preview file |
| `MarkAsCompleteFlow` | `mapAsync(1)` | database write |
| `DiscardDroppedFlow` | `mapAsync(1)` | database write, files |
| `SettleImportFileFlow` | `mapAsync(1)` | database write, a Watch folder's source file |
| `StripBinaryDataFlow` | `map` | nothing |

The stages that only read and decode the file work on several assets of a repository at once; no stage that writes to the database does, and `mapAsync` hands the assets on in upload order, so faces are matched, and people started, one asset at a time in the order uploaded, and SQLite's single write connection sees one writer per stage. A repository's import holds at most six connections at once, one per database stage. `DetectFacesFlow`, `MeasureImageFlow` and `AddPreviewFlow` each decode an image and release it inside their work, and no decoded image rides on the element, so a thread holds one at a time and the dispatcher bounds the decodes in flight at `importParallelism` in total, for every repository together, while an image is decoded three times over its import. `ImportParallelism.THREAD_COST` (512 MB) budgets a thread's YuNet, one decode of a large image and the file copy a decode leaves for the finalizer, and the working memory of its Scene model passes (about 45 MB), with a margin left on purpose for a larger image and for native allocator overhead; the two Scene models' sessions, shared by the threads, are `SCENE_MODELS_COST` (1152 MB) in `FIXED_COST` beside the ArcFace pool's `POOL_COST`. The detections ride on the element from `DetectFacesFlow` through `MeasureImageFlow` to `RecognizeFacesFlow` (`AssetWithData.detectedFaces`, a `DetectedFaces`), which `StripBinaryDataFlow` leaves behind. `MeasureImageFlow` (`AssetService.measureImage`) decodes a still image once more, measures its Image quality and perceptual hash (`util/ImageMeasurement`) over the frame and those detections' boxes and embeds the same upright `Mat` with the two Scene models (`util/SceneEmbedder`), putting the metrics, the hash and the embeddings on the asset for the completion stage to store, and each detection's Face sharpness, which recognition stores in the Face's one insert; a Video and an animated image pass through untouched.

Each stage's writes are a short transaction of its own, opened by the service it calls (`LibraryService.persistAndIndex` for the index stage, `FaceRecognitionService.recognizeAndStore` for the faces, `completeImport` for the completion, which also assigns the asset to the Sequence of its burst through `SequenceService.assign`, or sorts it into its Import's destination folder (**Sorted on arrival**), and settles its Import file, if it is a file of an Import, in that same transaction), so SQLite's one write connection runs them one after another, and a stage commits before the next one reads the asset. `Altitude.parallelism` (the core count) sizes the import and purge queues' buffers, not the concurrency. The purge queue's stages still run on the default dispatcher. Adding a new pipeline stage = add a `Flow` in `pipeline/flows/`, built with `PipelineUtils.stage`, and wire it into `ImportPipelineService.combinedFlow`.

The import and purge queues are each a `QueuedPipeline` (`pipeline/QueuedPipeline.scala`): the service's flow materialized once, for the life of the app, behind a `Source.queue` that `ImportPipelineService.addToQueue` (each uploaded file, from `ImportService.upload`, and each file of a Watch folder's scan, from `WatchFolderService`) and `PurgePipelineService.enqueue` offer to. It owns the queue, the stream with its supervision strategy, the completion log and `shutdown`, and runs its callbacks on the actor system's execution context. `run` materializes a service's flow per call instead (`LibraryService.addAsset`, tests). `offer` waits while the queue is full, with no thread held, and the offers take turns in the order they were made, the queue being handed one at a time (a `Source.queue` fails an offer made while as many as it admits wait for room), so any number of uploads and scans may offer at once (`ImportPipelineServiceTests`); it fails with `QueueRefusedException`, logged at WARN, when the queue does not take the element: it dropped it, it is closed, or its stream has stopped. `addToQueue` deletes the staged file the queue refused and passes the failure on, and `ImportService.upload` records the file failed, as a Watch folder's scan does, ending there (**Watch folders**); `enqueue` logs a refused asset at ERROR and goes on with the next, and the refused asset stays purge-pending for the next startup. The stream runs until `shutdown()` completes the queue, which then waits for the stream to finish what it has accepted, for at most the `pipeline.shutdown_timeout` Setting (30 s, whole seconds, read when `shutdown()` runs), and logs at WARN when the limit cuts it off. `Altitude.cleanup` stops the Watch folder scans (`WatchFolderService.stop`), shuts down the import queue, then the purge queue, before it closes the transaction manager. What a timeout cuts off is handled at the next startup: the prune discards an unfinished import, and `requeuePurgePending` queues a purge again.

A queue whose stream fails stays down: every later offer is refused. In development, `dev.restart_pipeline` restarts it instead (`Altitude.isPipelineRestartEnabled`, which both services pass to their `QueuedPipeline`): the stream is a `RestartSource.onFailuresWithBackoff` (1 s, doubling to 30 s, randomized by 0.2) over one factory, which logs each start at INFO and makes a new `Source.queue`, pre-materialized and stored as the current queue in an `AtomicReference`, that `offer` reads. The first start is made with the pipeline, so an offer always finds a queue. A restart is logged at ERROR with the failure's stack trace; a stream that completes is not restarted. What a restart loses: an offer during the backoff reads the stopped queue and is refused, and the assets in flight or buffered when the stream failed are gone (the next startup's prune discards an import `IndexFlow` had persisted, and startup empties staging). A `KillSwitches.single` follows the stream: when the current queue has stopped (the backoff), `shutdown()` ends the stream through it rather than waiting for a restart, and once shutdown has begun, a restart ends the stream instead of starting it again.

The pipeline works on **staged files**, never on byte arrays: `AssetWithData` carries the asset and the path of its file. An uploaded file lands in `data/staging/<uuid>` (`StagingService`; `ImportController.uploadFile` streams the request's body there), a Watch folder's scan streams a copy of its file there, a test or an `ImportAsset` stages a copy, and the checksum, the file's SHA-256 in lowercase hex, is streamed (`Sha256.hex(path)`, the same value as over the bytes). `FileStoreFlow` renames the staged file into `files/<id[0:2]>/<id>` (`FileStoreService.assetFile(id)` exposes it), so a staged file is consumed by exactly one import; after that flow the element's path is the stored file. `AssetWithData.bytes` reads the whole file for the image-only consumers (thumbnails, face detection, image measurement); an image's dimensions are read from its header alone (`AssetService.getDimensionsAndDuration`, through `ImageIO`'s readers), and so is an animated GIF's playing time (`ImageUtil.gifPlayingTimeMs`: the sum of its frame delays, a delay of 10 ms or less playing for 100 ms as in browsers), which becomes its `duration_ms`. Face detection, the image measurement and the preview are the only three decodes, all through `ImageUtil.decode`: OpenCV, or ImageIO for a format the bundled OpenCV has no codec for, GIF among them (an animated GIF's first frame), laid out as OpenCV would have, BGR, or BGRA for the preview of an image with alpha. The Preview (`ImageUtil.makeImageThumbnail`) is one OpenCV pipeline from the decoded image to the bytes: scaled with `INTER_AREA` to fit the 200 px box, turned upright by its EXIF orientation (`orient`: `Core.flip`, `rotate` and `transpose`), centered in the square box on a transparent border (`letterbox`, 8-bit BGRA through `toBgra`) and encoded by `encodePreview` as a lossy WebP (`image/webp`, `Const.AssetView.PREVIEW_WEBP_QUALITY` = 80; libwebp keeps the alpha plane exact, and drops it when every pixel is opaque); no PNG, ImageIO or `AffineTransform` in between. `FileSystemStoreService` writes it as `preview/<id[0:2]>/<id>.webp`. Face detection skips an animated image (`FaceRecognitionService.detect`: an image with a duration), and the grid gives it a Video's play badge and Duration row. `StripBinaryDataFlow`, after the last working stage, is where the file leaves the pipeline: an imported asset goes on to the sinks as its `Asset` alone; an asset the pipeline drops carries its staged file on in `InvalidAsset`, for `DiscardDroppedFlow` to delete. `Altitude` startup empties staging.

**Failures.** No single asset can stop the pipeline. Every stage runs its work for one asset under `PipelineUtils.guarded`, in the element's `PipelineContext` (`withContext` binds `RequestContext.repository`, `account` as the context has it, and `permissions`, the account's when it queued the element (none with no account), for the work alone, so a pooled thread never keeps a request's: an import always has one, the uploading account or a Watch folder's owner, the startup's requeue of purge-pending assets none): whatever the work throws drops the asset, an `InvalidAsset` with that cause, and the stream goes on. `PipelineUtils.stage(name, parallelism)` builds a `mapAsync` stage that runs its work under the guard, on the import dispatcher (`guardedAsync`), for an asset still in the pipeline and passes a dropped one on; `CheckMediaTypeFlow` (a `map` over the raw input) calls `guarded` itself; `AssignIdFlow` and `StripBinaryDataFlow` only reshape the element, and `DiscardDroppedFlow` and `SettleImportFileFlow` work on the import dispatcher outside the guard (see below). A stage catches a cause itself only to report it as another: `RecognizeFacesFlow` turns a `DuplicateException` into `SamePersonDetectedTwiceException`. A file whose decoder cannot read it has a named cause: `ImageException` when no image reader takes an image or can read its header (`AssetService.getDimensionsAndDuration`), or neither OpenCV nor its ImageIO fallback can decode it (`ImageUtil`, for face detection and the preview: a corrupt body), `VideoException` when FFmpeg cannot open a video or no frame of it decodes (`VideoService`). Each drop is logged once. A cause `PipelineUtils.isExpectedDrop` names (`UnsupportedMediaTypeException`, `ImageException`, `VideoException`, `DuplicateException`, `SamePersonDetectedTwiceException`, `ImporterUnavailableException`, `ImportDestinationException`) is logged at INFO in one line, with the repository, by `AssetErrorLoggingSink`; any other is logged at ERROR with its stack trace by the guard, naming the stage and the file. The measurement stage is the one stage that swallows its own failure: `AssetService.measureImage` logs it at WARN and the asset imports unmeasured, since the metrics are derived data and NULL is a state every reader handles. A failed Import file's reason names the expected causes and a `StorageException`, and any other by its exception's simple class name, never by its message (`PipelineUtils.dropReason`), which the Import history shows. A queue's stream resumes past a failure outside a stage's work (a supervision strategy that logs it at ERROR) as a last resort: such an element reaches no sink, so it is neither reported nor discarded, and no stage relies on it.

**A dropped asset leaves nothing behind.** `DiscardDroppedFlow` deletes a dropped asset's staged file and calls `LibraryService.discardImport`, which undoes what the import wrote, so the same file can be uploaded again at once (`AssetService.getByChecksum` sees every row, finished or not). It is a no-op for an asset never persisted (dropped before `IndexFlow`, or a duplicate the index refused) and for one that completed. In one transaction it locks the people of the asset's faces and moves every cover off those faces to the person's best face elsewhere (`PersonService.moveCoversOff`, through `PersonDao.lockAssetPeople`, `FOR UPDATE` on PostgreSQL), so a face another import gives one of them meanwhile keeps that person and no cover is left on a face that goes; gives back the face counts the import added (`recycleFacesForAssets`); deletes the row while `is_pipeline_processed = false`, which cascades to its faces, its Search document and its metadata parameters; and deletes each of those people left with no face row (`deletePeopleWithoutFaces`): recognition matches face rows, so only this import can have started such a person. After the commit it deletes the files: each face's (`PersonService.purgeFaceFiles`, which the purge queue shares), the stored file and the preview. A completion that fails is a drop like any other and is discarded the same way; the stats count an asset only once its import completes, so a discard changes none. A discard that fails is logged at ERROR and swallowed, so the drop is still reported with its own cause, and the next startup's prune tries again.

**Import records.** An **Import** and its **Import files** (`CONTEXT.md`) are the tables `import` and `import_file`, written through `ImportService` (`Altitude.service.imports`) alone: `open(source, name, destFolderId, watchFolderId, expectedFiles)` (the context account's: an upload's, or a Watch folder's scan's, which is its owner's; the destination folder and the Watch folder are read in the repository, and a destination in the Trash is refused), `addFile` (a pending file, refused once the Import is marked complete), `settle(fileId, outcome, reason, assetId)`, `close` (marks it complete: no more files will come), `list` (the ones in progress first, then the newest first, paged) and `files(importId, outcome)`, with what the Import history reads (**Import history and the status feed**). An Import's five counters (`pending`, `imported`, `duplicate`, `unsupported`, `failed`) are its files by outcome, and `settle` writes the file's outcome and moves the counters in one transaction, by single statements that read the row as they change it (`ImportFileDao.settle` takes only a pending file, `ImportDao.fileSettled` adds and subtracts in place and stamps `closed_at` when the Import `is_complete` and that was its last pending file), so files settling at once on PostgreSQL add up (`ImportServiceTests`, by `contend`); a file settled already keeps its first outcome. An Import is in progress until `closed_at` is set: complete and nothing pending. `expected_files` is how many files it was opened to hold, what an upload is about to send or a scan to offer, NULL when it was not told: `Import.expectedTotal` is that number while the Import takes files, or the files it has when it has more or was told none, and the files it has once it is complete, and `Import.remaining` its pending files with the ones expected and not given yet, which is what the Import history counts as remaining, so its bar fills as files settle rather than as they arrive. A file in the pipeline carries its Import file as `AssetWithData.origin`, an `ImportOrigin(importFileId, folderPath, source)`: the Import file, the folder names under the Import's destination that the file lands in (**Sorted on arrival**), and `source`, the file in its directory for a file of a Watch folder, none for an upload's; an `ImportAsset` and the tests' plain fixtures carry none and nothing is settled for them. An imported file is settled `imported`, with its asset, by `completeImport` in the completion's transaction, so a completion whose settle fails is a drop; a dropped one by `SettleImportFileFlow`, after the discard, through `ImportService.settleDropped`: a `DuplicateException` is `duplicate`, pointing at the asset that has the checksum with where it is as the reason ("Triage", "Top level" for the root folder, or the folder path), and only an asset whose own import is complete makes a file a duplicate: the stage settles a repository's files in the order they came, so the copy the file matched, an earlier file of the queue, has completed or was dropped and discarded by then, and a file whose content no completed asset has (the first of two copies failed for a reason that is not the content's, or the asset was recycled since) is `failed`, `Const.Msg.Err.COPY_NOT_IN_LIBRARY`, with no asset, never recorded as already in the Library; an `UnsupportedMediaTypeException` is `unsupported`, anything else `failed` with `dropReason`'s words. A settle that fails there is logged at ERROR and the file stays pending until the next startup. The stage then tells a Watch folder what became of its file, imported or dropped (an origin with a `source`: `WatchFolderService.settled`, **Watch folders**). At startup `App` runs `ImportService.startup()` before anything is offered to the import queue. Its first step is `failInterrupted()`: in every repository each file still pending becomes `failed`, "Interrupted by a restart", and each Import in progress is closed. A reason is a phrase in sentence case with no full stop, as `dropReason`'s are, shown as it is stored. An Import's name and a file's path are what a client sent, so `ImportService` logs them through `Util.printable` (`ImportService.logged`: control characters escaped, the path cut at 512 characters), and a line break in one starts no log line of its own. Its second is the prune: `ImportService.prune()` deletes, in every repository, the closed Imports opened more than the `import.history.days` Setting ago (Live, 90; 0 keeps them forever) with their files by the key's cascade, so an Import the first step closed that is older than that goes too, and has the Watch folders forget the files long absent from their directories (**Watch folders**). The prune runs at startup, for a server restarted more often than daily, and daily after: `Altitude` schedules it on the actor system, beside SQLite's optimize, and cancels it at cleanup. Both run it through `pruneOrLog()`, which logs a failure at ERROR and does not throw, so a failed prune neither stops the start nor ends the schedule.

**Uploads.** The Import page uploads through four routes of `ImportController`, each `@requirePermission(Permission.Import)` and answering JSON (`answeringJson`): `POST /import/r/:repoId/imports` opens an Import (`ImportService.openUpload`: the JSON body's optional `name`, the uploaded folder's, `destFolderId`, which takes Organize as well, a `ForbiddenException` once the folder is read, so another repository's folder is a 404 and never a 403, and `expectedFiles`, the number of files the page is about to send; a folder in the Trash is a 400, and so is a number that is no whole number from 0) and answers its ID; `POST …/imports/:importId/files?relPath=` takes one file, the request's body, which is streamed into staging (`StagingService.stage`) and handed to `ImportService.upload`: added to the Import, pending, described (`LibraryService.stagedFileToAsset`, under the name that ends the path) and offered to the import queue with its origin, the Import file and the folder names of the path, the request waiting while the queue is full; `POST …/imports/:importId/failures` records a file the page could not send after its retries (`ImportService.addFailedFile`: its `relPath` and `sizeBytes` in a JSON body, added and failed, "Upload failed", in one transaction); `POST …/imports/:importId/close` closes the Import (`ImportService.closeUpload`), which is also what cancelling an upload does. The three routes that name an Import take only an upload the account itself opened (`ImportService.ownUpload`, read in the repository first, so another repository's is a 404): any other Import of the Library, another account's upload or one that is no upload, is a `ForbiddenException`, a 403, so no account sends files into an Import whose destination it may not hold Organize for. The two that give the Import a file, the files and the failures routes, take Organize again when the Import has a destination (`ownUploadTakingFiles`, by the request's Permissions): an account whose Organize was taken away while its upload was open is answered 403 from its next file on, so it sorts no more files and creates no more folders, and the page stops sending and closes the Import, which the close route, taking `ownUpload` alone, still lets it do. A file's path is relative to what was chosen, its bare name for a file chosen on its own, names separated by "/" (`util/RelPath`): a path with an empty name, a ".." or a name imports ignore is refused with a 400 before its body is read, and so is an empty file, and none of them is recorded. `util/IgnoredFiles` is the one list of ignored names (a name starting with a dot, `Thumbs.db`, `desktop.ini`, `@eaDir`, `#recycle`, `$RECYCLE.BIN`, `*.part`, `*.tmp`, `*.crdownload`, compared in lower case), a file's or a directory's; the Import page is served it (`IgnoredFiles.toJson`) and leaves such files out before it sends anything. The files route answers the Import file with its outcome, and answers 200 whenever the file was recorded: a file that was added and then could not be described, or that the queue refused, is settled `failed` there (nothing else would settle it before the pipeline has it), its staged file deleted, and answered as failed, so the page does not send it again; a file that is not added leaves nothing staged. A file of an Import whose destination folder was recycled since it was opened is answered so too: the route asks `ImportService.failForLostDestination(importId, relPath, <the request's Content-Length>)` before it reads the body, which adds the file and fails it in one transaction with the reason its completion would give (`DESTINATION_IN_TRASH`), so every remaining file of such an upload is in the record and none is staged or run through the pipeline; a request that states no length is staged, and `upload` fails it the same way, never offering it. An Import that is not the Library's is a 404, and one that takes no more files a 409 on the files and failures routes (`answeringUpload`); on those and on the 403 the page stops sending.

**Sorted on arrival.** An Import with a destination folder (`import.dest_folder_id`) sorts its files as their imports complete, and one without leaves them in Triage. `LibraryService.completeImport` reads the destination through `ImportService.destinationOf(importFileId)` in the completion's transaction and, when there is one, resolves the folder the file lands in with `FolderService.ensurePath(destination, origin.folderPath)`, the destination itself for a file at the top, writes the asset's `folder_id`, clears `is_triaged`, assigns no Sequence and counts the asset as sorted. `ensurePath` walks the names from the parent down: a folder is found by its name key among its parent's folders (`FolderDao.getChild`), live or recycled, and reused, a recycled one restored alone, as `restoreRecycledAsset` restores an asset's folders, and a missing one added. So a folder is born in the transaction that completes the first asset landing in or below it: a folder of duplicates or unsupported files alone never appears. The creators of one folder take turns on `FolderDao.lockName(parentId, nameKey)`, an advisory lock, which `FolderService.add` takes too, so of two transactions that both miss a folder the second finds the one the first created (`FolderServiceTests`, by `contend`; on PostgreSQL it fails on `folder_02` without the lock). `FolderService.rename` and `move` take that lock too, for the name they bring a folder under, so a folder renamed or moved into a name an import is creating is the folder the import finds, or waits for the import and is refused as a duplicate; each of the three takes one lock and `ensurePath` takes its locks from the parent down, so none waits on another in a cycle. The completion of a file with a destination and a delete of a folder (`LibraryService.deleteFolderById`) take turns on `FolderDao.lockTree()`, an advisory lock on the Library's folder tree, which `ImportService.destinationOf` takes before it reads the destination and the delete before it reads what it deletes: a delete only marks its folders, which neither a reader nor an asset's key to its folder waits for, and it lists the folders and assets under the one it deletes before a completion in flight commits its own, so without the turn a file completing while its destination is deleted left a live asset, or a folder it created or restored, under a folder in the Trash. Whichever goes second sees what the first committed: the completion fails with the destination in the Trash, or the delete recycles what the completion sorted (`ImportPipelineServiceTests`, by `contend`; on PostgreSQL neither waits without the lock). Both take it first, before a name's lock or a row's, so it adds no cycle. `moveAssetsToFolder` does not take it: a move reads its destination without asking whether it is in the Trash at all, so the turn alone would close nothing there. A destination recycled while a file was in the pipeline (the upload route fails the files that arrive after it, **Uploads**), a folder name the folder rule refuses, and a name that is taken by the time the folder is added (past the lock, as the root's own name is under the root) fail the completion with `ImportDestinationException`, an expected drop whose message is the file's reason (`Const.Msg.Err.DESTINATION_IN_TRASH`, `DESTINATION_FOLDER_NAME` around the rule's own words or `FOLDER_NAME_TAKEN`): nothing of the path is created. `sortInto` turns the `DuplicateException` of such a name into that cause, since a `DuplicateException` reaching `SettleImportFileFlow` is a file whose content the Library has, and nothing else.

**Import history and the status feed.** The Import page's history is read by every account that holds Import in the Library, whichever account delivered an Import, through `routes/web/partial/ImportHistoryController`, both routes `@requirePermission(Permission.Import)`: `GET /htmx/import/r/:repoId/history?shown=` renders `htmx/import_history` over `ImportService.history(shown)`, the Library's first `shown` Imports as `list` orders them, each an `ImportEntry`: the Import, the moment it was opened as an instant (`ImportDao.instantOf`), the name of the account that delivered it (none for a deleted account; a Watch folder's scan carries its owner, and the history says "Watch folder" by the Import's `source`), its destination folder's path (`NamedPath.SEPARATOR`) and whether a restart failed files of it, one query over the closed Imports with failed files (`ImportFileDao.havingReason`, by the index on a file's Import and outcome); `GET /htmx/import/r/:repoId/imports/:importId/files?outcome=&shown=` renders `htmx/import_files` over `ImportService.filesShown`, the Import with its first `shown` files in path order, those of one outcome when `outcome` names one (an unknown one is a 400), their total the Import's counter, read in the same transaction. `shown` is held between a step and a most (`Const.ImportHistory`: 20 and 500 Imports, 50 and 500 files), so neither list is ever read whole; the page asks for a step more at a time. Every name is rendered by Twirl, escaped.

The history is kept live over the Library's WebSocket, `/import/r/:repoId/status` (`ImportController.pipelineStatus`, whose handshake checks the origin, the login, the Library and Import in it: **Request Lifecycle**). `ImportService` tells its listeners (`onChange`) of an Import after each commit that changes it: opened, given a file, a file of it settled, marked complete. `changed(importId)` registers the telling with `TransactionManager.afterCommit` and reads the Import then, so a change that rolls back is told to nobody, a completion's settle is told when the completion commits, and what is told is the Import as committed, never a state inside a transaction that changes it twice; two changes committed at once may be told out of order. `Altitude` wires the listener to `ImportStatusWsActor.ImportChanged`. The actor keeps its sockets by Library and account (`AddClient` answers a socket `{"connected": true}`) and each Import as it last heard of it, dropping a state that is no further along than the one it has (`progress`: files added, files settled, complete, closed, each of which only grows), and sends an Import's status to every socket of its Library: its first change, and one after an interval with none, at once; a change inside the interval (`PUSH_INTERVAL`, 1 s, a timer per Import) when the interval ends, as the Import stands then; and its close at once, the last message of the Import, which is remembered for a minute so a change told late is not pushed after it. A status is rendered once per push, and only when the Library has a socket. The message (`statusMessage`) is JSON as `hx-ws` takes it (`Api.Field.ImportStatus`): `content`, the Import's status element (`includes/import_status`: the bar and the count chips, with the title out of band, `includes/import_title`, since an upload of files is titled by its number of files, `Import.expectedTotal`), `target` and `swap`, the element of that ID replaced, and for the page's script `importId` and `closed`. The two includes take the Import as a parameter and read no request context, the actor having none. A change to what a Library's Watch folders show is a message of its own, `{"watchFolders": true}`, sent to every socket of the Library at once and swapping nothing (`ImportStatusWsActor.WatchFoldersChanged`): `Altitude` sends it for each change `WatchFolderService.onChange` tells of, and for an Import of a Watch folder opened or closed, which is when its card's counts change; the page reads the cards again. `ImportStatusWsActorTests` (unit suite) runs the actor on a system whose time the test moves (`ExplicitlyTriggeredScheduler`, of the classic test kit the build has) with sockets that keep what they are sent. The front end is in `views/AGENTS.md` (**Import page**).

## Watch folders

A **Watch folder** (`CONTEXT.md`) is a directory on the server that the app scans for one Library, importing the files that arrive in it; never a folder of the Library. It is the tables `watch_folder` (its name, its absolute `path`, unique in the instance, its destination folder, NULL for Triage, `deletes_imported`, `is_paused`, its owner `account_id`, `status_reason` and `last_scan_at`) and `watch_folder_file` (what it remembers of each file of its directory), written through `WatchFolderService` (`Altitude.service.watchFolder`) alone. A file is only ever copied out of the directory, and deleted from it when the Watch folder deletes imported files.

**Configuration and the path rules.** `add(spec)`, `update(id, spec)`, `remove`, `pause`, `resume` and `retryFailed` are an Admin's, by their routes (below), each one transaction. A `WatchFolderSpec` (name, path, destination, deletion) is held to the rules by `validated`, a refusal being a `ValidationException` that names every field refused (`FieldConst.WatchFolder.*`): a name, at most `Api.Constraints.MAX_WATCH_FOLDER_NAME_LENGTH` (80); a destination that is a live folder of the repository (one in the Trash is refused, one that is not the repository's is not found); and a path that is absolute (stored as typed, normalized) and, by `pathProblem`, an existing directory the server can list, writable when imported files are deleted, that overlaps neither one of the app's own directories nor another Watch folder of any Library, the same directory or one inside the other, each compared by real path, symbolic links resolved. The app's own directories (`ownDirectories`) are the ones it stores into, each resolved on its own, since any of them may be a symbolic link that leads out of the data directory (a store kept on another volume): the data directory, staging, the SQLite database's directory (`Altitude.sqliteDir`) and the file store down to each Library's directory and the directories in it. They are compared by what they are as well as by where (`OwnDirectories`: a directory's file key, `Files.isSameFile` where the file system gives none), the path's own ancestors and theirs included, so a second path to one of them that no symbolic link explains, a volume mounted twice, is refused too. `add` and `update` take `WatchFolderDao.lockPaths()` first, an advisory lock, so of two transactions adding overlapping directories at once the second checks its path against the first's row (`WatchFolderServiceTests`, by `contend`). The context account owns the Watch folder it adds or edits. An edit that changes the path forgets what was remembered of the old directory; one that switches the deletion on makes the handled files files to read again, so each is found a duplicate, or imported again if its asset is gone, and deleted then, never on the word of the memory alone; every edit clears what the last scan found wrong with the directory, and leaves a paused Watch folder paused, with no reason. `remove` deletes the row and, by the key's cascade, its memory: the directory's files stay, its Imports stay in the history (`import.watch_folder_id` is `ON DELETE SET NULL`), and a file of it still in the pipeline is imported and not deleted. `retryFailed` makes the `final`, `retry` and `parked` files files to read again, never tried.

**Scanning.** `App` calls `start()` last at startup: every Watch folder of every Library that is not paused is scanned at once (`scanAll`), which catches up on what arrived while the server was down, and a round of scans follows every `watch_folder.scan_interval` minutes (a Live setting, 10, from 2 to 360), each scheduled on the actor system by the one before it, with the Setting as it is then (`start` takes the schedule as a parameter, the actor system's by default, so a test drives the rounds itself); a round that fails is logged at ERROR and the next still comes. `stop()`, the first step of `Altitude.cleanup`, cancels the round to come, and a scan that is running hands the queue nothing more. `scanNow(id)` is "Scan now": a paused Watch folder, and one whose destination folder is in the Trash, is an `IllegalOperationException`. `scan(id)` runs on the import dispatcher, one scan of a Watch folder at a time, and its future ends when its last file is offered to the import queue: `ScanResult.Scanned(offered)`; `NotStarted` when a scan of it is running or the server is stopping; or `Blocked(reason)` for a Watch folder that is not scanned as it stands: one that is paused, one whose owner is no active Admin, which the scan pauses with that reason, and one whose destination folder is in the Trash (each logged at INFO, once per change), and one whose directory fails the path rules now, or holds one of the app's own directories wherever the walk meets it (below), which is stored as its `status_reason`, cleared by the next scan that walks it, and logged at WARN on each change. None of them touches what the Watch folder remembers, and each is tried again by the next scan.

A scan walks the directory's real path (`walk`): a symbolic link is neither followed nor read, a file or a directory under a name imports ignore (`util/IgnoredFiles`) is left out, a directory with everything in it, and so are an empty file, anything that is no regular file and whatever cannot be read. The walk goes on past a directory it cannot read, one it cannot open or one whose listing an I/O error ends midway (`postVisitDirectory`, whose default would throw and end the scan), so the rest of the tree is imported, and the scan stores which as the Watch folder's `status_reason` (`Walked.problem`: the directory's path, or how many with the first), cleared by the first scan that reads them all: the card says Unavailable with it, logged at WARN on each change. The walk never enters one of the app's own directories, told by what it is (`OwnDirectories.has`, the file key the walk reads with each directory), under whatever path the walk meets it: it ends there, nothing it found is remembered or read, and the Watch folder is Unavailable, its reason naming the directory (`Const.WatchFolder.PATH_HOLDS_DATA`). This is what keeps a scan out of a store that lies inside the watched directory under a second path, which the path rules cannot see from the outside. `remember` writes what the walk found to the memory, in one transaction, and returns the files to read, in path order. A file is remembered by its path under the directory (`rel_path`, names separated by "/"), its size and its modified time, in a state (`WatchFileState`): `seen` (not read yet), `handled` (imported, or a duplicate of an asset of the Library), `final` (unsupported, or an image or video that cannot be decoded), `retry` (failed, to be read again) or `parked` (failed `Const.WatchFolder.MAX_ATTEMPTS`, 3, times). A file whose size or modified time changed is a new file, `seen` and never tried, whatever became of it before. A `seen` file is read once it has rested: `last_seen_at`, for such a file the moment it was first seen as it is, is at least the rest (`REST`, `Const.WatchFolder.REST_SECONDS`, 5 s, far shorter than the scan interval) before this scan's walk began, so two scheduled scans in a row always span it and two presses of "Scan now" do not shorten it. A `retry` file is read by the next scan; a `handled`, `final` or `parked` one is left alone, and so is a file still in the pipeline (`inFlight`, in memory, by Import file; `remember` reads it before the rows, since a file leaves it only once its row is written, so a file that settles between the two reads is not handed to the pipeline again). A file found as it is remembered is stamped again only once its stamp is a day old (`LAST_SEEN_STEP`), so a scan that finds nothing new writes the Watch folder's `last_scan_at` alone.

Each file to read is handed to the pipeline as the Watch folder's owner, with every Permission (`take`): a copy is streamed into staging, never through a symbolic link put in the file's place (`LinkOption.NOFOLLOW_LINKS`), described (`LibraryService.stagedFileToAsset`, under the name that ends the path), added to the scan's Import and offered to the import queue with its origin, `ImportOrigin(importFileId, <the folder names of the path>, source = <the file>)`, one offer after another under the queue's backpressure, with no thread of the import dispatcher held while an offer waits. The file is never moved: its source is the retry. The scan's Import is opened by its first file (`ImportService.open`: `ImportSource.WatchFolder`, the Watch folder's name, destination and ID, expecting the files the scan is about to read) and marked complete after its last offer, so a scan with nothing to read opens none. Before each file the scan ends if the server is stopping or the Watch folder is not as the scan read it: removed, paused, with another path, destination or owner, or its destination in the Trash. A file that is gone, or not as the walk found it, or that changes while it is copied, is left for a later scan; one that cannot be read is recorded failed in the Import (`Const.WatchFolder.UNREADABLE_FILE`) and counts as an attempt; one the import queue refuses is recorded failed with the refusal as its reason, counts as no attempt, and ends the scan.

**The pipeline's end.** `SettleImportFileFlow` tells the Watch folder what became of each of its files, imported or dropped, once the transaction that settled the Import file has committed: `settled(origin, asset, cause)`. It writes the file's memory, while the file is remembered as it was staged: `handled` for an imported file and for a duplicate of an asset whose own import is complete; `final` for an `UnsupportedMediaTypeException`, an `ImageException` or a `VideoException`, and for a duplicate that is the stored file of the asset it matches under another path (`isStoredFileOf`, by `Files.isSameFile`: a hard link to it, or the store reached through a second mount; logged at WARN), which is thereby never `handled` and never deleted; one more attempt, `retry` or, at the third, `parked`, for any other failure; and nothing, so that a later scan reads the file again, for a failure that is the Watch folder's rather than the file's (an `ImporterUnavailableException`, an `ImportDestinationException` for a destination in the Trash) and for a duplicate of an asset whose import is not complete, or that is gone since. The Watch folder is read as it is then: one removed meanwhile remembers nothing. A failure of `settled` is logged at ERROR by the stage and leaves the memory as it was.

**Deletion.** A Watch folder with `deletes_imported` deletes a file from its directory once the write that made it `handled` has committed (`deleteSource`): an imported file, and a duplicate of an asset of the Library. An unsupported or failed file is never touched. The file must be the one that was read: under the directory's real path as it is now, below no symbolic link, a regular file with the size and the modified time it had when its copy was staged (its content is not read again); anything else is left where it is and logged, a changed file for the next scan to read as a new one. A file in one of the app's own directories or below one, by what the directories above it are (`OwnDirectories.at`), is never deleted, whatever path led the scan to it. The directories the delete leaves empty are removed, up to the watched directory, which stays, stopping at one that holds anything, an ignored file included, and at a symbolic link. A delete that fails is logged at WARN and the file stays `handled`. A paused Watch folder deletes nothing and leaves the file's memory as it is, so the file is read again, and deleted then, once it is resumed.

**Status and owner.** `cards()` is what the Import page shows of a Library's Watch folders, by name (`WatchFolderCard`): the status with its reason (`statusOf`: Paused, by an Admin or for its owner, with the `status_reason`; Paused while its destination folder is in the Trash, which nothing stores, so it resumes when the folder is restored or replaced; Unavailable, with the `status_reason` its last scan stored, why the directory was not scanned or which directories of it could not be read while the rest was; otherwise Watching), the destination's path, the last scan, whether a scan is running, and the imported and failed files of its Imports in the history (`ImportDao.countsByWatchFolder`, by `import_02`). `targeting(folderId)` lists the Watch folders that sort their files into a folder or a folder below it, for the folder Delete dialog's warning, and `fileCount(path, self)` counts the files a scan would find at a path, those it can read, none for a path that fails the rules, for the Watch folder dialog's deletion notice. The owner owns the assets the Watch folder imports, so it is an active Admin: a deactivation and a demotion pause the account's Watch folders in every Library (`pauseOwnedBy`, the reason `Const.WatchFolder.OWNER_DEACTIVATED` or `OWNER_DEMOTED`), a delete passes them to the deleting Admin with the assets (`passOn`; `watch_folder.account_id` has no delete action), and `resume` gives a Watch folder whose owner is no active Admin to the Admin who resumes it (**Account management**). With the Import history's prune (`ImportService.prune`), every Watch folder forgets the files absent from its directory for as long as an Import is kept, or for `Const.WatchFolder.FORGET_AFTER_DAYS` (30) when the history is kept forever (`forgetAbsent`): those last found that long ago and not by its last scan, so one that is not scanned forgets nothing. The memory is a table of its own, so pruning an Import never makes a file new. `onChange` tells its listeners, after the commit, of each change to what a Library's Watch folders show (one added, edited, paused, resumed, removed, found unavailable or available again, and a scan started or ended), which the status feed passes on (**Import history and the status feed**).

**Routes.** `routes/web/partial/WatchFolderController`, under `/htmx/watch-folders/r/:repoId`. `GET list` renders the cards (`htmx/watch_folders`) for a holder of Import, with their actions for an Admin alone; the Import page renders them itself (`ImportController.pipeline`, through `WatchFolderController.list`). Every other route is `@requireAdmin`: `GET dialogs/add` and `dialogs/edit?watchFolderId=` render the Watch folder dialog (`htmx/watch_folder_form`), `POST add` and `PUT edit` take its JSON (`Api.Field.WatchFolder`), `GET deletion-notice?path=&watchFolderId=` renders `includes/watch_folder_deletion_notice` over `fileCount`, `PUT pause`, `resume`, `scan` and `retry` name the Watch folder in a JSON body and answer 204, `scan` once the scan is started (a paused Watch folder, and a destination in the Trash, is a 409 saying so), and `GET dialogs/remove` and `DELETE watch-folder?watchFolderId=` remove one. A refused field re-renders the form through `dialogFormValidationResponse`, with the values submitted and the error under its field; "Keep folder structure" with no folder chosen is refused by the controller (`DESTINATION_REQUIRED`), which asks the service for a destination only with that switch on. A Watch folder's ID is a UUID or a 400, and one that is not the Library's a 404. The folder Delete dialog reads `targeting` (`FolderActionController`). The front end is in `views/AGENTS.md` (**Import page**).

## Library stats and purging

`StatsService` keeps six counters per repository in `stats`: the assets and the bytes that are sorted, in triage and recycled (the nav's Triage and Trash counts; the totals are summed on read). An asset counts from the moment its import completes (`LibraryService.completeImport`) until it is marked for purging, in one bucket: recycled when `is_recycled`, else triage when `is_triaged` (an asset recycled from triage keeps that flag), else sorted. Every library operation (recycle, move, restore, purge) writes the stats through `StatsService.transition(before, after)`, the assets as it read them and as it writes them, which is one `adjust`: the non-zero deltas, applied in one transaction in dimension-name order, so concurrent operations take the stat rows in one order on PostgreSQL. A stat row is `CHECK (dim_val >= 0)`: a write below zero, or to a dimension the repository has no row for, is a `ConstraintException` naming the dimension, and fails the operation's transaction.

The operations read the rows they change through one locking select in `AssetDao` (`getAssetsToRecycle`, `getAssetsToMove`, `getAssetsToRestore`, `getAssetsToPurge`; `lockTriaged`, the Sequence assignment's re-read of the undated matches, is the same select over the triaged rows): the context repository's completed assets that are not marked for purging, in ID order and `FOR UPDATE` on PostgreSQL (SQLite's one write connection serialises the writers). They count their stat changes from those rows and update exactly them, so an asset of another repository, an unfinished import and two requests for one asset are counted correctly. Restoring an ID that is no asset of the repository is a `NotFoundException`; a live asset, or one marked for purging, is ignored. A move (`moveAssetsToFolder`, which is also how an asset leaves the trash into a folder) writes `sequence_id` NULL in the same update that clears the triage flag, so a sorted asset never carries a Sequence; recycling and restoring leave the flag and the Sequence as they are.

A purge has two halves. The request marks the assets `is_purged` and takes them out of the recycled stats (`LibraryService.markForPurging`); from then on an asset is **purge-pending**, out of every library operation, and hidden from the trash view (`SearchRequestParser`). Once that commits, `PurgePipelineService.enqueue` feeds them to the purge queue one offer at a time, under its backpressure, and the queue moves every cover off each one's faces (`PersonService.moveCoversOff`: each person whose cover is one of them, whoever the person is, takes their best face on another asset not marked for purging, `FaceDao.getBestCoverCandidate`, or no cover when none is left), then deletes its face files (`PersonService.purgeFaceFiles`), files and row. An asset whose covers cannot be moved off is logged at ERROR and goes no further (`DeletePersonFilesFlow` passes it on to no later stage): its row, files and Faces stay, purge-pending, since the row's delete would drop a cover through the cover's key without a repick and lose the cover Face's files. A row whose delete fails is logged at ERROR and stays purge-pending (`DeletePurgedFromDBFlow`), so the queue goes on.

At startup `App` runs, once `Altitude` has migrated the database and loaded the Settings: `ImportService.startup()` (the Imports a stop interrupted failed and closed, then the Import history pruned; see **Import records** under **Import Pipeline**), `pruneDanglingAssets()` (each import a crash or a shutdown cut off, logged at WARN and undone by `discardImport`, files and face counts included, a cover on one of its faces moved off it first as on purge), `requeuePurgePending()` (every purge-pending row queued again, with no account: no request queued it, and a Library has no owner to stand in) and `reconcileStats()`, each through `forEachRepository`, which runs the operation in every repository's context and opens no transaction around it, so an operation's file deletes come after its own commit. Last, `WatchFolderService.start()` scans every Watch folder and schedules the scans to come (**Watch folders**): after the Imports a stop interrupted are failed, so no scan's Import is taken for one of them. `StatDao.reconcile` locks the repository's stat rows in write order, counts the assets that count with one aggregate bucketed as above, and sets the stats that differ; `StatsService.reconcile` logs each at WARN with its old and new value.

## Video

A Video is an asset whose `media_type` is `video` (there is no flag column); `LibraryService.SUPPORTED_MEDIA_TYPES` admits `image` and `video`, so an audio file stays unsupported. Decoding goes through FFmpeg by way of javacv: `build.mill` declares each bytedeco preset as its stub jar plus a `classifier=<platform>` jar with the natives of the detected platform (appending the platform to the version resolves nothing), and `VideoService` wraps `FFmpegFrameGrabber`, one grabber per call, nothing shared across threads. It takes a Settings supplier (`() => Settings`), not a `Config`, and reads the `video.*` Settings from one snapshot per call.

- `probe(path)` gives `VideoInfo`: the display size (the container's display matrix applied, so a phone's portrait recording is stored portrait, `width`/`height` on the asset), the duration (`asset.duration_ms`, NULL for a still image; an animated GIF's is its playing time), frame rate and audio presence. `AssetService.getDimensionsAndDuration` dispatches on media type.
- **Sampled frames**: `VideoService.sampleTimes(durationMs)` spaces Frame times evenly from the start at `max(video.faces.sample_interval_ms, duration / video.faces.max_sampled_frames)` (both Settings; defaults 1000 ms and 120), so a short clip is sampled every second and a two-hour recording about every minute. `sampledFrames(path, times)(consume)` decodes each as an upright BGR `org.opencv.core.Mat` for an iterator that lives as long as the call; the consumer releases each image. Frames are turned the way FFmpeg's own autorotate turns them: the container's counter-clockwise display rotation, negated, snapped to a quarter turn (`VideoService.uprightRotation`).
- **Preview**: `previewFrame(path)` is the first Sampled frame whose mean brightness clears the `video.preview.min_luminance` Setting (40 of 255, skipping a black leader), else the frame at a tenth of the duration, and a `VideoException` when no frame decodes; `AssetService.genPreviewData` hands the frame, a `Mat` upright already, to `makeImageThumbnail`'s `Mat` overload with orientation 1, so the 200 px WebP Preview, the map and the grid are the same as an image's.
- **Faces**: `FaceDetectionService.extractFaces` has a `Mat` overload (the byte-array one decodes and delegates). `FaceRecognitionService.detect` and `recognizeAndStore` dispatch on media type; for a Video, `detect` finds faces in every Sampled frame (each Face pinned to its Frame time, `face.frame_time_ms`, NULL for a Face in an image) and clusters the detections of the whole video by embedding: `FaceRecognitionService.cluster` is greedy leader clustering in descending Face quality (a detection joins the first cluster whose best member is within `face.recognition.cosine_distance_threshold`, else starts one), and `mergeClusters` then absorbs a cluster whose centroid is within the threshold of an earlier cluster's centroid, since a turning head drifts past a single leader. Each cluster is one Face: the crop, box, checksum, Frame time and quality of its best-quality detection, but the L2-normalized mean of all its members' embeddings as the vector, so the stored vector is steadier than any one frame and no longer derives from the saved crop. A cluster seen in fewer than `video.faces.min_cluster_frames` distinct frames (default 2) is match-only in that Video (see **Faces** below), so a passer-by in one frame cannot start a Person. One Face per Person per Video: when two clusters resolve to the same Person the lower-quality one is dropped, so a pose change does not fail the import. The debug artifacts of a frame are named by its Frame time (`<ms>ms-<file>-annotated.jpg`). Both pipelines get this through the service.
- **Dates and places**: metadata-extractor reads MP4 and QuickTime containers into `extracted_metadata`, so the resolvers still read persisted inputs only. `CaptureDateResolver` has two rungs below EXIF, XMP, IPTC and the PNG text chunk: `QuickTime Metadata` / `Creation Date` (`com.apple.quicktime.creationdate`, a local wall clock whose offset is discarded like every other; `qt_creation_date`), then, with the PNG tIME rung and above GPS and the filename, the container's `Creation Time` (`MP4 Video`, `QuickTime Video`, `MP4`, `QuickTime`; `container_creation_time`). The extractor describes that UTC instant in the JVM's zone, with a numeric offset on the track directories and a zone name on the container ones; `WallClockParser.parseUtcInstant` turns either back into the UTC wall clock, so the stored value does not depend on the server's zone, and the 1904 epoch remains a sentinel. The file-name rung, the last of the ladder, is described under **Search results and date grouping**. `GeoLocationResolver` tries EXIF `GPS`, then `QuickTime Metadata` / `ISO 6709` (`+37.3318-122.0312+015.000/`, also its degrees-minutes forms), then `MP4` / `Latitude` and `Longitude`. `Asset.getPublicMetadata` takes `deviceModel` from `QuickTime Metadata` / `Model` when EXIF has none.
- **Serving**: `ContentViewController` streams `file` content from the stored file through `RangeStreaming`, a `geny.Writable` window over a `FileChannel`: `Accept-Ranges: bytes`, a `206` with `Content-Range` for a single `bytes=a-b` range (`bytes=a-` and `bytes=-n` included), `416` past the end, `200` with `Content-Length` otherwise, and `Content-Type` is the asset's stored `mime_type` for images too. A player drops the connection whenever it has what it wants (a Video's metadata, the asset the user stepped away from), so a write the client refuses ends the response and is logged at DEBUG, while a failure to read the file is still an error. A `preview` is `image/webp` (`MimedPreviewData.MIME_TYPE`). The route has two gates (`requireLoginOrSignature`): a request with `exp` and `sig` is answered by the signature alone, with no account (a plain-text `403` when it is invalid or expired, one body for both, and a `404` for a repository that does not exist), and any other request, including one with only one of the two, by `requireLogin` (a redirect to login without a session, a `404` for a foreign repository). One route serves both, so the logged-in UI builds plain URLs and a share link is a signed URL to the same content, through the same code. The endpoint declares `exp` and `sig` only because cask answers a query parameter an endpoint does not declare with a `400`. Every response that serves content, an original's `206` and `416` included, carries `Cache-Control: private, max-age=31536000, immutable` (`withContentHeaders`): the bytes under a content URL never change, since a preview is written once per asset, a face image once per face, and an original is unique by checksum. It also carries `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, since an original is a user's upload served on the app's origin with its cookie, and must never render as a document that acts as the user. An original's `200` and `206` carry `Content-Disposition: inline` with its file name (`RangeStreaming.contentDisposition`, RFC 6266): `filename` as printable ASCII with every other character, `"` and `\` replaced by `_`, and `filename*` as RFC 5987 percent-encoded UTF-8, so a saved original keeps its name and no file name puts a control character in the header. An `itemId` that is not a UUID is a plain-text `400` (`Const.Msg.Err.VALUE_NOT_A_UUID`; the file store builds paths from the ID), and a `NotFoundException` (an unknown asset, a missing preview, face or original) or an unknown `dataType` a plain-text `404`; neither error is cached. `decorators.compress` is cask's gzip decorator except for a response that offers byte ranges, which is left uncompressed (a range names raw bytes), and for one whose `Content-Type` starts with `image/` (deflated already, so gzip would cost CPU and drop `Content-Length`).
- **Signed URLs**: `ContentSigner` (`app.service.contentSigner`) signs a content path for one item of one repository: `sign(path, expiresAt)` appends `exp` (Unix seconds) and `sig` (Base64URL without padding of `HMAC-SHA256(key, "<path>\n<exp>")`), and `verify(path, exp, sig, now)` is true only before `exp` and for exactly that `sig` text: the expected signature is encoded and compared with `MessageDigest.isEqual` (constant time), not `sig` decoded, so a padded spelling or one varied in the unused bits of its last character is refused; a malformed `exp` or `sig` is false. The key is `system.signing_key`, the Base64 of 32 random bytes, created once on first start by `SystemService.loadOrCreateSigningKey` and read back on every later one, so a signed URL survives a restart; the key is stored only while the column is NULL and then read back, so two instances starting at once end up with one key. The PASETO session key stays per process. The route logs an expired signature at DEBUG and one that does not match at WARN, never the `sig`, and with the path as requested (`getRequestURI`, still percent-encoded), since a decoded `%0D%0A` in the path would forge a log line. `ContentSignerTests` covers the signature, pinned to a known answer computed with `openssl` so an issued link survives any refactor, `SystemServiceTests` and `StartupTests` the stored key, `ContentViewControllerTests` the route's two gates.
- **Playback**: asset detail plays a Video in a media-chrome player, started as it is shown; see **Detail navigation** in `views/AGENTS.md`.
- **Tests**: `TestVideos` synthesizes short MP4s (`FFmpegFrameRecorder`, `mpeg4`) from the `people/` images at test time, with a display rotation or container metadata on request, so no binaries live in git; `VideoServiceTests` covers decoding, `AssetImportServiceTests` the import, `FaceRecognitionServiceTests` the faces, `ContentViewControllerTests` the ranges, the login and signature gates, the 400 and 404 answers and the content headers, `RangeStreamingTests` a client that goes away mid-stream, a missing file and the `Content-Disposition` encoding.

## Faces

The full walk-through, from detection to the People tab, is [docs/faces.md](../docs/faces.md).

A Face is a YuNet detection (`FaceDetectionService.detectFacesWithYunet`: score at least the `face.yunet.confidence_threshold` Setting, set with the NMS threshold on the thread's detector before each detection, box at least `face.detection.min_face_size`) with a 5-point-aligned 112 px crop and its ArcFace w600k_r50 embedding (`getArcFaceEmbedding`, an `Embedding` of the L2-normalized 512-d vector and the norm the raw output had). That norm is the Face's **quality** (`face.quality`): for a net trained with the ArcFace loss it tracks how recognizable the face was, dropping with blur and occlusion, and it costs nothing extra. On the test portraits sharp faces measure 18.8 to 22.4, the same faces blurred at 5% of their width 15 to 19.6, eyes covered 16 to 19.5; the numbers are in the help text of the `face.quality.*` Settings (`models/Settings.scala`), and `face.debug.enabled`, the one face key left in `reference.conf`, labels every crop with its quality for calibrating on one's own files.

Quality decides a Face's **tier**, stored as `face.is_enrolled` at import so a later change of the thresholds does not silently re-tier history:

- **Enrolled** (quality at least the `face.quality.enroll_threshold` Setting, default 18.0): may start a new Person and is a candidate in the vector search.
- **Match-only** (at least `face.quality.keep_threshold`, default 15, or a video cluster with too little support): may join an existing Person but never starts one and is never a candidate. A match-only Face that matches nobody is dropped, not stored (`FaceRecognitionService.recognizeFace` returns `None`). Changing either threshold never re-tiers Faces already stored.
- Below `keep_threshold` the detection is dropped by `extractFaces`, after the debug dump.

Recognition (`recognizeFace`) is a vote over the top `face.recognition.match_count` nearest candidates within `face.recognition.cosine_distance_threshold`, most votes winning and a tie going to the closest; the service reads both Settings from one snapshot per face and passes them to `FaceDao.searchClosestFaceMatches(features, matchCount, distanceThreshold)` (hand-written per engine; no DAO holds a Setting), which sees only enrolled Faces of people who are not a bad match, in the context repository; hidden people stay matchable, since hiding is a display preference. On PostgreSQL (`postgres.FaceDao.CLOSEST_MATCHES_SQL`) the candidates come from `face_03`, a partial HNSW index over the enrolled Faces' vectors at half precision (`features::halfvec(512)`, `WHERE is_enrolled`; the column is `vector(512)`): four times `match_count` of them, ordered by the same cast, and the statement then takes their exact `<=>` distances at full precision, applies the threshold and keeps the nearest. The search is approximate; over a handful of Faces it is exhaustive. On SQLite `vector_full_scan` is an exact scan of the `face` table, every repository's rows, filtered afterwards: sqlite-vector's quantized scan reads only the rows present when the table was last quantized, so it would miss a Face saved a moment ago. The same statement with one Person's Faces filtered out (`FaceDao.searchNearestFacesOfOthers`, `CLOSEST_OF_OTHERS_SQL` on PostgreSQL) serves the Change combobox's Suggested group, over a stored Face's vector read back through `FaceDao.getFeatures` (`getVectorField`); see **Corrections** in `docs/faces.md`. `face_01` makes a crop's checksum unique within its asset, not the repository, because two assets can share a byte-identical frame (a trimmed copy of a video, a re-exported photo); the same crop twice in one asset surfaces as `DuplicateException`, which `RecognizeFacesFlow` reports as `SamePersonDetectedTwiceException`. A person seen twice in one image (`twins.png`) is two Faces of one Person.

`FaceDetectionService` holds the networks. YuNet is thread-local (`yuNetLocal`): a `FaceDetectorYN` carries per-call state and costs about 70 MB, one per thread that detects, chiefly the import dispatcher's. ArcFace is shared (`arcFaceNets`, a `util/NetPool` of `ImportParallelism.ARCFACE_NETS`, one net, made on first use and kept for the life of the service): a `Net` is not thread-safe and holds about 370 MB with Winograd off, as this one is, against about 780 MB with it on, so `getArcFaceEmbedding` borrows it for its one forward pass, waiting while it is out, and copies the output inside the borrow, because the output shares its memory with the net and the next borrower's forward pass overwrites it. Measured on generated 24-megapixel JPEGs with 12 threads on 24 cores: a forward pass takes 40 to 52 ms, and one net tops out at about 24 embeddings a second, twelve at about 38. Each face borrows again, so with every thread on a 20-face photo a borrow waits about 400 ms and such a photo holds its thread and its decoded image for about 9 s. A second net cuts the wall time of an import about 3% on photos of three faces and 7% on photos of twenty, for roughly 350 MB. A borrow never nests another, so the wait cannot deadlock. `ImportParallelism.POOL_COST` budgets the pool at 384 MB a net.

## Sequences and Image quality

The terms are the glossary's (`CONTEXT.md`). A **Sequence** has no table: it is the `asset.sequence_id` (`CHAR(36)`, nullable, `COLLATE "C"` on PostgreSQL; the partial index `asset_sequence` over the rows that carry one) its members share, so there is no row to lock, to date or to delete, and it exists exactly while some asset carries it. **Image quality** is five nullable `asset` columns (`sharpness`, `luminance`, `clipped_highlights`, `crushed_shadows`, `image_quality`) read into `Asset.imageQuality: Option[ImageQuality]` through `ImageQuality.fromColumns`, the one rule both DAO mappings use (all five, or `None`); the **perceptual hash** is `perceptual_hash BIGINT`, `Asset.perceptualHash: Option[PerceptualHash]`; the **Scene embeddings** are `dinov2_embedding` and `clip_embedding`, `vector(768)` and `vector(512)` on PostgreSQL and `BLOB`s of raw little-endian float32 on SQLite (bound as bytes, not through `vector_as_f32`, and declared after `public_metadata` and `user_metadata` and before `extracted_metadata`: a row's columns are stored in order and a read walks the overflow pages of every large value before its column, so the JSON every general read selects comes first and the raw extracted metadata last), read into `Asset.sceneEmbeddings: SceneEmbeddings`. The models are `models/SceneEmbedding.scala`: `SceneModel` (`Dinov2`, `Clip`), each with its `name` (in the logs), `dimensions`, `column` (`FieldConst.Asset.DINOV2_EMBEDDING`, `CLIP_EMBEDDING`), `resourcePath` and the `mean` and `std` of its input (`IArray`s); `SceneEmbedding(values: IArray[Float])`, L2-normalized, equal by its values (`equals` and `hashCode` over the array, since a case class compares an array by reference; `toString` shows the dimensions and the first values), whose `similarity(other)` is the dot product, -1 to 1, and whose JSON form is the float array (no API answers it today); `SceneEmbeddings(dinov2, clip)` with `of(model)`. All of them are NULL together for a Video, an animated image, or a still image the pipeline did not measure, and an embedding alone for a still image its model could not embed; `AssetDao.markAsCompleted` (a hand-written update) writes the five metrics, the hash, the Histogram and both embeddings with the completion flag in one statement, refusing an embedding of another dimension count, so an asset is never complete without its metrics. The embeddings are bulky columns (a few kilobytes a row, toasted out of line on PostgreSQL) that the two candidates statements, `sequenceCandidatesStatement` and `undatedSequenceCandidatesStatement`, alone select and no other read transfers: `AssetRow` leaves them out, so `getById`, `queryRecords` and the search statements (their `assetColumns` built from its labels) never carry them, and `AssetDao`'s hand-written reads build their column lists from the same labels (`assetWithoutBulkyMetadata`: `AssetRow`'s columns without `user_metadata` and `extracted_metadata`, which `makeModel` reads as empty when absent, `public_metadata` staying for the rule's device model; `candidateColumns`: that list and the two embedding columns, read through `BaseDao.getVectorField`). There is no vector index: the rule compares a frame with the handful of candidates of its window, or an undated frame with the newest undated frames of its size up to a cap, in Scala. The **Histogram** is `asset.histogram`, `BYTEA` on PostgreSQL and `BLOB` on SQLite (declared after the two metadata JSON columns and before the embeddings), NULL as the five metrics are: `models/Histogram.scala`, `Histogram(luminance, red, green, blue)`, each channel `Histogram.BINS` (64) bins of the fraction of the pixels whose level fell in the bin, equal by its bins as an embedding is by its values. `toBytes` and `fromBytes` are the column's value on both engines, the four channels in that order as little-endian float32 (1,024 bytes; another length is refused), its JSON form those bytes in Base64 (no API answers it today), and `relativeBytes` what a view draws: a byte per bin, each bin over the tallest of the four, so the channels share one scale. It is bulky as the embeddings are and follows their rule: `Asset.histogram: Option[Histogram]` is set by the measurement and written by `markAsCompleted`, `AssetRow` leaves the column out, so no general read carries it, and the one read that selects it is `AssetDao.getHistograms(assetIds)`, the context repository's assets among the IDs that have one, which `CurationService.assess` calls for a set's frames (`CurationFrame.histogram`, for the stage's strip alone: `CurationRule` reads none of it). **Face sharpness** is `face.sharpness`, nullable, `Face.sharpness: Option[Double]`.

**Measurement.** `MeasureImageFlow` ("Image measurement", `mapAsync(importParallelism)`, after `DetectFacesFlow` and before `RecognizeFacesFlow`, so a Face's sharpness is in its one insert) calls `AssetService.measureImage`, which leaves a Video, an animated image (a `duration_ms`) and the test-only `x-none` type untouched, and for a still image decodes the staged file through `ImageUtil.matFromBytes`, takes the faces from `AssetWithData.detectedFaces` (no database read), runs `ImageMeasurement.measure(image, faces)`, which returns a `Measurement` of the quality, the hash, the faces in their order, each with its sharpness, and the Histogram, then `app.sceneEmbedder.embed(image, fileName)` over the same upright `Mat` (below), and hands back the element with all of them (`core/util/ImageMeasurement.scala`: pure functions over a `Mat` of one or three channels, as `ImageUtil.matFromBytes` decodes with `keepAlpha = false` (four channels are accepted too, for the API's sake), and the faces' boxes in the image's own pixels). The image is fitted to `MEASUREMENT_BOX_SIZE` (1280 px, `INTER_AREA`, never enlarged) and converted to gray; the box is a code constant and not the Live `face.detection.bounding_box_size`, although it is that Setting's default, because the score is calibrated against it and a Setting could not change it without silently rescaling every later score. `sharpness` is the variance of the `CV_64F` Laplacian over the whole frame, always, so two images compare on it whichever faces were detected in each; a Face's `sharpness` is the same variance inside its box, scaled and clamped to the fitted image, or `None` under `MIN_FACE_AREA_PX` (2500, a 50 × 50 face at the box scale), and it falls as a face fills more of the frame, so it compares only between Faces of one Person at a similar size, and an absolute threshold on it means nothing; `luminance` is the mean gray over 255; `clippedHighlights` the fraction of pixels at `CLIPPED_LEVEL` (250) or above and `crushedShadows` the fraction at `CRUSHED_LEVEL` (5) or below; the Histogram is four `Imgproc.calcHist` counts over the fitted image, 64 bins over the levels 0 to 255 each divided by the pixel count: the luminance over the gray `Mat` the two fractions are counted on, and red, green and blue over the image's planes (OpenCV's order is blue, green, red; an alpha plane is left out, and a gray image's three colors are its luminance); `score` is `round(100 × s / (s + SHARPNESS_HALF_POINT) × (1 − min(1, CLIPPED_WEIGHT × clipped + CRUSHED_WEIGHT × crushed + |luminance − TARGET_LUMINANCE|)))`, where `s` is the variance over the union of the face boxes when they cover at least `MIN_FACE_AREA_PX`, so one tiny face does not decide it and a sharp portrait on a flat sky is not dragged down, and the whole frame's otherwise. `s` is not stored, since its region varies from image to image: a change to the formula means measuring again, and two scores do not compare when only one image's faces clear the floor, so no reader ranks frames by score. `SHARPNESS_HALF_POINT` is 30 (the sharpness of a photo softened by about a pixel: on the `people/` fixtures fitted to the box the sharp photos measure 90 to 410, their sigma-1 Gaussian blurs 10 to 85, sigma-2 under 10), both weights 2 and the target 0.45. The constants are code, calibrated on the fixtures, not Settings: a change to the formula is a code change. `matFromBytes` applies the EXIF orientation as it decodes (`IMREAD_ANYCOLOR` without `IMREAD_IGNORE_ORIENTATION`), so the image is upright and a Face's box is in upright pixels, while `asset.width` and `height` come from the file's header and can be the other way round. The hash is OpenCV's `Img_hash.pHash` (the DCT hash of a 32 × 32 downscale, in the contrib `img_hash` module the bundled OpenCV ships) over the fitted image, eight bytes read big-endian into `PerceptualHash(bits: Long)`, a value class with `BITS` (64) and `distance(other)`, the Hamming distance; its JSON form is 16 lowercase hex digits whatever the value, since upickle would write a Long past 2^53 as a string and change the field's type on the way out. Measurement is the one stage that swallows its own failure: a `NonFatal` throw from the decode or the measurement (a file OpenCV decodes for detection but not here, a channel count the measurement refuses) is logged at WARN with the file name and the asset goes on unmeasured, with no embedding, because the metrics are derived data and NULL is a state every reader handles. The stage touches no database; `completeImport` stores the metrics, the hash, the Histogram and the embeddings, assigns the Sequence and counts the stats in the completion transaction.

**Scene embedding.** `util/SceneEmbedder.scala` holds the `SceneEmbedder` trait (`embed(image, name)`, `AutoCloseable`) and `OnnxSceneEmbedder`, which runs the two Scene models through ONNX Runtime (`com.microsoft.onnxruntime:onnxruntime` in `build.mill`, the CPU artifact, whose one jar bundles the natives for Linux x64 and aarch64, macOS and Windows, so deployment does not change): the process's one `OrtEnvironment` and one `OrtSession` per model, opened in the constructor in order (a later session failing to open closes the ones open already before the failure propagates) with one intra-op and one inter-op thread each, since the parallelism is the import threads' and twelve concurrent passes each spreading over every core would thrash; a session is thread-safe, so there is no pool. The embedder is the instance's: `Altitude` takes `newSceneEmbedder` (`OnnxSceneEmbedder()` by default, which production and the dev server use; the test instances build `SwitchableSceneEmbedder`, see **Test Structure**) and builds `sceneEmbedder` in the constructor, before the services, as the ArcFace pool is built with its service, so a missing model file fails the start and never an import (a library imported without embeddings would fall back to the hash silently). `Altitude.cleanup` closes it once the pipelines have shut down, since their threads run the sessions (a second `close()` is a no-op). `OnnxSceneEmbedder.embed(image, name)` prepares the image once for both models, with a transform of this project's own rather than the checkpoints' reference one (DINOv2's processor resizes the short side to 256 bicubic and crops 224, CLIP's resizes it to 224 bicubic): the short side fitted to `INPUT_SIZE` (224; `INTER_AREA` for the downscale an import is, which averages the pixels it drops, and `INTER_CUBIC` where an image under the input size is enlarged), a center crop of that square, converted to RGB from the gray, BGR or BGRA `matFromBytes` decodes; then per model scaled to 0..1 and normalized with its mean and std (folded into one multiply and add per channel), laid out NCHW, run, and the output row L2-normalized, so two embeddings compare by their dot product. The export script checks the models on the same transform, and the similarity thresholds are calibrated to it, so a change to it means calibrating again. A model whose pass fails gives no embedding, logged at WARN with the file name, and the other model's stands; an image that cannot be prepared at all (a channel count no decode produces) gives neither. The models are `resources/onnx/dinov2_vitb14.onnx` (DINOv2 ViT-B/14, `facebook/dinov2-base`, Apache 2.0: the pooled CLS token, 768 floats, ImageNet normalization) and `resources/onnx/clip_vitb16_image.onnx` (the CLIP ViT-B/16 image tower, `openai/clip-vit-base-patch16`, MIT: the projected image embedding, 512 floats, CLIP's normalization), about 350 MB each, git-ignored like the ArcFace model and exported by `scripts/fetch-models.py` (`uv run scripts/fetch-models.py`, its torch, transformers and onnx versions pinned in a PEP 723 header, torch from the PyTorch CPU index: opset 17, a static batch of 1, one input `image` and one output `embedding`, each export run through ONNX Runtime on a sample image and compared with the PyTorch model to within 1e-4 before it is written). Measured on the machine of `ImportParallelism`'s figures (24 cores, 31 GB, generated 24-megapixel JPEGs): the two sessions hold about 1,050 MB resident once opened and about 50 MB more after a first pass of each (691 MB of weights, which the runtime pre-packs for its GEMM kernels and keeps both copies of; `session.disable_prepacking` would save 300 MB for passes 8 to 10% slower and is not set), budgeted as `SCENE_MODELS_COST` (1152 MB); on one thread a pass takes about 365 ms for DINOv2 and 270 ms for CLIP, with ONNX Runtime's graph optimizations making under 10% of difference since the GEMMs run at the core's AVX2 limit, and fitting a 24-megapixel image adds about 50 ms, so an image costs its thread about 0.7 s; with 12 threads embedding at once a pass of both takes about 1.1 s and the process embeds about 10.7 images a second, the passes' working memory adding about 45 MB a thread, inside `THREAD_COST`. A test import runs the models only in a suite that turns them on (see **Test Structure**). On `BurstFrames` (`images/2.jpg`, each frame shifted and brightened a little) the frames measure 0.98 to 1.00 alike by DINOv2 and 0.97 to 1.00 by CLIP, a frame against the far picture (`people/meme-ben.jpg` at the frames' size) about 0.26 and 0.62, a half-size copy 0.99 by either, so only the size test keeps it out, and CLIP is near-invariant to a horizontal mirror (0.99) where DINOv2 is not (0.96).

**Assignment.** `SequenceService.assign(asset)` (`Altitude.service.sequence`) runs under its own `withTransaction`, which joins the completion's, one asset of a repository at a time in upload order, so the earlier uploads of a burst are completed candidates already. An eligible asset takes `AssetDao.lockSequences()` first, as `CurationService.resolve` and `reopen` do: the writers of a repository's Sequences take turns (an advisory transaction lock keyed by the repository on PostgreSQL; on SQLite the one write connection already does it). Row locks cannot do it. A write transaction is `READ COMMITTED`, and a frame completing is in no row a resolve's `FOR UPDATE` read finds until it commits, however long that statement waits on another row, since the statement keeps its snapshot; and a merge repoints members outside its candidates and a selection recycles frames outside its Picks' Sequences, so neither locks all its rows in one ordered pass, which is a deadlock with the other. `SequenceRule` (`core/util`, pure over the models) decides. A frame is of one of two kinds, each a still image (`Asset.isStillImage`: `media_type` `image`, no `duration_ms`) in triage with a hash: `isDated` has a capture time from the camera's own clock (`CameraClockSources`: the `exif_original`, `exif_digitized`, `xmp_create_date` and `filename` rungs; the file name counts because the gap test needs whole seconds, which a name gives, while the fraction of a second a camera writes only orders the frames inside one second, and frames with none order by import time and then ID, as `CurationRule` orders them) and needs no camera model, since a frame saved out of a messaging app names none; `isUndated` has no capture time at all. A time from a clock that is not the camera's (a container's creation time, a GPS timestamp) makes an image neither kind: it cannot space the frames of a burst, and it is not a time that was stripped, so the image is measured and hashed but never joins. `isEligible` is either kind; the two are read and paired apart and never share a Sequence. `matches(asset, candidate, settings)` holds for two dated frames captured at most `sequence.max_gap_ms` apart on the same camera (both name the same device model, `Asset.getPublicMetadata`'s `Exif IFD0` / `Model`, or neither names one, so an original and its metadata-stripped copy are never a burst), and for two undated frames whatever camera either names (a frame stripped of its time is stripped of its camera too), each pair at the same `width` and `height` and looking alike (`lookAlike`): by some Scene model whose embedding both carry, their cosine similarity is at least that model's threshold (`sequence.dinov2.min_similarity` or `sequence.clip.min_similarity`), and where no model embedded both, their hashes are at most `sequence.max_hash_distance` bits apart. One model's likeness is enough, so the Sequences are the union of what either model finds, a burst one model misses caught by the other, and two Sequences the models would draw over the same frames merge as any overlapping Sequences do; a pair compared by any model is never rescued by its hashes. The similarity replaces the hash test rather than joining it, since the hash at any usable distance rejects a reframed or zoomed shot of the scene, which the embedding holds under; each model has its own threshold because their cosines live on different scales (CLIP's are compressed toward 1); and the size test stays beside the embedding, since a portrait and a landscape frame of one scene can embed alike and are not one Sequence. The check is symmetric, and a dated frame and an undated one never match, either way round. `assign` reads the two thresholds, the gap and the hash distance from one Settings snapshot per asset, gates the asset's eligibility once, takes the lock, and reads the candidates of the asset's kind. A dated frame's come through `AssetDao.getSequenceCandidates(asset, gapMs)` (`sequenceCandidatesStatement`, hand-written JDBC): the context repository's completed, triaged still images captured within the window, in the trash or not but not purge-pending (a frame recycled from triage keeps its Sequence, so the next frame of its burst joins it there), every calendar day the window spans bound through `dayOf` (the engine's capture-day expression, the one spelling of `SearchDialect.dayWrapper`) and then `BETWEEN` on the timestamp, with the flags as literals and `is_recycled IN (FALSE, TRUE)` probing both values of the index's second column, so `asset_triage_date_taken` answers it; prefiltered in SQL to rows with a hash and a camera-clock source (the source list derived from `CameraClockSources`; the device model is not in SQL and stays in Scala), a derived copy of the Scala rule, which stays the authority; the asset itself left out; `FOR UPDATE` on PostgreSQL, so a move sorting a candidate meanwhile holds the row and, once the move commits, the row is re-evaluated and left out (SQLite's one write connection serializes the two). An undated frame's come through `AssetDao.getUndatedSequenceMatches(asset, limit)(keep)` (`undatedSequenceCandidatesStatement`, hand-written JDBC over `BaseDao.collectBySqlQuery`): the context repository's completed, triaged still images, in the trash or not but not purge-pending, with a hash and no capture time, at the asset's `width` and `height`, the asset itself left out, `ORDER BY created_at DESC, id DESC LIMIT ?`; the predicates on the media type, the duration, the hash, the capture time and the triage flag are a derived copy of `isUndated`, and the size test is `matches`'s, the rule staying the authority. The flags are literals, and the partial index `asset_triage_undated` (`repository_id, width, height, created_at, id` over the triaged rows with no capture time) answers it on both engines: the repository's undated triage rows of the size are one run of the index in the statement's order, which the engine walks backwards from the newest and stops at the limit, and the other predicates are heap checks over those rows alone, so an import costs the limit at most and never reads the rest of triage (the statement does not probe `is_recycled`, which this index does not hold; the two statements share their common `WHERE`, `sequenceCandidatesWhere`). The rows stream through the DAO: each candidate is built with `makeModel`, kept when `keep` (`SequenceRule.matches(asset, _, settings)`) holds and dropped otherwise, so at most the matches' embeddings are alive at once, and the DAO answers `Collected(kept, scanned)`. No row locks on the read: the Sequence writers take turns through `lockSequences` already, and the matches, a few rows, are then re-read through `AssetDao.lockTriaged` (the library operations' locking select, over the triaged rows among the IDs, in ID order, `FOR UPDATE` on PostgreSQL), so a candidate a concurrent move is sorting, which the unlocked read still returns on PostgreSQL, waits for the move and is left out once it commits, with the Sequence each match carries now; only the locked rows go on, so the asset is never stamped alone. The limit is the cap, `Altitude.undatedSequenceCandidates`: `Const.Sequence.UNDATED_CANDIDATES_PER_CORE` (5,000) times `Runtime.getRuntime.availableProcessors`, computed once at startup and logged at INFO with the core count, and `SequenceService`'s constructor parameter (`undatedCandidates`), so a test builds the service with a cap of its own. The reasoning: a candidate costs about 6 KB to read, its two Scene embeddings, so a core's share is about 30 MB per undated import, and the compare itself is two dot products a candidate; undated frames have no capture time to window them by, so without the cap the cost of one import would grow with every undated frame triage holds. When the read scanned as many rows as the cap, older undated frames of the size went uncompared, which `assign` logs at DEBUG. Then, for either kind: no match, no Sequence, since a lone image is never one; matches with no Sequence, a new `BaseDao.genId` for the asset and every match; matches in one Sequence, the asset joins it; matches in several, a burst being transitive, they merge: `countSequenceMembers(ids)` (one grouped count with `MIN(original_created_at)`, a `SequenceMembers` per id) picks the survivor by most members, then the earliest first capture, then the id (`minByOption`: a count that comes back empty, the members all gone meanwhile, starts a new id rather than failing the import; an undated Sequence has no first capture, and since the matches are all of the asset's kind a merge is of dated Sequences or of undated ones, so among undated Sequences the tie falls to the id), `repointSequences(fromIds, toId)` moves the other Sequences' members by `sequence_id` in one update (logged at INFO), and `setSequence(assetIds, sequenceId)` stamps the asset and the matches that had none, one `$inIdSet` bind, writing only rows still in triage (`is_triaged = TRUE`), a shortfall, which the row locks held from the read to the write rule out, logged at DEBUG rather than failing the import. Each assignment is logged at DEBUG with the Sequence and the matches.

| Operation | Effect on membership |
|---|---|
| Move out of triage (`moveAssetsToFolder`, also the way out of the trash into a folder) | The move's one update writes `sequence_id` NULL with the triage flag. A sorted asset never carries a Sequence; a Sequence whose last member moved is gone with it. |
| Recycle from triage | Nothing: the asset keeps its triage flag and its Sequence, and a Sequence whose members are all in the trash still exists. A recycled asset in triage stays a candidate, so the next frame of its burst imported meanwhile joins it, and a restore brings the pair together. |
| Restore | Nothing: the asset is back in triage with its Sequence. |
| Curation's resolve (`CurationService.resolve`, also Keep all) | In one transaction, each of the Picks' Sequences decided on its own: when the set holds all of its frames still out of the trash (`getLiveSequenceMembers`, locked in ID order), its Picks leave it (`clearSequence`), and otherwise they stay, to be compared with the other frames from the queue. The frames recycled keep it, as under Recycle from triage. A cleared frame stays a candidate of `assign`, so a later frame of its burst forms a new Sequence with it or stamps it into the Sequence of another match. A resolve answers with each Pick and the Sequence it left. |
| Curation's reopen (`CurationService.reopen`) | The Undo of a resolve, in one transaction, reported as a restore is: the recycled frames come back (a duplicate stays in the trash, and keeps the Sequence), and the Picks go back through `setSequence`, so one moved into a folder since stays sorted. |
| Purge, discard of a dropped import, repository delete | Nothing beyond the row's delete. |

A lone frame never enters it, recycling a frame can take a Sequence out or put it behind another, and a restore can bring it back. `countQueue()` is how many (`countSequencesToCurate`: the grouped statement inside a count, without the cover, since the toolbar reads it after every mutation). `sequenceSet(sequenceId)` is a Sequence's frames still out of the trash, whatever a search shows of them, and reads a window: Sequences chain transitively, so a static 1 s time-lapse is one Sequence of however many frames it has, and a set's frames each cost their Faces and memberships. `getSequenceFrames` sorts and cuts in SQL, the first `Const.Curation.MAX_SEQUENCE_FRAMES` (100, beside the selection's cap) in capture order (`original_created_at IS NULL, original_created_at, created_at, id`: a frame with no capture time last on both engines, the import time breaking a tie before the ID, so an undated Sequence's frames come as they were uploaded rather than by their random IDs; `CurationRule.captureOrder` sorts the same way), and when the window is full `countSequenceFrames` tells `CurationSet.heldBack` how many are past it, which the rail shows ("Showing the first 100 of 2,000 frames"). A window is a set that holds part of a Sequence, as a selection can: `resolve` decides by the whole membership, so its Picks stay in the Sequence and the Sequence stays in the queue, a Resolve recycles only the window's other frames, and a Keep all changes nothing, whatever frames are held back. The next read's window starts with those Picks and goes on past the frames recycled. `selectionSet(assetIds)` keeps the still images among the IDs (`Asset.isStillImage`, the one spelling of that test, shared with `SequenceRule.isEligible` and `AssetService.measureImage`), in the context repository, completed and not recycled. Either set is `None` under two frames. The queue, its count, a Sequence's window and its count read `asset_sequence`, so they cost the rows that carry a Sequence and not the library, which matters since the toolbar reads the count after every asset mutation. A set's read adds each frame's Faces (`PersonService.getFacesOfAssets`, through `FaceDao.getFacesOfAssets`: `getAssetFaces`' join over one `$inIdSet` bind, so the Faces of hidden and bad-match people are left out) and whether it is in any album or Location (`getAssetsInAnyAlbum`, `getAssetsInAnyLocation`), and hands `CurationFrame(asset, faces, inAlbumOrLocation)`s and the current Settings snapshot to the rule.

**The rule.** `CurationRule.assess` (`core/util`, pure over the models as `SequenceRule` is; the models are `models/CurationSet.scala`) runs when a set is read and returns a `CurationSet(frames, notices, bundles, contenders)`, so a changed threshold applies from the next read. The frames, each Bundle's frames and the Contenders are in capture order (`captureOrder`: a frame with no capture time last, then the import time and then the ID breaking a tie, the order of `AssetDao.sequenceFramesStatement`), so the order does not depend on how the frames were read and an undated Sequence's frames show as they were uploaded.

| Bundle | Holds a frame when |
|---|---|
| **Poor faces** | One of its Faces' quality is at least `curation.face_quality_gap` below the same Person's best in the set's other frames. Or, among the set's frames of its Sequence, a Person found in at least half of them has no Face in it. |
| **Blurry** | A Person it shares with another frame, at a similar size (box areas within 2×, `SIMILAR_SIZE_FACTOR`), has `face.sharpness` under `curation.blur_ratio` of that Person's best at that size. A frame with no such Person, in a Sequence, is compared on `asset.sharpness` against the sharpest other frame of its Sequence, with the same ratio. A frame with neither is never Blurry. |
| **Too dark** | `crushed_shadows` is at least `curation.crushed_fraction`, or `luminance` is under `curation.dark_luminance`. Or, in a Sequence, its luminance is on the dark side of `ImageMeasurement.TARGET_LUMINANCE` and at least `curation.luminance_gap` farther from it than the other frame of the Sequence nearest it. |
| **Too bright** | `clipped_highlights` is at least `curation.clipped_fraction`, or `luminance` is over `curation.bright_luminance`. Or, in a Sequence, the same gap on the bright side of the target. |

The relative tests compare only what is comparable: sharpness and exposure across different scenes mostly reflect content, so the Sequence clauses apply only among frames of one Sequence, while the same-Person tests apply anywhere in the set. Face sharpness and Face quality never compare across Persons, and a Person's best is taken from the other frames, since a Person twice in one frame (`twins.png`) is nothing a Pick can tell apart. A frame sits under its most serious problem, in the order of the table (`BundleKind`), as a `BundledFrame` holding that problem's reasons, and its other problems are chips. An absolute Too dark or Too bright that holds for every frame cannot be fixed by picking, so it is a `CurationNotice` on the set ("Every frame: 8% blown highlights"), neither a Bundle nor a chip; an unmeasured frame stops it, and the relative tests still bundle. A notice names the tests every frame is past, or else each test some frame is past, each at its mildest value, so its words hold for all the frames. A `CurationReason` says what is wrong, how much and compared to what, and `htmx/curation_set` words it. The rule never reads `image_quality`, and the view never shows it: it suggests nothing except a sole Contender (`soleContender`), and a set with no Bundle is Too close to call (`isTooCloseToCall`). A frame with no metrics (`isMeasured`) is a Contender with a note, whose Faces still count for the others. `CurationSet` also derives what the view lays out by: the rail's order (`railFrames`: the Contenders, then each Bundle), the frames a set opens on (`openingFrames`) and the face strip's rows (`faceRows`).

**A set's outcome.** `resolve(keepIds, recycleIds)` and `reopen(keepIds, recycleIds, sequenceOf)` are the two writes, each one transaction that takes `lockSequences` first (see **Assignment**) and changes membership as the table above says. `keepIds` must be non-empty and disjoint from `recycleIds`; `resolve` also refuses a Pick that is no live asset of the repository, which would recycle the set with nothing kept, and `reopen` a Sequence given for a frame that is no Pick; each refusal is an `IllegalOperationException`. `resolve` recycles through `LibraryService.recycleAssets`, counting the stats as any recycle does, and answers with each Pick that left its Sequence, which `reopen` takes back. `reopen` restores through `restoreRecycledAssets`, so it fails as a restore does: an ID that is no asset of the repository is a `NotFoundException` that changes nothing. Keep all is `resolve` with nothing to recycle: on a whole Sequence it is how a wrongly grouped Sequence is dismissed, and on part of one it changes nothing. Recycling a Bundle is no call of this service: the client uses the grid's recycle endpoint and reads the set again, so its Bundles are recomputed against the frames left, and undoes it through the restore endpoint. A move of the queue's walk reaches no server. Two effects of recycling reach the user: a recycled frame leaves its albums and Locations and a restore does not add it back, which the set's footer says with a count when a frame to be recycled is in any (`inAlbumOrLocation`); and its Faces leave its Person's `num_of_faces`, so an unnamed Person known mostly from a burst can fall under the Matched line.

## Models

All models extend `BaseModel` and are case classes with a upickle `JsonCodec` read/writer plus a `ujson.Value` conversion in their companion:

```scala
object Folder:
  given JsonCodec.ReadWriter[Folder] = JsonCodec.macroRW
  given Conversion[ujson.Value, Folder] = json => JsonCodec.read[Folder](json)
```

`JsonCodec` emits snake_case field names. DAOs build typed models from result rows in `makeModel`, so services and DAOs exchange models, not JSON. JSON APIs that need a different shape (camelCase, derived fields such as the folder tree's `isRoot`) build their `ujson.Obj` by hand in the controller.

`FolderService.getTree` assembles the folder tree in memory from one folder query and one per-folder asset count query (`SearchDao.countByFolder`: the default view's matches grouped by folder, `SearchQueries.folderCounts`, which the capture-day index answers alone), filling `children`, `numOfChildren`, and the recursive `numOfAssets` on every node; `FolderController` only serializes it.

`BaseDao.updateById` / `updateByQuery` take an untyped `Map[String, Any]`; `Columns.literal` binds the scalar types the old hand-built SQL accepted and, only for a `SET`, an `Option` (`None` renders `NULL`, `Some(v)` binds `v`). A `None` in a `Query` predicate would render `= NULL` and never match, so that path does not use it. `deleteByQuery` builds its predicate through the same `DynamicFilter`. A hand-written JDBC statement tests a column against a set of IDs with `column $inIdSet` and one bind, `idSet(ids)` (the dialect overrides: `= ANY(?)` with a `varchar[]`, or `IN (SELECT value FROM json_each(?))`), so a selection of any size is one parameter, as `Columns.isInSet` is for a typed statement.

## Names

Every name the app keeps unique is compared under its **name key** (`CONTEXT.md`), and one function computes it: `altitude.core.util.NameKey.of(name)`, `NFKC(lower(upper(lower(NFKC(name)))))` with each case mapping under `Locale.ROOT`. It folds letter case in any script ("Straße", "STRASSE" and "STRAẞE" are one name, and so are a Greek name with a final sigma and the same name with a plain one), canonical forms (a precomposed "é" and an "e" with a combining accent, which macOS file names carry) and compatibility forms (a full-width "Ａlbum", the "ﬁ" ligature, "①"). It does not fold accents ("Émile" and "Emile" are two names), and it is the same on both engines and under any JVM default locale. `NameKey`'s scaladoc says why each step is there and where the key differs from Unicode's `NFKC_Casefold`. The name as stored and shown is `NameKey.normalized(name)`: the name as typed, in NFC, its compatibility forms kept.

The keyed names: an account's email address and username (`account.email_key` under `account_01` and `account.username_key` under `account_02`, instance-wide; **Accounts and access**), a Library's (`repository.name_key`, `repository_01`, instance-wide; **Libraries**), a folder's among its siblings (`folder.name_key`, `folder_02`), an album's (`album.name_key`, `album_01`), a Location's or Category's in one pool (`location.name_key`, `location_01`), a metadata field's (`metadata_field.name_key`, `metadata_field_02`, which `UserMetadataService.addField` also checks before its insert), these four within a repository, and a live Person's (`person.name_for_sort` under `person_01`, through `PersonService.nameKey`; `docs/faces.md`). Each model derives its key, `val nameKey: String = NameKey.of(name)`; the DAO's insert and every rename write it beside the name, and the album, Location and folder lists order by it. `face-combobox.js` mirrors the fold in its `nameKey` to tell whether a typed name is an existing Person, and finds a typed part of a name in that key with every final sigma read as a plain one (`partialMatchKey`, since the fold gives a sigma at the end of a word, "σοφοσ" typed on the way to "Σοφοσάκης", the final form); the server stays the authority. A metadata value is folded the same way: two values of one field on one asset are one value when their keys are equal (`UserMetadataValue.checksum` hashes the key and is the value's equality), a value is stored in NFC (`UserMetadataService`'s value cleaning), and a keyword's `metadata_parameter` row holds the key (**Search results and date grouping**).

**Length.** A name is held to its length once normalized, since NFC can lengthen it (U+FB2C is three code points in NFC): `Validators.validName(name, field, maxLength, minLength)` normalizes the name and refuses it with a `ValidationException` whose message is also the name field's error (`VALUE_TOO_SHORT`, `VALUE_TOO_LONG`, the request validator's texts) when it is outside its length, counted in code points as the `VARCHAR` name columns count them (an emoji is one), or when its name key passes `NameKey.MAX_KEY_BYTES` (2000 UTF-8 bytes; `NAME_KEY_TOO_LONG`). The cap keeps every key within PostgreSQL's btree row limit (2704 bytes, SQLSTATE 54000) without relying on the index's compression: a key is no longer than its name but for what NFKC spells out, so only a name of compatibility characters reaches it (U+FDFA, one character, is a 33-byte key; no other character's key passes 5 bytes, so 250 characters stay under 1250). The services run it on every add and rename, folders, albums, Locations and categories at 250 (`Api.Constraints.MAX_FOLDER_NAME_LENGTH`, `MAX_ALBUM_NAME_LENGTH`, `MAX_LOCATION_NAME_LENGTH`), metadata fields at 250 (`MAX_METADATA_FIELD_NAME_LENGTH`) and Person names at 2 to 80 (`MIN_`/`MAX_NAME_LENGTH`, in `PersonService.validName` with the reserved-name check); the Library rule (`Repository.validName`) counts the same way and caps the key too. A dialog's request validator checks what was typed, as the browser's `maxlength` does, and the folder, album and Location dialogs show the service's refusal as the form's field error as well.

The rule for a new named thing: store `NameKey.normalized(name)` through `Validators.validName`, keep `NameKey.of(name)` in a `name_key TEXT NOT NULL` column under a unique index (`TEXT` on both engines, since a fold can lengthen a name: "ß" becomes "ss", "ﬃ" becomes "ffi"), and let the index's violation surface as a `DuplicateException` (`BaseService.add` and `updateById` turn it into one). Fold nowhere else: not in SQL (no `lower()`, no collation for name equality: SQLite's `lower()` folds ASCII only and PostgreSQL's folds by the database's collation), and not with `toLowerCase` in Scala.

## Albums

An `Album` is a flat, repository-scoped, uniquely named (under its name key, `album_01`; see **Names**) list of pointers to assets: the `album` table plus the `album_asset` membership table, which has no model of its own and is written only through `AlbumDao`. An asset can be in any number of albums. Nothing album-related touches an asset: adding to, removing from, renaming, or deleting an album (a hard delete; memberships cascade) changes membership rows only. The reverse direction is `LibraryService.recycleAssets`, which drops recycled assets from every album in the same transaction (so folder deletion does too); restoring does not re-add them, and purging deletes the asset row, whose foreign key cascades. `Album.numOfAssets` is computed on read (`AlbumDao.getAll`); `AlbumService.getAlbumsOfAsset` reads an asset's albums by name through `album_asset_02`, without the count, for the Detail panel. `AlbumService.getById` is scoped to the context repository, as `LocationService.getById` is, so another repository's album is neither read, renamed nor added to. The batch ops' Add to album dialog (`AlbumActionController`, `PUT /htmx/album/r/:repoId/assets`) adds the selection to an album, or creates one for it in the same transaction (`AlbumService.addAssetsToNewAlbum`). Searching within an album is the `albumIds` filter of `SearchQuery` (`asset.id IN (SELECT asset_id FROM album_asset ...)`), reached through the `albumId` search parameter.

## Search results and date grouping

Two search paths share one definition of "what matches": `LibraryService.search` (full `Asset` records for the ungrouped HTML grid) and `LibraryService.searchGrouped` (a grouped page for the grouped HTML grid). Both resolve the scope the same way (`withResolvedScope`: the root folder means no folder filter, any other folder means itself plus its current descendants, and Search text is resolved against the repository's names, see **Text search**) and then use the engine's `SearchDao`, which builds every predicate once, for both, in `SearchQueries.matching` (`core/dao/sql/search/`): a typed ScalaSql relation carrying repository scoping, view flags, pipeline completion, column filters, and text, folder, person, album, Location, Date Taken and Date Imported range, Triage subset, bounding-box and user-metadata filters. Everything joined in is a semi-join on `asset.id` - the metadata one counts an asset's matching values with its own `GROUP BY`/`HAVING` - so a search reads `FROM asset` alone, with no duplicate rows and nothing to deduplicate on the outside. Every statement over the relation is a hand-written shell built through `SearchQueries.statement`, which puts the Search text's CTEs at its head (see **Text search**), so no shell can leave them out. Two counts read the same relation, scoped like `search`: `LibraryService.count`, exact, which `PersonService.merge` recounts a person's assets by and the Triage routes count by (see **Triage summary, scope dialogs and Quick view**), and `LibraryService.cappedCount`, the map layout's total.

**Pages and totals.** A flat page (`SearchQueries.flat`) decides its rows over narrow ones and then reads only those in full, in the shell of a grouped page without its group counts: a materialized `candidates (id, day, sort_value, second_sort_value)` slice over `matching`, ordered by the sort, then (under the Relevance sort) the newest capture time, then the ID, `LIMIT rpp + 1`; the `page`; and the page joined back to `asset`. A page past the first is continued by cursor, never by page number or `OFFSET`: the slice starts after the cursor's anchor (`afterBySort` with `seeks`, which adds an inclusive bound on the sort value so that an index on it seeks to the anchor), so a page costs the same however far in it is. Where the sort puts the rows without a value last (SQLite's legacy NULL import times, descending), a continuation reads them in a second, guarded slice (`candidatesCte`), since a range never reaches NULL. Sorted by capture time, the candidates are `dayCandidates`, the day-ordered slices a page grouped by day reads, the days in the sort's direction: the capture day followed by the capture time is the order of the capture time alone, and the order of `asset_search_date_taken`, which neither engine reads in order for the time alone; the cursor then carries the last asset's day as its key. Under the Relevance sort the candidates read `scored`, as a grouped page does. `asset_search_created` serves the default Date Imported sort and carries the ID, so the slice reads the index alone, within a Date Taken range too (**People match and date ranges**). The DAO returns `SearchRow`s (the `Asset`, its day under the capture-time sort, its `SortValue` as stored, its `secondSortValue`) in a `SearchPage` (rows, `total` on a first page, `hasMore`); `SearchService.search` builds `SearchResult.nextCursor` from the last row (`cursorAt`, shared with the grouped search), and `LibraryService.search` checks a cursor against the search's fingerprint as `searchGrouped` does (`continued`). The cursor decides `data-app-search-after`; a flat page needs `rpp` of at least 1 (`IllegalArgumentException` otherwise), so no search reads an unbounded set of full rows. A first page also carries a **capped count**, `SELECT count(*) FROM (<matching ids> LIMIT cap + 1)`, the cap being `SearchQuery.totalCap` (`Const.Search.TOTAL_CAP`, 10,000; tuning carried on the query for tests, not part of the cursor fingerprint): a result one past the cap means more than it. `SearchResult.total` and `GroupedSearchResult.total` are present on a first page only, and not even there for a search asked for without one (`SearchQuery.withoutTotal`, `countsTotal = false`, which `isTotalCounted` reads, so the page's statement leaves the count out): Quick view, which counts exactly; the flat and grouped first pages and the map layout (`cappedCount`) report the capped count, and `includes/search_results` renders `data-results-total` (at most the cap) and `data-results-total-capped`. The Location filter (`SearchQuery.locationIds`) is the album filter's shape over `location_asset`. The Triage subset (`SearchQuery.subset`, a `util/TriageSubset`: `UnknownPeople` or `NoLocation`, the assets two of the Triage summary's counts show, as a scope) is one of two semi-joins: `unknownPeopleFilter` matches an asset with a Face whose Person is an Unknown person (unnamed, and neither hidden, merged away nor a bad match, whatever their bucket), and `noLocationFilter` an asset no `location_asset` row points at, whatever its own GPS position, the predicate the trailing "No location" group of **Group by Location** reads too. The bounding-box filter (`SearchQuery.bbox`, a `util/BoundingBox` of south, west, north, east; `west > east` crosses the antimeridian and becomes two open-ended longitude ranges) matches an asset by its own point or, when it has none, by the pin of any Location it is in - the rule the map plots by - as plain `BETWEEN` arithmetic, no dialect hook. It is one semi-join over the union of two ID sets (`SearchQueries.bboxFilter`): the view's assets with a point in the box, which repeats the repository and the view's flags so that `asset_geo` bounds it, and the members without a point of the Locations pinned in the box. The two rules as alternatives on the asset's own row would leave every matching asset to be tested.

**People match and date ranges.** `SearchQuery.peopleMatch` (a `util/PeopleMatch`, `All` unless the query says `Any`) says how `personIds` combine (`SearchQueries.peopleFilter`): `Any` is one semi-join over the set (`personFilter`), `All` one semi-join per person, AND-ed, in ID order so that one search renders one statement. An asset is matched once however many Faces a person has in it, and with one person the two are the same statement. Each person's faces are read from an index alone, never the table: `face_02` by the person, and on PostgreSQL the planner may probe `face_01` by the asset for a person after the first. `SearchQuery.takenRange` and `importedRange` are each an optional `util/DateRange(from, to)` of whole calendar days, both ends included and either left open; a range with no end, or whose first day is after its last, is an `IllegalArgumentException` when it is constructed. A Date Taken range (`takenFilter`) compares `SearchDialect.day` of `original_created_at`, the expression `asset_search_date_taken` is built on, with the bound days, so it is a seek in that index and a count over it reads the index alone. Its days are the camera's wall-clock days, as the day grouping has them, whatever the server's zone, and an asset with no capture time has a NULL day, which fails either comparison: it is in no range, not even one open at an end. A Date Imported range (`importedFilter`) is a half-open range on `created_at` itself, with no day expression around it, from the instant the first day begins in the server's time zone to the instant the day after the last begins there, so it is a seek in `asset_search_created` and a day the clocks change is as long as the zone makes it. Each of the two indexes carries the other's date, `asset_search_created` the capture time and `asset_search_date_taken` the import time: a page sorted by one date within a range on the other, which reads the sort's index in order when the range holds much of the library, tests the range on what that index carries and never on the table, so its slice reads the index alone (an index-only scan on PostgreSQL, a covering index on SQLite). `triaged=true` changes nothing in that, since the repository view then tests no triage flag and reads the same two indexes. The indexes of the triaged assets do not carry the other date: a search reads them in the triage view alone, where a range tests the rows of a triage set and not of the library. A range that ends on 31 December 9999 is open at that end: the day after begins, by UTC, in a year of five digits, which SQLite's text writes with a sign (`+10000-01-01 …`) and so orders before every stored value, and no import is that late; with no first day either, the filter is `created_at IS NOT NULL`. The server's zone is the JVM's (`ZoneId.systemDefault`), read as `matching` is built, the one thing `SearchQueries` reads that is not an argument. Each bound is an `OffsetDateTime`, which the dialect binds as its engine stores an import time: a `timestamptz` on PostgreSQL, the UTC wall clock as `SqliteOverrides.DATETIME_FORMATTER` text on SQLite, which orders as the instants do because every stored value is in that canonical form; a legacy SQLite row with no import time is in no range. `SearchQuery.copyWith` keeps all three, so the copies a search is resolved through (the folder scope, the Search text) still carry them, and `SearchRequestParser.Scope` carries them into the query it builds, as `parse` reads them from the request (below): the people match from `peopleMatch`, all when it is left out, and each range from its two dates, none when both are left out.

`SearchQuery.grouping` (`SearchGrouping(GroupBy.DateTaken, direction)`, `SearchGrouping(GroupBy.Location)` or `SearchGrouping(GroupBy.Sequence)`) turns a query into a grouped one. `GroupBy` carries the date column behind a date grouping (`dateField`, `None` for Location and Sequence); `SearchDao.searchGrouped` dispatches on it to one of three statements that share one shell. `SearchQueries.grouped` emits **one statement** per page: a materialized, narrow `candidates` slice (`dayCandidates`: ID, day, sort key and `second_sort_value`, the capture time under the Relevance sort and NULL under a column sort; `LIMIT rpp + 1` to detect continuation), the `page`, `day_counts` as one correlated count per distinct day on the page, the page joined back to `asset` for its full rows and, on a first page only, `total`, the capped count. Under the Relevance sort the statement first materializes `scored (id, day, sort_value, second_sort_value)` (`ScoredRow`) over the matches, with the Relevance computed once as `sort_value`; the candidate slices, the cursor comparison and the order read its columns, and the Location statement joins its Locations to it. Everything is ordered by day, then the sort, then `asset.id` (`SearchQueries.orderWithinGroup` over a `Position`, the row's ID, day, sort value and capture time as the sliced relation has them, the asset or `scored`; under the Relevance sort the newest capture time comes before the ID). It is a hybrid: every branch is the same typed `matching` relation rendered into a hand-written `WITH` shell, because `MATERIALIZED`, the guarded `LIMIT CASE` on the trailing null slice and SQLite's planner hint cannot be expressed as a typed query - but each fragment carries its own bind values, so no branch can drift from the counts beside it. The engine-specific `SearchDialect`s (`Postgres`/`Sqlite`) supply the day expression (`date(col)` on SQLite, `col::date` on PostgreSQL), the full-text predicate over a Search document (`textMatch`), null placement, the `SortValue` type mapper, and on SQLite a unary `+` on the secondary sort term so the planner keeps the grouping day index. The DAO returns `GroupedSearchRow`s (the `Asset`, its group as a `SearchGroupKey`, its `SortValue` exactly as stored, its `secondSortValue`, its group's count) in a `GroupedSearchPage` (rows, `total` on a first page, `hasMore`); `SearchService.searchGrouped` folds consecutive rows of one group into `AssetGroup`s and builds the next cursor. `GroupedSearchResult` also carries `continuesGroup`, whether the first group is the one the previous page ended in when this page was reached by cursor.

**Group by Location** (`SearchQueries.groupedByLocation`) is the same shell over two relations instead of one, because its shape differs from the day statement on every axis: `located` is `matching` joined to `location_asset`, `location` and a left-joined category - **one row per asset × Location**, so an asset in two Locations appears under both and the group counts may sum to more than the total, which still counts assets - and `unlocated` is `matching` less every asset in a Location, which is always the trailing "No location" group. A page Location's count reads that Location's own members (`location_asset` joined to `asset` under the `matching` predicates), so it costs the size of the page's Locations and not of the library; the "No location" count runs only on the pages that reach that group. Groups are in **path order**, the order the sidebar lists them in: the key is the category's name key and the Location's own joined by U+0001 (`SearchQueries.PATH_SEPARATOR`, below every printable character, so the composite orders as the pair would and cannot collide with a top-level name), or the Location's name key alone at the top level; then the Location's ID as a deterministic tiebreaker, the sort within the group, the asset ID. The direction is fixed: `SearchResultsController` refuses `groupDirection` with `groupBy=location`. A cursor whose anchor was in a Location slices `located` after it and lets `unlocated` fill the page only once `located` has run out (the day statement's guarded `LIMIT CASE`, on `located`); a cursor without a group key slices `unlocated` alone. The `SearchGroupKey` enum is `Day(date)`, `Location(id, pathKey, name, categoryName)`, all `None` for the trailing group, or `Sequence` (below); the grouped grid heads a Location group `Category › Location`.

**Group by Sequence** (`SearchQueries.groupedBySequence`, `GroupBy.Sequence`) is that shell over its own two relations: `sequenced` is `matching` with a Sequence, and `unsequenced` the rest, always the trailing "No sequence" group. A frame is in one group, so its cell ID is the plain one. Groups are in the order of Curation's queue and it is fixed: the first capture of the group's matching frames, oldest first with those that have none last on both engines, then the Sequence's ID, the sort within the group and the asset ID. The first capture is a window over the matching frames, so a search showing some of a Sequence's frames orders and counts its group by those, and `sequence_frames` (`SequenceFrameRow`) materializes it for the cursor to compare; a page costs the frames that carry a Sequence, through `asset_sequence`, and not the library. A group's count is one correlated count per distinct Sequence on the page, and the "No sequence" count runs only on the pages that reach that group. The key is `SearchGroupKey.Sequence(id, firstCapturedAt)`, all `None` for the trailing group: `cursorKey` is the first capture and `cursorGroupId` the Sequence, so `SearchCursor` keeps its shape. A cursor with a `groupId` slices `sequenced` after its anchor and lets `unsequenced` fill the page only once `sequenced` has run out (the guarded `LIMIT CASE`); one without slices `unsequenced` alone. A Sequence is told by its ID before its first capture (`afterSequence`, `SearchGroupKey.continues`), since the first capture moves when the frame that set it leaves: the frames already shown must not count as a later group, and those still to come must not be lost. Another Sequence can therefore overtake it on the next page, and it opens again after that one with a second header. `SearchResultsController.parseGrouping` makes `sequence` outside the Triage view no grouping and not a 400, since only a frame in triage carries a Sequence and grouping survives a change of view: the page is a flat one whose fragment names no grouping, while `HX-Replace-Url` and the search store keep what was asked for, so a return to Triage groups by Sequence again.

**Text search** (`q`, the Search text; the terms are defined in the root `CONTEXT.md`). `util/SearchWords.of` is the one word-splitting rule, applied to the stored body of a Search document, to every name read at query time and to the typed text: decompose (NFD) and drop the combining marks, split on anything that is not a letter or a digit, on lower-to-upper camelCase humps and on letter/digit boundaries, then lower-case (`IMG_1234-beachSunset.final.jpg` is `img 1234 beach sunset final jpg`). The hump is the only boundary that depends on case, so each of the three uses reads a text through `SearchWords.variants`: its words, then, only when the text has a hump, the same rule without it (`McDonald_beachSunset.jpg` is `mc donald beach sunset jpg` or `mcdonald beachsunset jpg`), and nothing for text without a word. A word written with a hump and the same word written in one case therefore find each other: `mcdonald` finds `McDonald`, and `McDonald` finds `Mcdonald` and `MCDONALD`. `util/SearchText.parse` turns the typed text into an `Option[SearchExpression]` and never fails: space-separated terms are AND-ed into `SearchGroup`s, an upper-case `OR` between two terms makes them alternatives of one group (it binds tighter than AND), a leading `-` excludes that one term, and a `"quoted phrase"` is one term of whole words. A `SearchTerm` carries the variants of what was typed and matches when any of them does. A bare term's last word matches the start of a word; a bare term that splits into several words (`IMG_12`) is those words in sequence, the last one a prefix. An unbalanced quote closes at the end of the text, a term without a word and a dangling `OR` are dropped, terms past `SearchText.MAX_TERMS` (16) are dropped and logged at DEBUG, and text with no term left is `None`, which is no text everywhere: no filter, no Relevance, not refused in the trash.

A term can match in six **Search sources** (`util/ResolvedSearchText.scala`, `SearchSource`), each with the Relevance a match there is worth:

| Source | Matches assets | Relevance |
|---|---|---|
| Person: named, not hidden, not merged away (`is_deleted`), not a bad match | with a Face of that Person | 5 |
| Location | in that Location | 4 |
| Category | in any Location of that Category | 3 |
| Folder, not recycled, not the root | in that folder or any folder below it | 2 |
| Album | in that album | 2 |
| Search document: file name and user metadata values | whose document has the term | 1 |

Only the last is stored. The **Search document** is one `search_document` row per asset whose `body` is the words of the file name followed by those of every user metadata value, each in every one of its `SearchWords.variants` in turn (`McDonald_beachSunset.jpg` is `mc donald beach sunset jpg mcdonald beachsunset jpg`; a value without a hump contributes its words once), joined by spaces, so the engines index words the application already split. `SearchDao.writeDocument` (JDBC DAO, one `INSERT ... ON CONFLICT DO UPDATE` for both engines) writes it once from `indexAsset` and `reindexAsset`, after the metadata parameters, and from `addMetadataValue`, always inside the service transaction that changes the asset: the import pipeline's index flows, the metadata edits of `UserMetadataService` (which reads the asset after storing the value, so the document has it), and `AssetService.rename`, which reindexes. Every field type's values are in the document. Which of them also get `metadata_parameter` rows, the only thing the metadata filters read, is the JDBC DAO's rule, applied by its `addParameters` on import, reindex and value additions alike: `FACETED_FIELD_TYPES` (`KEYWORD`, `NUMBER`, `BOOL`) are the types whose value column the insert writes, so a `TEXT` or `DATETIME` value is found by its words and never by a metadata filter. A keyword's column, `field_value_kw`, holds `NameKey.of(value)`, and `SearchQueries.valueMatch` folds a keyword filter's value with `NameKey.of` before comparing, so the filter finds a value typed in any case or Unicode form (see **Names**). Recycling and restoring do not touch it (the view's `is_recycled` filter keeps a recycled asset out); purging deletes it through the `asset_id` cascade on both engines. Schema, in both `all.sql` files: PostgreSQL has `search_document (repository_id, asset_id, body, tsv)` with `tsv` `GENERATED ALWAYS AS (to_tsvector('simple', body)) STORED` under a GIN index (no stemming, no stop words); SQLite has an ordinary `search_document (id INTEGER PRIMARY KEY, repository_id, asset_id, body)` table plus `search_document_fts`, an FTS5 external-content table over `body` (`content_rowid='id'`, a declared key `VACUUM` cannot renumber; `tokenize='unicode61 remove_diacritics 0'`, `prefix='2 3 4'`) kept in step by insert, delete and update triggers. Both have the unique index `search_document_01` on `(asset_id, repository_id)`, which serves the purge cascade and the selective path's probes; the upsert's `ON CONFLICT (repository_id, asset_id)` still finds it, since a conflict target names a set of columns, and it rewrites only a changed body (`WHERE search_document.body <> excluded.body`), which on SQLite also spares the FTS entry. `SearchDocumentRow` maps the three shared columns; `tsv`, SQLite's `id` and the FTS table appear only as raw fragments in the dialects.

Names of people, Locations, Categories, folders and albums are never copied into a document, so a rename, merge, hide, move, delete or membership change shows in the next search with nothing to reindex. `SearchService.resolveText(expression, probeLimit)` reads the candidates of every name source in one read-only transaction (`SearchDao.searchNames(sources)`, which reads the sources it is asked for and no other: `SearchSource.names`, all five, here), matches each term against the variants of each name in memory (`SearchTerm.isIn`: any variant of the term within one variant of the name, the rule a document is matched by, confined to one reading of one name), probes the result (see the paths below) and returns a `ResolvedSearchText`: per term, the matching IDs of each source that had any, and the probe's verdict. A Category's hits become the IDs of its Locations and a folder's hits are expanded to every folder below them, so each source is a plain ID filter. The names are read fresh on every request; their words are not recomputed, since `SearchWords.variants` remembers the readings of up to 50,000 texts in a bounded LRU map, a text's readings being a pure function of it. `SearchQuery` keeps `text` as typed and carries the resolution beside it (`resolvedText`, `withResolvedText`); `LibraryService.withResolvedScope` resolves it next to the folder scope for `search`, `searchGrouped`, `count`, `cappedCount`, `mapCells` and `mapBounds`, afresh on every request and every page, and `SearchQueries.matching` refuses text that was not resolved (`requireResolvedText`) rather than searching the documents alone.

A term's **sources** (`SearchQueries.TextSource`, in declaration order: the name sources it resolved to any IDs in, then always its document) are relations of asset IDs: `face.asset_id` by person, `location_asset.asset_id` by Location (a Category as its Locations), `album_asset.asset_id` by album, and `search_document.asset_id` through the dialect's `textMatch`; a folder is the asset's own `folder_id`. `textFilter` ORs a term's sources (negating them for an excluded alternative), ORs the alternatives of a group and ANDs the groups. A text is matched in one of two ways, decided per request by a **probe** that `SearchService.resolveText` runs in the same read transaction after resolving names:

- `SearchDao.probeText` (`SearchQueries.textProbe`) is one statement with a branch per positive group (none of whose alternatives is excluded): the `UNION ALL` of the group's sources, limited to `limit + 1` rows; the document source is scoped to the repository by its own `repository_id`, and the name sources need no scope, since their IDs were resolved from the repository's names, so each reads the index that leads with its ID and carries the asset (`face_02`, `location_asset_01`, `album_asset_01`) and nothing else, the limit being `SearchQuery.textProbeLimit` (`Const.Search.TEXT_PROBE_LIMIT`, 5,000; tuning carried on the query for tests, not part of the cursor fingerprint). A group with at most `limit` rows is complete (`ResolvedSearchGroup.isComplete`), and `ResolvedSearchText.candidates` is the intersection of the complete groups' hits: `None` (no complete group, or no positive group, which is not probed) means broad, and an empty set answers the search with nothing, without reading the library (`SearchDao.matchesNothing`).
- **Selective path** (candidates present): `matching` filters `asset.id` by the candidate set (one bind); the complete groups need nothing more, and every other group, excluded term and source tested for the Relevance is a correlated probe on the asset's own row (`EXISTS` on `face`, `location_asset`, `album_asset` or `search_document` by `asset_id`, each through an index that leads with it; the folder by its column).
- **Broad path** (no candidates): each source relation of each term is a `MATERIALIZED` CTE at the head of the statement (`text_<group>_<alternative>_<source>`), and every predicate and the Relevance test membership in them, so a source is built once per statement whatever the shell renders `matching` into. A group of one excluded term is an anti-join on each source (`SearchDialect.excludes`: `NOT EXISTS` on PostgreSQL, a hash anti-join; `NOT IN` over the CTE on SQLite, which indexes the set once); an `OR` group with an excluded alternative negates its memberships.

The person filter reads `face.person_id` alone, and the document source has no repository predicate of its own outside the probe (the asset is scoped). An ID set is one bind parameter whatever its size (`Columns.isInSet`: `= ANY(?)` with a `varchar[]` on PostgreSQL, `IN (SELECT value FROM json_each(?))` on SQLite), which the `personIds`, `albumIds`, `locationIds` and folder-scope filters use too. `textMatch` is a positive match of one term, with the query string built from `SearchWords` output only: PostgreSQL binds `beach:*`, `img <-> 12:*` or, for a phrase, `golden <-> gate` into `tsv @@ to_tsquery('simple', ?)`; SQLite binds `"beach" *`, `"img 12" *` or `"golden gate"` into `id IN (SELECT rowid FROM search_document_fts WHERE search_document_fts MATCH ?)`. A term with two variants is still one bind, the OR of its readings: `mc <-> donald:* | mcdonald:*` (`<->` binds tighter than `|`) on PostgreSQL, `"mc donald" * OR "mcdonald" *` on SQLite. The body is one string, so in the document a phrase or a several-word term can match across the boundary between the file name and a metadata value, between two values, or between the two readings of one value.

**Relevance** (`sort=relevance`, `SearchSort.Relevance`) is the one sort that is not an asset column. `SearchQueries.relevance` renders it from the same `termMatches` pairs, only when it is the sort: the sum, over the groups of the text, of a `CASE` whose branches are the group's non-excluded alternatives' sources, highest score first, so a term counts as the best source it matched and alternatives joined by `OR` count once, as the best of them. Excluded terms score nothing, and text made of exclusions alone gives every match 0. The order, flat or within a group, is Relevance descending, capture time `DESC NULLS LAST`, then ID. The value is computed once per row: in a flat page's select list, and in a grouped statement's `scored` CTE, whose columns the cursor comparison (`afterBySort`, `afterByCaptureTime`) and the order read. `SearchQuery` throws for the Relevance sort without usable text, and `SearchResultsController` answers that request with a 400 before building one. The map layout has no sort and plots the text's matches like any other filter.

Paging is by cursor only: `SearchCursor` (version 6) is an opaque, versioned Base64URL token holding the last returned image's group (`key`, the ISO day, the Location path key or the Sequence's first capture, plus `groupId`, the Location's or the Sequence's ID; both absent in the trailing group, and a Sequence with no capture time has `groupId` alone), sort value and ID, and a fingerprint of the search as requested (engine, repository, filters including `locationIds`, `peopleMatch`, `takenRange`, `importedRange`, `bbox` and `subset`, grouping, ordering; a folder filter as given, not its expanded descendants, the Search text as typed, not the names it resolved to, and a date range as its days, not the instants a Date Imported day begins and ends at). Under the Relevance sort the position is a triple, so the token also holds the second sort value (`s2`, the capture time, which may be null); under a column sort `s2` is null and never read, and a Relevance cursor without it is a `SearchCursorException`. `LibraryService.searchGrouped` recomputes the fingerprint and rejects a mismatch with `SearchCursorException`; a cursor supplies a position only, never access or SQL, and the page size is not part of it. Results are live: a cursor continues from values, so deleting its anchor or inserting before it neither skips nor repeats the remaining images, while the counts describe the current matching set.

`routes/SearchRequestParser` is the shared parameter-to-scope parser for the HTML search, the map cells/bounds endpoints, the Triage routes' counts and the advanced search panel's form: `view`, `q`, folder/person/album/Location IDs, `peopleMatch`, the four dates of the two ranges, `bbox`, `triaged` and `subset`. A route builds one `SearchRequestParser.Params` from its query parameters, each by name, and hands it on whole (`parse(params)`, and `SearchResultsController.browserViewUrl` for the bookmarkable URL), so no two of the same-typed values can change places on the way. `parse` returns a scope (`Scope`, the people and the Locations in the order the request names them, as lists) that each controller turns into a `SearchQuery` with its own sort, grouping and paging. The view sets the scope's flags: `view=triage` is the triaged assets that are not recycled (an asset recycled from triage keeps `is_triaged`; `SearchQuery.TRIAGE_VIEW`, the flags `LibraryService.triageSummary` counts by too), `view=trashbin` the recycled assets not yet marked for purging, and any other view, the repository view, the sorted assets, neither recycled nor triaged, whatever the folder, person, album, Location, text or map area. `triaged` (a boolean) changes that rule on `is_triaged`: `triaged=true` adds the triaged assets to the repository view, where `false` is the same as leaving it out, and in the trash it tells the assets recycled from triage from the rest; `view=triage&triaged=false` is refused (`The triage view holds only triaged assets`, a plain-text 400 in HTML search, a JSON 400 from the map endpoints). The flag is a column filter in `SearchQuery.params`, so it is part of the cursor's fingerprint like the view's own flags. The scope has Search text only when `q` has a usable term (`SearchText.parse`); `q` that parses to nothing is no text, for the filter and for the default sort alike. Text with `view=trashbin` is refused (`Search text does not search the trash`): a plain-text 400 in HTML search, a JSON 400 from the map endpoints. `bbox` is the grid's and the crowded-pin panel's filter only: the map endpoints and the map layout never read it, and a malformed one is a plain-text 400 in HTML search. `subset` (`unknownPeople` or `noLocation`, `TriageSubset.fromApiValue`) narrows the scope to a Triage subset, the assets one of the Triage summary's counts shows; only Triage offers it, but every view takes it, and any other value, empty included, is refused (`Unknown subset value`, a plain-text 400 in HTML search, a JSON 400 from the map endpoints).

**Advanced search parameters.** `personId` and `locationId` each name one ID or several, separated by commas (`SearchRequestParser.idsOf`, each ID once, in the order given, an empty segment no ID: `personId=`, `personId=,` and `personId=a,` name nobody, nobody and one person, as the browser's store reads them); the folder and the album stay one ID. Several Locations match any of them, and several people all of them, or any with `peopleMatch=any` (`PeopleMatch.fromApiValue`; `all` is the default, and any other value, empty included, is refused: `Unknown peopleMatch value`). `takenFrom` and `takenTo` are the Date Taken range and `importedFrom` and `importedTo` the Date Imported range, each an ISO date (`2024-06-01`, read by `SearchRequestParser.ISO_DAY`: four digits of year, two of month and two of day, of a day the calendar has, so `2024-02-30` and a longer, signed year, `+10000-01-01`, are refused), either end left out for a range open there, and no range when both are. The parser refuses, with the message of a 400 (plain text in HTML search and the panel, JSON from the map endpoints): a date that is not an ISO day, naming its parameter; a range whose first day is after its last, naming both (`DateRange`'s own refusal); an unknown `peopleMatch`; more than `SearchRequestParser.MAX_IDS` (10) IDs in `personId` or in `locationId`, each parameter counted on its own; and an album or a subset beside what only the panel combines (`A search by several filters takes no album and no subset`): a date range, several people, several Locations, or more than one of the Search text, a folder, a person and a Location, since such a search searches the view by the panel's filters alone. The parser counts any folder there, the root included, having no repository at hand. An ID that names nothing in the repository is no error and matches nothing: beside others it adds nothing to the Locations or to the people matching any, and leaves the people matching all with no match. An advanced search searches outside the trash, as text does: a date range, several people or several Locations with `view=trashbin` are refused (`A date range does not search the trash`, `Several people or Locations do not search the trash`), while one person or one Location there is taken as before. `triaged=true` adds the triaged assets to an advanced search as to any other. `SearchResultsController` and both map routes take the five parameters and hand them to the parser; `TriageController`'s scope dialog and Quick view name one folder, Person or Location and take none of them. **The results title of a filtered search.** A search is a **filtered search** (`CONTEXT.md`) when it has a date range, two people or more, two Locations or more, or more than one of the Search text (a usable term), a folder, a person and a Location, the root folder counting as no folder (`SearchResultsController.isFiltered`). Its results title is "Search results" over a chip per filter (`views/AGENTS.md`, **Results title**), whose names the controller reads through `SearchService.filterNames`, as the panel's form does, with the people and the Locations in the order the scope holds them, the request's, into a `models/SearchFilters` (the text, the `SearchFilterNames`, the people match and the two ranges) that `includes/search_results` renders; a date range reads as `DateRange.label` (`1 Jun – 30 Jun 2024`, a single day once, `from …` or `until …` for an open end, each end's year when the two differ, a month by its first three letters in English, September `Sep`: `Util.humanReadableShortDate` and `humanReadableDayAndMonth`, the formatter of Curation's rail, which the panel's date field matches from a table of its own, `MONTHS` in `date-range.js`, so neither side reads a locale's abbreviations). The names are read for a first page alone: a continuation (`isContinuousScroll`) renders cells and no title, so it reads none. An ID of a filtered search that names nothing in the repository, unknown or another repository's, is therefore no 404: it has no chip and matches nothing. Any other search names one scope at most, the person, the folder's path, the album or the Location, which the controller reads by ID on every page, so one that is not the repository's is a 404 that names nothing of it. `Api.Field.Search` names the parameters (`PEOPLE_MATCH`, `TAKEN_FROM`, `TAKEN_TO`, `IMPORTED_FROM`, `IMPORTED_TO`).

`layout` is separate from `view`: `grid` (default) or `map`. With `layout=map`, grouping, paging and the `bbox` filter are ignored (`bbox` is the panel's scope and stays in the URL), `LibraryService.cappedCount` supplies the asset total of the whole search, and `mapBounds` supplies the initial plotted bounds. `includes/search_results` renders the toolbar with Group disabled and `htmx/map_view` directly, without `#assets`. The fragment carries `data-results-location-id`, `data-results-bbox`, `data-results-q` (the Search text the results were matched by, empty without a usable term), `data-results-layout` and the grouping the server used (`data-results-group-by`, and `data-results-group-direction`, empty for a Location or a Sequence grouping); `HX-Replace-Url` includes non-default layout, Location, subset and bbox scope, and the people match and the four dates as given, after the Location. Map searches omit the ignored grouping from that URL. In the browser, `js/map/map-view.js` plots the search by asking the cells endpoint for every settled viewport and clustering the cells once more on screen; a crowded pin opens a panel whose grid is an ordinary search with `bbox` set. See **Map view** in `views/AGENTS.md`.

An options fragment is `role="option"` elements alone, at most `Const.Search.MAX_FILTER_OPTIONS` (50), the first in order. `SearchService.offered` picks them in one read-only transaction over the candidates a Search text is resolved against, so the options and the text cannot disagree about what a name is. Each route reads the names it uses and no other: the folders `SearchDao.searchNames(Set(Folder))`, the Locations the Location and Category sources, which are one table and one read, and the people `PersonService.getListedSearchable`, the same people with their counts (its query spells `searchablePeople`'s four flags, and `SearchServiceTests` holds the two to one answer). `q` is parsed as a Search text (`SearchText.parse`) and an option is offered when its own name has it, every group of terms by `SearchTerm.isIn` over the name's `SearchWords.variants`, an excluded term not; `q` with no usable term, nothing typed included, offers every name. A match is in the option's own name, never in its path: text naming a Category or an ancestor folder offers nothing below it. The order is by name key (`NameKey.of`, a segment's computed once a request and a name's key built once), a folder's path compared segment by segment, which is the order the explorer lists them in; the first 50 are kept in a heap as the names are passed over once (`firstOf`), so nothing typed, which every folder matches, sorts none of a Library's folder tree. Names are matched in memory on every request, so the browser never holds a Library's folder tree to filter and a rename shows in the next request.

The panel reads its parameters through `SearchRequestParser.parse` as a search of the repository view does, so what a search refuses (a malformed date, a reversed range, an unknown `peopleMatch`, more than 10 IDs) is a plain-text 400. `SearchService.filterNames(folderId, personIds, locationIds)` then names what is left, in one read-only transaction, as a `SearchFilterNames` (the same names a filtered search's results title shows, above), each read by its ID and never from the name candidates: the folder's path through `FolderService.getPath` (one recursive read, the folder and the folders above it), the Locations with their Categories' names through `LocationService.getLocationsByIds`, the people through `PersonService.getLive`, each list in the order its IDs were given in. A person is any live one, hidden or with no name included, since a search can be scoped to them from the People tab; an ID that names nothing there (one that no longer exists, another repository's, a Person merged away or marked as a bad match, a Category given as a Location, the root folder, which is the whole repository, a recycled folder) has no chip and no place in the form's inputs, and is never a 404, so the panel shows what is left of a bookmarked search. Tests: `SearchRequestParserTests` (unit: the parameters and every refusal), `SearchServiceTests` (both engines: the options' matching and order, the filter names, and which name sources each of them reads), `SearchPanelControllerTests` (the fragments, the cap, and a People option's count with triaged items hidden and shown), `SearchResultsControllerTests` (the parameters on the search routes, and a filtered search's title: which searches are filtered, the chips, their order and the dates' wording, an ID that names nothing, and a continuation reading no names), `MapControllerTests` (the parameters on the map routes) and `RouteTableTests`. The panel's markup is in `views/AGENTS.md` under **Advanced search panel fragments**, and what it does in the browser under **Advanced search panel**.

Date storage behind this: `original_created_at` is the camera's wall-clock time with no zone (PostgreSQL `TIMESTAMP WITHOUT TIME ZONE`, SQLite `yyyy-MM-dd HH:mm:ss` text with a fraction of a second appended only when there is one) and is parsed and bound as a `LocalDateTime` with no instant conversion, so its calendar day never depends on the JVM or server zone. `CaptureDateResolver` adds the camera's `Sub-Sec Time Original` or `Sub-Sec Time Digitized` tag (`Exif SubIFD`), to the microsecond, to the EXIF original or digitized date it sits beside, so burst frames within one second keep their order, and keeps the fraction an XMP date spells itself (`xmp_create_date`, ISO 8601), to the microsecond as well; every other rung is whole seconds, and an unset clock stays a sentinel whatever subsecond it carries. The file name is the last rung (`filename`), read when no metadata rung is plausible, in five shapes (`CaptureDateResolver.nameShapes`), each a regex anchored at the start of the name that spells a time to the second, with a boundary after the seconds so an incidental digit run never reads as a time: the compact camera form (`IMG_20240704_080910`, with an optional `IMG`, `VID`, `MVIMG`, `Screenshot`, `signal` or `photo` prefix), a Pixel name (`PXL_20240704_080910123`, the three millisecond digits after the seconds dropped), the dashed timestamp (`2024-07-04 08.09.10`, with an optional `Screenshot`, `Screen Shot`, `WhatsApp Image`, `photo` or `Image` prefix, a separator or ` at ` before the time, its parts dashed, dotted or coloned, and an optional `AM`/`PM` after a plain space or the narrow no-break space (U+202F) macOS writes there making the hour a 12-hour one: 12 AM is 0, 12 PM is 12, hours 1 to 12 only; a duplicate's `~2` or `(1)` suffix is a boundary after the seconds like a space or the extension), Apple's export (`Photo Dec 24 2023, 2 55 06 PM`, also `Image` and `Video`, on the same 12-hour clock) and Facebook's epoch (`FB_IMG_` and 13 digits of milliseconds or 10 of seconds, read as the UTC wall clock of that instant, as the container and GPS rungs are, whatever the JVM's zone). A name gives whole seconds only, never a fraction; a name that spells a date and no time (`IMG-20240704-WA0001`, `Photo Dec 24 2023`) resolves nothing, since a midnight time would put a day's frames inside one Sequence gap; and every shape's wall clock goes through `WallClockParser.parse`'s strict calendar check and the plausibility rules, so a plausible metadata date always wins over the name. `created_at` on assets is bound explicitly in UTC by `AssetDao.add` (an `OffsetDateTime` on PostgreSQL, UTC text on SQLite, the clock's reading truncated to the microsecond first, so both engines store one value for it) instead of relying on the engine default. When no rung yields a capture time the column stays NULL and the asset joins the "No date" group. The index `asset_search_date_taken` is `(repository_id, is_recycled, is_pipeline_processed, <day expression>, <raw timestamp>)` carrying `id`, `folder_id`, `is_triaged` and `created_at` (`INCLUDE` on PostgreSQL, trailing columns on SQLite): the day gives seeks, per-day counts and the bounds of a Date Taken range, the trailing timestamp makes a same-field grouping and sort read in index order, a pass over the library that tests text membership, a folder or a day reads the index and not the table, and so does a read in its order that tests a Date Imported range, by the import time it carries. Nulls sort where each engine puts them (no `NULLS LAST`, which would forfeit index-ordered reads; the one exception is the Relevance sort's capture-time tiebreaker, which no index orders anyway); SQLite's `created_at` can still be null on legacy rows, which matters only when it is the sort column. There is no incremental migration for any of this: the capture columns and the index live in `all.sql` only, the schema version stays 2, and a database is created from scratch.

The rest of the search's indexes, in both `all.sql` files: `asset_search_created` (`repository_id, is_recycled, is_pipeline_processed, created_at`, carrying `id`, `is_triaged` and `original_created_at`, as `INCLUDE` or trailing columns likewise) for the Date Imported sort, the bounds of a Date Imported range and, by the capture time it carries, a Date Taken range tested as the index is read in order; `asset_triage_created` and `asset_triage_date_taken`, the same two keys over the triaged assets alone (`WHERE is_triaged`), carrying `id`, the latter `folder_id` too, and neither the triage flag nor the other date, so the triage view of a large library reads only its triage set, `PersonDao.getTriagedAssetCounts` (the People list's triaged assets per person, its statement `triagedAssetCountsStatement`, its flags written as literals) starts from one of them, so that it follows the size of the triage set and not of the library, and the latter also answers `AssetDao.getSequenceCandidates` (the days of a capture-time window, then the window); `asset_triage_undated` (`repository_id, width, height, created_at, id` over the triaged assets with no capture time) for `AssetDao.getUndatedSequenceMatches`, walked backwards from the newest import of a size and stopped at the cap; `asset_sequence` (`sequence_id`, over the rows that carry one) for Curation's reads and the Sequence grouping; `asset_owner` (`owner_user_id`) for the key from `account`, which a delete of an account checks; `asset_folder` (`folder_id`) for folder browsing and the folder source of text (on SQLite it also lets an OR of sources be planned as a multi-index OR); and `face_01` (`asset_id, repository_id, checksum`, on PostgreSQL carrying `person_id`), `search_document_01` and `metadata_parameter_01` (`asset_id`), which lead with the asset for the purge cascades, `clearMetadata` and the selective path's probes. `metadata_parameter_02` (`field_id`) serves the cascade from a deleted metadata field. The membership tables are indexed in both directions, each index holding both columns (`album_asset_01`/`location_asset_01` lead with the album or Location, `album_asset_02`/`location_asset_02` with the asset), so a probe from either side reads its index alone. `face_02` (`person_id, detection_score`) carries `asset_id`, so the person source and the person filter, matching any or all, read the index alone. `asset_01` is unique on (`repository_id, checksum`) over the live assets only (`WHERE NOT is_recycled`): a repository has one live copy of a content, and the recycle bin any number. Both checksums, the asset's (its file's SHA-256) and the Face's (its crop's), are `CHAR(64)`, 64 lowercase hex characters, `COLLATE "C"` on PostgreSQL as the IDs are. `account_01` is unique on `email_key` and `account_02` on `username_key`, the name keys of the email address and the username, and both lookups by email compare `email_key`. `person_01`, `person_02` and `person_03` are partial on the live people (`is_deleted = FALSE`), so a merged-away person's name and cover face are free for others. `person_01` is unique on (`repository_id, name_for_sort`) over the people neither merged away nor a bad match; a named person's `name_for_sort` is its name key, and `PersonDao.getLiveByNameKey` (the statement `PersonDao.liveByNameKey`) reads the index to find who holds a name. The key is folded in Scala (`PersonService.nameKey`), as every name key is, never by an index: SQLite's `lower()` and `NOCASE` fold ASCII only and PostgreSQL folds by its collation, so a fold in the database would make "Élodie" and "élodie" one name on PostgreSQL and two on SQLite. SQLite matches a partial index to a flag a statement binds by the value bound, as long as it is bound as a number, which is how every ScalaSql comparison binds a boolean; a flag bound as text does not match, and `SqliteOverrides.nativeBool` binds `"1"`/`"0"`, so a hand-written JDBC statement that should read a partial index writes the flag as a literal. On PostgreSQL every ID column is `CHAR(36) COLLATE "C"` (compared, sorted and grouped byte-wise, as SQLite does) and `asset` has `toast_tuple_target = 128`, so its `jsonb` metadata lives out of line and the heap row a search reads stays narrow; SQLite's `asset` declares its three metadata JSON columns last, after `updated_at`, so reading any other column does not walk their overflow pages. `SearchPlans` (test trait) reads a statement's plan over a seeded, analyzed library, rolled back afterwards, for the suites that check which index a search or lookup reads; `indexOnlyPlanOf` says whether an index alone can answer a statement, which on PostgreSQL takes costing the seeded tables as vacuumed and ruling out scans of them.

Coordinates: `latitude` / `longitude` on `asset` are WGS84 decimal degrees, nullable, and are parsed on import only, in `ExtractMetadataFlow` through `util/GeoLocationResolver`. Like `CaptureDateResolver`, it reads only persisted inputs - the `GPS` directory of `extracted_metadata`, where metadata-extractor stores each coordinate as a signed degrees-minutes-seconds description plus its `N`/`S`/`E`/`W` ref tag - so a later backfill needs no file. The ref decides the hemisphere whenever present, because the description's integer degree part drops the sign of a value between -1 and 0 (London's longitude). Unparseable or out-of-range values and 0/0 resolve to nothing, and a coordinate whose ref tag is missing has no description at all: `MetadataExtractionService` skips a tag with a null description instead of storing a null (which the JSON column cannot hold). There is no editing and no backfill of existing rows. The partial index `asset_geo` `(repository_id, is_recycled, is_pipeline_processed, latitude, longitude) WHERE latitude IS NOT NULL` is for the map's bounding-box queries, and carries `id` and `original_created_at`, what a map cell names and is ranked by, and `is_triaged`, the repository view's filter, so a viewport's own points are read from the index alone; `SearchMapTests` checks on both engines that a cells statement reads through it (on Postgres over a few thousand analyzed rows, because its planner costs by statistics and every index ties on a handful; the rows are rolled back once the plan is read and the table analyzed again, since the schema is shared by the suites that follow). The `location` and `location_asset` tables are described under **Locations**.

The root folder is a 400 |

## Locations

A `Location` (`models/Location.scala`) is one row of the `location` table, and `LocationKind` says which of two things it is: a **Category** (a named container, exactly one level deep, no pin, no assets) or a **Location** (a WGS84 pin, optionally under a Category). Both kinds share one name pool per repository under the name key (`location_01` on `(repository_id, name_key)`, holding `Location.nameKey`, `NameKey.of` of the name; see **Names**), so a category and a Location cannot have the same name in any case or Unicode form, and both kinds surface a clash as `DuplicateException` through `BaseService.add` / `updateById`. The model's constructor keeps the kinds honest (a Category has no pin and no Category; a Location has a pin in range) and the schema repeats the rules as CHECK constraints; "a Location's category must be a category" is a `LocationService` check (`IllegalOperationException`), as is "only a Location can be moved" and "a category holds no assets".

Membership is `location_asset`, the `album_asset` shape: no model, written only through `LocationDao`, an asset in any number of Locations, unknown / foreign / recycled asset IDs dropped on add, adds idempotent. `LibraryService.recycleAssets` drops recycled assets from every Location beside every album; restoring does not re-add; purging cascades. `Location.numOfAssets` and `categoryName` are computed by `LocationDao.getAll`, which lists the repository in **path order** (`LocationService.getLocationsOfAsset` reads an asset's Locations in the same order with their category names, through `location_asset_02`, for the Detail panel): categories and top-level Locations interleaved by name key, each category directly followed by its own Locations by name key (`ORDER BY COALESCE(category.name_key, name_key), category first, name_key`; the explicit category-first key matters because a Location named "Alba" would otherwise sort before its category "Italy"). Deleting either kind is a hard delete; a category's Locations are moved to the top level in the same transaction first (`LocationDao.moveChildrenToRoot`), and the `category_id` foreign key has no cascade, so a delete that forgot the re-category fails instead of orphaning. `LocationService.getById` is repository-scoped, and every mutation goes through it, so a foreign ID is a `NotFoundException` and changes nothing. The `locationIds` and `bbox` search filters and **Group by Location** are described under **Search results and date grouping**, the map's queries under **Map**; `LocationController` exposes `/api/location/r/:repoId/list` as flat camelCase JSON in path order (nullable `categoryId`, `categoryName` and pin), and `PUT`/`DELETE /api/location/r/:repoId/assets` accept `{locationId, assetIds: [...]}` and return `{added}`/`{removed}`. Malformed membership payloads and category targets are JSON 400s; a foreign Location is a JSON 404. `LocationActionController` owns `/htmx/location/r/:repoId/tab`, all six dialogs, and add/add-category/rename/move/assets/delete. Its dialog membership payload carries a comma-separated `assetIds` string, and its success response carries `{"added": n}` in the `App-Success-Detail` header (`BaseController.dialogSuccessResponse`, `Api.Field.SUCCESS_DETAIL_HEADER`), which the client merges into the dialog's success detail, so the dialog reports what the server applied rather than the size of the selection. Name, coordinate and Category errors replace the form through `dialogFormValidationResponse`; duplicate names share that path. Coordinates arrive as decimal strings from the dialog's hidden inputs (the pin is placed on a map, never typed; `views/AGENTS.md` **Location pin editor**) or as JSON numbers; a missing or out-of-range coordinate is reported once, as `Const.Msg.Err.PIN_REQUIRED`. An empty/null Category means the top level. Invalid hidden IDs are plain-text 400s, foreign IDs plain-text 404s. The Locations tab, its dialogs and the membership flows are described under **Locations** in `views/AGENTS.md`, and the map editor of the Add location dialog under **Location pin editor** there.

## Map

The map never receives a result set: a repository can hold millions of assets, so the browser asks for a viewport and gets back aggregates. Both aggregates are one statement each in `SearchQueries`, over a `points` CTE of the search's **plotted points** (`plottedPoints`, the rule the `bbox` filter also follows): a matching asset with coordinates of its own is plotted there and only there; one without is plotted at the pin of *each* Location it is in, so an asset in two Locations is two points, as it is two cells in the Location grid. The CTE is a `UNION ALL` of two typed relations over `matching`, so the map carries every filter the grid does.

- `mapCells(query, bbox, cellDegrees)`: the points inside the box, each assigned to a square cell by `floor(coordinate / cellDegrees)`, then one window pass per cell for the count of plotted points, the centroid, and the rank of each point by newest capture time (nulls last on both engines, through a `CASE`) then ID; the rank-one row is the cell and its asset **represents** it, so the thumbnail standing for a cell is stable across pans. A cell of one point carries that point's asset. `SearchService.cellDegrees(zoom)` is `360 / 2^zoom / 4` degrees - a quarter tile, about 64 pixels - with the zoom clamped to 0..20. `floor` is built into both engines (SQLite is compiled with its math functions).
- `mapLocations(query, bbox)`: one statement for the Locations pinned inside the box that hold at least one matching asset, with that count and the category's name: `matched AS MATERIALIZED (SELECT asset.id ... WHERE <matching> AND asset.id IN (<members of the Locations in the box>))`, then the repository's Locations in the box joined to `location_asset` with members in `matched`, grouped by Location. The matches are read once, not once per Location, and only among those members, so `matched` is as large as the memberships of the Locations in view and not as the library; the count agrees with the grid scoped to the Location.
- `mapBounds(query)`: `min`/`max` of both coordinates and the count of every plotted point of the search, not clipped, for fitting the map to a result; `None` when nothing is plotted. Points on both sides of the antimeridian span the whole longitude range.

`LibraryService.mapCells(query, bbox, zoom)` returns `MapCells` (the cells and the Locations, read in one read-only transaction) and `LibraryService.mapBounds(query)` an `Option[MapBounds]`; both resolve the folder scope and the Search text like `search`. The models (`MapCell`, `MapLocation`, `MapCells`, `MapBounds`, `GeocoderResult`) are plain case classes: the JSON shape is the controller's.

`GeocoderService` is the place-name search behind the Add Location dialog, proxied through the server so the browser never talks to the geocoder and the identifying `User-Agent` the Nominatim policy asks for is set in one place. It takes a Settings supplier and reads the switch on every search: it is **off by default** (the `map.geocoder.enabled` Setting; `search` throws `IllegalOperationException` when disabled, which `MapController` answers with a JSON 404) because every query is sent to a third party; the `map.geocoder.url` Setting is a Nominatim-compatible endpoint (`?q=&format=json&limit=5`, a list of `display_name`/`lat`/`lon`). A blank query asks nothing; a place without coordinates is skipped; an unreachable endpoint, a non-200 answer or a body that is not a list is a `GeocoderException`. The `map.tile.url` and `map.tile.attribution` Settings are the basemap the pin editor and the map view render with, read once per request by `SearchResultsController` and `LocationActionController`; the OSM defaults and the privacy trade-off of each are in their help text on the Settings screen.

`MapController` exposes `/api/map/r/:repoId/cells?viewport=s,w,n,e&zoom=n` (`cells`, `locations`, `countsPlottedPoints: true`), `/bounds` (the four bounds and plotted count, or `{count: 0}`), and `/geocode?q=` (camelCase `{label, latitude, longitude}` entries). Cells and bounds take the shared scope and, through `cask.QueryParams`, accept the client's search parameters verbatim: the ones that only shape a grid (`sort`, `layout`, grouping, paging) and the `bbox` filter are ignored, so the map behind an open panel plots the whole search, while `subset` narrows what it plots as it narrows the grid. A scope the parser refuses (Search text with the trash view, `triaged=false` with the triage view, an unknown `subset`, and an advanced search's malformed date, reversed range, unknown `peopleMatch`, more than 10 people or Locations, or filters with the trash view) is a JSON 400 carrying its message. `viewport` (`Api.Field.Map`) is the map's own clipping box, passed separately to the service and never an asset filter: a visible Location counts every member of the search even when its own GPS point is outside the viewport. A missing or malformed `viewport` and a non-integer `zoom` are JSON 400s naming the parameter; out-of-range integer zooms use the service's 0..20 clamp. JSON routes build their responses with `BaseController.jsonResponse` / `jsonError`. The geocoder is a JSON 404 when disabled (`IllegalOperationException` from the one read of the switch) and a JSON 502 on an upstream `GeocoderException`. All Location and Map routes require login.

**SQL explain log** (`transactions/SqlExplainer.scala`, `transactions/ExplainingConnection.scala`). A development aid, off by default: with `dev.sql_explain=true` in `application-dev.conf` and `ENV=dev` (any other environment ignores the key with a WARN), `Altitude` gives its `TransactionManager` a `SqlExplainer`, and `connection(readOnly)` then hands out each connection wrapped in a `java.lang.reflect.Proxy`. The proxy forwards everything and offers the explainer every prepared statement whose first keyword is `SELECT`, `WITH`, `INSERT`, `UPDATE` or `DELETE`, with its recorded binds, just before it first runs or is added to a batch; statements run through `createStatement` are never explained: transaction housekeeping, DDL, and also a statement with no bind values, which both ScalaSql (an update) and commons-dbutils' `QueryRunner` send that way (`SELECT nextval(...)`, an unfiltered count). No DAO knows about it, and with the switch off a transaction runs on the pooled connection itself.

- A query is explained the first time its shape is seen in the process: the SQL with whitespace collapsed, a placeholder list reduced to one placeholder and numeric literals replaced by a marker, so the permutations of one query log once.
- The explain runs on the statement's own connection with the same binds. PostgreSQL: `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` for a read, which runs the read one extra time, and `EXPLAIN (SETTINGS)` for anything containing the word `INSERT`, `UPDATE` or `DELETE`, which is never executed; both inside a savepoint that is rolled back, so a refused or timed-out explain does not abort the transaction. SQLite: `EXPLAIN QUERY PLAN`. A failed explain is logged in place of the plan and never reaches the request. `RequestContext` query counts do not change.
- Entries go to `sql-debug.log` in `Environment.ROOT_PATH` (git-ignored), emptied when the server starts: a numbered header (`READ`/`WRITE`, time), `Origin` (the innermost `altitude.*` frame, the DAO line) and, for a DAO statement, `Called from` (the first frame above it outside `altitude.core.dao`), the SQL as prepared, a `Runnable` form with the first-seen values as literals, and the engine's plan verbatim.

## Schema migrations

`schemaVersion` in `Altitude.scala` is the current version. `Altitude.migrationService` (`MigrationService(app, currentVersion, migrationsDir)`) runs `migrate()` in the constructor, in every environment, after the DAOs and before the Settings load: a fresh database (version 0, which a missing `system` table also means) runs `migrations/<engine>/all.sql` once and is stamped with the current version; a database behind would run `migrations/<engine>/<version>.sql` per version, but no such files exist. The service reaches the database through the system metadata DAO and the transaction manager alone, since no service exists yet, and rethrows any read failure other than a missing table, so a locked or refused read never passes for a fresh database. The suite bundles wipe the schema and migrate again after constructing the app (`TestDatabase.reset`).

DO NOT add new migrations or bump the version number. All changes go into `all.sql` for both Postgres and SQLite, as original table/index definitions as if it were a fresh schema (no ALTER); `schemaVersion` stays 2, and a database is recreated from scratch.

## Config & Environments

`ENV` env var controls mode (`dev` | `test` | `prod`). Config resolution order:
- **dev**: `application-dev.conf` → `reference.conf` (defaults in `altitude/resources/`)
- **prod**: `application.conf` → `reference.conf`
- **test**: system env overrides → the `reference.conf` files on the test classpath, merged with the main one first, so a key both files set keeps the main value (the test file's `db.engine` among them: controller tests run on SQLite). Test values that must differ are set in `Altitude`'s test branch: the test database URL and credentials.

The config files hold only what decides the shape of the process at startup: `fs.data.dir`, `storage.engine.default`, `db.engine`, `db.sqlite.*`, `db.postgres.user`, `db.postgres.password`, `db.postgres.url`, `db.postgres.pool_size`, `db.postgres.options`, `db.pool.leak_detection_threshold`, `face.debug.enabled`, `import.parallelism.max`, `dev.*` and the test `test.dir`. Everything an Admin tunes is a Setting (next section); a leftover key for one of those in `application.conf` is ignored, as `reference.conf` says at its top. `import.parallelism.max` is the exception on both counts: it caps a Setting on purpose, for a machine where no Admin tunes anything, and a leftover `import.parallelism=N` is not simply ignored: to HOCON the two are a number and an object at one path, so the number, unless the cap follows it in the same file, replaces the object and hides the cap, which `ImportParallelism.configuredCap` treats as no cap, logging a WARN.

To skip login during frontend dev work, set `dev.user` (a username or an email address) and `dev.password` in `application-dev.conf`; they are read once at startup through `Environment.devSetting` (`UserService.devCredentials`), the text counterpart of `devSwitch`: their values only under `ENV=dev`, and ignored, with a WARN, anywhere else. `UserService.getDevUser` checks the password until it first succeeds and then builds the account's claims from the database on every request (`claimsOf`), so a page of thumbnails does not cost a bcrypt check each, and a change to the account is seen at once; a dev login that fails is not tried again for 30 seconds, so it costs one bcrypt check and one audit event rather than one per request. To log the plan of each new query to `sql-debug.log`, set `dev.sql_explain=true` there (see "SQL explain log"). To have a pipeline queue whose stream fails restart it, set `dev.restart_pipeline=true` (see **Import Pipeline**). Both are read through `Environment.devSwitch`, the one rule for a development-only key: on only when it is `true` and `ENV=dev`, and off, with a WARN, when it is set in any other environment.

`Environment.isDev` is the check for anything that exists in dev only (an unset `ENV` is prod; an unrecognised value is dev). The **style guide** is such a thing: `App.allRoutes` registers `StyleGuideController` (`routes/web/`) only in dev, so its routes are 404s anywhere else, and `includes/nav.scala.html` renders its button under the same check. The page (`/style-guide/r/:repoId`) scans the source tree on every request with `StyleGuideScan.scan` (`core/util`), a pure function over `altitude/static/css`, `altitude/static/js` and `altitude/views` that finds the design tokens (`:root`, scoped, and set at runtime), their reference counts, the color literals and the length literals (px, rem and em in a font size, a width or height, a `min-*` or `max-*` bound, a `grid-template-*` and an inset) written past them, and the icons in use; the result is embedded in the page as JSON, and `GET /style-guide/scan.json` serves it (with a `version` of 1, the sources schema) to the **design tweaks panel** (the vendored tokentweak package `static/js/lib/tokentweak.js`, configured by the adapter `static/js/design-tweaks.js`: the other dev-only thing, whose boot script and adapter `includes/header_common` loads under the same check; it has no nav entry, `Ctrl+Alt+T` toggles it). The controller's other routes serve a sample dialog that validates like a real one and persists nothing, and the New library sample: the real `htmx/new_library_dialog` in error, posting to a route that applies the Library name rule (`Repository.validName`) and creates nothing. Controller tests reach the routes through a test-only `cask.Main` (`DevApp` in `StyleGuideControllerTests`), and assert that a non-dev app answers the routes 404 and renders neither the Style Guide button nor the panel script. The page and the panel are described under **Style guide** and **Design tweaks** in `views/AGENTS.md`.

## Settings

A **Setting** (`CONTEXT.md`) is a system-wide tunable with a default that an Admin edits on the Settings screen. Its one home is the `setting` table (`name`, `value`, `default_value`), seeded in both `all.sql` files; the keys keep their dotted names (`face.yunet.confidence_threshold`), so logs read as before. The registry is the companion of `models/Settings.scala`: every Setting's name constant, group (`SettingGroup`, the screen's sections: Face detection, Face recognition and quality, Video, Triage, Map, Operations), label, help text (the explanations `reference.conf` used to carry), `SettingType` (`Decimal` with bounds, `Integer` with a floor and an optional cap, `Flag`, `Text`, `TileUrl` with `{z}`/`{x}`/`{y}`, `HttpUrl`), kind and engine. A **Live setting** (`SettingKind.Live`, all but one) is used from the next operation that reads it; the **Restart setting** `import.parallelism` from the next server start. `face.recognition.hnsw_ef_search` and `db.postgres.read_statement_timeout` carry `engine = postgres`: they are neither shown nor saved on SQLite. Durations are whole seconds, but for the Watch folder scan interval, in whole minutes. `Settings.validate(values, engine)` returns the error of every failing field: the type's rule, then the four cross rules (box size ≥ smallest face, `hnsw_ef_search` ≥ 4 × `match_count`, enroll ≥ keep threshold, `max_sampled_frames` ≥ `min_cluster_frames`), a cross rule judged only when its field applies to the engine.

`SettingsService` (`Altitude.settings`, constructed first and empty, loaded once the schema is in place) holds the values as one immutable typed snapshot, the `Settings` case class (typed accessors such as `faceQualityEnrollThreshold`, `value(name)` and `default(name)` as text, both from the rows), replaced whole on every `load()` and `save()`, so a reader never sees a half-written set. `atStartup` is the snapshot of the first load, the running value of a Restart setting, and `pendingRestart` lists the Restart settings whose saved value differs from it. `currentIfLoaded` is `None` before the first load; `current` and `atStartup` throw then. `applicable` is the registry filtered to the engine. `save(values)` trims every value, merges them over the current set (a Setting not submitted keeps its value), validates for the engine and, when any field fails, throws `ValidationException` naming every failing field and writes nothing; otherwise it writes only the changed rows (`SettingDao.updateValues`, one batch in one transaction, `NotFoundException` when a row is missing), logs each change at INFO with the old and the new value, and swaps the snapshot. A value that spells the current one differently (`0.850` for `0.85`) is not a change, for the write and for the restart notice alike. Loads and saves are `synchronized`, so the table and the snapshot agree; readers never wait. `load()` fails on a missing or invalid row and WARNs on a row the registry does not know, so a retired Setting does not keep the server from starting.

A reader takes its value from `app.settings.current` at the moment it needs it, never in a constructor, and from one snapshot per operation: `FaceDetectionService` sets the YuNet score and NMS thresholds on the thread-local detector before each detection and reads the box size, the smallest face and the two quality tiers once per `extractFaces`; `FaceRecognitionService` reads the match count, the cosine distance and the minimum cluster frames per call and passes the first two into `FaceDao.searchClosestFaceMatches`, so no DAO holds a Setting; `VideoService` and `GeocoderService` take `() => Settings`; `TransactionManager` takes `() => Option[Settings]` (`currentIfLoaded`) for the read statement timeout and `hnsw.ef_search`, and sets neither before the first load; the import and purge queues read the shutdown timeout when `shutdown()` runs; `ImportService.prune` reads the Import history's days as it runs, and `WatchFolderService` the scan interval as it schedules each round; `SearchResultsController` and `LocationActionController` read the tile URL and attribution once per request; `CurationService` hands `CurationRule` one snapshot per set read; `Altitude.importParallelism` reads `atStartup` once, and the cap from the config (`ImportParallelism.configuredCap`), before the actor system is built. An import in flight picks a changed Live setting up at its next stage. The face quality thresholds never re-tier Faces already stored.

The screen is `GET /settings/r/:repoId` (`routes/web/SettingsController`, a full page with the shared nav) and its one form's save, `POST /htmx/settings/r/:repoId` (`routes/web/partial/SettingsFormController`, which also renders the form for the page), both `@requireLogin() @requireAdmin()`. `decorators.requireAdmin` runs after `requireLogin`, which put the account in the context (it throws when none is there), and answers a User or Guest with 403: JSON for an API request, a plain-text page otherwise, no redirect. The nav shows the Settings link to an Admin only, so `NavController`, whose fragment the import page polls, requires login too. The form posts JSON (`hx-json-enc`): the controller renders and reads only the applicable Settings, stringifies a JSON `true`/`false` or number, reports any other JSON type as `INCORRECT_VALUE_TYPE`, and takes an unchecked checkbox as `false`. A failed validation is `BaseController.dialogFormValidationResponse` with the form re-rendered over the submitted values and the errors beside their fields, so nothing is written; a success answers the saved form, and the client dispatches the form's declared `SETTINGS_SAVED_EVENT` to the snackbar. Each field shows its default and a Reset that fills the input with it (nothing is written until Save); a Restart setting with a saved value that is not the running one carries a notice naming both until the restart. `import.parallelism` always shows what is running and why: `SettingsFormController.form` passes `Altitude.importParallelismResolution` (the value and its reason, logged at INFO at startup) as a note per Setting name. The page's markup and scripts are described in `views/AGENTS.md` under **Settings screen**.

The application's stylesheet is built, not served from source: `cssBundle` in `build.mill` inlines the `@import` lines of `static/css/app.css` (recursively, failing the build on a missing file, a file outside `static/css`, a cycle, or any other `@import` form) into `assets/app.<hash>.css` on the classpath, and `assetManifest` generates `altitude.core.Assets.appCss`, its URL, which `includes/header_common` links. `StaticController` serves only that one name under `/assets/`, cached for good; `/static/` serves the vendored stylesheets, webfonts and JS modules under their own names, revalidated on every use (`@revalidated`). The hash is compiled in, so a CSS edit needs a recompile and a restart, which `make watch` does; `mill altitude.resources` alone leaves the running server linking the old name, which now answers 404.

The model files are not in git: the ArcFace net (`resources/opencv/w600k_r50.onnx`, downloaded from a pinned Hugging Face revision and checked against its SHA-256) and the two Scene models (`resources/onnx/dinov2_vitb14.onnx` and `clip_vitb16_image.onnx`, exported). `uv run scripts/fetch-models.py` fetches all three, skipping a model already in place unless given `--force`; the README has the steps. Without them `Altitude` fails to start, and so does the controller bundle, whose server's instance (`App.altitude`) builds the ONNX embedder. The integration bundles' instances need the ArcFace net alone (see **Scene models in tests**); without the Scene models, the unit suite's `SceneEmbedderTests` and the tests that turn the models on fail.

`make test`, `make test-local` and `make test-focused` run the bundles at once (`mill -j4`, `-j3`): Mill hands each selected bundle class to a worker JVM of its own, in its own sandbox (`out/altitude/test/testOnly.dest/worker-N/sandbox`), so each bundle has its own relative `test-data` (the SQLite file and the file store) and the bundles share no file; the PostgreSQL bundle alone uses the test database. Output lines are prefixed per worker, each worker's output is also in `out/altitude/test/testOnly.dest/worker-N.log`, and the merged report is `test-report.xml` beside them. The wall time is the slowest bundle's: about 4 minutes for `make test` (the PostgreSQL bundle) and 3 for `make test-local` (the SQLite bundle) on the 24-core dev machine.

> **Run `make test` only when the `altitude-core-postgres-test` container is up.** Otherwise use `make test-local`, or one bundle: `make test-sqlite`, `make test-controllers`, `make test-unit`.
> **Do not run tests if only the frontend was changed** (Twirl templates, CSS, JS, HTML) — these can be manually verified in the browser without running the full test suite.

To focus a test, tag it with the `Focused` tag:
```scala
test("my wip test", Focused) { ... }
```

A test that seeds a library's worth of rows (`SearchPlans.atScale`), runs a model many times over, or binds tens of thousands of IDs is tagged `Slow` (`org.scalatest.tagobjects.Slow`, the per-test form of `org.scalatest.tags.Slow`, which on a `FunSuite` could only tag a whole suite):
```scala
test("A Date Taken page reads the capture-day index in order", Slow) { ... }
```
Every target but `make test-with-slow` and the `test-focused*` ones leaves them out (`-l org.scalatest.tags.Slow`, `SKIP_SLOW` in the `Makefile`), so a focused `Slow` test still runs. **Never run `make test-with-slow` unless the user asks for it.** To check a `Slow` test you changed, focus it.

## Test Structure

Integration tests extend `IntegrationTestCore`. `beforeEach` turns every account's new-Library switch off (a bundle's database keeps every test's accounts, and a Library created grants each one whose switch is on), auto-creates a fresh repository and file-store directory, and gives the test's thread every Permission (`RequestContext.permissions`), as an Admin's request has; a test of a rule that reads them narrows them around its calls (`RequestContext.permissions.withValue`, as `AssetPermissionTests` does). `ControllerTestCore.beforeEach` does the same for the fixtures a controller test builds through the suite's instance; the server's requests read theirs from the login token. A bundle's database keeps every test's repositories and a Library name is unique instance-wide (`repository_01`), so `TestContext.persistRepository` numbers its names across the test JVM (`TestContext.nextRepositoryName()`: "Test Repository 1", "Test Repository 2", ...) and a test naming its own Library makes the name unique, as `RepositoryServiceTests` does with a random suffix. `persistRepository` records no last active Library: a login lands through `landingRepositoryOf`, and a test of the landing records one itself. A Library has no owner, so `persistRepository()` takes none and grants nobody access; it persists an account first when the context has none, since every asset has an owner. `TestContext.persistUser` takes a username (a random one by default, as `makeUser` gives, with an email address that holds an "@", since a login without one is a username) and `TestContext.grant(account, repository, permissions)` gives access (every Permission by default). `ControllerTestCore.login()` logs the context's account in, first granting a User every Permission (a Guest none) in the context's first Library when it holds no grant there; `cookiesOf(host, account)` logs an account in to a running server and returns its session cookies (for a test with several accounts); `loginAs(accountType, permissions)` persists an account of the type and a Library it can see (an Admin by type, anyone else by a grant of `permissions`, which every caller states: all of them for an Admin, none for a Guest) and returns the Library's ID. `ControllerTestCore` also has the helpers of the Library tests: `addLibrary(name, account)` (a Library `account` can see: by type for an Admin, by a grant of every Permission for a User, of none for a Guest), `lastActiveRepoIdOf(user)`, `clearAccountUpdatedAt` and `accountWritten` (whether a load wrote the account), and `assertPageRecords`, which loads a full page with another Library recorded and asserts the page records its own and a reload writes nothing. Tests run against both DB engines via `SqliteSuiteBundle` / `PostgresSuiteBundle` without code changes; their instances, and `StartupTests`' second one, are built by `TestAltitudeApp.build(dbEngine)`. `TestContext.setAssetDates` rewrites an asset's capture and import timestamps in each engine's storage form for date-dependent fixtures, and `TestContext.setAssetCoordinates` gives an asset a point for map and bounding-box fixtures. Controller tests run against SQLite through a real HTTP server (`ControllerTestCore`); the server is a second `Altitude` (`App.altitude`) over the same file, so `beforeEach` resets the database (`SqliteSuiteBundle.setup()`) and reloads that instance's Settings (`App.altitude.settings.load()`).

`TestDatabase.wipe(testApp)` drops the schema of either engine and `reset(testApp)` wipes, migrates and loads the Settings: the suite bundles' `beforeAll`, `ControllerTestCore.beforeEach`, and `StartupTests`' fresh-database test, which builds a second `Altitude` against a wiped database and cleans it up (`cleanup()`, then the actor system). `IntegrationTestCore.contend(first, second)` runs two transactions on threads of their own, the first held open until the second waits for it (for a row or advisory lock on PostgreSQL, for the write connection on SQLite), for the tests of concurrent writers. `IntegrationTestCore.refuse(event, table, rowId)` has the database refuse a write of one row (a trigger, on either engine) until the cleanup it returns runs, and `breakFileStore(repository)` makes every store of an asset of a repository fail until `restoreFileStore`, for the tests of a failure inside a stage. `TestContext.letWatchedFilesRest()` stamps every Watch folder file not read yet as first seen a minute ago, so a test's next scan reads it without waiting out the rest. `IntegrationTestCore.withSetting(name, value)(f)` saves a Setting around `f` and saves its default back, so the other suites see the seeds (`SettingsServiceTests` restores them in `afterEach` the same way). Unit tests build a snapshot with `TestSettings(overrides)` over the seeds (`TestSettings.seeds`, which `SettingsServiceTests` also asserts against the rows). `NominatimStub` is a local Nominatim-compatible endpoint (`url`, `response`, the last query and `User-Agent` seen) for the geocoder tests.

**Scene models in tests.** `TestAltitudeApp.build` gives the test instances `SwitchableSceneEmbedder`, off by default: a fixture import is measured and hashed but carries no Scene embedding, so frames pair by the hash alone, and it costs no model pass (about 0.7 s an image). A suite whose subject is the embeddings turns the models on: `override def usesSceneModels = true` for all its tests (`IntegrationTestCore.beforeAll` turns the switch on and `afterAll` turns it off; `SequenceServiceTests`), or `withSceneModels { ... }` around one test (`AssetImportServiceTests`' tests of a still image's stored Scene embeddings and of a Video's having none). The double opens the real `OnnxSceneEmbedder` when a suite first turns the switch on (`turnOn`, on the test's thread), so a model that fails to open aborts the suite or fails the test with its own error rather than an import thread's WARN, and a test JVM that never turns it on never loads the sessions (about 1.1 GB); it closes them with the instance only if it opened them. It keeps the real models' answers for the instance's life by the SHA-256 of the image's pixels, so the synthesized frames (`BurstFrames`) the suites import test after test are embedded once each; a model pass is a pure function of the pixels, so a test cannot tell. The controller server's own instance (`App.altitude`) builds the ONNX embedder, as production does; the controller tests import their fixtures through the suite's instance, never over HTTP. The unit suite's `SceneEmbedderTests` builds `OnnxSceneEmbedder` itself.

**Fixtures.** `TestContext.persistAsset` imports a random image through the whole pipeline: a file, a Preview, face detection, Image quality and a hash. `TestContext.insertAsset(asset)` persists, indexes and completes an asset without it (`library.persistAndIndex`, then `completeImport`): no file, Preview, faces, Image quality, hash or Scene embeddings, and so in no Sequence until a test stamps one (`setAssetSequence`). Bulk fixtures whose tests read none of those use `insertAsset` (`CurationServiceTests.longSequence`, `CurationActionControllerTests.frame`, `StatsServiceTests.importedAsset`); a test that reads a file, a Preview or a measurement it does not set uses `persistAsset`.
