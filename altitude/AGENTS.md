## Architecture Overview

Altitude is a Scala 3 application built with Mill: Cask serves HTTP, Twirl renders the templates, Pekko Streams runs the import and purge pipelines, ScalaSql and JDBC reach SQLite or PostgreSQL, and OpenCV and FFmpeg (through Bytedeco) decode media. The versions are in `build.mill`.

`App.scala` is the single entrypoint (extends `cask.Main`). It registers all routes and wires the app via `new Altitude()`, whose constructor migrates the database and loads the Settings before it builds the actor system (see **Settings** and **Schema migrations**); `App` then prunes, requeues and reconciles (see **Library stats and purging**).

The frontend is organized around a thin composition root in `static/js/frontend-app.js`.
Feature logic is split into focused ES module folders instead of accumulating in one large file:

`Altitude.scala` is the central dependency-injection object. It creates every DAO, service, and the Pekko `ActorSystem` inline, in a fixed startup order: the settings service (empty) → the transaction manager → the DAOs → `migrationService.migrate()` → `settings.load()` → `importParallelism` → the actor system → the services. `migrationService` and `settings` sit on `Altitude` itself, above `service`, because they run before any service exists. The `DAO` inner object and the `service` inner object both use `dataSourceType match` blocks to mix in the correct DB-specific trait:

```scala
val asset: dao.AssetDao = dataSourceType match {
  case Const.DbEngineName.POSTGRES => new dao.postgres.AssetDao(app.config)
  case Const.DbEngineName.SQLITE   => new dao.jdbc.AssetDao(app.config) with dao.sqlite.SqliteOverrides
}
```

Never instantiate services or DAOs elsewhere — always inject `app: Altitude` and use `app.service.*` / `app.DAO.*`.

## Request Lifecycle

Every request gets its authenticated user and repository injected into **thread-local** `DynamicVariable`s in `RequestContext` (account, repository). These are set by:

- `decorators.repoContext()` — clears both (request threads are pooled, so a value would otherwise outlive its request), then parses `/r/:repoId` from the URL and calls `repository.setContextFromRequest`
- `decorators.requireLogin` — validates the PASETO token (Bearer header or cookie), populates `account`, and answers a repository in the path that the user does not own (`owner_account_id`), or one that does not exist, with the same 404 (JSON for an API request), as for any foreign entity
- `decorators.requireLoginOrSignature` — the content route's: a request with both `exp` and `sig` query parameters is answered by `ContentSigner.verify` over the request path alone, with no account in the context (a plain-text 403 when the signature is invalid or expired, no redirect; a 404 for a repository that does not exist, as `requireLogin` answers it); any other request is `requireLogin`'s

All three global decorators are applied in `App.mainDecorators`: `compress → requestResponseLogger → repoContext`. Per-route authentication uses `@requireLogin` (`@requireLoginOrSignature` on the content route); an Admin-only route adds `@requireAdmin` after `@requireLogin`, which answers a User or Guest with 403 (JSON for an API request, plain text otherwise, no redirect) and throws if no account is in the context. `compress` gzips for a client that accepts it (never a 304, which has no body), and marks every response it may gzip with `Vary: Accept-Encoding`. `@cachedForever` is for a file under a content-hashed name (the stylesheet bundle's route): it adds `Cache-Control: public, max-age=31536000, immutable` to a 200 only, so a miss is never cached. `@revalidated` is for files whose names stay when their content changes (everything under `/static/`: the vendored libraries, the fonts, the JS modules): a 200 gets `Cache-Control: no-cache` and a weak `ETag` hashed from the bytes on every request, and a request whose `If-None-Match` holds it is answered 304 with no body, so a reload costs a round trip per file rather than its bytes, and a file refreshed under a running dev server is never answered as unchanged.

The DB connection is `RequestContext.conn`, a `ThreadVariable`: the thread's own value, which a thread started meanwhile does not inherit (a `DynamicVariable` is inherited). Only `TransactionManager` binds it, for as long as the outermost transaction of the thread lasts.

## DAO / Service Layer

- `BaseService` wraps every DAO call in `txManager.withTransaction{}` (writes) or `txManager.asReadOnly{}` (reads). Controllers call services; services call DAOs — never skip a layer.
- `BaseDao` (JDBC) has abstract methods (`jsonFunc`, `nativeBool`, `nativeLocalDateTime`, `nativeUtcTimestamp`, `getBooleanField`, `getDateTimeField`, `getDateField`, `getSortValueField`, `forUpdate`) filled in by `PostgresOverrides` or `SqliteOverrides` traits. `rowProcessor` is how result rows become maps: `PostgresOverrides` reads `timestamp`, `timestamptz` and `date` columns as `java.time` values so a wall-clock timestamp never round-trips through an instant in the JVM zone.
- DB-specific DAO overrides live in `dao/postgres/` and `dao/sqlite/`. The JDBC base lives in `dao/jdbc/`.
- Face vector search requires `txManager.withFaceVector{}`: the outermost `withFaceVector` of a thread sets the transaction up for it before running its block (the calls nested in it do not set it up again). Every SQLite connection loads the vector extension when it is opened, and the setup registers `face.features` with it (`vector_init`), since that needs the `face` table, which a database being created does not have when its first connections are opened. On PostgreSQL the setup is `SET LOCAL hnsw.ef_search` (the PostgreSQL-only `face.recognition.hnsw_ef_search` Setting, 100, read from the current snapshot when the outermost `withFaceVector` runs; nothing is set before the Settings are first loaded) and `SET LOCAL hnsw.iterative_scan = relaxed_order`, so a search of the vector index goes on until its limit is met by rows that pass the repository and bad-match filters.
- A DAO never manages a transaction of its own (`BaseDao` has no transaction manager): the service around it does.
- **Transaction boundaries.** A public service method that reaches a DAO opens or joins a transaction itself (`withTransaction`, or `asReadOnly` when it only reads), even when every current caller already has one: joining costs one check. An operation that must be atomic is one service method under one wrapper, never a loop of wrapped calls, which commits each call on its own (`LibraryService.restoreRecycledAssets` restores a whole batch in one transaction, skipping and reporting an asset whose content was imported again after it was recycled, so any other failure restores nothing). Pipeline flows, controllers and DAOs never open a transaction or reach a DAO. `TransactionBoundaryTests` (unit suite) parses the sources with Scalameta and enforces the syntactic part: a DAO reference in a non-`private` service method must sit inside a wrapper (a `private` helper is covered by its caller's), and nothing under `dao/`, `pipeline/` or `routes/` names the transaction manager. It cannot see the loop of wrapped calls. Mill runs tests in a sandbox, so `build.mill` hands it the source directory as `ALTITUDE_SOURCE_DIR`.

**Connections and transactions** (`transactions/TransactionManager.scala`). Every transaction borrows a connection from a HikariCP pool, opened on first use and closed at `Altitude.cleanup` (`TransactionManager.shutdown`); `connection(readOnly)` borrows one with its transaction begun, so the suites' setup code takes one as before, and a transaction started inside another on the same thread joins it through `RequestContext.conn`, which is bound for exactly as long as the outermost one runs. A write commits; a read, and any transaction that failed, ends with a rollback, and a rollback that fails is logged at WARN and never thrown, so a failed transaction fails with its own exception. Neither wrapper logs the exception it rethrows. A pool logs, with the borrower's stack trace, a connection held longer than `db.pool.leak_detection_threshold` (60 s; 0 turns it off).

- PostgreSQL has one pool, of `db.postgres.pool_size` connections; left unset, a connection per core for requests running at once plus five for the import pipeline (a transaction at most per database stage of a repository's import: the duplicate check, indexing, face recognition, completion and the discard of a dropped asset), never below 10. Every connection opens with `db.postgres.options` (`-c jit=off -c plan_cache_mode=force_custom_plan -c work_mem=64MB`, reasons in `reference.conf`). A read transaction is `REPEATABLE READ, READ ONLY`, so all of its statements see one snapshot, and begins with `SET LOCAL statement_timeout` (the PostgreSQL-only `db.postgres.read_statement_timeout` Setting, 30 s, read from the current snapshot as the transaction begins; a read before the Settings are first loaded, the migration of a fresh database, has no limit; the tests of the limit save 1 s through `withSetting`). `Db.read` turns a statement cancelled by it (SQLSTATE `57014`) into `QueryTimeoutException`, which `SearchResultsController` answers with a plain-text 503 and `MapController` with a JSON 503 (`Const.Msg.Err.SEARCH_TIMED_OUT`).
- SQLite has a read pool (`db.sqlite.read_pool_size`, 4) and a write pool of one connection over the same file, opened through `SQLiteConfig` with `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=10000`, `temp_store=MEMORY`, a 64 MiB cache and a 1 GiB mmap. When opened, each connection loads the vector extension and runs `PRAGMA optimize=0x10002`; the write connection checkpoints the WAL every 500 pages, and a read connection is `query_only`, so a write nested in a read transaction fails instead of vanishing in the closing rollback. A write transaction begins `IMMEDIATE`, taking the write lock when it starts, and the single write connection queues writers in the process instead of failing them with `SQLITE_BUSY`; a read transaction reads one WAL snapshot. `PRAGMA optimize` runs hourly on the write connection, scheduled on the actor system, and once more at cleanup.

## Import Pipeline

Pekko Streams pipeline in `service/ImportPipelineService.scala` and `pipeline/flows/`: one flow for both engines, a substream per repository. A stage's work runs in a future on the import dispatcher (`Altitude.importDispatcher`, `altitude.import-dispatcher`: a `thread-pool-executor` with a fixed pool of `Altitude.importParallelism` threads: the `import.parallelism` Setting as it was saved when the server started, a Restart setting, where 0, the default, means half the cores and never fewer than 2; added to the app's config when `Altitude` creates the actor system), never on the default dispatcher, which the stream actors, the status ticker and the SQLite optimize schedule share: a stream actor only routes, so the stages of every repository's import work at once without asynchronous boundaries, and the dispatcher's threads bound the work of all of them. Per repository, in order:

| Stage | Operator | Touches |
|---|---|---|
| `CheckMediaTypeFlow` | `map` | nothing |
| `CheckDuplicateFlow` | `mapAsync(1)` | database read |
| `AssignIdFlow` | `map` | nothing |
| `ExtractMetadataFlow` (metadata, dimensions) | `mapAsync(importParallelism)` | file |
| `IndexFlow` | `mapAsync(1)` | database write |
| `DetectFacesFlow` | `mapAsync(importParallelism)` | file |
| `RecognizeFacesFlow` | `mapAsync(1)` | database write, face files |
| `FileStoreFlow` | `mapAsync(1)` | rename |
| `AddPreviewFlow` | `mapAsync(importParallelism)` | stored file, preview file |
| `StripBinaryDataFlow` | `map` | nothing |
| `MarkAsCompleteFlow` | `mapAsync(1)` | database write |
| `DiscardDroppedFlow` | `mapAsync(1)` | database write, files |

The stages that only read and decode the file work on several assets of a repository at once; no stage that writes to the database does, and `mapAsync` hands the assets on in upload order, so faces are matched, and people started, one asset at a time in the order uploaded, and SQLite's single write connection sees one writer per stage. A repository's import holds at most five connections at once, one per database stage. The detections ride on the element from `DetectFacesFlow` to `RecognizeFacesFlow` (`AssetWithData.detectedFaces`, a `DetectedFaces`), which `StripBinaryDataFlow` leaves behind.

Each stage's writes are a short transaction of its own, opened by the service it calls (`LibraryService.persistAndIndex` for the index stage, `FaceRecognitionService.recognizeAndStore` for the faces, `completeImport` for the completion), so SQLite's one write connection runs them one after another, and a stage commits before the next one reads the asset. `Altitude.parallelism` (the core count) sizes the import and purge queues, not the concurrency. The purge queue's stages still run on the default dispatcher. Adding a new pipeline stage = add a `Flow` in `pipeline/flows/`, built with `PipelineUtils.stage`, and wire it into `ImportPipelineService.combinedFlow`.

The import and purge queues are each a `QueuedPipeline` (`pipeline/QueuedPipeline.scala`): the service's flow materialized once, for the life of the app, behind a `Source.queue` that `ImportPipelineService.addToQueue` (each staged upload, from `ImportController`) and `PurgePipelineService.enqueue` offer to. It owns the queue, the stream with its supervision strategy, the completion log and `shutdown`, and runs its callbacks on the actor system's execution context. `run` materializes a service's flow per call instead (`LibraryService.addAsset`, tests). `offer` waits while the queue is full and fails with `QueueRefusedException`, logged at WARN, when the queue does not take the element: it dropped it, it is closed, or its stream has stopped. `addToQueue` deletes the staged file of an upload the queue refused and passes the failure on, so the upload request fails; `enqueue` logs a refused asset at ERROR and goes on with the next, and the refused asset stays purge-pending for the next startup. The stream runs until `shutdown()` completes the queue, which then waits for the stream to finish what it has accepted, for at most the `pipeline.shutdown_timeout` Setting (30 s, whole seconds, read when `shutdown()` runs), and logs at WARN when the limit cuts it off. `Altitude.cleanup` shuts down the import queue, then the purge queue, before it closes the transaction manager. What a timeout cuts off is handled at the next startup: the prune discards an unfinished import, and `requeuePurgePending` queues a purge again.

A queue whose stream fails stays down: every later offer is refused. In development, `dev.restart_pipeline` restarts it instead (`Altitude.isPipelineRestartEnabled`, which both services pass to their `QueuedPipeline`): the stream is a `RestartSource.onFailuresWithBackoff` (1 s, doubling to 30 s, randomized by 0.2) over one factory, which logs each start at INFO and makes a new `Source.queue`, pre-materialized and stored as the current queue in an `AtomicReference`, that `offer` reads. The first start is made with the pipeline, so an offer always finds a queue. A restart is logged at ERROR with the failure's stack trace; a stream that completes is not restarted. What a restart loses: an offer during the backoff reads the stopped queue and is refused, and the assets in flight or buffered when the stream failed are gone (the next startup's prune discards an import `IndexFlow` had persisted, and startup empties staging). A `KillSwitches.single` follows the stream: when the current queue has stopped (the backoff), `shutdown()` ends the stream through it rather than waiting for a restart, and once shutdown has begun, a restart ends the stream instead of starting it again.

The pipeline works on **staged files**, never on byte arrays: `AssetWithData` carries the asset and the path of its file. An upload lands in `data/staging/<uuid>` (`StagingService`; `ImportController` moves Undertow's temp file there, since Undertow deletes it when the request ends, before the queued pipeline runs), a test or an `ImportAsset` stages a copy, and the checksum is streamed (`MurmurHash.hash32(path)`, the same value as over the bytes). `FileStoreFlow` renames the staged file into `files/<id[0:2]>/<id>` (`FileStoreService.assetFile(id)` exposes it), so a staged file is consumed by exactly one import; after that flow the element's path is the stored file. `AssetWithData.bytes` reads the whole file for the image-only consumers (thumbnails, face detection); an image's dimensions are read from its header alone (`AssetService.getDimensionsAndDuration`, through `ImageIO`'s readers), and so is an animated GIF's playing time (`ImageUtil.gifPlayingTimeMs`: the sum of its frame delays, a delay of 10 ms or less playing for 100 ms as in browsers), which becomes its `duration_ms`. Face detection and the preview are the only two decodes, both through `ImageUtil.decode`: OpenCV, or ImageIO for a format the bundled OpenCV has no codec for, GIF among them (an animated GIF's first frame), laid out as OpenCV would have, BGR, or BGRA for the preview of an image with alpha. The Preview (`ImageUtil.makeImageThumbnail`) is one OpenCV pipeline from the decoded image to the bytes: scaled with `INTER_AREA` to fit the 200 px box, turned upright by its EXIF orientation (`orient`: `Core.flip`, `rotate` and `transpose`), centered in the square box on a transparent border (`letterbox`, 8-bit BGRA through `toBgra`) and encoded by `encodePreview` as a lossy WebP (`image/webp`, `Const.AssetView.PREVIEW_WEBP_QUALITY` = 80; libwebp keeps the alpha plane exact, and drops it when every pixel is opaque); no PNG, ImageIO or `AffineTransform` in between. `FileSystemStoreService` writes it as `preview/<id[0:2]>/<id>.webp`. Face detection skips an animated image (`FaceRecognitionService.detect`: an image with a duration), and the grid gives it a Video's play badge and Duration row. `StripBinaryDataFlow` is where the file leaves the pipeline; an asset the pipeline drops carries its staged file on in `InvalidAsset`, for the last stage to delete. `Altitude` startup empties staging.

**Failures.** No single asset can stop the pipeline. Every stage runs its work for one asset under `PipelineUtils.guarded`, in the element's `PipelineContext` (`withContext` binds `RequestContext.repository` and `account` for the work alone): whatever the work throws drops the asset, an `InvalidAsset` with that cause, and the stream goes on. `PipelineUtils.stage(name, parallelism)` builds a `mapAsync` stage that runs its work under the guard, on the import dispatcher (`guardedAsync`), for an asset still in the pipeline and passes a dropped one on; `CheckMediaTypeFlow` (a `map` over the raw input) calls `guarded` itself and `MarkAsCompleteFlow` (over `Asset`, past the point where the file leaves the pipeline) `guardedAsync`; `AssignIdFlow` and `StripBinaryDataFlow` only reshape the element, and `DiscardDroppedFlow` works on the import dispatcher outside the guard (see below). A stage catches a cause itself only to report it as another: `RecognizeFacesFlow` turns a `DuplicateException` into `SamePersonDetectedTwiceException`. A file whose decoder cannot read it has a named cause: `ImageException` when no image reader takes an image or can read its header (`AssetService.getDimensionsAndDuration`), or neither OpenCV nor its ImageIO fallback can decode it (`ImageUtil`, for face detection and the preview: a corrupt body), `VideoException` when FFmpeg cannot open a video or no frame of it decodes (`VideoService`). Each drop is logged once. A cause `PipelineUtils.isExpectedDrop` names (`UnsupportedMediaTypeException`, `ImageException`, `VideoException`, `DuplicateException`, `SamePersonDetectedTwiceException`) is logged at INFO in one line, with the repository, by `AssetErrorLoggingSink`; any other is logged at ERROR with its stack trace by the guard, naming the stage and the file. The status ticker (`ImportStatusWsActor`) names the expected causes and a `StorageException`, and shows any other by its exception's simple class name, never by its message. A queue's stream resumes past a failure outside a stage's work (a supervision strategy that logs it at ERROR) as a last resort: such an element reaches no sink, so it is neither reported nor discarded, and no stage relies on it.

**A dropped asset leaves nothing behind.** The last stage, `DiscardDroppedFlow`, deletes a dropped asset's staged file and calls `LibraryService.discardImport`, which undoes what the import wrote, so the same file can be uploaded again at once (`AssetService.getByChecksum` sees every row, finished or not). It is a no-op for an asset never persisted (dropped before `IndexFlow`, or a duplicate the index refused) and for one that completed. In one transaction it locks the people of the asset's faces (`PersonService.lockAssetPeople`, `FOR UPDATE` on PostgreSQL), so a face another import gives one of them meanwhile keeps that person; gives back the face counts the import added (`recycleFacesForAssets`); deletes the row while `is_pipeline_processed = false`, which cascades to its faces, its Search document and its metadata parameters; and deletes each of those people left with no face row (`deletePeopleWithoutFaces`): recognition matches face rows, so only this import can have started such a person. After the commit it deletes the files: each face's (`PersonService.purgeFaceFiles`, which the purge queue shares: the cover face of a person who stays keeps its files), the stored file and the preview. A completion that fails is a drop like any other and is discarded the same way; the stats count an asset only once its import completes, so a discard changes none. A discard that fails is logged at ERROR and swallowed, so the drop is still reported with its own cause, and the next startup's prune tries again.

## Library stats and purging

`StatsService` keeps six counters per repository in `stats`: the assets and the bytes that are sorted, in triage and recycled (the nav's Triage and Trash counts; the totals are summed on read). An asset counts from the moment its import completes (`LibraryService.completeImport`) until it is marked for purging, in one bucket: recycled when `is_recycled`, else triage when `is_triaged` (an asset recycled from triage keeps that flag), else sorted. Every library operation (recycle, move, restore, purge) writes the stats through `StatsService.transition(before, after)`, the assets as it read them and as it writes them, which is one `adjust`: the non-zero deltas, applied in one transaction in dimension-name order, so concurrent operations take the stat rows in one order on PostgreSQL. A stat row is `CHECK (dim_val >= 0)`: a write below zero, or to a dimension the repository has no row for, is a `ConstraintException` naming the dimension, and fails the operation's transaction.

The operations read the rows they change through one locking select in `AssetDao` (`getAssetsToRecycle`, `getAssetsToMove`, `getAssetsToRestore`, `getAssetsToPurge`): the context repository's completed assets that are not marked for purging, `FOR UPDATE` on PostgreSQL (SQLite's one write connection serialises the writers). They count their stat changes from those rows and update exactly them, so an asset of another repository, an unfinished import and two requests for one asset are counted correctly. Restoring an ID that is no asset of the repository is a `NotFoundException`; a live asset, or one marked for purging, is ignored.

A purge has two halves. The request marks the assets `is_purged` and takes them out of the recycled stats (`LibraryService.markForPurging`); from then on an asset is **purge-pending**, out of every library operation, and hidden from the trash view (`SearchRequestParser`). Once that commits, `PurgePipelineService.enqueue` feeds them to the purge queue one offer at a time, under its backpressure, and the queue deletes each one's face files (every face's but the cover face of its person, whoever the person is, through `PersonService.purgeFaceFiles`), files and row. A row whose delete fails is logged at ERROR and stays purge-pending (`DeletePurgedFromDBFlow`), so the queue goes on.

At startup `App` runs, once `Altitude` has migrated the database and loaded the Settings: `pruneDanglingAssets()` (each import a crash or a shutdown cut off, logged at WARN and undone by `discardImport`, files and face counts included), `requeuePurgePending()` (every purge-pending row queued again, with the repository's owner as the pipeline's account) and `reconcileStats()`, each through `forEachRepository`, which runs the operation in every repository's context and opens no transaction around it, so an operation's file deletes come after its own commit. `StatDao.reconcile` locks the repository's stat rows in write order, counts the assets that count with one aggregate bucketed as above, and sets the stats that differ; `StatsService.reconcile` logs each at WARN with its old and new value.

## Video

A Video is an asset whose `media_type` is `video` (there is no flag column); `LibraryService.SUPPORTED_MEDIA_TYPES` admits `image` and `video`, so an audio file stays unsupported. Decoding goes through FFmpeg by way of javacv: `build.mill` declares each bytedeco preset as its stub jar plus a `classifier=<platform>` jar with the natives of the detected platform (appending the platform to the version resolves nothing), and `VideoService` wraps `FFmpegFrameGrabber`, one grabber per call, nothing shared across threads. It takes a Settings supplier (`() => Settings`), not a `Config`, and reads the `video.*` Settings from one snapshot per call.

- `probe(path)` gives `VideoInfo`: the display size (the container's display matrix applied, so a phone's portrait recording is stored portrait, `width`/`height` on the asset), the duration (`asset.duration_ms`, NULL for a still image; an animated GIF's is its playing time), frame rate and audio presence. `AssetService.getDimensionsAndDuration` dispatches on media type.
- **Sampled frames**: `VideoService.sampleTimes(durationMs)` spaces Frame times evenly from the start at `max(video.faces.sample_interval_ms, duration / video.faces.max_sampled_frames)` (both Settings; defaults 1000 ms and 120), so a short clip is sampled every second and a two-hour recording about every minute. `sampledFrames(path, times)(consume)` decodes each as an upright BGR `org.opencv.core.Mat` for an iterator that lives as long as the call; the consumer releases each image. Frames are turned the way FFmpeg's own autorotate turns them: the container's counter-clockwise display rotation, negated, snapped to a quarter turn (`VideoService.uprightRotation`).
- **Preview**: `previewFrame(path)` is the first Sampled frame whose mean brightness clears the `video.preview.min_luminance` Setting (40 of 255, skipping a black leader), else the frame at a tenth of the duration, and a `VideoException` when no frame decodes; `AssetService.genPreviewData` hands the frame, a `Mat` upright already, to `makeImageThumbnail`'s `Mat` overload with orientation 1, so the 200 px WebP Preview, the map and the grid are the same as an image's.
- **Faces**: `FaceDetectionService.extractFaces` has a `Mat` overload (the byte-array one decodes and delegates). `FaceRecognitionService.detect` and `recognizeAndStore` dispatch on media type; for a Video, `detect` finds faces in every Sampled frame (each Face pinned to its Frame time, `face.frame_time_ms`, NULL for a Face in an image) and clusters the detections of the whole video by embedding: `FaceRecognitionService.cluster` is greedy leader clustering in descending Face quality (a detection joins the first cluster whose best member is within `face.recognition.cosine_distance_threshold`, else starts one), and `mergeClusters` then absorbs a cluster whose centroid is within the threshold of an earlier cluster's centroid, since a turning head drifts past a single leader. Each cluster is one Face: the crop, box, checksum, Frame time and quality of its best-quality detection, but the L2-normalized mean of all its members' embeddings as the vector, so the stored vector is steadier than any one frame and no longer derives from the saved crop. A cluster seen in fewer than `video.faces.min_cluster_frames` distinct frames (default 2) is match-only in that Video (see **Faces** below), so a passer-by in one frame cannot start a Person. One Face per Person per Video: when two clusters resolve to the same Person the lower-quality one is dropped, so a pose change does not fail the import. The debug artifacts of a frame are named by its Frame time (`<ms>ms-<file>-annotated.jpg`). Both pipelines get this through the service.
- **Dates and places**: metadata-extractor reads MP4 and QuickTime containers into `extracted_metadata`, so the resolvers still read persisted inputs only. `CaptureDateResolver` has two rungs below EXIF, XMP, IPTC and the PNG text chunk: `QuickTime Metadata` / `Creation Date` (`com.apple.quicktime.creationdate`, a local wall clock whose offset is discarded like every other; `qt_creation_date`), then, with the PNG tIME rung and above GPS and the filename, the container's `Creation Time` (`MP4 Video`, `QuickTime Video`, `MP4`, `QuickTime`; `container_creation_time`). The extractor describes that UTC instant in the JVM's zone, with a numeric offset on the track directories and a zone name on the container ones; `WallClockParser.parseUtcInstant` turns either back into the UTC wall clock, so the stored value does not depend on the server's zone, and the 1904 epoch remains a sentinel. `GeoLocationResolver` tries EXIF `GPS`, then `QuickTime Metadata` / `ISO 6709` (`+37.3318-122.0312+015.000/`, also its degrees-minutes forms), then `MP4` / `Latitude` and `Longitude`. `Asset.getPublicMetadata` takes `deviceModel` from `QuickTime Metadata` / `Model` when EXIF has none.
- **Serving**: `ContentViewController` streams `file` content from the stored file through `RangeStreaming`, a `geny.Writable` window over a `FileChannel`: `Accept-Ranges: bytes`, a `206` with `Content-Range` for a single `bytes=a-b` range (`bytes=a-` and `bytes=-n` included), `416` past the end, `200` with `Content-Length` otherwise, and `Content-Type` is the asset's stored `mime_type` for images too. A player drops the connection whenever it has what it wants (a Video's metadata, the asset the user stepped away from), so a write the client refuses ends the response and is logged at DEBUG, while a failure to read the file is still an error. A `preview` is `image/webp` (`MimedPreviewData.MIME_TYPE`). The route has two gates (`requireLoginOrSignature`): a request with `exp` and `sig` is answered by the signature alone, whoever owns the repository (a plain-text `403` when it is invalid or expired, one body for both, and a `404` for a repository that does not exist), and any other request, including one with only one of the two, by `requireLogin` (a redirect to login without a session, a `404` for a foreign repository). One route serves both, so the logged-in UI builds plain URLs and a share link is a signed URL to the same content, through the same code. The endpoint declares `exp` and `sig` only because cask answers a query parameter an endpoint does not declare with a `400`. Every response that serves content, an original's `206` and `416` included, carries `Cache-Control: private, max-age=31536000, immutable` (`withContentHeaders`): the bytes under a content URL never change, since a preview is written once per asset, a face image once per face, and an original is unique by checksum. It also carries `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, since an original is a user's upload served on the app's origin with its cookie, and must never render as a document that acts as the user. An original's `200` and `206` carry `Content-Disposition: inline` with its file name (`RangeStreaming.contentDisposition`, RFC 6266): `filename` as printable ASCII with every other character, `"` and `\` replaced by `_`, and `filename*` as RFC 5987 percent-encoded UTF-8, so a saved original keeps its name and no file name puts a control character in the header. An `itemId` that is not a UUID is a plain-text `400` (`Const.Msg.Err.VALUE_NOT_A_UUID`; the file store builds paths from the ID), and a `NotFoundException` (an unknown asset, a missing preview, face or original) or an unknown `dataType` a plain-text `404`; neither error is cached. `decorators.compress` is cask's gzip decorator except for a response that offers byte ranges, which is left uncompressed (a range names raw bytes), and for one whose `Content-Type` starts with `image/` (deflated already, so gzip would cost CPU and drop `Content-Length`).
- **Signed URLs**: `ContentSigner` (`app.service.contentSigner`) signs a content path for one item of one repository: `sign(path, expiresAt)` appends `exp` (Unix seconds) and `sig` (Base64URL without padding of `HMAC-SHA256(key, "<path>\n<exp>")`), and `verify(path, exp, sig, now)` is true only before `exp` and for exactly that `sig` text: the expected signature is encoded and compared with `MessageDigest.isEqual` (constant time), not `sig` decoded, so a padded spelling or one varied in the unused bits of its last character is refused; a malformed `exp` or `sig` is false. The key is `system.signing_key`, the Base64 of 32 random bytes, created once on first start by `SystemService.loadOrCreateSigningKey` and read back on every later one, so a signed URL survives a restart; the key is stored only while the column is NULL and then read back, so two instances starting at once end up with one key. The PASETO session key stays per process. The route logs an expired signature at DEBUG and one that does not match at WARN, never the `sig`, and with the path as requested (`getRequestURI`, still percent-encoded), since a decoded `%0D%0A` in the path would forge a log line. `ContentSignerTests` covers the signature, pinned to a known answer computed with `openssl` so an issued link survives any refactor, `SystemServiceTests` and `StartupTests` the stored key, `ContentViewControllerTests` the route's two gates.
- **Playback**: asset detail plays a Video in a media-chrome player, started as it is shown; see **Detail navigation** in `views/AGENTS.md`.
- **Tests**: `TestVideos` synthesizes short MP4s (`FFmpegFrameRecorder`, `mpeg4`) from the `people/` images at test time, with a display rotation or container metadata on request, so no binaries live in git; `VideoServiceTests` covers decoding, `AssetImportServiceTests` the import, `FaceRecognitionServiceTests` the faces, `ContentViewControllerTests` the ranges, the login and signature gates, the 400 and 404 answers and the content headers, `RangeStreamingTests` a client that goes away mid-stream, a missing file and the `Content-Disposition` encoding.

## Faces

The full walk-through, from detection to the People tab, is [docs/faces.md](../docs/faces.md).

A Face is a YuNet detection (`FaceDetectionService.detectFacesWithYunet`: score at least the `face.yunet.confidence_threshold` Setting, set with the NMS threshold on the thread's detector before each detection, box at least `face.detection.min_face_size`) with a 5-point-aligned 112 px crop and its ArcFace w600k_r50 embedding (`getArcFaceEmbedding`, an `Embedding` of the L2-normalized 512-d vector and the norm the raw output had). That norm is the Face's **quality** (`face.quality`): for a net trained with the ArcFace loss it tracks how recognizable the face was, dropping with blur and occlusion, and it costs nothing extra. On the test portraits sharp faces measure 18.8 to 22.4, the same faces blurred at 5% of their width 15 to 19.6, eyes covered 16 to 19.5; the numbers are in the help text of the `face.quality.*` Settings (`models/Settings.scala`), and `face.debug.enabled`, the one face key left in `reference.conf`, labels every crop with its quality for calibrating on one's own files.

Quality decides a Face's **tier**, stored as `face.is_enrolled` at import so a later change of the thresholds does not silently re-tier history:

- **Enrolled** (quality at least the `face.quality.enroll_threshold` Setting, default 18.0): may start a new Person and is a candidate in the vector search.
- **Match-only** (at least `face.quality.keep_threshold`, default 15, or a video cluster with too little support): may join an existing Person but never starts one and is never a candidate. A match-only Face that matches nobody is dropped, not stored (`FaceRecognitionService.recognizeFace` returns `None`). Changing either threshold never re-tiers Faces already stored.
- Below `keep_threshold` the detection is dropped by `extractFaces`, after the debug dump.

Recognition (`recognizeFace`) is a vote over the top `face.recognition.match_count` nearest candidates within `face.recognition.cosine_distance_threshold`, most votes winning and a tie going to the closest; the service reads both Settings from one snapshot per face and passes them to `FaceDao.searchClosestFaceMatches(features, matchCount, distanceThreshold)` (hand-written per engine; no DAO holds a Setting), which sees only enrolled Faces of people who are not a bad match, in the context repository; hidden people stay matchable, since hiding is a display preference. On PostgreSQL (`postgres.FaceDao.CLOSEST_MATCHES_SQL`) the candidates come from `face_03`, a partial HNSW index over the enrolled Faces' vectors at half precision (`features::halfvec(512)`, `WHERE is_enrolled`; the column is `vector(512)`): four times `match_count` of them, ordered by the same cast, and the statement then takes their exact `<=>` distances at full precision, applies the threshold and keeps the nearest. The search is approximate; over a handful of Faces it is exhaustive. On SQLite `vector_full_scan` is an exact scan of the `face` table, every repository's rows, filtered afterwards: sqlite-vector's quantized scan reads only the rows present when the table was last quantized, so it would miss a Face saved a moment ago. `face_01` makes a crop's checksum unique within its asset, not the repository, because two assets can share a byte-identical frame (a trimmed copy of a video, a re-exported photo); the same crop twice in one asset surfaces as `DuplicateException`, which `RecognizeFacesFlow` reports as `SamePersonDetectedTwiceException`. A person seen twice in one image (`twins.png`) is two Faces of one Person.

## Models

All models extend `BaseModel` and are case classes with a upickle `JsonCodec` read/writer plus a `ujson.Value` conversion in their companion:

```scala
object Folder:
  given JsonCodec.ReadWriter[Folder] = JsonCodec.macroRW
  given Conversion[ujson.Value, Folder] = json => JsonCodec.read[Folder](json)
```

`JsonCodec` emits snake_case field names. DAOs build typed models from result rows in `makeModel`, so services and DAOs exchange models, not JSON. JSON APIs that need a different shape (camelCase, derived fields such as the folder tree's `isRoot`) build their `ujson.Obj` by hand in the controller.

`FolderService.getTree` assembles the folder tree in memory from one folder query and one per-folder asset count query (`SearchDao.countByFolder`: the default view's matches grouped by folder, `SearchQueries.folderCounts`, which the capture-day index answers alone), filling `children`, `numOfChildren`, and the recursive `numOfAssets` on every node; `FolderController` only serializes it.

`BaseDao.updateById` / `updateByQuery` take an untyped `Map[String, Any]`; `Columns.literal` binds the scalar types the old hand-built SQL accepted and, only for a `SET`, an `Option` (`None` renders `NULL`, `Some(v)` binds `v`). A `None` in a `Query` predicate would render `= NULL` and never match, so that path does not use it. `deleteByQuery` builds its predicate through the same `DynamicFilter`. A hand-written JDBC statement tests a column against a set of IDs with `column $inIdSet` and one bind, `idSet(ids)` (the dialect overrides: `= ANY(?)` with a `varchar[]`, or `IN (SELECT value FROM json_each(?))`), so a selection of any size is one parameter, as `Columns.isInSet` is for a typed statement.

## Albums

An `Album` is a flat, repository-scoped, uniquely named (case-insensitive) list of pointers to assets: the `album` table plus the `album_asset` membership table, which has no model of its own and is written only through `AlbumDao`. An asset can be in any number of albums. Nothing album-related touches an asset: adding to, removing from, renaming, or deleting an album (a hard delete; memberships cascade) changes membership rows only. The reverse direction is `LibraryService.recycleAssets`, which drops recycled assets from every album in the same transaction (so folder deletion does too); restoring does not re-add them, and purging deletes the asset row, whose foreign key cascades. `Album.numOfAssets` is computed on read (`AlbumDao.getAll`). Searching within an album is the `albumIds` filter of `SearchQuery` (`asset.id IN (SELECT asset_id FROM album_asset ...)`), reached through the `albumId` search parameter.

## Search results and date grouping

Two search paths share one definition of "what matches": `LibraryService.search` (full `Asset` records for the ungrouped HTML grid) and `LibraryService.searchGrouped` (a grouped page for the grouped HTML grid). Both resolve the scope the same way (`withResolvedScope`: the root folder means no folder filter, any other folder means itself plus its current descendants, and Search text is resolved against the repository's names, see **Text search**) and then use the engine's `SearchDao`, which builds every predicate once, for both, in `SearchQueries.matching` (`core/dao/sql/search/`): a typed ScalaSql relation carrying repository scoping, view flags, pipeline completion, column filters, and text, folder, person, album, Location, bounding-box and user-metadata filters. Everything joined in is a semi-join on `asset.id` - the metadata one counts an asset's matching values with its own `GROUP BY`/`HAVING` - so a search reads `FROM asset` alone, with no duplicate rows and nothing to deduplicate on the outside. Every statement over the relation is a hand-written shell built through `SearchQueries.statement`, which puts the Search text's CTEs at its head (see **Text search**), so no shell can leave them out. Two counts read the same relation, scoped like `search`: `LibraryService.count`, exact, which `PersonService.merge` recounts a person's assets by, and `LibraryService.cappedCount`, the map layout's total.

**Pages and totals.** A flat page (`SearchQueries.flat`) decides its rows over narrow ones and then reads only those in full, in the shell of a grouped page without its group counts: a materialized `candidates (id, day, sort_value, second_sort_value)` slice over `matching`, ordered by the sort, then (under the Relevance sort) the newest capture time, then the ID, `LIMIT rpp + 1`; the `page`; and the page joined back to `asset`. A page past the first is continued by cursor, never by page number or `OFFSET`: the slice starts after the cursor's anchor (`afterBySort` with `seeks`, which adds an inclusive bound on the sort value so that an index on it seeks to the anchor), so a page costs the same however far in it is. Where the sort puts the rows without a value last (SQLite's legacy NULL import times, descending), a continuation reads them in a second, guarded slice (`candidatesCte`), since a range never reaches NULL. Sorted by capture time, the candidates are `dayCandidates`, the day-ordered slices a page grouped by day reads, the days in the sort's direction: the capture day followed by the capture time is the order of the capture time alone, and the order of `asset_search_date_taken`, which neither engine reads in order for the time alone; the cursor then carries the last asset's day as its key. Under the Relevance sort the candidates read `scored`, as a grouped page does. `asset_search_created` serves the default Date Imported sort and carries the ID, so the slice reads the index alone. The DAO returns `SearchRow`s (the `Asset`, its day under the capture-time sort, its `SortValue` as stored, its `secondSortValue`) in a `SearchPage` (rows, `total` on a first page, `hasMore`); `SearchService.search` builds `SearchResult.nextCursor` from the last row (`cursorAt`, shared with the grouped search), and `LibraryService.search` checks a cursor against the search's fingerprint as `searchGrouped` does (`continued`). The cursor decides `data-app-search-after`; a flat page needs `rpp` of at least 1 (`IllegalArgumentException` otherwise), so no search reads an unbounded set of full rows. A first page also carries a **capped count**, `SELECT count(*) FROM (<matching ids> LIMIT cap + 1)`, the cap being `SearchQuery.totalCap` (`Const.Search.TOTAL_CAP`, 10,000; tuning carried on the query for tests, not part of the cursor fingerprint): a result one past the cap means more than it. `SearchResult.total` and `GroupedSearchResult.total` are present on a first page only; the flat and grouped first pages and the map layout (`cappedCount`) report the capped count, and `includes/search_results` renders `data-results-total` (at most the cap) and `data-results-total-capped`. The Location filter (`SearchQuery.locationIds`) is the album filter's shape over `location_asset`. The bounding-box filter (`SearchQuery.bbox`, a `util/BoundingBox` of south, west, north, east; `west > east` crosses the antimeridian and becomes two open-ended longitude ranges) matches an asset by its own point or, when it has none, by the pin of any Location it is in - the rule the map plots by - as plain `BETWEEN` arithmetic, no dialect hook. It is one semi-join over the union of two ID sets (`SearchQueries.bboxFilter`): the view's assets with a point in the box, which repeats the repository and the view's flags so that `asset_geo` bounds it, and the members without a point of the Locations pinned in the box. The two rules as alternatives on the asset's own row would leave every matching asset to be tested.

`SearchQuery.grouping` (`SearchGrouping(GroupBy.DateTaken, direction)` or `SearchGrouping(GroupBy.Location)`) turns a query into a grouped one. `GroupBy` carries the date column behind a date grouping (`dateField`, `None` for Location); `SearchDao.searchGrouped` dispatches on it to one of two statements that share one shell. `SearchQueries.grouped` emits **one statement** per page: a materialized, narrow `candidates` slice (`dayCandidates`: ID, day, sort key and `second_sort_value`, the capture time under the Relevance sort and NULL under a column sort; `LIMIT rpp + 1` to detect continuation), the `page`, `day_counts` as one correlated count per distinct day on the page, the page joined back to `asset` for its full rows and, on a first page only, `total`, the capped count. Under the Relevance sort the statement first materializes `scored (id, day, sort_value, second_sort_value)` (`ScoredRow`) over the matches, with the Relevance computed once as `sort_value`; the candidate slices, the cursor comparison and the order read its columns, and the Location statement joins its Locations to it. Everything is ordered by day, then the sort, then `asset.id` (`SearchQueries.orderWithinGroup` over a `Position`, the row's ID, day, sort value and capture time as the sliced relation has them, the asset or `scored`; under the Relevance sort the newest capture time comes before the ID). It is a hybrid: every branch is the same typed `matching` relation rendered into a hand-written `WITH` shell, because `MATERIALIZED`, the guarded `LIMIT CASE` on the trailing null slice and SQLite's planner hint cannot be expressed as a typed query - but each fragment carries its own bind values, so no branch can drift from the counts beside it. The engine-specific `SearchDialect`s (`Postgres`/`Sqlite`) supply the day expression (`date(col)` on SQLite, `col::date` on PostgreSQL), the full-text predicate over a Search document (`textMatch`), null placement, the `SortValue` type mapper, and on SQLite a unary `+` on the secondary sort term so the planner keeps the grouping day index. The DAO returns `GroupedSearchRow`s (the `Asset`, its group as a `SearchGroupKey`, its `SortValue` exactly as stored, its `secondSortValue`, its group's count) in a `GroupedSearchPage` (rows, `total` on a first page, `hasMore`); `SearchService.searchGrouped` folds consecutive rows of one group into `AssetGroup`s and builds the next cursor. `GroupedSearchResult` also carries `continuesGroup`, whether the first group is the one the previous page ended in when this page was reached by cursor.

**Group by Location** (`SearchQueries.groupedByLocation`) is the same shell over two relations instead of one, because its shape differs from the day statement on every axis: `located` is `matching` joined to `location_asset`, `location` and a left-joined category - **one row per asset × Location**, so an asset in two Locations appears under both and the group counts may sum to more than the total, which still counts assets - and `unlocated` is `matching` less every asset in a Location, which is always the trailing "No location" group. A page Location's count reads that Location's own members (`location_asset` joined to `asset` under the `matching` predicates), so it costs the size of the page's Locations and not of the library; the "No location" count runs only on the pages that reach that group. Groups are in **path order**, the order the sidebar lists them in: the key is the category's lower-cased name and the Location's own joined by U+0001 (`SearchQueries.PATH_SEPARATOR`, below every printable character, so the composite orders as the pair would and cannot collide with a top-level name), or the Location's name alone at the top level; then the Location's ID as a deterministic tiebreaker, the sort within the group, the asset ID. The direction is fixed: `SearchResultsController` refuses `groupDirection` with `groupBy=location`. A cursor whose anchor was in a Location slices `located` after it and lets `unlocated` fill the page only once `located` has run out (the day statement's guarded `LIMIT CASE`, on `located`); a cursor without a group key slices `unlocated` alone. The `SearchGroupKey` enum is `Day(date)` or `Location(id, pathKey, name, categoryName)`, all `None` for the trailing group; the grouped grid heads a Location group `Category › Location`.

**Text search** (`q`, the Search text; the terms are defined in the root `CONTEXT.md`). `util/SearchWords.of` is the one word-splitting rule, applied to the stored body of a Search document, to every name read at query time and to the typed text: decompose (NFD) and drop the combining marks, split on anything that is not a letter or a digit, on lower-to-upper camelCase humps and on letter/digit boundaries, then lower-case (`IMG_1234-beachSunset.final.jpg` is `img 1234 beach sunset final jpg`). The hump is the only boundary that depends on case, so each of the three uses reads a text through `SearchWords.variants`: its words, then, only when the text has a hump, the same rule without it (`McDonald_beachSunset.jpg` is `mc donald beach sunset jpg` or `mcdonald beachsunset jpg`), and nothing for text without a word. A word written with a hump and the same word written in one case therefore find each other: `mcdonald` finds `McDonald`, and `McDonald` finds `Mcdonald` and `MCDONALD`. `util/SearchText.parse` turns the typed text into an `Option[SearchExpression]` and never fails: space-separated terms are AND-ed into `SearchGroup`s, an upper-case `OR` between two terms makes them alternatives of one group (it binds tighter than AND), a leading `-` excludes that one term, and a `"quoted phrase"` is one term of whole words. A `SearchTerm` carries the variants of what was typed and matches when any of them does. A bare term's last word matches the start of a word; a bare term that splits into several words (`IMG_12`) is those words in sequence, the last one a prefix. An unbalanced quote closes at the end of the text, a term without a word and a dangling `OR` are dropped, terms past `SearchText.MAX_TERMS` (16) are dropped and logged at DEBUG, and text with no term left is `None`, which is no text everywhere: no filter, no Relevance, not refused in the trash.

A term can match in six **Search sources** (`util/ResolvedSearchText.scala`, `SearchSource`), each with the Relevance a match there is worth:

| Source | Matches assets | Relevance |
|---|---|---|
| Person: named, not hidden, not merged away (`is_deleted`), not a bad match | with a Face of that Person | 5 |
| Location | in that Location | 4 |
| Category | in any Location of that Category | 3 |
| Folder, not recycled, not the root | in that folder or any folder below it | 2 |
| Album | in that album | 2 |
| Search document: file name and user metadata values | whose document has the term | 1 |

Only the last is stored. The **Search document** is one `search_document` row per asset whose `body` is the words of the file name followed by those of every user metadata value, each in every one of its `SearchWords.variants` in turn (`McDonald_beachSunset.jpg` is `mc donald beach sunset jpg mcdonald beachsunset jpg`; a value without a hump contributes its words once), joined by spaces, so the engines index words the application already split. `SearchDao.writeDocument` (JDBC DAO, one `INSERT ... ON CONFLICT DO UPDATE` for both engines) writes it once from `indexAsset` and `reindexAsset`, after the metadata parameters, and from `addMetadataValue`, always inside the service transaction that changes the asset: the import pipeline's index flows, the metadata edits of `UserMetadataService` (which reads the asset after storing the value, so the document has it), and `AssetService.rename`, which reindexes. Every field type's values are in the document. Which of them also get `metadata_parameter` rows, the only thing the metadata filters read, is the JDBC DAO's rule, applied by its `addParameters` on import, reindex and value additions alike: `FACETED_FIELD_TYPES` (`KEYWORD`, `NUMBER`, `BOOL`) are the types whose value column the insert writes, so a `TEXT` or `DATETIME` value is found by its words and never by a metadata filter. Recycling and restoring do not touch it (the view's `is_recycled` filter keeps a recycled asset out); purging deletes it through the `asset_id` cascade on both engines. Schema, in both `all.sql` files: PostgreSQL has `search_document (repository_id, asset_id, body, tsv)` with `tsv` `GENERATED ALWAYS AS (to_tsvector('simple', body)) STORED` under a GIN index (no stemming, no stop words); SQLite has an ordinary `search_document (id INTEGER PRIMARY KEY, repository_id, asset_id, body)` table plus `search_document_fts`, an FTS5 external-content table over `body` (`content_rowid='id'`, a declared key `VACUUM` cannot renumber; `tokenize='unicode61 remove_diacritics 0'`, `prefix='2 3 4'`) kept in step by insert, delete and update triggers. Both have the unique index `search_document_01` on `(asset_id, repository_id)`, which serves the purge cascade and the selective path's probes; the upsert's `ON CONFLICT (repository_id, asset_id)` still finds it, since a conflict target names a set of columns, and it rewrites only a changed body (`WHERE search_document.body <> excluded.body`), which on SQLite also spares the FTS entry. `SearchDocumentRow` maps the three shared columns; `tsv`, SQLite's `id` and the FTS table appear only as raw fragments in the dialects.

Names of people, Locations, Categories, folders and albums are never copied into a document, so a rename, merge, hide, move, delete or membership change shows in the next search with nothing to reindex. `SearchService.resolveText(expression, probeLimit)` reads the candidates of every name source in one read-only transaction (`SearchDao.searchNames`), matches each term against the variants of each name in memory (`SearchTerm.isIn`: any variant of the term within one variant of the name, the rule a document is matched by, confined to one reading of one name), probes the result (see the paths below) and returns a `ResolvedSearchText`: per term, the matching IDs of each source that had any, and the probe's verdict. A Category's hits become the IDs of its Locations and a folder's hits are expanded to every folder below them, so each source is a plain ID filter. The names are read fresh on every request; their words are not recomputed, since `SearchWords.variants` remembers the readings of up to 50,000 texts in a bounded LRU map, a text's readings being a pure function of it. `SearchQuery` keeps `text` as typed and carries the resolution beside it (`resolvedText`, `withResolvedText`); `LibraryService.withResolvedScope` resolves it next to the folder scope for `search`, `searchGrouped`, `count`, `cappedCount`, `mapCells` and `mapBounds`, afresh on every request and every page, and `SearchQueries.matching` refuses text that was not resolved (`requireResolvedText`) rather than searching the documents alone.

A term's **sources** (`SearchQueries.TextSource`, in declaration order: the name sources it resolved to any IDs in, then always its document) are relations of asset IDs: `face.asset_id` by person, `location_asset.asset_id` by Location (a Category as its Locations), `album_asset.asset_id` by album, and `search_document.asset_id` through the dialect's `textMatch`; a folder is the asset's own `folder_id`. `textFilter` ORs a term's sources (negating them for an excluded alternative), ORs the alternatives of a group and ANDs the groups. A text is matched in one of two ways, decided per request by a **probe** that `SearchService.resolveText` runs in the same read transaction after resolving names:

- `SearchDao.probeText` (`SearchQueries.textProbe`) is one statement with a branch per positive group (none of whose alternatives is excluded): the `UNION ALL` of the group's sources, limited to `limit + 1` rows; the document source is scoped to the repository by its own `repository_id`, and the name sources need no scope, since their IDs were resolved from the repository's names, so each reads the index that leads with its ID and carries the asset (`face_02`, `location_asset_01`, `album_asset_01`) and nothing else, the limit being `SearchQuery.textProbeLimit` (`Const.Search.TEXT_PROBE_LIMIT`, 5,000; tuning carried on the query for tests, not part of the cursor fingerprint). A group with at most `limit` rows is complete (`ResolvedSearchGroup.isComplete`), and `ResolvedSearchText.candidates` is the intersection of the complete groups' hits: `None` (no complete group, or no positive group, which is not probed) means broad, and an empty set answers the search with nothing, without reading the library (`SearchDao.matchesNothing`).
- **Selective path** (candidates present): `matching` filters `asset.id` by the candidate set (one bind); the complete groups need nothing more, and every other group, excluded term and source tested for the Relevance is a correlated probe on the asset's own row (`EXISTS` on `face`, `location_asset`, `album_asset` or `search_document` by `asset_id`, each through an index that leads with it; the folder by its column).
- **Broad path** (no candidates): each source relation of each term is a `MATERIALIZED` CTE at the head of the statement (`text_<group>_<alternative>_<source>`), and every predicate and the Relevance test membership in them, so a source is built once per statement whatever the shell renders `matching` into. A group of one excluded term is an anti-join on each source (`SearchDialect.excludes`: `NOT EXISTS` on PostgreSQL, a hash anti-join; `NOT IN` over the CTE on SQLite, which indexes the set once); an `OR` group with an excluded alternative negates its memberships.

The person filter reads `face.person_id` alone, and the document source has no repository predicate of its own outside the probe (the asset is scoped). An ID set is one bind parameter whatever its size (`Columns.isInSet`: `= ANY(?)` with a `varchar[]` on PostgreSQL, `IN (SELECT value FROM json_each(?))` on SQLite), which the `personIds`, `albumIds`, `locationIds` and folder-scope filters use too. `textMatch` is a positive match of one term, with the query string built from `SearchWords` output only: PostgreSQL binds `beach:*`, `img <-> 12:*` or, for a phrase, `golden <-> gate` into `tsv @@ to_tsquery('simple', ?)`; SQLite binds `"beach" *`, `"img 12" *` or `"golden gate"` into `id IN (SELECT rowid FROM search_document_fts WHERE search_document_fts MATCH ?)`. A term with two variants is still one bind, the OR of its readings: `mc <-> donald:* | mcdonald:*` (`<->` binds tighter than `|`) on PostgreSQL, `"mc donald" * OR "mcdonald" *` on SQLite. The body is one string, so in the document a phrase or a several-word term can match across the boundary between the file name and a metadata value, between two values, or between the two readings of one value.

**Relevance** (`sort=relevance`, `SearchSort.Relevance`) is the one sort that is not an asset column. `SearchQueries.relevance` renders it from the same `termMatches` pairs, only when it is the sort: the sum, over the groups of the text, of a `CASE` whose branches are the group's non-excluded alternatives' sources, highest score first, so a term counts as the best source it matched and alternatives joined by `OR` count once, as the best of them. Excluded terms score nothing, and text made of exclusions alone gives every match 0. The order, flat or within a group, is Relevance descending, capture time `DESC NULLS LAST`, then ID. The value is computed once per row: in a flat page's select list, and in a grouped statement's `scored` CTE, whose columns the cursor comparison (`afterBySort`, `afterByCaptureTime`) and the order read. `SearchQuery` throws for the Relevance sort without usable text, and `SearchResultsController` answers that request with a 400 before building one. The map layout has no sort and plots the text's matches like any other filter.

Paging is by cursor only: `SearchCursor` (version 5) is an opaque, versioned Base64URL token holding the last returned image's group (`key`, the ISO day or the Location path key, plus `groupId`, the Location's ID; both absent in the trailing group), sort value and ID, and a fingerprint of the search as requested (engine, repository, filters including `locationIds` and `bbox`, grouping, ordering; a folder filter as given, not its expanded descendants, and the Search text as typed, not the names it resolved to). Under the Relevance sort the position is a triple, so the token also holds the second sort value (`s2`, the capture time, which may be null); under a column sort `s2` is null and never read, and a Relevance cursor without it is a `SearchCursorException`. `LibraryService.searchGrouped` recomputes the fingerprint and rejects a mismatch with `SearchCursorException`; a cursor supplies a position only, never access or SQL, and the page size is not part of it. Results are live: a cursor continues from values, so deleting its anchor or inserting before it neither skips nor repeats the remaining images, while the counts describe the current matching set.

`routes/SearchRequestParser` is the shared parameter-to-scope parser for the HTML search and the map cells/bounds endpoints: `view`, `q`, folder/person/album/Location IDs, `bbox` and `triaged`. It returns a scope that each controller turns into a `SearchQuery` with its own sort, grouping and paging. The view sets the scope's flags: `view=triage` is the triaged assets that are not recycled (an asset recycled from triage keeps `is_triaged`), `view=trashbin` the recycled assets not yet marked for purging, and any other view the assets that are not recycled. `triaged` (a boolean) overlays the view's rule on `is_triaged`: `triaged=false` hides the triaged assets of the repository view, which holds them with the sorted ones, and in the trash it tells the assets recycled from triage from the rest; `view=triage&triaged=false` is refused (`The triage view holds only triaged assets`, a plain-text 400 in HTML search, a JSON 400 from the map endpoints). The flag is a column filter in `SearchQuery.params`, so it is part of the cursor's fingerprint like the view's own flags. The scope has Search text only when `q` has a usable term (`SearchText.parse`); `q` that parses to nothing is no text, for the filter and for the default sort alike. Text with `view=trashbin` is refused (`Search text does not search the trash`): a plain-text 400 in HTML search, a JSON 400 from the map endpoints. `bbox` is the grid's and the crowded-pin panel's filter only: the map endpoints and the map layout never read it, and a malformed one is a plain-text 400 in HTML search.

`layout` is separate from `view`: `grid` (default) or `map`. With `layout=map`, grouping, paging and the `bbox` filter are ignored (`bbox` is the panel's scope and stays in the URL), `LibraryService.cappedCount` supplies the asset total of the whole search, and `mapBounds` supplies the initial plotted bounds. `includes/search_results` renders the toolbar with Group disabled and `htmx/map_view` directly, without `#assets`. The fragment carries `data-results-location-id`, `data-results-bbox`, `data-results-q` (the Search text the results were matched by, empty without a usable term), `data-results-layout` and the grouping the server used (`data-results-group-by`, and `data-results-group-direction`, empty for a Location grouping); `HX-Replace-Url` includes non-default layout, Location and bbox scope. Map searches omit the ignored grouping from that URL. In the browser, `js/map/map-view.js` plots the search by asking the cells endpoint for every settled viewport and clustering the cells once more on screen; a crowded pin opens a panel whose grid is an ordinary search with `bbox` set. See **Map view** in `views/AGENTS.md`.

The contract on `GET /htmx/search/r/:repoId` is HTML only: JSON negotiation (`Accept` or the legacy `Content-Type: application/json`) is a 400 with a `{"error": ...}` body, grouped or not. Nothing in the app asks for results as JSON - the detail modal walks the rendered grid (see **Detail navigation** in `views/AGENTS.md`).

A first page renders `includes/search_results` with `htmx/results_grid_grouped` and an `HX-Replace-Url` carrying `groupBy` and `groupDirection`; a continuation renders the grid alone and is a 204 when the continuation is empty, grouped or not. A cell's `id` is `asset-<id>`, except under a Location: an asset in two Locations has a cell in each group, so there it is `asset-<id>-in-<locationId>`, and the client finds an asset's cells by the `data-asset-id` of their thumbnails (`js/search-results/cells.js`). Validation errors and rejected cursors are plain-text 400s, reported by the snackbar. The frontend side - the Group choice menu, the `groupBy`/`groupDirection` parameters in the `searchParams` store, cursor continuation shared by the scroll observer and the detail modal, the window of loaded pages, and the header counts - is documented in `views/AGENTS.md` under **Search parameters**, **Infinite scroll + lazy load** and **Detail navigation**.

Date storage behind this: `original_created_at` is the camera's wall-clock time with no zone (PostgreSQL `TIMESTAMP WITHOUT TIME ZONE`, SQLite `yyyy-MM-dd HH:mm:ss` text) and is parsed and bound as a `LocalDateTime` with no instant conversion, so its calendar day never depends on the JVM or server zone. `created_at` on assets is bound explicitly in UTC by `AssetDao.add` (an `OffsetDateTime` on PostgreSQL, UTC text on SQLite) instead of relying on the engine default. When no metadata rung yields a capture time the column stays NULL and the asset joins the "No date" group. The index `asset_search_date_taken` is `(repository_id, is_recycled, is_pipeline_processed, <day expression>, <raw timestamp>)` carrying `id` and `folder_id` (`INCLUDE` on PostgreSQL, trailing columns on SQLite): the day gives seeks and per-day counts, the trailing timestamp makes a same-field grouping and sort read in index order, and a pass over the library that tests text membership, a folder or a day reads the index and not the table. Nulls sort where each engine puts them (no `NULLS LAST`, which would forfeit index-ordered reads; the one exception is the Relevance sort's capture-time tiebreaker, which no index orders anyway); SQLite's `created_at` can still be null on legacy rows, which matters only when it is the sort column. There is no incremental migration for any of this: the capture columns and the index live in `all.sql` only, the schema version stays 2, and a database is created from scratch.

The rest of the search's indexes, in both `all.sql` files: `asset_search_created` (`repository_id, is_recycled, is_pipeline_processed, created_at`, carrying `id`) for the Date Imported sort; `asset_triage_created` and `asset_triage_date_taken`, the same two shapes over the triaged assets alone (`WHERE is_triaged`), so the triage view of a large library reads only its triage set; `asset_folder` (`folder_id`) for folder browsing and the folder source of text (on SQLite it also lets an OR of sources be planned as a multi-index OR); and `face_01` (`asset_id, repository_id, checksum`, on PostgreSQL carrying `person_id`), `search_document_01` and `metadata_parameter_01` (`asset_id`), which lead with the asset for the purge cascades, `clearMetadata` and the selective path's probes. The membership tables are indexed in both directions, each index holding both columns (`album_asset_01`/`location_asset_01` lead with the album or Location, `album_asset_02`/`location_asset_02` with the asset), so a probe from either side reads its index alone. `face_02` (`person_id, detection_score`) carries `asset_id`, so the person source reads the index alone. `asset_01` is unique on (`repository_id, checksum`) over the live assets only (`WHERE NOT is_recycled`): a repository has one live copy of a content, and the recycle bin any number. `account_01` is unique on `lower(email)`, and both lookups by email compare `lower(email)`. `person_01`, `person_02` and `person_03` are partial on the live people (`is_deleted = FALSE`), so a merged-away person's name and cover face are free for others. SQLite matches a partial index to a flag a statement binds by the value bound, as long as it is bound as a number, which is how every ScalaSql comparison binds a boolean; a flag bound as text does not match, and `SqliteOverrides.nativeBool` binds `"1"`/`"0"`, so a hand-written JDBC statement that should read a partial index writes the flag as a literal. On PostgreSQL every ID column is `CHAR(36) COLLATE "C"` (compared, sorted and grouped byte-wise, as SQLite does) and `asset` has `toast_tuple_target = 128`, so its `jsonb` metadata lives out of line and the heap row a search reads stays narrow; SQLite's `asset` declares its three metadata JSON columns last, after `updated_at`, so reading any other column does not walk their overflow pages. `SearchPlans` (test trait) reads a statement's plan over a seeded, analyzed library, rolled back afterwards, for the suites that check which index a search or lookup reads; `indexOnlyPlanOf` says whether an index alone can answer a statement, which on PostgreSQL takes costing the seeded tables as vacuumed and ruling out scans of them.

Coordinates: `latitude` / `longitude` on `asset` are WGS84 decimal degrees, nullable, and are parsed on import only, in `ExtractMetadataFlow` through `util/GeoLocationResolver`. Like `CaptureDateResolver`, it reads only persisted inputs - the `GPS` directory of `extracted_metadata`, where metadata-extractor stores each coordinate as a signed degrees-minutes-seconds description plus its `N`/`S`/`E`/`W` ref tag - so a later backfill needs no file. The ref decides the hemisphere whenever present, because the description's integer degree part drops the sign of a value between -1 and 0 (London's longitude). Unparseable or out-of-range values and 0/0 resolve to nothing, and a coordinate whose ref tag is missing has no description at all: `MetadataExtractionService` skips a tag with a null description instead of storing a null (which the JSON column cannot hold). There is no editing and no backfill of existing rows. The partial index `asset_geo` `(repository_id, is_recycled, is_pipeline_processed, latitude, longitude) WHERE latitude IS NOT NULL` is for the map's bounding-box queries, and carries `id` and `original_created_at`, what a map cell names and is ranked by, so a viewport's own points are read from the index alone; `SearchMapTests` checks on both engines that a cells statement reads through it (on Postgres over a few thousand analyzed rows, because its planner costs by statistics and every index ties on a handful; the rows are rolled back once the plan is read and the table analyzed again, since the schema is shared by the suites that follow). The `location` and `location_asset` tables are described under **Locations**.

## Locations

A `Location` (`models/Location.scala`) is one row of the `location` table, and `LocationKind` says which of two things it is: a **Category** (a named container, exactly one level deep, no pin, no assets) or a **Location** (a WGS84 pin, optionally under a Category). Both kinds share one case-insensitive name pool per repository (`location_01` on `(repository_id, name_lc)`), so a category and a Location cannot have the same name, and both kinds surface a clash as `DuplicateException` through `BaseService.add` / `updateById`. The model's constructor keeps the kinds honest (a Category has no pin and no Category; a Location has a pin in range) and the schema repeats the rules as CHECK constraints; "a Location's category must be a category" is a `LocationService` check (`IllegalOperationException`), as is "only a Location can be moved" and "a category holds no assets".

Membership is `location_asset`, the `album_asset` shape: no model, written only through `LocationDao`, an asset in any number of Locations, unknown / foreign / recycled asset IDs dropped on add, adds idempotent. `LibraryService.recycleAssets` drops recycled assets from every Location beside every album; restoring does not re-add; purging cascades. `Location.numOfAssets` and `categoryName` are computed by `LocationDao.getAll`, which lists the repository in **path order**: categories and top-level Locations interleaved by name, each category directly followed by its own Locations by name (`ORDER BY COALESCE(category.name_lc, name_lc), category first, name_lc`; the explicit category-first key matters because a Location named "Alba" would otherwise sort before its category "Italy"). Deleting either kind is a hard delete; a category's Locations are moved to the top level in the same transaction first (`LocationDao.moveChildrenToRoot`), and the `category_id` foreign key has no cascade, so a delete that forgot the re-category fails instead of orphaning. `LocationService.getById` is repository-scoped, and every mutation goes through it, so a foreign ID is a `NotFoundException` and changes nothing. The `locationIds` and `bbox` search filters and **Group by Location** are described under **Search results and date grouping**, the map's queries under **Map**; `LocationController` exposes `/api/location/r/:repoId/list` as flat camelCase JSON in path order (nullable `categoryId`, `categoryName` and pin), and `PUT`/`DELETE /api/location/r/:repoId/assets` accept `{locationId, assetIds: [...]}` and return `{added}`/`{removed}`. Malformed membership payloads and category targets are JSON 400s; a foreign Location is a JSON 404. `LocationActionController` owns `/htmx/location/r/:repoId/tab`, all six dialogs, and add/add-category/rename/move/assets/delete. Its dialog membership payload carries a comma-separated `assetIds` string, and its success response carries `{"added": n}` in the `App-Success-Detail` header (`BaseController.dialogSuccessResponse`, `Api.Field.SUCCESS_DETAIL_HEADER`), which the client merges into the dialog's success detail, so the dialog reports what the server applied rather than the size of the selection. Name, coordinate and Category errors replace the form through `dialogFormValidationResponse`; duplicate names share that path. Coordinates arrive as decimal strings from the dialog's hidden inputs (the pin is placed on a map, never typed; `views/AGENTS.md` **Location pin editor**) or as JSON numbers; a missing or out-of-range coordinate is reported once, as `Const.Msg.Err.PIN_REQUIRED`. An empty/null Category means the top level. Invalid hidden IDs are plain-text 400s, foreign IDs plain-text 404s. The Locations tab, its dialogs and the membership flows are described under **Locations** in `views/AGENTS.md`, and the map editor of the Add location dialog under **Location pin editor** there.

## Map

The map never receives a result set: a repository can hold millions of assets, so the browser asks for a viewport and gets back aggregates. Both aggregates are one statement each in `SearchQueries`, over a `points` CTE of the search's **plotted points** (`plottedPoints`, the rule the `bbox` filter also follows): a matching asset with coordinates of its own is plotted there and only there; one without is plotted at the pin of *each* Location it is in, so an asset in two Locations is two points, as it is two cells in the Location grid. The CTE is a `UNION ALL` of two typed relations over `matching`, so the map carries every filter the grid does.

- `mapCells(query, bbox, cellDegrees)`: the points inside the box, each assigned to a square cell by `floor(coordinate / cellDegrees)`, then one window pass per cell for the count of plotted points, the centroid, and the rank of each point by newest capture time (nulls last on both engines, through a `CASE`) then ID; the rank-one row is the cell and its asset **represents** it, so the thumbnail standing for a cell is stable across pans. A cell of one point carries that point's asset. `SearchService.cellDegrees(zoom)` is `360 / 2^zoom / 4` degrees - a quarter tile, about 64 pixels - with the zoom clamped to 0..20. `floor` is built into both engines (SQLite is compiled with its math functions).
- `mapLocations(query, bbox)`: one statement for the Locations pinned inside the box that hold at least one matching asset, with that count and the category's name: `matched AS MATERIALIZED (SELECT asset.id ... WHERE <matching> AND asset.id IN (<members of the Locations in the box>))`, then the repository's Locations in the box joined to `location_asset` with members in `matched`, grouped by Location. The matches are read once, not once per Location, and only among those members, so `matched` is as large as the memberships of the Locations in view and not as the library; the count agrees with the grid scoped to the Location.
- `mapBounds(query)`: `min`/`max` of both coordinates and the count of every plotted point of the search, not clipped, for fitting the map to a result; `None` when nothing is plotted. Points on both sides of the antimeridian span the whole longitude range.

`LibraryService.mapCells(query, bbox, zoom)` returns `MapCells` (the cells and the Locations, read in one read-only transaction) and `LibraryService.mapBounds(query)` an `Option[MapBounds]`; both resolve the folder scope and the Search text like `search`. The models (`MapCell`, `MapLocation`, `MapCells`, `MapBounds`, `GeocoderResult`) are plain case classes: the JSON shape is the controller's.

`GeocoderService` is the place-name search behind the Add Location dialog, proxied through the server so the browser never talks to the geocoder and the identifying `User-Agent` the Nominatim policy asks for is set in one place. It takes a Settings supplier and reads the switch on every search: it is **off by default** (the `map.geocoder.enabled` Setting; `search` throws `IllegalOperationException` when disabled, which `MapController` answers with a JSON 404) because every query is sent to a third party; the `map.geocoder.url` Setting is a Nominatim-compatible endpoint (`?q=&format=json&limit=5`, a list of `display_name`/`lat`/`lon`). A blank query asks nothing; a place without coordinates is skipped; an unreachable endpoint, a non-200 answer or a body that is not a list is a `GeocoderException`. The `map.tile.url` and `map.tile.attribution` Settings are the basemap the pin editor and the map view render with, read once per request by `SearchResultsController` and `LocationActionController`; the OSM defaults and the privacy trade-off of each are in their help text on the Settings screen.

`MapController` exposes `/api/map/r/:repoId/cells?viewport=s,w,n,e&zoom=n` (`cells`, `locations`, `countsPlottedPoints: true`), `/bounds` (the four bounds and plotted count, or `{count: 0}`), and `/geocode?q=` (camelCase `{label, latitude, longitude}` entries). Cells and bounds take the shared scope and, through `cask.QueryParams`, accept the client's search parameters verbatim: the ones that only shape a grid (`sort`, `layout`, grouping, paging) and the `bbox` filter are ignored, so the map behind an open panel plots the whole search. A scope the parser refuses (Search text with the trash view, `triaged=false` with the triage view) is a JSON 400 carrying its message. `viewport` (`Api.Field.Map`) is the map's own clipping box, passed separately to the service and never an asset filter: a visible Location counts every member of the search even when its own GPS point is outside the viewport. A missing or malformed `viewport` and a non-integer `zoom` are JSON 400s naming the parameter; out-of-range integer zooms use the service's 0..20 clamp. JSON routes build their responses with `BaseController.jsonResponse` / `jsonError`. The geocoder is a JSON 404 when disabled (`IllegalOperationException` from the one read of the switch) and a JSON 502 on an upstream `GeocoderException`. All Location and Map routes require login.

**SQL explain log** (`transactions/SqlExplainer.scala`, `transactions/ExplainingConnection.scala`). A development aid, off by default: with `dev.sql_explain=true` in `application-dev.conf` and `ENV=dev` (any other environment ignores the key with a WARN), `Altitude` gives its `TransactionManager` a `SqlExplainer`, and `connection(readOnly)` then hands out each connection wrapped in a `java.lang.reflect.Proxy`. The proxy forwards everything and offers the explainer every prepared statement whose first keyword is `SELECT`, `WITH`, `INSERT`, `UPDATE` or `DELETE`, with its recorded binds, just before it first runs or is added to a batch; statements run through `createStatement` are never explained: transaction housekeeping, DDL, and also a statement with no bind values, which both ScalaSql (an update) and commons-dbutils' `QueryRunner` send that way (`SELECT nextval(...)`, an unfiltered count). No DAO knows about it, and with the switch off a transaction runs on the pooled connection itself.

- A query is explained the first time its shape is seen in the process: the SQL with whitespace collapsed, a placeholder list reduced to one placeholder and numeric literals replaced by a marker, so the permutations of one query log once.
- The explain runs on the statement's own connection with the same binds. PostgreSQL: `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` for a read, which runs the read one extra time, and `EXPLAIN (SETTINGS)` for anything containing the word `INSERT`, `UPDATE` or `DELETE`, which is never executed; both inside a savepoint that is rolled back, so a refused or timed-out explain does not abort the transaction. SQLite: `EXPLAIN QUERY PLAN`. A failed explain is logged in place of the plan and never reaches the request. `RequestContext` query counts do not change.
- Entries go to `sql-debug.log` in `Environment.ROOT_PATH` (git-ignored), emptied when the server starts: a numbered header (`READ`/`WRITE`, time), `Origin` (the innermost `altitude.*` frame, the DAO line) and, for a DAO statement, `Called from` (the first frame above it outside `altitude.core.dao`), the SQL as prepared, a `Runnable` form with the first-seen values as literals, and the engine's plan verbatim.

## Schema migrations

`schemaVersion` in `Altitude.scala` is the current version. `Altitude.migrationService` (`MigrationService(app, currentVersion, migrationsDir)`) runs `migrate()` in the constructor, in every environment, after the DAOs and before the Settings load: a fresh database (version 0, which a missing `system` table also means) runs `migrations/<engine>/all.sql` once and is stamped with the current version; a database behind would run `migrations/<engine>/<version>.sql` per version, but no such files exist. The service reaches the database through the system metadata DAO and the transaction manager alone, since no service exists yet, and rethrows any read failure other than a missing table, so a locked or refused read never passes for a fresh database. The suite bundles wipe the schema and migrate again after constructing the app (`TestDatabase.reset`).

DO NOT add new migrations or bump the version number. All changes go into `all.sql` for both Postgres and SQLite, as original table/index definitions as if it were a fresh schema (no ALTER); `schemaVersion` stays 2, and a database is recreated from scratch.

## Config & Environments

`ENV` env var controls mode (`dev` | `test` | `prod`). Config resolution order:
- **dev**: `application-dev.conf` → `reference.conf` (defaults in `altitude/resources/`)
- **prod**: `application.conf` → `reference.conf`
- **test**: system env overrides → the `reference.conf` files on the test classpath, merged with the main one first, so a key both files set keeps the main value (the test file's `db.engine` among them: controller tests run on SQLite). Test values that must differ are set in `Altitude`'s test branch: the test database URL and credentials.

The config files hold only what decides the shape of the process at startup: `fs.data.dir`, `storage.engine.default`, `db.engine`, `db.sqlite.*`, `db.postgres.user`, `db.postgres.password`, `db.postgres.url`, `db.postgres.pool_size`, `db.postgres.options`, `db.pool.leak_detection_threshold`, `face.debug.enabled`, `dev.*` and the test `test.dir`. Everything an Admin tunes is a Setting (next section); a leftover key for one of those in `application.conf` is ignored, as `reference.conf` says at its top.

To skip login during frontend dev work, set `dev.user` and `dev.password` in `application-dev.conf`; `UserService.getDevUser` checks the password until it first succeeds and then reads the user by ID, so a page of thumbnails does not cost a bcrypt check each. To log the plan of each new query to `sql-debug.log`, set `dev.sql_explain=true` there (see "SQL explain log"). To have a pipeline queue whose stream fails restart it, set `dev.restart_pipeline=true` (see **Import Pipeline**). Both are read through `Environment.devSwitch`, the one rule for a development-only key: on only when it is `true` and `ENV=dev`, and off, with a WARN, when it is set in any other environment.

`Environment.isDev` is the check for anything that exists in dev only (an unset `ENV` is prod; an unrecognised value is dev). The **style guide** is such a thing: `App.allRoutes` registers `StyleGuideController` (`routes/web/`) only in dev, so its routes are 404s anywhere else, and `includes/nav.scala.html` renders its button under the same check. The page (`/style-guide/r/:repoId`) scans the source tree on every request with `StyleGuideScan.scan` (`core/util`), a pure function over `altitude/static/css`, `altitude/static/js` and `altitude/views` that finds the design tokens (`:root`, scoped, and set at runtime), their reference counts, the color literals and the length literals (px, rem and em in a font size, a width or height, a `min-*` or `max-*` bound, a `grid-template-*` and an inset) written past them, and the icons in use; the result is embedded in the page as JSON, and `GET /style-guide/scan.json` serves it (with a `version` of 1, the sources schema) to the **design tweaks panel** (the vendored tokentweak package `static/js/lib/tokentweak.js`, configured by the adapter `static/js/design-tweaks.js`: the other dev-only thing, whose boot script and adapter `includes/header_common` loads under the same check; it has no nav entry, `Ctrl+Alt+T` toggles it). The controller's other two routes serve a sample dialog that validates like a real one and persists nothing. Controller tests reach the routes through a test-only `cask.Main` (`DevApp` in `StyleGuideControllerTests`), and assert that a non-dev app answers the routes 404 and renders neither the Style Guide button nor the panel script. The page and the panel are described under **Style guide** and **Design tweaks** in `views/AGENTS.md`.

## Settings

A **Setting** (`CONTEXT.md`) is a system-wide tunable with a default that an Admin edits on the Settings screen. Its one home is the `setting` table (`name`, `value`, `default_value`), seeded in both `all.sql` files; the keys keep their dotted names (`face.yunet.confidence_threshold`), so logs read as before. The registry is the companion of `models/Settings.scala`: every Setting's name constant, group (`SettingGroup`, the screen's sections: Face detection, Face recognition and quality, Video, Map, Operations), label, help text (the explanations `reference.conf` used to carry), `SettingType` (`Decimal` with bounds, `Integer` with a floor, `Flag`, `Text`, `TileUrl` with `{z}`/`{x}`/`{y}`, `HttpUrl`), kind and engine. A **Live setting** (`SettingKind.Live`, all but one) is used from the next operation that reads it; the **Restart setting** `import.parallelism` from the next server start. `face.recognition.hnsw_ef_search` and `db.postgres.read_statement_timeout` carry `engine = postgres`: they are neither shown nor saved on SQLite. Durations are whole seconds. `Settings.validate(values, engine)` returns the error of every failing field: the type's rule, then the four cross rules (box size ≥ smallest face, `hnsw_ef_search` ≥ 4 × `match_count`, enroll ≥ keep threshold, `max_sampled_frames` ≥ `min_cluster_frames`), a cross rule judged only when its field applies to the engine.

`SettingsService` (`Altitude.settings`, constructed first and empty, loaded once the schema is in place) holds the values as one immutable typed snapshot, the `Settings` case class (typed accessors such as `faceQualityEnrollThreshold`, `value(name)` and `default(name)` as text, both from the rows), replaced whole on every `load()` and `save()`, so a reader never sees a half-written set. `atStartup` is the snapshot of the first load, the running value of a Restart setting, and `pendingRestart` lists the Restart settings whose saved value differs from it. `currentIfLoaded` is `None` before the first load; `current` and `atStartup` throw then. `applicable` is the registry filtered to the engine. `save(values)` trims every value, merges them over the current set (a Setting not submitted keeps its value), validates for the engine and, when any field fails, throws `ValidationException` naming every failing field and writes nothing; otherwise it writes only the changed rows (`SettingDao.updateValues`, one batch in one transaction, `NotFoundException` when a row is missing), logs each change at INFO with the old and the new value, and swaps the snapshot. A value that spells the current one differently (`0.850` for `0.85`) is not a change, for the write and for the restart notice alike. Loads and saves are `synchronized`, so the table and the snapshot agree; readers never wait. `load()` fails on a missing or invalid row and WARNs on a row the registry does not know, so a retired Setting does not keep the server from starting.

A reader takes its value from `app.settings.current` at the moment it needs it, never in a constructor, and from one snapshot per operation: `FaceDetectionService` sets the YuNet score and NMS thresholds on the thread-local detector before each detection and reads the box size, the smallest face and the two quality tiers once per `extractFaces`; `FaceRecognitionService` reads the match count, the cosine distance and the minimum cluster frames per call and passes the first two into `FaceDao.searchClosestFaceMatches`, so no DAO holds a Setting; `VideoService` and `GeocoderService` take `() => Settings`; `TransactionManager` takes `() => Option[Settings]` (`currentIfLoaded`) for the read statement timeout and `hnsw.ef_search`, and sets neither before the first load; the import and purge queues read the shutdown timeout when `shutdown()` runs; `SearchResultsController` and `LocationActionController` read the tile URL and attribution once per request; `Altitude.importParallelism` reads `atStartup` once, before the actor system is built. An import in flight picks a changed Live setting up at its next stage. The face quality thresholds never re-tier Faces already stored.

The screen is `GET /settings/r/:repoId` (`routes/web/SettingsController`, a full page with the shared nav) and its one form's save, `POST /htmx/settings/r/:repoId` (`routes/web/partial/SettingsFormController`, which also renders the form for the page), both `@requireLogin() @requireAdmin()`. `decorators.requireAdmin` runs after `requireLogin`, which put the account in the context (it throws when none is there), and answers a User or Guest with 403: JSON for an API request, a plain-text page otherwise, no redirect. The nav shows the Settings link to an Admin only, so `NavController`, whose fragment the import page polls, requires login too. The form posts JSON (`hx-json-enc`): the controller renders and reads only the applicable Settings, stringifies a JSON `true`/`false` or number, reports any other JSON type as `INCORRECT_VALUE_TYPE`, and takes an unchecked checkbox as `false`. A failed validation is `BaseController.dialogFormValidationResponse` with the form re-rendered over the submitted values and the errors beside their fields, so nothing is written; a success answers the saved form, and the client dispatches the form's declared `SETTINGS_SAVED_EVENT` to the snackbar. Each field shows its default and a Reset that fills the input with it (nothing is written until Save); a Restart setting with a saved value that is not the running one carries a notice naming both until the restart. The page's markup and scripts are described in `views/AGENTS.md` under **Settings screen**.

## Build & Test Commands

```sh
make compile              # mill altitude.compile – always do this after editing
make watch                # hot-reload dev server (ENV=dev)
make lint                 # scalafmt + scalafix + prettier/eslint (eslint.config.js: no-undef, no-unused-vars, import/no-cycle)
make test-sqlite          # safe: no Postgres needed
make test-controllers     # safe: controller-only tests
make test-psql            # integration tests against the Postgres test container (docker compose, port 5433)
make test-focused-sqlite  # run tests tagged `Focused` against SQLite only
make publish              # fat JAR → target/
make vendor-tokentweak    # refresh the vendored tokentweak package in static/js/lib (TOKENTWEAK=<version|tarball|checkout>)
```

The application's stylesheet is built, not served from source: `cssBundle` in `build.mill` inlines the `@import` lines of `static/css/app.css` (recursively, failing the build on a missing file, a file outside `static/css`, a cycle, or any other `@import` form) into `assets/app.<hash>.css` on the classpath, and `assetManifest` generates `altitude.core.Assets.appCss`, its URL, which `includes/header_common` links. `StaticController` serves only that one name under `/assets/`, cached for good; `/static/` serves the vendored stylesheets, webfonts and JS modules under their own names, revalidated on every use (`@revalidated`). The hash is compiled in, so a CSS edit needs a recompile and a restart, which `make watch` does; `mill altitude.resources` alone leaves the running server linking the old name, which now answers 404.

> **Do not run `make test`** (requires a live Postgres container). Use `make test-sqlite` and `make test-controllers`, and `make test-psql` when the `altitude-core-postgres-test` container is up.
> **Do not run tests if only the frontend was changed** (Twirl templates, CSS, JS, HTML) — these can be manually verified in the browser without running the full test suite.

To focus a test, tag it with the `Focused` tag:
```scala
test("my wip test", Focused) { ... }
```

## Test Structure

Integration tests extend `IntegrationTestCore`. `beforeEach` auto-creates a fresh repository and file-store directory. Tests run against both DB engines via `SqliteSuiteBundle` / `PostgresSuiteBundle` without code changes. `TestContext.setAssetDates` rewrites an asset's capture and import timestamps in each engine's storage form for date-dependent fixtures, and `TestContext.setAssetCoordinates` gives an asset a point for map and bounding-box fixtures. Controller tests run against SQLite through a real HTTP server (`ControllerTestCore`); the server is a second `Altitude` (`App.altitude`) over the same file, so `beforeEach` resets the database (`SqliteSuiteBundle.setup()`) and reloads that instance's Settings (`App.altitude.settings.load()`).

`TestDatabase.wipe(testApp)` drops the schema of either engine and `reset(testApp)` wipes, migrates and loads the Settings: the suite bundles' `beforeAll`, `ControllerTestCore.beforeEach`, and `StartupTests`' fresh-database test, which builds a second `Altitude` against a wiped database and cleans it up (`cleanup()`, then the actor system). `IntegrationTestCore.contend(first, second)` runs two transactions on threads of their own, the first held open until the second waits for it (for a row lock on PostgreSQL, for the write connection on SQLite), for the tests of concurrent writers. `IntegrationTestCore.withSetting(name, value)(f)` saves a Setting around `f` and saves its default back, so the other suites see the seeds (`SettingsServiceTests` restores them in `afterEach` the same way). Unit tests build a snapshot with `TestSettings(overrides)` over the seeds (`TestSettings.seeds`, which `SettingsServiceTests` also asserts against the rows). `NominatimStub` is a local Nominatim-compatible endpoint (`url`, `response`, the last query and `User-Agent` seen) for the geocoder tests.
