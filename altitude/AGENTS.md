# Altitude DAM – Agent Guide

## Do

These apply to every change, server or frontend.

- Avoid documentation drift: a change that adds, changes or removes code updates the guide that owns it, in the same change. This guide owns the architecture, design patterns and anything else future developers should know; [views/AGENTS.md](views/AGENTS.md) the frontend; [docs/faces.md](../docs/faces.md) faces; [docs/image-edits.md](../docs/image-edits.md) the Edit's geometry, math and renderers; the root [CONTEXT.md](../CONTEXT.md) glossary the domain terms; [docs/READINESS.md](../docs/READINESS.md) any change that closes or opens one of its security, data safety or operational readiness items. Guidance never goes in the root `AGENTS.md`, which only routes.
- When adding or changing behavior, review the nearby comments and docstrings, update them, and warn about any that contradict the code.
- Comment any logic that is not trivial, unless the comment only restates the code (a simple getter, setter or similar). A comment that starts "This is needed because..." or "This exists to work around..." is a cue to consider refactoring the need away.
- Log important events at INFO and events useful for debugging at DEBUG; events too noisy for DEBUG go to TRACE where available.
- Extract logic that appears more than once, the same or similar, into a shared function.

### Server-side

- Use test-driven development with a strict red-green-refactor cycle, using integration tests. Skip TDD for documentation-only or configuration-only changes and for frontend-facing code.
- Write the minimal code that keeps clarity, readability and maintainability. Minimal does not mean leaving dead or redundant code behind after a change or refactor.
- DO NOT add new migrations or bump the schema version: see **Schema migrations**.

### Tests

- Every test opens with a Scaladoc comment, the first thing in its body, in this format: the sections in this order, a blank ` *` line after each name and between sections.

  ```scala
  test("Folder tree JSON carries recursive asset counts") {

    /**
     * Setup:
     *
     * A logged-in user's repository with folder1 and its child folder1_1: two imported assets in folder1_1, one in folder1, and
     * one triaged asset outside any folder.
     *
     * Mocks:
     *
     * External service is mocked to avoid outside HTTP calls.
     *
     * Assertions:
     *
     * The folder tree API nests folder1_1 under folder1 under the root, and gives each folder its number of children and an asset
     * count that includes the assets of every folder below it.
     *
     * Edge cases:
     *
     * The triaged asset is counted nowhere, not even in the root.
     */
  ```

- `Setup:` (the state the test starts from) and `Assertions:` (the behavior it proves) are required. `Mocks:` (what the test mocks and why) and `Edge cases:` (the boundary or exclusion the test also proves) appear only when they apply. There are no other sections.
- Write the sections as plain sentences about behavior, not a line-by-line retelling of the code. A `//` comment in the body still explains one specific line.
- When a test changes, its comment changes with it.
- The Unit and SQLite suites run on Linux, macOS and Windows (the jars workflow). A test resource's path comes from its URL's URI (`Path.of(url.toURI)`, as `TestResources.importFile` does), never `URL.getPath`, which is `/D:/…` on Windows and keeps a space as `%20`. A path compared as text is joined with `/` or compared as a real path (macOS' temp folder is under `/var`, a link); an absolute path is built from the file system's root, not written from `/`; a log line ends in `System.lineSeparator`. A test that cannot prove its behavior without POSIX permissions or a directory's size `assume`s them first, before a `try` whose `finally` undoes what it set. Where only some assertions need them and have nothing to check without them, an `if` on the file system's support skips those alone (`TempFolderTests`).

## Architecture Overview

Altitude is a Scala 3 application built with Mill: Cask serves HTTP, Twirl renders the templates, Pekko Streams runs the import and purge pipelines, ScalaSql and JDBC reach SQLite or PostgreSQL, OpenCV and FFmpeg (through Bytedeco) decode media, and ONNX Runtime runs the Scene models and the text tower of the Describe search. The versions are in `build.mill`.

`App.scala` (`object App extends cask.Main`) is the single entrypoint. It registers every route (`allRoutes`), builds the app with `new Altitude()` and registers its cleanup for the stop, then runs the startup tasks before anything is offered to the import queue, the Watch folder scans last; only then does its `main` build and start the HTTP server. `App.altitude` is a lazy val: that start runs when `main`, or a test's server, first asks for the instance, never in the object's initializer. The order and its reasons are under **Startup** and **Shutdown** in **Library stats and purging**.

`Altitude.scala` is the dependency-injection root. Its constructor first loads the config (**Config & Environments**) and refuses an empty Data directory, PostgreSQL with an empty password, an empty `server.host` and a `server.port` that is no port number, then builds everything in a fixed order: the settings service (empty) → the transaction manager → the DAOs → `migrationService.migrate()` → `settings.load()` → `importParallelism` → the model files (`models`, downloaded if missing; see **Model files**) → the actor system → the Scene and Describe embedders (see **Sequences and Image quality**) → the services. The comment above `settings` in `Altitude.scala` gives the reason for each step; a new component keeps to it (see **Settings** and **Schema migrations**).

- `migrationService` and `settings` are members of `Altitude`, not of `service`, because they run before any service exists.
- `object DAO` picks each DAO's engine variant with a `dataSourceType match`: the engine's own class (`dao.postgres.AssetDao`) or the JDBC base with the engine's overrides trait (`dao.jdbc.FolderDao with dao.sqlite.SqliteOverrides`). The services in `object service` are engine-agnostic; only the file store is chosen, by `fileStoreType`.
- Never instantiate services or DAOs elsewhere: inject `app: Altitude` and use `app.service.*` / `app.DAO.*`.

The frontend starts from `static/js/frontend-app.js`, a thin composition root: it initializes the stores, creates the feature coordinators, registers the listeners, starts Alpine, binds drag and drop, and hydrates the initial fragments. Feature logic lives in focused ES module folders under `static/js/`, never in `frontend-app.js`; **JS Directory ↔ Template Mapping** in `views/AGENTS.md` maps each folder to the templates it serves.

- A non-htmx request goes through the shared axios client `static/js/http/client.js`, never raw `fetch()`: see its row in **Key Files** in `views/AGENTS.md`.

## Request Lifecycle

`RequestContext` holds the request's state in **thread-local** `DynamicVariable`s (`account`, `repository`, `permissions`, `grants`, `sessionExpiresAt`), set by the decorators in `routes/decorators.scala`:

- `repoContext()` — global. It clears the context first (request threads are pooled, so a value would otherwise outlive its request), then sets `repository` from `/r/:repoId` (none for an unknown ID).
- `requireLogin` — authenticates (`decorators.authenticate`: the dev user, a Bearer token or the cookie; see **Login and the token**) and fills the context from the token alone: the gate reads no database. A Library in the path that the token gives no access to, or that does not exist, gets the same 404 as any foreign entity, so the two cannot be told apart. A rebuilt token is set as the answer's cookie unless the answer sets the session cookie itself (a password change mints a newer one), and a refused cookie is cleared only when it can never be good again (see **Account versions**). With no login: a 302 to the login with `redirect`, a JSON 401 for an API request, and for an htmx request a 401 with `HX-Redirect`, since htmx's fetch would follow a 302 and swap the login page in as the partial (**Requests and a refused session** in `views/AGENTS.md`).
- `requireLoginOrSignature` — the content route's. A request with both `exp` and `sig` is answered by `ContentSigner.verify` over the path alone, with no account in the context (a 403 when bad or expired, never a redirect; the signature and its key: **Signed URLs** under **Video**); any other request is `requireLogin`'s.

`App.mainDecorators` is `compress → requestResponseLogger → repoContext`. They run on WebSocket handshakes too, so a global decorator must pass through a `WsHandler` or `WebsocketResult.Response` result, not only a `Raw`.

**Log context.** `requestResponseLogger` owns the MDC of a request's log lines (keys in `Const.LogContext`), which the logback patterns print and the JSON format writes whole (**Logging** in **Config & Environments**).

- It clears the MDC at every request's start, since request threads are pooled, then sets `REQUEST_ID` and logs the request's START and END lines at DEBUG. A request under `/static/`, `/assets/` or `/content` gets neither the lines nor a request ID, so a signed URL's `sig` is never logged.
- `UserService.switchContextToUser` is the one place a request gets its account, and sets `USER` to the account's ID, never a name, username or email address. Every way a request is signed in ends there (a token, the dev login, a login, Setup), and a new one must too. A request's START line is logged before it, so it carries no user.
- The context is the request thread's alone. What runs on another thread (a pipeline stage, an Edit render, a Watch folder scan, an actor, an open WebSocket's messages) logs with neither key: `PipelineUtils.withContext` binds the account, not the MDC.
- Tests: `LogContextControllerTests`. `LoggedLine` (`altitude/test/src/altitude/test/`) captures each line with the MDC of the thread that logged it, and `ControllerTestCore.withServer(app, requestThreads = Some(1))` serves on one request thread, so a test sees what one request leaves for the next.

Per route: `@requireLogin`, then at most one gate (`@requirePermission(...)`, `@requireMember`, `@requireAccountCreator`, `@requireLibraryCreator`, `@requireAdmin`; see **Permissions on routes**). A gate answers a refusal 403, never a redirect, and throws when `requireLogin` did not run before it. A full page of a Library adds `@rememberRepository` last, which records the Library as the account's last active one on a 200 (see **Libraries**).

A `RawDecorator` cannot wrap a WebSocket endpoint, so `ImportController.pipelineStatus` (`/import/r/:repoId/status`) does every check itself: the origin (`decorators.isSameOriginOrNone`, 403), the login (`decorators.authenticate`, 401), the Library (404, as `requireLogin` answers) and Import in it (403, a Guest included).

Caching: `@cachedForever` is for content-hashed names only (the stylesheet bundle under `/assets/`). `@revalidated` is for names whose content changes (`/static/`): its ETag is hashed from the bytes on every request, so a file refreshed under a running dev server is never answered as unchanged. `compress` skips an `image/` response (already compressed; gzip would drop `Content-Length`) and one that offers byte ranges (a range names raw bytes), and sets `Vary: Accept-Encoding` on what it may gzip. The content route's own headers are under **Serving** in **Video**.

The DB connection is `RequestContext.conn`, a `ThreadVariable` rather than a `DynamicVariable`: a thread started inside a transaction does not inherit it, as it would a `DynamicVariable`. Only `TransactionManager` binds it, for as long as the thread's outermost transaction lasts.

## DAO / Service Layer

- Controllers call services; services call DAOs; never skip a layer. `BaseService` wraps its DAO calls in `txManager.withTransaction{}` (writes) or `txManager.asReadOnly{}` (reads). A DAO never manages a transaction (`BaseDao` has no transaction manager).
- The JDBC base lives in `dao/jdbc/`, engine-specific DAOs in `dao/postgres/` and `dao/sqlite/`; `PostgresOverrides` and `SqliteOverrides` fill in `BaseDao`'s engine-dependent members. Those a hand-written statement needs:
  - `jsonText(column, key)` and `dayOf(column)` spell a JSON key and a capture day exactly as their indexes do, so the statement uses the index.
  - `instantOf` (public) turns a model's `LocalDateTime` of an instant column into its instant (JVM zone on PostgreSQL, UTC on SQLite); use it before a moment goes to the browser (`UserService.accountTimes`).
  - Locks, all empty on SQLite, whose one write connection serializes writers: `forUpdate`; `forKeyShare` (a foreign key check's lock: blocks a delete or `FOR UPDATE` of the row; `UserDao.shareLock`); `forNoKeyUpdate` (blocks writers of the row but not a foreign key check, so a writer of a referencing row never waits; `AssetDao.lockUnpurged`, **Image edits**; `UserDao.lockActiveAdmins`); `advisoryLock(key)`, for transactions that must take turns where no row lock can, because the row is one they will insert (`AssetDao.lockSequences`, `PersonDao.lockName`, `FolderDao.lockName`, `FolderDao.lockTree`, and `WatchFolderDao.lockPaths`, the one instance-wide key).
  - `vectorPlaceholder`, `vectorBind` and `getVectorField` place, bind and read a Scene embedding.
  - `column $inIdSet` with `idSet(ids)` binds a set of IDs as one parameter whatever its size (an array on PostgreSQL, a JSON array on SQLite), so a set of thousands neither grows the statement nor reaches the engine's parameter limit (PostgreSQL's driver refuses a statement of more than 65,535 parameters). `Columns.isInSet` is its twin in a typed statement, and the generic path takes it too: `DynamicFilter` binds a `Query.IN` whose values are all strings through it, so `getByIds` and every `updateByQuery` or `queryAll` by IDs take a set of any size; a `Query.IN` of other values binds one parameter per value (`Columns.isIn`), for small sets alone. A hand-written statement over a set that can grow binds it with `$inIdSet`, never an `IN (?, …)` built per element (`WatchFolderDao.targeting`, over a folder's whole subtree). Tests: `DynamicFilterTests` (unit: the bound forms), `BaseDaoTests`, `WatchFolderServiceTests` (`targeting`), `LibraryServiceRecycleTests` (66,000 assets recycled, moved, deleted with their folder and purged); each test of 70,000 IDs or 66,000 rows is `Slow`.
- On PostgreSQL `rowProcessor` reads `timestamp`, `timestamptz` and `date` as `java.time` values, so a wall-clock timestamp never round-trips through a JVM-zone instant. A hand-written read uses `manyBySqlQuery` (materializes) or `collectBySqlQuery(sql, values)(f)` (streams with a fetch size, so the PostgreSQL driver does not buffer the whole result; keeps what `f` returns; answers `BaseDao.Collected(kept, scanned)` so a caller reading to a limit knows when it was reached).
- Face vector search runs under `txManager.withFaceVector{}`, or `withFaceVectorReadOnly{}` for a search that stores nothing (`PersonService.suggestedPeople`, `assignablePeople`): one snapshot on PostgreSQL, and SQLite's write connection stays free. The outermost wrapper of a thread sets the transaction up: on PostgreSQL `SET LOCAL hnsw.ef_search` from the PostgreSQL-only `face.recognition.hnsw_ef_search` Setting (not set before the Settings first load) and `hnsw.iterative_scan = relaxed_order`, so the scan goes on until the limit is met by rows that pass the repository and bad-match filters. SQLite needs nothing per transaction (see **Connections and transactions**).
- **A vector search of a limit.** `txManager.withVectorSearch(limit){}` is a read transaction set up to find the `limit` rows nearest a vector (**Describe search**). All three wrappers share `settingUpVectorSearch(limit)`, the face ones passing 0. On PostgreSQL `hnsw.ef_search` is the larger of the Setting and `limit`, capped at pgvector's 1,000, and a limit above 0 also lifts `hnsw.max_scan_tuples` and sets `hnsw.scan_mem_multiplier` to 8. Why: pgvector 0.8.2 stops an iterative scan at 20,000 tuples or `work_mem` of memory and returns only what it visited, so a search whose filters drop many rows (a small Library in a large instance) would return fewer rows than its limit while more exist. At 8 the read statement timeout ends a long scan before its memory cap does (measurements on `TransactionManager.HNSW_SCAN_MEM_MULTIPLIER`): a search ends at its limit, the index's end or the timeout, and one that cannot finish is a 503, never a short result. A face search keeps pgvector's caps. A nested call sets up again only for a higher limit, which stays until the transaction ends (`SET LOCAL`). On SQLite the wrapper is a plain read and the scan is exact. Tests: `TransactionManagerTests` (the settings under each wrapper and nested), `DescribeSearchTests` (a limit past 1,000; a `Slow` small-Library-in-a-large-instance case).
- **Repository scoping.** Every DAO is scoped to the context repository by default (`BaseDao.repositoryScoped`): its generic reads and writes, by ID or by query, add `repository_id` from `RequestContext.getRepository`, which throws when the context has none, so another repository's row looks exactly like a missing one. Six DAOs opt out: `RepositoryDao`, `UserDao`, `SettingDao`, `SystemMetadataDao` (no `repository_id`), `RepositoryGrantDao` and `AuditEventDao` (used with no Library in the context). `updateByQuery` or `deleteByQuery` with an empty query throws `IllegalArgumentException`, scoped or not.
- `FolderDao`'s recursive statements (`getAncestors`, `getPath`, `getChildrenRecursive`) end at a folder their path has already visited (`FolderDao.Acyclic`: PostgreSQL's `CYCLE` clause; on SQLite a text of the visited IDs the recursive arm checks), so a cycle stored in `parent_id` ends them instead of recursing until the read statement timeout, or forever in a write.
- Hand-written SQL on a scoped table carries `repository_id = ?` itself, in both arms of a recursive statement (`FolderDao`) and in a statement that selects the rows it writes (`AlbumDao.addAssets`). Exactly six statements reach a Library's table without its Library, and no other may: `AssetDao.countOwnedBy`, `reassignOwner` and `rewriteImporterRecords` (**Account management**), and `WatchFolderDao.everywhere`, `pauseOwnedBy` and `reassignOwner` (**Watch folders**). Their writes run in the transaction of the account write they serve.
- A `BaseDao` write returns its row count; `BaseService.updateById`, `deleteById` and `increment` turn 0 into `NotFoundException`, so a write to an unknown or foreign ID is never a silent no-op. A service calling a DAO write directly checks with `BaseService.requireFound`. An ID a request names as a reference is read through the scoped `getById` in the write's transaction (`LibraryService.moveAssetsToFolder`, `FolderService.add`, `PersonService.setFaceAsCover`).
- A service checks a Permission (`AssetRules`, **Permissions on routes**) only over rows it read scoped, so a foreign ID is a `NotFoundException`, a 404 that names nothing of it, never a 403 (the status mapping: **Route Layout**).
- `RouteTableTests` (controller suite) holds every route of `App.allRoutes` in one table with who may call it (**Permissions on routes**), and fails a route missing from it or an ID path parameter or body ID field no probe sends. Each probe asserts another repository's IDs get an unknown ID's answer, that it names nothing of that repository, and that no row of either changes; a route that answers otherwise by design says why in the table. `RouteTableTests.idFieldsOf` finds body ID fields with Scalameta: the ID-shaped `Api.Field` values a route's method, or a member it reaches by name, names. So read a body field through `Api.Field`, never a string literal, or the test cannot see it; list a field named but not acted on with `ignoring` and a reason; and give a member of an object under `routes/` a name of its own, not a common method's (`AccountForm.submittedIn`, not `read`, which every `ujson.read` would reach).
- `RepositoryIsolationTests` (both engines) covers the DAOs and services; `TestContext.rowsOf(repository)` reads a repository's scoped tables (`TestContext.SCOPED_TABLES`) whole, so a test compares repositories.
- **Schema guards.** `all.sql` (both engines) makes the database refuse a reference across repositories: `repository_id NOT NULL` on every scoped table, `UNIQUE (id, repository_id)` on each referenced table (led by the ID so it never competes with indexes led by the repository), and each reference a foreign key over `(repository_id, <ref>_id)`. A NULL reference is not checked: a triaged asset has `folder_id` NULL, which `AssetDao` maps to and from the model's `""`. Three references are single-column keys, `ON DELETE SET NULL` (a composite key's would clear `repository_id`): `person.cover_face_id`, `import_file.asset_id` and `import.watch_folder_id`, each indexed for its delete action (`person_04`, `import_file_02`, `import_02`). Code checks their repository: a path that deletes a cover Face picks another cover first, and `ImportService.settle` and `open` read the asset and the Watch folder in the context repository before writing the reference. `repository.root_folder_id` has no key: the repository row is written before its root folder. Trap: on SQLite every constraint violation has error code 19, which `Util.newDuplicateExceptionOrRethrow` reads as a duplicate, so check a write in code before the database would refuse it.
- **Transaction boundaries.** A public service method that reaches a DAO opens or joins a transaction itself (`withTransaction`, or `asReadOnly` when it only reads), even when every current caller already has one: joining costs one check. An operation that must be atomic is one service method under one wrapper, never a loop of wrapped calls, each of which commits on its own (`LibraryService.restoreRecycledAssets`). Pipeline flows and controllers never reach a DAO, and they and DAOs never open a transaction. `TransactionBoundaryTests` (unit suite, Scalameta) enforces the syntactic part: a DAO reference in a non-`private` service method sits inside a wrapper, nothing under `dao/`, `pipeline/` or `routes/` names the transaction manager, and nothing under `pipeline/` or `routes/` selects the `DAO` registry. It cannot see a loop of wrapped calls. Mill runs tests in a sandbox, so `build.mill` passes the source directory as `ALTITUDE_SOURCE_DIR`.

**Connections and transactions** (`transactions/TransactionManager.scala`). Every transaction borrows a connection from a HikariCP pool, opened on first use and closed at `Altitude.cleanup`. A transaction started inside another on the same thread joins it through `RequestContext.conn` (**Request Lifecycle**). A write commits, then runs the actions registered with `afterCommit`; a read, and any failed transaction, rolls back and drops them. A failed rollback is logged, never thrown, so a transaction fails with its own exception; neither wrapper logs what it rethrows. A connection held past `db.pool.leak_detection_threshold` is logged with the borrower's stack trace.

- PostgreSQL has one pool (size from `db.postgres.pool_size`, see `reference.conf`), every connection opened with `db.postgres.options`. A read transaction is `REPEATABLE READ, READ ONLY` (one snapshot) and begins with `SET LOCAL statement_timeout` from the PostgreSQL-only `db.postgres.read_statement_timeout` Setting, with no limit before the Settings first load (a fresh database's migration). `Db.read`, the path of the typed and search reads, turns a statement cancelled by the limit into `QueryTimeoutException`, which `SearchResultsController` and `MapController` answer with a 503 (`Const.Msg.Err.SEARCH_TIMED_OUT`); `manyBySqlQuery` and `collectBySqlQuery` leave it a `SQLException`.
- SQLite has a read pool (`db.sqlite.read_pool_size`) and a write pool of one connection over the same file, `foreign_keys=ON`. Each connection, as it opens, loads the vector extension and registers the columns it scans (`face.features`, `asset.siglip2_embedding`) when their tables exist. A fresh database has none then, so `MigrationService` calls `txManager.schemaCreated()` after creating the schema, which replaces the pooled connections. A read connection is `query_only`, so a write nested in a read transaction fails instead of vanishing in the closing rollback. A write transaction begins `IMMEDIATE`, and the single write connection queues writers in the process instead of failing them with `SQLITE_BUSY`. `PRAGMA optimize` runs hourly on the write connection and at cleanup.
  - The extension is sqlite-vector's build for the platform (`TransactionManager.vectorExtensionPath`), one per supported platform under `altitude/resources/sqlite-vector/`: Linux x86-64 and arm64, Apple Silicon, Windows x64. With the `altitude.native.dir` system property set, it is loaded from that folder, which must hold it: the image sets the property to `/app/native`, and a native jar's start to the folder it unpacks its libraries into (`NativeLibraries`). Unset or empty, it is the build on the classpath, which must be a file, as in a classes folder (Mill's `run`, the tests): SQLite loads an extension from a file alone, and a build inside a jar with no `Altitude-Build` (any jar but `./mill altitude.platformJar`'s) fails the connection, naming the jar and the property (`TransactionManagerTests`). A pool replaces its connections every half hour, each loading the extension anew from that folder, which a native jar's instance therefore keeps fresh (**Packaging**).

**Lock order** (PostgreSQL; on SQLite the one write connection serializes writers). A transaction that takes several locks takes them in this order, the rows of each kind in ID order, so no two wait on each other in a cycle. A deadlock (`40P01`) is a bug to fix by the order, never retried.

1. **Turns** (`advisoryLock`), before any row lock: `WatchFolderDao.lockPaths`; `AssetDao.lockSequences`, then `FolderService.lockTree` (a Curation reopen takes both, since its restore takes the tree's). A folder's name lock (`FolderDao.lockName`) comes after the tree's (**Sorted on arrival**), and a restore takes it after its asset rows; `PersonDao.lockName`: `docs/faces.md`.
2. **Accounts.** Setup's first statement locks the `system` row, before the account it adds (`SystemService.initializeSystem`); nothing else holds that row with another lock. An account write locks the active Admins (`UserDao.lockActiveAdmins`, `FOR NO KEY UPDATE`), then its target or its grantees (`lockById`, `lockGrantees`, `FOR UPDATE`), before any other row it writes: its Watch folders, grants and assets. A write that locks other rows and stores a reference to an account share-locks that account before its first write (`UserDao.shareLock`, `FOR KEY SHARE`): an import its importer (`UserService.lockImporter`), its completion the asset's owner (`UserService.shareLock`, whatever the account's state), an Edit save its saver and a Watch folder's edit or resume its editor (`UserService.lockActor`, after `lockPaths`, refusing an editor no longer an active Admin). It then waits for a write of that account or is waited for, never both. The Admins' lock lets a foreign key check and a share lock through, so an Admin's import, Edit or Watch folder edit does not wait for another Admin's write of a third account; the target's `FOR UPDATE` still stops them.
3. **Assets**, in one pass: `AssetDao.lockAssets` (behind `getAssetsTo*`, `lockCompleted`, `lockSequenceFrames`), `lockLiveFrames`, `shareLockLive` (`FOR KEY SHARE`: an album or Location add) and `lockUnpurged` (one asset). Recycle, move, restore and purge lock this way and take no `lockSequences`, so each Sequence writer locks everything it writes in its one pass: an assignment its matches with every member a merge repoints, a resolve its Picks' Sequences with the frames it recycles, a reopen its Picks with the frames it restores (**Sequences and Image quality**). An account write's `reassignOwner` and `rewriteImporterRecords` lock their rows through an ID-ordered subquery, not in their scan's order; they reach every asset of the account, an import still completing and an asset marked for purging included. So a completion share-locks the asset's owner before its own row, which it locks before its turns and its burst's frames: no library operation sees that row before it commits, and an account write waits for the completion or is waited for. A purge's delete locks its marked asset (`AssetDao.lockPurged`) before the people of its Faces.
4. **People**, then their Faces (`docs/faces.md`).
5. **Rows that hang off those**: an asset's Edit (**Image edits**), album and Location memberships (an add writes them in asset ID order, so two adds of the same assets wait on each other's rows in one order), stat rows in dimension-name order (**Library stats and purging**), a Watch folder's files after its row (an edit, a removal and a scan's `remember` all write the Watch folder's row first).

Tests: one two-thread PostgreSQL test per pair, in the suite of the service that locks (`IntegrationTestCore.whileHolding` for an interleaving of three, `contend` for two): `SystemServiceTests`, `SequenceServiceTests`, `CurationServiceTests`, `AccountManagementTests`, `AssetEditServiceTests`, `WatchFolderServiceTests`, `AlbumServiceTests`, `LocationServiceTests`, `RepositoryServiceTests`, `FaceRecognitionServiceTests`, `EditRenderServiceTests`, `LibraryServiceRestoreTests`.

## Route Layout

| Directory | Purpose |
|---|---|
| `routes/web/` | Full-page Twirl responses |
| `routes/web/partial/` | HTMX partials, under `/htmx/`: always return `"<!doctype html>" + template(...)` (`BaseController.htmlResponse`); `noContentResponse` is a 204 with nothing to swap |
| `routes/api/` | JSON API, under `/api/` |

A route that reads by ID runs in `BaseController.answering` (plain-text refusals, `textError`, which the snackbar shows) or `answeringJson` (`{"error": ...}`). Both answer `ValidationException` 400, `ForbiddenException` 403 (`decorators.forbidden`) and `NotFoundException` 404. `IllegalOperationException` is 409 in `answering`, which the client shows as a warning (**Event Flow** in `views/AGENTS.md`), but 400 in `answeringJson`.

**No stack trace reaches a client outside dev.** `App.debugMode` is true in dev alone, so anywhere else cask answers an exception a route lets out, and a request it cannot bind, with the status line as the whole body (`Error 500: Internal Server Error`); cask prints the exception itself, to stderr (`ErrorAnswerControllerTests`).

- A route that takes a form is `@formPost` (`decorators.formPost`, as `/login` is), never `@cask.postForm`: cask's form and JSON endpoints write the parser's exception and stack trace into their 400 whatever the debug mode. `formPost` answers a body that is no form a bare 400 (`LoginControllerTests`).
- For the same reason no route is `@cask.postJson`: a JSON body is read with `BaseController.unscrubbedJson`.
- **A body anyone can send is limited.** A route with no login that reads its body whole into memory limits it to `decorators.SMALL_BODY_BYTES` (64 KB): `formPost` does by itself (Undertow's form parsers hold a field's value in memory), and a JSON route takes `@smallBody()` above its endpoint (`/htmx/setup`, which reads its body before it asks whether the instance is set up). `decorators.bounded` sets the limit on the exchange before anything reads the body. A declared length over it is a bare 413 with none of the body read; a chunked body is read up to the limit, where Undertow throws `RequestTooBigException` and closes the connection itself, so that client gets no answer. Without the limit one request of gigabytes exhausts the heap, and the image's JVM exits on an `OutOfMemoryError`. The server sets no limit of its own (`MAX_ENTITY_SIZE`): an upload is large by design and is streamed to a file. A JSON body behind a login is not limited (`docs/READINESS.md`, **Malicious files**). Tests: `LoginControllerTests`, `SetupFormControllerTests` (`ControllerTestCore.rawPostStatus` posts over a socket of its own, since an HTTP client reports a refused upload as a broken connection).

A path scoped to a Library contains `/r/:repoId/`, from which `decorators.repoContext` sets `RequestContext.repository` (**Request Lifecycle**).

## Libraries

A **Library** (`CONTEXT.md`) is a `Repository` in the code: the UI says "library"; the code, the tables and the URLs say `repository`. A Library has no owner: it belongs to the server, an Admin reaches every one by account type and anyone else those it holds a grant in (**Accounts and access**), so deleting an account never deletes a Library. The nav's Library menu switches between them (`views/AGENTS.md`, **Nav**).

**The name rule.** `Repository.validName(name)` is the one rule for a Library name, shared by setup and the New library dialog through `RepositoryService.addRepository`. It normalizes the name (`Repository.normalizedName`: whitespace runs collapsed and trimmed, then NFC) and refuses it with a `ValidationException` on `FieldConst.Repository.NAME`: required, no control characters (invisible `Cf` format characters included, but ZWJ and ZWNJ allowed; `isControlCharacter` says why), 2 to 80 code points, a name key within `NameKey.MAX_KEY_BYTES` (**Names**).
- The name is stored normalized and is unique instance-wide by name key (`repository.name_key`, unique index `repository_01`). `addRepository` turns the violation into a `DuplicateException` (`LIBRARY_NAME_TAKEN`), so the index decides a race between two adds.
- Neither caller trims or request-validates the name: a trim would drop the control characters at its ends that the rule refuses. `SetupFormController` runs `validName` beside its request validator to put the error under the Library name field.
- Neither name field sets `minlength` or `maxlength`: the rule counts the normalized name, which the browser cannot.

**Listing and landing.** `RepositoryService.getAccessibleTo(account)` returns the Libraries the account can see, sorted in Scala by `util.NaturalOrder` (digit runs as numbers, text by case-insensitive collation, total; see its scaladoc). `landingRepositoryOf(user)` is the Library login and `/` open: the account's `last_active_repo_id`, read from the database, while the account can still see it; otherwise the first it can see, which is then recorded; `None` when it sees none (`IndexController` answers a plain-text 404, `NO_LIBRARY`; the login redirect goes to `/`). The login token (**Login and the token**) never carries the last active Library, since every switch would make it stale: a `User` built from the token has no `lastActiveRepoId`.

**Recording the last active Library.** `decorators.rememberRepository` goes on the full pages of a Library (the main page, the asset page, Import, Settings, Users, the style guide) and records the Library through `UserService.rememberLastActiveRepository` once the page answers 200.
- The write happens only on a change, so reloading the recorded Library takes no write lock (on SQLite, the one write connection). It is one conditional `UPDATE … IS DISTINCT FROM ?`, so of two racing loads the second writes nothing.
- A failure to record is logged at WARN and the page is still served.
- Partials, API routes and non-200 answers do not record, so a nav reload, a search or a not-found page never moves where the user lands. Setup records nothing; the redirect's load of the new Library does.
- Each page's URL names its Library, so tabs are independent; the tab loaded last decides where the next login lands.

**The New library dialog.** `LibraryActionController` (`routes/web/partial/`), both routes `@requireLogin() @requireLibraryCreator()` (an Admin, or the Create Libraries flag). The create (`POST /htmx/library/r/:repoId/new`) reads the name from the unscrubbed JSON body and calls `addRepository` with the request's account as creator, who gets every Permission when it is no Admin (**New-Library grants**). A refused name, or a creator at its bound of grants (`IllegalOperationException`, `TOO_MANY_GRANTS`), re-renders the form through `dialogFormValidationResponse`; success answers `HX-Redirect` to the new Library's Import page, whose load records it. Front end: `views/AGENTS.md`, **New library dialog**.

The repository cache (`RepositoryService.getById`, `Altitude.repositoriesById`) is never invalidated, because nothing changes a Library once it is created; a change that edits a Library must invalidate it.

## Accounts and access

An **Account** (`CONTEXT.md`) is a `User` in the code, a row of `account`. Its email address and username are each unique under a name key (`NameKey.of`; `email_key`/`account_01`, `username_key`/`account_02`), so a value that differs from a held one only in case or Unicode form is a `DuplicateException`. The login lookup (`UserDao.getWithPasswordHash`) compares the key column itself, so lookup and index cannot differ. A username keeps to `User.validUsername` (3 to 32 of `[A-Za-z0-9._-]`), so it never holds an "@" or a character that folds: the login relies on this.

**Setup.** `/htmx/setup` needs no login and creates the first Admin and Library (`SystemService.initializeSystem`). The route refuses an instance whose in-memory flag (`Altitude.isInitialized`, read from the `system` row at the start) says it is set up; the transaction's first statement marks the `system` row set up only while it is not (`SystemMetadataDao.setInitialized`, answering whether it did) and refuses otherwise (`IllegalOperationException`, `ALREADY_INITIALIZED`), which the route answers with the same 400. So of two submissions at once the second waits on the row and is refused, adding nothing, and the flag is set only once the change commits (`afterCommit`), so a failed commit leaves Setup open. Tests: `SystemServiceTests`, `SetupFormControllerTests`.

**Permissions and grants.** Each `Permission` (`models/Permission.scala`) has a stable bit; the bitmask (`Permissions`, JSON as the bare number, refusing unknown bits) is stored and carried in tokens, so a bit is never reused or renumbered. A `repository_grant` row (account, Library, `Permissions`) gives a User or a Guest access; a Guest's holds no Permission, and an Admin needs none, reaching every Library by type.
- `RepositoryService.setGrant` (upsert) and `replaceGrants` (all of an account's grants at once: what account management writes) lock the account's row and check its stored type. They refuse a grant to an Admin and a Permission to a Guest (`IllegalOperationException`), and more than `MAX_GRANTS_PER_ACCOUNT` (35, `TOO_MANY_GRANTS`) Libraries, the bound a login token fits (**Login and the token**). The row lock makes two grants racing past the bound take turns on PostgreSQL. Both bump the account's version after commit (**Account versions**).
- `requireLogin`'s gate reads the token's grants, never the table.
- An account's delete cascades its grants, never a Library; the database refuses to delete an account that owns an asset.

**Permissions on routes.** Every route declares who may call it by its decorators (`routes/decorators.scala`), and `RouteTableTests` holds one row per route, which must match the decorators: a new route needs a row. Levels: anyone (no decorator); any account with access to the path's Library (`@requireLogin()` alone); or `@requireLogin()` plus one gate: `@requirePermission(p, ...)` (any one of them in the path's Library, `RequestContext.permissions`: all for an Admin, none for a Guest), `@requireMember()` (no Guest: the Triage partials), `@requireAccountCreator()` (an Admin, or Create Users or Create Guests in any Library, not only the path's: `RequestContext.createsAccounts`), `@requireLibraryCreator()` (an Admin or the Create Libraries flag) or `@requireAdmin()`.

Every gate (`decorators.allowedOnly`) logs at WARN, reads no database, and answers with `decorators.forbidden(why, json)`, the one 403 for any refusal for lack of a Permission, from a gate, a route or a service (`ForbiddenException`): `{"error": why}` or "Forbidden: why". On a full page the gate precedes `@rememberRepository`, so a refused page records nothing. `RouteTableTests` fails a route that changes a Library (any method under `/r/:repoId` except GET and a WebSocket handshake) with no gate past the login; a route that checks access itself has an `Access.HolderInRoute` or `LoginInRoute` row, which the table's 403 test enforces. The table is the per-route map of Permission to feature. The cases that are not plain decorators: opening an upload with a destination folder also takes Organize (`ImportService.openUpload`, **Uploads**); the import status WebSocket checks Import itself (**Request Lifecycle**); the asset API's recycle and restore take Recycle or a Curate Permission; changing one's own password (`PUT /htmx/account/password`) names no Library and is any account's.

A rule a decorator cannot decide is checked where its input is:
- A Guest sees Browse alone. A route taking the view as a parameter refuses a Guest Triage, the Trash and `triaged=true` (`decorators.maySeeView`, `refusedView`). A route taking an asset's ID answers a Guest a triaged or recycled asset as 404, after the scoped read (`maySeeAsset`, `visibleOnly`). A Face's crop stays served, as it may be the cover of a Person the Guest sees.
- A rule that depends on the asset is `AssetRules`, called by the service in its write's transaction over assets read scoped to the Library. `requireRecycle` (`Permissions.mayRecycle`: a triaged asset, including one recycled from Triage, takes a Curate Permission, a sorted one Recycle) guards `LibraryService.recycleAssets` (so a folder's delete), `restoreRecycledAssets`, and `moveAssetsToFolder` for assets leaving the trash. `requireCurate` (Curate all, or Curate own on an asset whose `owner_user_id` is the account: the one rule that reads the owner) guards the triaged Picks of `CurationService.resolve` and `reopen`, which first read every ID scoped (`requireKnown`), so an unknown or foreign ID is a 404, never a 403. One refused asset throws `ForbiddenException` and the whole operation rolls back.
- With Curate own but not Curate all, Curation shows the account its own frames alone (`AssetRules.curatedOwner`, the `owner` of `AssetDao`'s Curation statements, and `CurationService.curatableFrameCounts`), so a set never holds a frame its outcome would be refused for, and `resolve` judges a Sequence complete over the frames shown.
- The rules read `RequestContext.permissions` and `account`: a request's, or a pipeline stage's (`PipelineUtils.withContext`). No pipeline, startup task or purge reaches them.
- A template renders an action control only where the account may use it: `views/AGENTS.md`, **Controls follow Permissions**.

**Assets.** `asset.owner_user_id` is the owning account, `NOT NULL REFERENCES account (id)` with no delete action, so its assets must move before an account can be deleted. `asset.original_owner` is the importer record (`AccountSnapshot` JSON), which outlives the account. `persistAndIndex` rebuilds the importer record from the account as stored at insert (`UserService.lockImporter`, a `FOR KEY SHARE` lock), so a write of that account, whose `FOR UPDATE` conflicts, waits for the insert and then sees the asset (**Lock order**). An account deleted or deactivated while the file waited fails the file with `ImporterUnavailableException`, shown as the file's reason in the Import history, never a foreign-key error. Neither field reaches the browser: `Asset.toBrowserJson` leaves both out, since they name an account to anyone who can see the Library.

**Login and the token.** `UserService.loginAndSetUser` folds the login with `NameKey.of` and looks it up by `email_key` when it holds an "@", by `username_key` otherwise; a login with a control character is not looked up (PostgreSQL refuses a NUL in a text parameter). An unknown login checks a dummy hash, and it, a wrong password and a deactivated account get the same 401. The lookup and bcrypt run read-only, so on SQLite they hold no write connection. Then the account's version is read, and a short write transaction locks the account (`lockWithPasswordHash`), refuses the login if the hash changed since the check (a password change the version may predate), and records `last_login_at` (`recordLogin` leaves `updated_at`, the stamp of an account change) and the audit event. A failed login's event has no actor and keeps the login as typed through `Util.printable` (64 characters).

The token is PASETO v2.local (`PasetoService`) with a key random per process. Its claims (`TokenClaims`) carry the account, its grants as Library ID to bitmask (none for an Admin), its version and the expiry. `PasetoService.readToken` is the one place claims are read, with no database query. The 4096-byte cookie bounds the grants: about 57 bytes each over about 1820 for the longest account (an 80-character name of four-byte characters, escaped to 12 bytes each) fits 37, hence `MAX_GRANTS_PER_ACCOUNT` = 35 (`LoginTokenTests` asserts the fit). The bound rests on `User.valid`'s limits (name 2 to 80 characters, email 3 to 80 ASCII); raising one or adding a claim means re-checking it. `createToken` logs at ERROR a token past `MAX_TOKEN_BYTES` (3950). Every expiry is `UserService.tokenExpiry` (7 days), and the cookie lives as long as its token (`SessionController.authCookie`); it is `Secure` unless `server.secure_cookies` is false (**Environment variables** in **Config & Environments**), and the cookie that clears it follows the same key.

**Account versions.** `AccountVersions.processWide` is one in-memory map per process, shared by every `Altitude` in it, holding per account a current and a revoked-below version (both 0 for an account never changed). It is not persisted, since the token key dies with the process too. A token carries the version read before the account is read, so a change committed meanwhile leaves it stale, never wrong.
- `UserService.checkToken(token, renewable)` judges a token against one `Snapshot`: `Current`; `Renewed` (below current: claims rebuilt from the database with the old expiry, and the new token set as the cookie by `requireLogin` and `/`); or `Refused` (stale where it cannot be replaced, as a Bearer header's; account deactivated or deleted; or below revoked-below). When a refusal clears the cookie: **Request Lifecycle**.
- `bump` makes an account's tokens stale; `revoke` refuses them (a password change, and a deactivation, so a reactivated account logs in again). Account writes call one in `TransactionManager.afterCommit`, so a rebuild reads the change.
- `onChange`: `Altitude` closes the account's import status sockets in every Library (`ImportStatusWsActor.CloseAllFor`): a bump with 1013, which the client reconnects on, its handshake re-checking Import; a revocation with 1008, which `hx-ws` does not, so the page reconnects after its own password change (`js/listeners/account.js`).
- The dev user's claims (`UserService.getDevUser`) are built from the database on every request.

**Account management.** `UserService` holds the Users page's writes (`create`, `update`, `deactivate`, `reactivate`, `delete`, `setPassword`, `changeOwnPassword`), each in one transaction with its audit event, reading the actor from the database, never the token. Each bumps the account's version after commit, except a password change and a deactivation, which `revoke`; the session that changed its own password gets a new token (`OwnPasswordController.renewedSession`).
- Refusals of the account rules (`User.valid`, the password lengths, 1 to `MAX_GRANTS_PER_ACCOUNT` Libraries for a User or Guest) are `ValidationException`s naming their field (`FieldConst.User.*`), as is a taken email or username (`whileKeysFree` reads the `account_01`/`account_02` violation off the driver's message).
- `shapedByType`: an Admin keeps no grant, Create Libraries flag or new-Library grant; a Guest keeps its Libraries with no Permissions. With the new-Library switch off, its Permissions are cleared.
- A create locks the creator's row and refuses an inactive one. A creator who is not an Admin stays within its ceiling (`withinCeiling`, over its grants read in the transaction and what was asked before shaping): a User only where it holds Create Users, a Guest only where it holds Create Guests, with Permissions it holds there; never an Admin, the Create Libraries flag or the new-Library grant. A Library it holds nothing in is refused the same whether or not it exists.
- Every other write is an Admin's: it locks the active Admins' rows in ID order (`UserDao.lockActiveAdmins`, `FOR NO KEY UPDATE`, which two such writes take in turn while a foreign key check against an Admin goes on) and the actor must be among them, so two Admins' writes take turns (`AccountManagementTests`, on both engines). That, with the refusal of the actor's own account (`OWN_ACCOUNT`), keeps an active Admin.
- An update is checked against the state its form opened over: `UserService.editState`, a SHA-256 of the fields the form shows and the grants, carried back as `OPENED_STATE` and compared under the account's row lock, which every write of the account and its grants takes. A mismatch is `ACCOUNT_CHANGED` and writes nothing.
- A wrong current password in `changeOwnPassword` is logged at WARN and recorded (`PasswordChangeFailed`).
- A change of name, username or email rewrites the importer records of the account's assets in every Library (`AssetDao.rewriteImporterRecords`, its rows locked in ID order: **Lock order**). A delete gives the account's assets and Watch folders to the acting Admin (`AssetDao.reassignOwner`, `WatchFolderService.passOn`); its grants cascade, accounts it created lose their creator, importer records stay.
- A deactivation, or a demotion from Admin, pauses the account's Watch folders in the same transaction (`WatchFolderService.pauseOwnedBy`), since a Watch folder's owner must be an active Admin (**Watch folders**).
- `accountsVisibleTo(viewer)`: every account for an Admin; for anyone else the non-Admins it created, with only their grants in Libraries the viewer holds one in.

**New-Library grants.** `RepositoryService.addRepository` grants, in its transaction, every non-Admin account whose new-Library switch is on its new-Library Permissions, and a creator who is not an Admin every Permission. Lock order: the active Admins' rows first (as every Admin account write takes them), then every grantee and the creator in one pass in ID order (`UserDao.lockGrantees`), so creates and Admin edits cannot deadlock (`RepositoryServiceTests`, on PostgreSQL). Each grant is recorded as `PermissionsChanged`. An account refused for its bound is skipped with a WARN, but the creator's refusal fails the whole add, so no Library is left its creator cannot open. A refused add restores the request's previous Library, so the dialog answering the refusal names the Library it was opened from.

**The Users page.** `UsersController` and `routes/web/partial/UserActionController`: the cards and the Add User modal and its create are `@requireAccountCreator()`; editing, passwords, deactivation, reactivation and delete are `@requireAdmin()`. Every account and Library ID a request names must pass `Validators.isUuid` (`UserActionController.uuid`), else a 400 before it reaches a statement or a log line. A Permission given in a Library gives access to it too. The form renders the creator's ceiling and nothing above it (`ceilingOf`); a field refusal returns the form with every field's error (`UserService.fieldErrors`), and a request above the ceiling is a 403. The own-password dialog is `OwnPasswordController`, whose paths name no Library. The front end: `views/AGENTS.md`, **Users page**.

**Audit log.** `audit_event` is append-only. `AuditService.record` writes in the caller's transaction, so an event commits or rolls back with its change, and logs at INFO only after the outermost commit (`TransactionManager.afterCommit`). The type is stored by `AuditEventType.dbValue`, never the enum name; actor and target are `AccountSnapshot`s, as accounts change and are deleted. `AuditService` has no generic writes and reads nothing back; there is no screen. Recorded: logins, the writes of **Account management** (with `BaseController.clientIpOf`), the setup Admin's creation (`SystemService.initializeSystem`, `"setup": true`), and each grant of **New-Library grants**.

## Import Pipeline

Pekko Streams pipeline in `service/ImportPipelineService.scala` (`combinedFlow`) and `pipeline/flows/`: one flow for both engines, a substream per repository.

- Every stage's work runs in a future on the import dispatcher (`Altitude.importDispatcher`, a fixed pool of `Altitude.importParallelism` threads), never on the default dispatcher, which the stream actors, the import status feed and the schedules share. A stream actor only routes, so every repository's import works at once and the dispatcher's threads bound all of them together.
- `importParallelism` is resolved once at startup (`util/ImportParallelism.resolve`): the `import.parallelism` Setting (a Restart setting), or at 0 what the cores and memory afford, never under 2, capped by `import.parallelism.max` (**Config & Environments**). The cost model and its measurements are in the `ImportParallelism` scaladoc.

Per repository, in order:

| Stage | Operator | Touches |
|---|---|---|
| `CheckMediaTypeFlow` | `map` | nothing |
| `CheckDuplicateFlow` | `mapAsync(1)` | database read |
| `AssignIdFlow` | `map` | nothing |
| `ExtractMetadataFlow` (metadata, dimensions) | `mapAsync(importParallelism)` | file |
| `IndexFlow` | `mapAsync(1)` | database write |
| `DetectFacesFlow` | `mapAsync(importParallelism)` | file |
| `MeasureImageFlow` (Image quality, perceptual hash, Face sharpness, Scene embeddings) | `mapAsync(importParallelism)` | file |
| `RecognizeFacesFlow` | `mapAsync(1)` | database write, face files |
| `FileStoreFlow` | `mapAsync(1)` | rename |
| `AddPreviewFlow` | `mapAsync(importParallelism)` | stored file, preview file |
| `MarkAsCompleteFlow` | `mapAsync(1)` | database write |
| `DiscardDroppedFlow` | `mapAsync(1)` | database write, files |
| `SettleImportFileFlow` | `mapAsync(1)` | database write, a Watch folder's source file |
| `StripBinaryDataFlow` | `map` | nothing |

- Only the stages that read and decode the file work on several assets of a repository at once; no database stage does. `mapAsync` keeps upload order, so faces are matched, and people started, one asset at a time in upload order, and SQLite's single write connection sees one writer per stage. A repository's import holds at most six connections, one per database stage.
- No decoded image rides on the element: `DetectFacesFlow`, `MeasureImageFlow` and `AddPreviewFlow` each decode and release inside their work, so the decodes in flight stay bounded at `importParallelism` overall, at the price of three decodes per image. The detections do ride (`AssetWithData.detectedFaces`) through `MeasureImageFlow`, which adds each Face sharpness, to `RecognizeFacesFlow`, which stores each Face in one insert (measurement: **Sequences and Image quality**).
- Each stage's writes are a short transaction of its own, opened by the service it calls (`LibraryService.persistAndIndex`, `FaceRecognitionService.recognizeAndStore`, `LibraryService.completeImport`), so a stage commits before the next one reads the asset. The completion's one transaction marks the asset complete with its measurements, places it (its burst's Sequence, or its Import's destination: **Sorted on arrival**), counts it in the stats and settles its Import file.
- `Altitude.parallelism` (the core count) sizes the import and purge queues' buffers, not the concurrency. The purge queue's stages run on the default dispatcher.
- To add a stage: a `Flow` in `pipeline/flows/` built with `PipelineUtils.stage`, wired into `combinedFlow`.

The import, purge and edit-render queues are each a `QueuedPipeline` (`pipeline/QueuedPipeline.scala`): the service's flow materialized once for the life of the app behind a `Source.queue`. `run` materializes the flow per call instead (`LibraryService.addAsset`, tests).

- `offer` waits while the queue is full, holding no thread, and offers take turns in order: a `Source.queue` fails an offer made while as many as it admits already wait, so `QueuedPipeline` hands it one at a time, and any number of uploads and scans may offer at once (`ImportPipelineServiceTests`).
- A refused offer (dropped, queue closed, stream stopped) fails with `QueueRefusedException`. `ImportPipelineService.addToQueue` then deletes the staged file and the caller records the file failed (`ImportService.upload`, a Watch folder's scan); `PurgePipelineService.enqueue` logs it, and the asset stays purge-pending for the next startup.
- `shutdown()` completes the queue and waits for what it accepted, up to the `pipeline.shutdown_timeout` Setting. `stop()`, for a queue whose elements the next startup finds again (edit-render), ends the stream at once, dropping the buffer, and leaves started work to its owner.
- `Altitude.cleanup` order: `WatchFolderService.stop`, the import queue, the purge queue, `EditRenderService.shutdown`, the embedders, and only then the transaction manager. The server's stop runs it before the HTTP server stops (**Shutdown** in **Library stats and purging**), and the next startup handles what a timeout cut off (**Startup**, there too).
- A queue whose stream fails stays down: every later offer is refused. With `dev.restart_pipeline` (`Altitude.isPipelineRestartEnabled`) it restarts after a backoff with a new `Source.queue`, losing the offers made during the backoff and the assets in flight or buffered (startup discards a persisted one and empties staging). Once `shutdown()` has begun, a restart ends the stream instead.

The pipeline works on **staged files**, never on byte arrays: `AssetWithData` carries the asset and its file's path.

- Every file lands in `data/staging/<uuid>` first (`StagingService`; an upload and a Watch folder's scan stream it there), and startup empties staging. The checksum is the file's streamed SHA-256 in lowercase hex (`Sha256.hex(path)`).
- `FileStoreFlow` renames the staged file to `files/<id[0:2]>/<id>`, so a staged file is consumed by exactly one import; after it the element's path is the stored file. A dropped asset carries its staged file in `InvalidAsset` for `DiscardDroppedFlow` to delete, and `StripBinaryDataFlow` sends an imported one on to the sinks as its `Asset` alone.
- Dimensions and an animated GIF's playing time (its `duration_ms`) come from the header alone (`AssetService.getDimensionsAndDuration`). Face detection, the measurement and the preview are the only decodes, through `ImageUtil` (OpenCV, with an ImageIO fallback for formats the bundled OpenCV lacks, GIF among them). An animated image (an image with a duration) gets neither face detection nor measurement.
- The Preview (`ImageUtil.makeImageThumbnail`) is one OpenCV pipeline from the decoded image to a lossy WebP letterboxed in the 200 px box, with no PNG, ImageIO or `AffineTransform` step.

**Failures.** No single asset can stop the pipeline.

- Every stage runs one asset's work under `PipelineUtils.guarded` (through `PipelineUtils.stage`; `CheckMediaTypeFlow` calls it itself): whatever it throws drops the asset as an `InvalidAsset` with that cause, and the stream goes on. `DiscardDroppedFlow` and `SettleImportFileFlow` run outside the guard, so their own failure never replaces the drop's cause.
- The guard binds the element's `PipelineContext` (repository, account, Permissions as queued) to `RequestContext` for the work alone (`withContext`), so a pooled thread never keeps a request's context. An import always has an account (the uploader, or a Watch folder's owner); the startup requeue of purges has none.
- A stage catches a cause only to report it as another (`RecognizeFacesFlow`: `DuplicateException` becomes `SamePersonDetectedTwiceException`). An unreadable file is an `ImageException` or a `VideoException`.
- Each drop is logged once: a cause `PipelineUtils.isExpectedDrop` names at INFO in one line (`AssetErrorLoggingSink`), any other at ERROR with its stack trace (the guard).
- The measurement is the one working stage whose failure does not drop the asset: `AssetService.measureImage` logs a `NonFatal` throw at WARN and the asset imports unmeasured, with no embedding, since the metrics are derived and NULL is a state every reader handles. The one exception is a Scene embedder closed by a stop (`SceneEmbedderClosedException`), which drops the asset, an expected drop (**Scene embedding** under **Sequences and Image quality**).
- An Import file's reason (`PipelineUtils.dropReason`) names the expected causes, and any other by its class's simple name, never by its message.
- As a last resort a queue's supervision strategy resumes past a failure outside a stage's work (logged at ERROR). That element reaches no sink, so it is neither reported nor discarded; no stage may rely on it.

**A dropped asset leaves nothing behind.** `DiscardDroppedFlow` deletes the staged file and calls `LibraryService.discardImport`, which undoes what the import wrote, so the same file can be uploaded again at once (`AssetService.getByChecksum` sees every live row, finished or not). It is a no-op for an asset never persisted or already complete.

- Its transaction locks the people of the asset's faces first (`PersonDao.lockAssetPeople`, through `PersonService.moveCoversOff`), so a face another import gives one of them meanwhile keeps that person and no cover is left on a face that goes. It deletes the row only while `is_pipeline_processed = false`, and deletes each of those people left with no face: recognition matches face rows, so only this import can have started such a person. The files go after the commit.
- A failed completion is a drop and is discarded the same way. The stats count an asset only once complete, so a discard changes none.
- A discard that fails is logged at ERROR and swallowed, so the drop keeps its own cause; the next startup's `pruneDanglingAssets` tries again.

**Import records.** An **Import** and its **Import files** (`CONTEXT.md`) are the tables `import` and `import_file`, written through `ImportService` (`Altitude.service.imports`) alone.

- The five counters are the files by outcome. `settle` moves them in the file's transaction with single statements that read the row as they change it (`ImportFileDao.settle`, `ImportDao.fileSettled`), so concurrent settles on PostgreSQL add up (`ImportServiceTests`, `contend`) and a settled file keeps its first outcome. An Import is in progress until `closed_at` is set: marked complete (`close`) with nothing pending.
- `expected_files` is how many files the Import was opened to hold, NULL when not told. `Import.expectedTotal` and `Import.remaining` count it, so the history's bar fills as files settle, not as they arrive.
- A file in the pipeline carries its Import file as `AssetWithData.origin` (`ImportOrigin`; none for an `ImportAsset` or a plain test fixture, so nothing is settled for them). An imported file is settled in the completion's transaction (`completeImport`), so a failing settle makes the completion a drop. A dropped file is settled by `SettleImportFileFlow` after the discard (`ImportService.settleDropped`), which then tells a Watch folder what became of its file (`WatchFolderService.settled`, **Watch folders**). A settle that fails there is logged at ERROR, and the file stays pending until the next startup.
- A file is a `duplicate` only of an asset whose own import is complete. The stage settles a repository's files in arrival order, so the copy matched has completed or been discarded by then; when no completed asset has the content, the file is `failed` with `Const.Msg.Err.COPY_NOT_IN_LIBRARY`, never recorded as already in the Library.
- A reason is a phrase in sentence case with no full stop, shown as stored. A client-sent Import name or file path is logged through `Util.printable`, so a line break in one never starts a log line.
- At startup `App` runs `ImportService.startup()` before anything is offered to the import queue: `failInterrupted()` fails every pending file ("Interrupted by a restart") and closes every Import in progress, then `prune()` deletes the closed Imports older than the `import.history.days` Setting (0 keeps them forever) and has the Watch folders forget files long absent. The prune runs at startup, for a server restarted more often than daily, and daily after, both through `pruneOrLog()`, which logs a failure at ERROR and never throws.

**Uploads.** The Import page uploads through four `ImportController` routes, each `@requirePermission(Permission.Import)` and answering JSON: `POST /import/r/:repoId/imports` opens an upload (`ImportService.openUpload`) and answers its ID; `…/imports/:importId/files?relPath=` streams one file into staging and hands it to `ImportService.upload`, the request waiting while the queue is full; `…/failures` records a file the page could not send after its retries; `…/close` closes it, which is also what cancelling does.

- A destination takes Organize as well, checked after the folder is read, so another repository's folder is a 404, never a 403.
- The routes that name an Import take only an upload the account itself opened (`ImportService.ownUpload`: another repository's is a 404, any other Import a 403), so no account sends files into an Import whose destination it may not hold Organize for. The files and failures routes re-check Organize for an Import with a destination (`ownUploadTakingFiles`), so an account that loses it mid-upload gets a 403 from its next file on; `close` does not, so the page can still close.
- An Import that takes no more files is a 409 (`answeringUpload`). On a 403, 404 or 409 the page stops sending.
- A path (`util/RelPath`) with an empty name, a ".." or an ignored name is a 400 before the body is read (`ImportService.requireTakes`), and an empty file a 400 once staged; neither is recorded. `util/IgnoredFiles` is the one list of ignored names, served to the Import page (`IgnoredFiles.toJson`), which leaves such files out before sending.
- The files route answers 200 with the Import file's outcome whenever the file was recorded. A file added and then not described, or refused by the queue, is settled `failed` right there (nothing else would settle it), so the page does not resend it.
- When the destination was recycled since the Import opened, the route calls `ImportService.failForLostDestination` with the request's Content-Length before reading the body, recording the file failed with `DESTINATION_IN_TRASH`, so every remaining file is recorded and none is staged. A request with no stated length is staged, and `upload` fails it the same way without offering it.

**Sorted on arrival.** An Import with a destination folder (`import.dest_folder_id`) sorts its files as their imports complete; one without leaves them in Triage. `completeImport` reads the destination through `ImportService.destinationOf` and puts the asset in `FolderService.ensurePath(destination, origin.folderPath)`, out of Triage and in no Sequence.

- `ensurePath` reuses a folder of the name, restores a recycled one alone and adds a missing one, so a folder is born with the first completed asset in or below it; a folder of duplicates or unsupported files alone never appears. `FolderService.add` restores a recycled folder of the name the same way, under the name as typed, so a deleted folder never keeps its name from a new one; a live one is a duplicate.
- `rename` and `move` onto the name of a recycled sibling take it (`FolderService.takeName`): the sibling's `name_key` becomes `Recycled <its ID>`, which no name folds to (folded keys are lower case), and its name stays, so the Trash still shows it. Restoring an asset brings its folders back through `FolderService.restoreRecycled`, which gives a folder moved aside its key back when no live sibling holds it (moving a recycled holder aside in turn) and otherwise names it the first free "name (2)", "name (3)"…, the name shortened by whole characters when the number would take it past the folder rule (`FolderServiceTests`).
- The creators of one folder take turns on `FolderDao.lockName(parentId, nameKey)`, an advisory lock that `FolderService.add`, `rename` and `move` also take for the name they bring a folder under, so of two transactions that both miss a folder the second finds the first's (`FolderServiceTests`, `contend`; on PostgreSQL it fails on `folder_02` without the lock). An add, a rename and a move each take one lock, after the tree's; `ensurePath` takes its locks parent-down; a restore takes several (`restoreRecycled`: the folders of each asset in turn, and each numbered name it tries) but only after the tree's lock, which no two restores hold at once. So there is no wait cycle.
- A completion with a destination, a folder delete (`LibraryService.deleteFolderById`), a restore (`LibraryService.restoreRecycledAssets`, so a delete under way is seen done and its folders come back with the asset), and `FolderService.add` and `move` take turns on `FolderService.lockTree` (`FolderDao.lockTree`), each before it reads, and before any name or row lock. A delete only marks its folders, which nothing waits for, so without the turn a file completing during the delete of its destination is left live under a folder in the Trash; with it, the second sees what the first committed (`ImportPipelineServiceTests`, `contend`). `add` and `move` refuse a parent or destination in the Trash, and `move` and `rename` a folder in it (`IllegalOperationException`; the add form shows `PARENT_FOLDER_IN_TRASH`), and of two moves at once the second checks its ancestors against what the first committed, so two opposite moves never commit a cycle (`FolderServiceTests`, `contend`). `moveAssetsToFolder` takes it too, before its reads, for its turn with the restores (**Library stats and purging**), though it does not check whether its destination is in the Trash.
- A destination recycled meanwhile, a name the folder rule refuses, and a name taken by the time the folder is added fail the completion with `ImportDestinationException`, an expected drop that creates nothing of the path. `sortInto` turns a taken name's `DuplicateException` into it, because a `DuplicateException` reaching `SettleImportFileFlow` must mean the Library has the file's content.

**Import history and the status feed.** Every account holding Import in the Library reads the Library's Import history, whoever delivered each Import (`routes/web/partial/ImportHistoryController`: `ImportService.history`, then `filesShown` for one Import's files).

- `shown` is clamped between a step and a maximum (`Const.ImportHistory`), so neither list is read whole. Every open Import page re-reads the history as Imports open and close, so `ImportDao.list` reads the few in progress by the partial index `import_03` and the closed ones off `import_01` from the newest end: a read costs the Imports it shows (`ImportServiceTests` checks the plans).
- It is kept live over the Library's WebSocket, `/import/r/:repoId/status` (`ImportController.pipelineStatus`; its handshake: **Request Lifecycle**). `ImportService` tells its listeners of an Import only after the commit that changes it (`changed`, `TransactionManager.afterCommit`), reading it then, so a rolled-back change is told to nobody; changes committed at once may be told out of order.
- `ImportStatusWsActor` drops a state no further along than the one it has (`progress`), pushes an Import at most once per `PUSH_INTERVAL` (1 s), and pushes its close at once as the last message, remembered a minute so a late change is not pushed after it. The message is JSON as `hx-ws` takes it (`statusMessage`); its includes take the Import as a parameter and read no request context, since the actor has none.
- A change to what a Library's Watch folders show is its own message, `{"watchFolders": true}`, which swaps nothing and makes the page read the cards again.
- `ImportStatusWsActorTests` (unit suite) drives the actor's time with `ExplicitlyTriggeredScheduler`. The front end: **Import page** in `views/AGENTS.md`.

## Watch folders

A **Watch folder** (`CONTEXT.md`) is a directory on the server that the app scans for one Library, importing the files that arrive in it; it is never a folder of the Library. It is the tables `watch_folder` and `watch_folder_file` (its memory of each file of its directory), written through `WatchFolderService` (`Altitude.service.watchFolder`) alone. A file is only ever copied out of the directory, and deleted from it only when the Watch folder has `deletes_imported`. The service's docstrings (`add`, `update`, `scan`, `walk`, `remember`, `take`, `settled`, `deleteSource`) state each rule in detail; what follows is what spans files and the traps.

**Configuration and the path rules.** `add`, `update`, `remove`, `pause`, `resume` and `retryFailed` are Admin-only (by their routes), each one transaction; the context account becomes the owner on add and on every edit. `validated` refuses with a `ValidationException` naming every refused field.
- `pathProblem`: an absolute, existing, listable directory (writable when deleting) that overlaps neither one of the app's own directories nor another Watch folder in any Library, compared by real path.
- `ownDirectories` resolves each own directory on its own (any may be a symbolic link out of the data directory), and `OwnDirectories` also compares by identity (file key, or `Files.isSameFile`), ancestors included, so a second path no link explains (a volume mounted twice) is refused too.
- `add` and `update` take `WatchFolderDao.lockPaths()` (advisory lock) first, so the second of two concurrent overlapping adds sees the first's row (`WatchFolderServiceTests`, `contend`). `update` and `resume`, which may make the acting Admin the owner, then share-lock that account (`UserService.lockActor`) before they write the Watch folder's row, so a write of that account takes its turn with them, and refuse it (`ForbiddenException`) when it is no active Admin by then: deactivated, deleted or demoted meanwhile (**Lock order**; `WatchFolderServiceTests`, on PostgreSQL).
- Switching deletion on sets `handled` files back to `seen`, so each is re-checked against the Library before it is deleted: nothing is ever deleted on the memory's word alone. A path change forgets the memory.
- `remove` cascades the memory only: the files stay, and its Imports stay in the history (`import.watch_folder_id` is `ON DELETE SET NULL`).

**Scanning.**
- `App` calls `start()` after `imports.startup()`, so a scan's Import is never failed as one a stop interrupted. It scans every unpaused Watch folder at once (catching up on the downtime), then every `watch_folder.scan_interval` minutes (Live Setting), each round scheduled by the previous one with the Setting as it is then. A failed round is logged and the next still comes. `start` takes the scheduler as a parameter so tests drive the rounds.
- `stop()` is the first step of `Altitude.cleanup`, before the import queue closes.
- `scan(id)` runs on the import dispatcher, one scan per Watch folder at a time, and returns a `ScanResult` once its last file is offered. A `Blocked` scan never touches the memory. `remember` writes the Watch folder's row (`last_scan_at`) before its files', as an edit and a removal write it first, and a Watch folder removed during the walk ends the scan as `Blocked(REMOVED)` with nothing remembered (`WatchFolderServiceTests`, on PostgreSQL). An owner who is no active Admin makes the scan pause the Watch folder. An unavailable directory (fails the path rules now, or the walk meets an own directory) is stored as `status_reason` and cleared by the next scan that walks it.
- `walk` follows no symbolic link, skips `util/IgnoredFiles` names, empty and non-regular files. It goes on past an unreadable directory: `postVisitDirectory` is overridden because the default throws and would end the scan. Those directories become `status_reason` (`Walked.problem`) while the rest is imported.
- The walk never enters an own directory, recognized by file key (`OwnDirectories.has`) under whatever path: it stops, nothing found is remembered or read, and the reason is `PATH_HOLDS_DATA`. This catches a store inside the watched directory under a second path, which the path rules cannot see from outside.
- The memory keys a file by `rel_path` plus size and modified time, in a `WatchFileState`. A changed size or modified time makes it a new `seen` file with no attempts, whatever became of it before.
- A `seen` file is read once it has rested: `last_seen_at` at least `REST` (`Const.WatchFolder.REST_SECONDS`) before this scan's walk began, so two quick "Scan now" presses do not shorten it.
- `remember` reads `inFlight` (in memory, files in the pipeline) before the rows on purpose: a file leaves `inFlight` only after its row is written, so one that settles between the two reads is not offered twice.
- A file found unchanged is re-stamped only once its stamp is a day old (`LAST_SEEN_STEP`), so an idle scan writes only `last_scan_at`.
- `take` runs as the Watch folder's owner with every Permission, copies with `LinkOption.NOFOLLOW_LINKS`, never moves the file (its source is the retry), and offers it with `ImportOrigin(importFileId, <folder names>, source = <the file>)`. Offers wait for the queue's backpressure without holding an import-dispatcher thread, which the stages need to drain the queue.
- The scan's Import is opened by its first file (`ImportSource.WatchFolder`) and marked complete after its last offer, so a scan with nothing to read opens none. Before each file the scan ends if the Watch folder is not as it read it (removed, paused, edited, destination in the Trash). An unreadable file counts as an attempt; a queue refusal counts none and ends the scan.

**The pipeline's end.** `SettleImportFileFlow` calls `settled(origin, asset, cause)` after the Import file's settle has committed; a failure there is logged at ERROR and leaves the memory as it was. The memory is written only while the file is remembered as staged:
- `handled`: imported, or a duplicate of an asset whose own import is complete.
- `final`: unsupported or undecodable; and a duplicate that is the matched asset's own stored file under another path (`isStoredFileOf`: a hard link, or the store through a second mount; an I/O error counts as a match), so it is never `handled` and never deleted.
- Untouched, for a later scan: a failure that is the Watch folder's, not the file's (`ImporterUnavailableException`, a destination in the Trash), and a duplicate of an asset not yet complete or gone.
- Otherwise one more attempt, `parked` at `MAX_ATTEMPTS`.

**Deletion.** `deleteSource` runs only after the write that made a file `handled` has committed.
- The file must still be the one read: under the directory's current real path, below no symbolic link, a regular file with its staged size and modified time. Anything else stays.
- A file in or below an own directory, by identity (`OwnDirectories.at`), is never deleted, whatever path led to it.
- Emptied directories are removed up to, not including, the watched directory, stopping at a non-empty one (an ignored file counts) or a symbolic link.
- A failed delete is logged at WARN; the file stays `handled`.
- A paused Watch folder deletes nothing and leaves the memory as it is, so the file is read and deleted after resume.

**Status and owner.**
- `cards()` builds the Import page's cards. "Paused while the destination is in the Trash" is computed by `statusOf`, never stored, so it clears when the folder is restored or replaced. Counts come from `ImportDao.countsByWatchFolder` (index `import_02`).
- `targeting(folderId)` feeds the folder Delete dialog's warning (`FolderActionController`); `fileCount(path, self)` feeds the Watch folder dialog's deletion notice.
- The owner owns the imported assets, so it must be an active Admin: demotion and deactivation pause its Watch folders in every Library (`pauseOwnedBy`), deletion passes them to the deleting Admin (`passOn`; `watch_folder.account_id` has no delete action), and `resume` gives an orphaned one to the resuming Admin (**Account management**).
- `ImportService.prune` calls `forgetAbsent`, which forgets files absent for as long as an Import is kept (`FORGET_AFTER_DAYS` when the history is kept forever), never those the last scan found, so an unscanned Watch folder forgets nothing. The memory is its own table, so pruning an Import never makes a file new.
- `onChange` notifies after commit of any change a card shows, including scan start and end; the status feed passes it on (**Import history and the status feed**).

**Routes.** `routes/web/partial/WatchFolderController`, under `/htmx/watch-folders/r/:repoId`.
- `GET list` serves any holder of Import, with card actions for an Admin only; the Import page renders the cards itself (`ImportController.pipeline` via `WatchFolderController.list`). Every other route is `@requireAdmin`.
- `PUT scan` answers 204 once the scan has started, 409 when paused or the destination is in the Trash.
- A refused field re-renders the form through `dialogFormValidationResponse`. "Keep folder structure" with no folder is refused by the controller (`DESTINATION_REQUIRED`), which sends a destination to the service only with that switch on.
- A Watch folder ID is a UUID or a 400; one not in the Library is a 404.
- The front end is in `views/AGENTS.md` (**Import page**).

## Library stats and purging

`StatsService` keeps six counters per repository in `stats`: assets and bytes for sorted, triage and recycled (the nav's Triage and Trash counts). An asset counts from `LibraryService.completeImport` until it is marked for purging, in one bucket: recycled, else triage, else sorted (an asset recycled from triage keeps `is_triaged` but counts as recycled). `StatDao.reconcile` must bucket the same way.

- Library operations (recycle, move, restore, purge) write stats only through `StatsService.transition(before, after)`: one `adjust`, deltas applied in dimension-name order so concurrent operations lock stat rows in one order on PostgreSQL. `CHECK (dim_val >= 0)` makes a write below zero, or to a missing dimension, a `ConstraintException` that fails the operation.
- They read the rows they change through one locking select (`AssetDao.lockAssets`, behind the `getAssetsTo*` methods, `lockCompleted` and `lockSequenceFrames`): completed, not purge-pending, ID order, `FOR UPDATE` on PostgreSQL. Deltas come from those rows and only those rows are updated, so another repository's asset, an unfinished import or two requests for one asset never skew the stats.
- What a move, recycle or restore does to a Sequence is the membership table under **Assignment** in **Sequences and Image quality**.
- A restore and a move out of the Trash leave an asset in the Trash, reported among the `duplicates` of the `RestoreResult` both answer, when its content is live (`asset_01` holds one live copy of a content) or leaves earlier in the same operation, in ID order (`LibraryService.leavingTheTrash`, which reads the live contents in one statement, `AssetService.liveChecksums`); the rest go on. The move route answers that result as the restore route does (`BaseController.restoreResponse`).
  - Both take the tree's turn first (`FolderService.lockTree`), so of two restores or moves of copies of one content the second reads what the first left live, where on PostgreSQL both would read none and the second fail on `asset_01`.
  - An import takes no turn with them: a copy it inserted but had not committed when the live contents were read makes the write fail on `asset_01` once it commits, and the operation is refused whole with an `IllegalOperationException` (`CONTENT_IMPORTED_MEANWHILE`, a JSON 400 the snackbar shows), after which a retry leaves that asset as a duplicate. An import that loses the other way gets the `DuplicateException` of any duplicate.
  - Tests: `LibraryServiceRestoreTests` (both engines; the two-thread cases red on PostgreSQL without the turn and the refusal), `AssetControllerTests`.

**Purging.** `LibraryService.markForPurging` sets `is_purged` and takes the assets out of the stats; the asset is then **purge-pending**: out of every library operation and hidden from the trash view (`SearchRequestParser`). After the commit, `PurgePipelineService.enqueue` feeds the purge queue, which moves covers off the asset's Faces (`PersonService.moveCoversOff`), then deletes face files, asset files (`FileSystemStoreService.purgeAssetById`, edited images included) and the row (`LibraryService.deletePurgedAsset`), which cascades to its Faces and its Edit (**Image edits**), and in the same transaction the unnamed people it left with no Face; a named person keeps their row and name with no Face (**People** in [docs/faces.md](../docs/faces.md)). Edited images, like Previews, count in no stat.

- When the covers cannot be moved, the asset stops there, logged at ERROR, purge-pending with its row, files and Faces: deleting the row would null the cover (`ON DELETE SET NULL`) with no repick and lose the cover Face's files.
- A failed row delete is logged at ERROR and stays purge-pending; the queue goes on. Startup requeues both.

**Startup.** `App.scala` runs, in order: `ImportService.startup()` (**Import records** under **Import Pipeline**) before anything reaches the import queue; `pruneDanglingAssets()`; `requeuePurgePending()` and `EditRenderService.requeuePendingRenders()`, with no account (no request queued them, and a Library has no owner to stand in); `reconcileStats()`; and last `WatchFolderService.start()` (**Watch folders**), so no scan's Import is mistaken for an interrupted one. The steps before it run per repository through `LibraryService.forEachRepository`, which opens no transaction, so each operation's file deletes follow its own commit. `StatDao.reconcile` locks the stat rows in write order before counting, so a concurrent operation has either committed or adds its delta to the corrected value.

Around those tasks, in `App`:

- First of all `TempFolder.prepare()` empties the JVM's temp folder, where it is the server's own: only with the `altitude.tmpdir.own=true` system property, which the image passes with a temp folder of its own (**Packaging** under **Build & Test Commands**). Anywhere else the temp folder is the system's shared one and nothing in it is touched.
- Before anything is built, `LogSettings.requireValid` refuses an unknown logging variable (**Logging** in **Config & Environments**); then `NativeLibraries.prepare()` points ONNX Runtime, sqlite-jdbc and sqlite-vector at the native jar's libraries unpacked into the per-user cache, before any of them loads (**The native jars** under **Packaging**; it does nothing elsewhere); then OpenCV and all of FFmpeg's libraries load (`FFmpegFrameGrabber.tryLoad()`, so a system library they link that is missing fails the start rather than the first Video), `new Altitude()` runs its constructor (**Architecture Overview**), and the stop's cleanup is registered at once (`ServerShutdown.registerCleanup`), so a stop during the tasks cleans up too (**Shutdown**).
- After them `App.main` builds the HTTP server on `server.host` and `server.port`, registers the stop's tasks of the requests and starts it, so no request arrives before the tasks are done, the model download included. When a stop began meanwhile, the server is not started.
- **A start that fails ends the process.** `App.main` catches whatever the start throws (the instance's constructor, a startup task, the server's bind), logs one ERROR line, `Altitude could not start: <the reason>`, with the stack trace, and exits with status 1. On Linux, where OpenCV or FFmpeg could not load GTK 2, ALSA or XCB (`libgtk-x11-2.0`, `libasound`, `libxcb`, …), which bytedeco's libraries link and a headless server may lack, the reason is the linker's message and the Debian and Ubuntu packages to install, under both their names (`SystemLibraries`, `SystemLibrariesTests`), which **Linux** in `README-NATIVE.md` lists too. Left alone, a start that fails once the actor system exists would stay up with no server: Pekko's threads are no daemon threads, a container would sit `starting` until its health check's start period ran out, and no restart policy would fire. The exit runs the shutdown hooks, so an instance that was built is cleaned up by the stop's task. A start that fails because a stop is cleaning its instance up is logged at INFO and exits with the stop. `App.altitude` keeps a failed start's failure and throws it to whoever asks again (a test's server never runs `main`): the start is never run twice.
- `server.host` and `server.port` are checked as the instance is built (`Altitude.serverHostOf`, `serverPortOf`), so an empty host or a port that is no port number fails the start before a database is opened or a model downloaded, naming its variable. An address that cannot be bound fails last of all, naming the address.
- Tests: `AppStartTests` (unit) runs `App` as a second JVM (`ChildJvm`, `altitude/test/src/altitude/test/`; `ChildJvm.start` leaves it running for a test that stops it, and a kill reaches every process it started).
- `logStart` then logs the address, the Data directory, the Models directory and the time zone, a WARN while `server.secure_cookies` is false, and a WARN while no Admin exists, which names the address and says its first visitor runs Setup.

**Shutdown.** `ServerShutdown` adds three tasks to Pekko's coordinated shutdown: the last one as soon as `App` has built its instance, before the startup tasks (`registerCleanup`), and the two of the requests from `App.main`, once there is a server (`registerRequests`). Pekko runs it from a JVM shutdown hook, so a SIGTERM, a Ctrl-C and a container's stop all stop the server this way:

| Phase | Task |
|---|---|
| `service-unbind` | The `GracefulShutdownHandler` in front of every route answers new requests 503. |
| `service-requests-done` | The requests under way get `ServerShutdown.REQUESTS_GRACE` (10 seconds) to finish. |
| `service-stop` | `Altitude.cleanup()` (its order: **Import Pipeline**), then Undertow, when `main` has built it, and cask's execution context stop, also when the cleanup fails. |

- A stop during the startup tasks (a large Library's stats, requeued purges and renders) drains and closes like any other: the cleanup's task is registered before them, and the tasks then fail or finish on an instance that is cleaned up, which the next start puts right. For that the start is not in `App`'s initializer: a thread that calls into a class still initializing waits for its initializer, and the task's functions are `App`'s, so the stop would drain nothing until the startup tasks had ended. They take the local instance, never `App.altitude`, for the same reason. A stop that began during the start leaves the HTTP server unstarted (`ServerShutdown.hasBegun`).
- `App.main` builds Undertow itself, over the handler around `defaultHandler`, and never calls cask's `main`: cask registers a shutdown hook of its own that stops the server at once, beside these tasks. Undertow's `SHUTDOWN_TIMEOUT` (`SERVER_STOP_TIMEOUT`, 5 seconds) keeps a request still held from hanging the stop.
- The phase timeouts (15 seconds for `service-requests-done`; 10 minutes for `service-stop`, a backstop, since `cleanup()` bounds itself by `pipeline.shutdown_timeout` for each of its three queues) are set in the config overlay the actor system is built with in `Altitude.scala`, not in `reference.conf`, whose order against Pekko's own `reference.conf` is not fixed. Pekko's default of 5 seconds would cut both.
- A task's blocking work runs on a daemon thread of its own (`onOwnThread`), never on Pekko's dispatcher, and a hung stop cannot keep the JVM up. The task ends whatever its work ends with, an `Error` included, so no phase waits out its timeout for a thread that is gone; and the server stops after a cleanup that failed with anything at all.
- `cleanup()` does not terminate the actor system, which the queues run on: the coordinated shutdown does, in a later phase.
- Whatever stops the process must allow three times the Pipeline shutdown timeout Setting plus 30 seconds. The Setting's help text says so, and `compose.yaml`'s `stop_grace_period` (120 seconds) is that sum at the default of 30: change the three together, with **Stopping** in `README-DOCKER.md` and **Stopping the jar** in `README-NATIVE.md`.
- ONNX Runtime registers a shutdown hook too, which releases its environment while the drain still embeds: `OnnxEnvironment` holds it alive (**Scene embedding** under **Sequences and Image quality**).
- Tests: `ServerShutdownTests` (both engines; a second instance behind a real server, stopped as a SIGTERM stops it). `scripts/smoke-docker.sh` stops the image mid-import and `scripts/smoke-jar.sh` stops a platform jar through its launcher; they read the log lines of `ServerShutdown`, `QueuedPipeline`, `ImportService`, `NativeLibraries`, `SceneEmbedder` and `App` by their text, so rewording one of them breaks them. That holds for the lines they must not find too (`forbid_own_line`, in `scripts/smoke-common.sh`): each is first looked up in a string of `altitude/src`, since a text no source logs is absent from every log. The image's stop mid-import is a race against the machine, so that import grows with the cores and the step is tried a second time, with other photos, before it fails for its timing.

## Video

A Video is an asset whose `media_type` is `video` (there is no flag column); `LibraryService.SUPPORTED_MEDIA_TYPES` admits `image` and `video`, so audio stays unsupported. `VideoService` decodes through FFmpeg (javacv) with one `FFmpegFrameGrabber` per call, nothing shared across threads, and reads one snapshot of the `video.*` Settings per call from its `() => Settings` supplier (not a `Config`). A file with no real video stream, such as an audio file whose cover art is a one-frame picture stream, is a `VideoException`. In `build.mill` each bytedeco preset is a stub jar plus a `classifier=<platform>` natives jar; appending the platform to the version resolves nothing.

- `probe(path)` gives the display size with the container's rotation applied (a portrait phone recording is stored portrait) and the duration (`asset.duration_ms`: NULL for a still image, the playing time for an animated GIF). `AssetService.getDimensionsAndDuration` dispatches on media type.
- **Sampled frames**: `VideoService.sampleTimes` spaces Frame times evenly at `max(video.faces.sample_interval_ms, duration / video.faces.max_sampled_frames)`, so a short clip is sampled every second and a two-hour recording about every minute. `sampledFrames` yields upright BGR `Mat`s through an iterator valid only inside the call; the consumer releases each one.
- **Preview**: the Preview is a Sampled frame (`previewFrame`, which skips a black leader by `video.preview.min_luminance`). `AssetService.genPreviewData` thumbnails it as an upright image (`makeImageThumbnail`'s `Mat` overload, orientation 1), so the grid and the map treat it as an image's Preview.
- **Faces**: `FaceRecognitionService.detect` detects faces in every Sampled frame (`FaceDetectionService.extractFaces`'s `Mat` overload) and clusters the whole video into Faces; the clustering, support and one-Face-per-Person rules are in `docs/faces.md` (**Videos**), and a Face's tier is under **Faces** below.
- **Dates and places**: metadata-extractor reads MP4 and QuickTime containers into `extracted_metadata`, so the resolvers read persisted inputs only. `CaptureDateResolver` has two Video rungs: `QuickTime Metadata` / `Creation Date` (`qt_creation_date`, below the PNG text chunk; a local wall clock whose offset is discarded like every other), and the container's `Creation Time` (`container_creation_time`, beside PNG tIME, above GPS and the file name). The container time is a UTC instant that the extractor describes in the JVM's zone; `WallClockParser.parseUtcInstant` turns it back into the UTC wall clock, so the stored value never depends on the server's zone. The 1904 epoch is a sentinel. The file-name rung is under **Search results and date grouping**. `GeoLocationResolver` tries EXIF `GPS`, then `QuickTime Metadata` / `ISO 6709`, then `MP4` / `Latitude` and `Longitude`. `Asset.getPublicMetadata` falls back to `QuickTime Metadata` / `Model` for `deviceModel`.
- **Serving** (every asset's content route, not a Video's alone): `ContentViewController` streams a `file` through `RangeStreaming` with byte ranges, typed by the asset's stored `mime_type`. A player drops the connection whenever it has enough, so a client gone mid-stream ends the response at DEBUG; a failure to read the file stays an error. `preview` and `display` take `v`, the edited images' revision (**Image edits**).
  - One route, two gates (`requireLoginOrSignature`, see **Request Lifecycle**): the logged-in UI builds plain URLs, and a signed URL reaches the same content through the same code. The endpoint declares `exp` and `sig` only because cask answers an undeclared query parameter with a `400`.
  - Every response that serves an item, an original's `206` and `416` included, is `Cache-Control: private, max-age=31536000, immutable` (`withContentHeaders`); an edited image's redirect and miss are `no-store` (**Edited images and caching**). This is safe only because a content URL's bytes never change for a page that builds it: a Preview and a face image are written once, an original is unique by checksum, and each edit render takes a new revision.
  - Each is also `nosniff` with `Content-Security-Policy: sandbox`: an original is a user's upload served on the app's origin with its cookie, and must never render as a document that acts as the user.
  - `RangeStreaming.contentDisposition` names an original inline in both RFC 6266 forms, so a saved original keeps its name and no file name can inject a control character into the header.
  - `decorators.compress` leaves ranged and image responses unzipped (**Request Lifecycle**).
- **Signed URLs**: `ContentSigner` (`app.service.contentSigner`) signs one item's content path: `sign` appends `exp` (Unix seconds) and `sig` (unpadded Base64URL of `HMAC-SHA256(key, "<path>\n<exp>")`). `verify` accepts only the exact spelling `sign` makes, compared in constant time. The key is `system.signing_key`, written by `SystemService.loadOrCreateSigningKey` only while the column is NULL and then read back, so a signed URL survives a restart and two instances starting at once share one key; the PASETO session key stays per process. The decorator never logs `sig`, nor the decoded path, which could forge a log line. No code issues a signed URL yet (`sign` is called from tests only; share links are open in `docs/READINESS.md`). `ContentSignerTests` pins the signature to a known answer computed with `openssl`, so an issued link survives any refactor.
- **Playback**: asset detail plays a Video in a media-chrome player, started as it is shown; see **Detail navigation** in `views/AGENTS.md`.
- **Tests**: `TestVideos` synthesizes short MP4s from the `people/` images at test time, with a display rotation or container metadata on request, so no video binaries live in git. Suites: `VideoServiceTests`, `AssetImportServiceTests`, `FaceRecognitionServiceTests`, `ContentSignerTests`, `SystemServiceTests` and `StartupTests` (the stored key), `ContentViewControllerTests` (ranges, both gates, error answers, content headers) and `RangeStreamingTests` (a client gone mid-stream, a missing file, `Content-Disposition`).

## Faces

[docs/faces.md](../docs/faces.md) is the faces guide (detection, recognition, Videos, storage, people, corrections, the Settings table); read it before working on faces. This section keeps only the rules that reach past the face code.

A Face is a YuNet detection, its aligned 112 px crop and its ArcFace embedding (`FaceDetectionService.extractFaces`). Its **quality** (`face.quality`, the glossary's Face quality) is the raw embedding's norm before L2 normalization: it drops with blur and occlusion and costs nothing extra. Every `face.*` key is a Setting (`models/Settings.scala`; the help text holds the measured quality ranges) except `face.debug.enabled` in `reference.conf`, which labels every crop with its quality for calibrating the thresholds.

Quality decides a Face's **tier**, stored at import as `face.is_enrolled`, so changing a threshold never re-tiers stored Faces:

- **Enrolled** (quality at least `face.quality.enroll_threshold`): may start a Person and is a recognition candidate.
- **Match-only** (at least `face.quality.keep_threshold`, or a Video cluster with too little support): may join an existing Person, never starts one, is never a candidate. Matching nobody, it is not stored (`FaceRecognitionService.assign` gives it no owner).
- Below `keep_threshold`, `extractFaces` drops the detection after the debug dump.

Recognition is a vote of the nearest enrolled Faces of people who are neither a bad match nor merged away, in the context repository; hidden people stay matchable. An asset's recognition votes first and locks the people the vote gives a Face to, in ID order and under a savepoint (`TransactionManager.undoingIf`), before it stores its first Face, as every transaction locking people locks them; one that finds a Person gone gives the locks back and takes them again (**Recognition** in the faces guide). The service reads the Settings and passes them to `FaceDao.searchClosestFaceMatches`: no DAO reads a Setting. The SQL is hand-written per engine. PostgreSQL uses `face_03`, a partial HNSW index on `features::halfvec(512)`, so the search is approximate. SQLite uses `vector_full_scan`, an exact scan: sqlite-vector's quantized scan misses rows added since the last quantize, such as the previous Face of the same image.

`face_01` makes a crop's checksum unique within its asset, not the repository, because two assets can share a byte-identical frame. The same crop twice in one asset is a `DuplicateException`, which `RecognizeFacesFlow` reports as `SamePersonDetectedTwiceException`.

`FaceDetectionService` holds the networks; its comments and `util/ImportParallelism` carry the memory and throughput measurements.

- YuNet is one `FaceDetectorYN` per thread (`yuNetLocal`), since the detector carries per-call state.
- ArcFace is one shared `Net` (`arcFaceNets`, a `util/NetPool` of `ImportParallelism.ARCFACE_NETS`, Winograd off to halve its memory). A `Net` is not thread-safe: `getArcFaceEmbedding` borrows it for one forward pass and copies the output inside the borrow, because the next borrower's pass overwrites it. Never borrow inside a borrow; the pool would deadlock. `ImportParallelism.POOL_COST` budgets 384 MB a net.

## Sequences and Image quality

The terms are the glossary's (`CONTEXT.md`). [docs/curation-batch-detection.md](../docs/curation-batch-detection.md) tells the whole feature as a narrative, with its UX and research notes. The rules for changing it are here.

- A **Sequence** has no table. It is the `asset.sequence_id` its members share (`CHAR(36)`, `COLLATE "C"` on PostgreSQL, partial index `asset_sequence`). So there is no row to lock, date or delete, and a Sequence exists exactly while some asset carries it.
- **Image quality** is five nullable `asset` columns, read through `ImageQuality.fromColumns`, the one rule both DAO mappings use (all five, or `None`). The **perceptual hash** is `perceptual_hash BIGINT` (`PerceptualHash`). Its JSON form is always 16 hex digits, since upickle would write a Long past 2^53 as a string and so change the field's type.
- The **Scene embeddings** are `dinov2_embedding` and `siglip2_embedding`: `vector(768)` on PostgreSQL, a BLOB of little-endian float32 on SQLite. Their model is `models/SceneEmbedding.scala`. A `SceneEmbedding` is L2-normalized, compares by `similarity` (the dot product), and is equal by its values, since a case class compares an array by reference. Both models give 768 floats, so only the field per model in `SceneEmbeddings` keeps their vectors apart. Embeddings of different models never compare.
- The **Histogram** is `asset.histogram` (`models/Histogram.scala`). `toBytes` and `fromBytes` give the column's value on both engines. `relativeBytes` is what a view draws, with the four channels on one scale. **Face sharpness** is `face.sharpness`.
- All of these are NULL together for a Video, an animated image, or a still image the pipeline did not measure. A single embedding is NULL when its model could not embed the image. `AssetDao.markAsCompleted` writes all of them together with the completion flag, in one statement, and refuses an embedding of the wrong dimension count. So an asset is never complete without its metrics.
- **Bulky columns stay out of general reads.** The embeddings (a few KB a row) and the Histogram are not in `AssetRow`, so `getById`, `queryRecords` and the search statements never carry them.
  - Only the two Sequence candidates statements select the embeddings (`AssetDao.candidateColumns`).
  - Only `AssetDao.getHistograms` selects the Histogram. It feeds `CurationFrame.histogram`, which the stage's strip draws and `CurationRule` never reads.
  - Every statement that names asset columns takes them from `AssetRow.columnList(BulkyMetadata.Kept | Omitted | AsNull)`. `public_metadata` stays in every form, because the Sequence rule reads the device model from it.
- **SQLite column order is a cost rule.** A SQLite read walks the overflow pages of every large value stored before the column it wants. So the columns run in this order: the metadata JSON that general reads select, then the Histogram, then the embeddings, and `extracted_metadata` last. A new bulky column follows the same rule.
- No vector index serves the Sequence rule: it compares the frames in Scala. `asset_describe` is the Describe search's index (**Describe search**).

**Measurement.** `MeasureImageFlow` (its place among the stages, and why: **Import Pipeline**) calls `AssetService.measureImage`, which measures only `Asset.isStillImage` assets. It decodes the staged file and runs `ImageMeasurement.measure` and then `app.sceneEmbedder.embed` over the same `Mat`, with the faces from `AssetWithData.detectedFaces` (no database read). `completeImport` stores the results and assigns the Sequence, both in the completion transaction. `core/util/ImageMeasurement.scala` is pure, and its scaladoc defines the metrics, the Histogram, the hash and the score. What the code does not say:

- `ImageUtil.matFromBytes` applies the EXIF orientation when OpenCV decodes the file, so a Face's box is in upright pixels. Its ImageIO fallback, for a format the bundled OpenCV cannot decode (GIF among them), does not. `asset.width` and `height` come from the file's header and can be swapped.
- `MEASUREMENT_BOX_SIZE` (1280) is a code constant. It is not the Live `face.detection.bounding_box_size`, although it equals that Setting's default, because the score is calibrated against it: a Setting would silently rescale every later score. All the constants are calibrated on the `people/` fixtures. Changing one is a code change and means measuring the library again.
- `sharpness` is always the whole frame's, so two images compare on it whatever faces they hold. A Face's sharpness (`None` under `MIN_FACE_AREA_PX`) falls as the face fills more of the frame. So it compares only between Faces of one Person at a similar size, and an absolute threshold on it means nothing.
- The score reads the sharpness of the face boxes' union when that union clears `MIN_FACE_AREA_PX`, and the whole frame's otherwise. That input is not stored, so two scores do not compare, and no reader ranks frames by score.
- A failed measurement does not drop the asset (**Failures** under **Import Pipeline**).

**Scene embedding.** `util/SceneEmbedder.scala` holds `SceneEmbedder` and `OnnxSceneEmbedder`, which runs both Scene models through ONNX Runtime (the CPU artifact, whose one jar bundles every platform's natives). The process has one `OrtEnvironment` and one `OrtSession` per model. Sessions are thread-safe, so there is no pool. Each session gets one intra-op and one inter-op thread (`OnnxSessions.open`): the parallelism comes from the import threads, and a dozen passes each spread over every core would thrash.

- **The environment.** `OnnxEnvironment` (same file) owns the process's `OrtEnvironment`: both embedders take it from `OnnxEnvironment.get`, never from `OrtEnvironment.getEnvironment`. It does two things the API alone does not.
  - **Telemetry off.** ONNX Runtime's official builds send usage telemetry to Microsoft unless `ORT_DISABLE_TELEMETRY=1` is in the process's environment before the native library initializes; the API's own switch, which `get` also turns off, comes too late for the device ID and the first event. `forkEnv` in `build.mill` sets the variable for every JVM Mill forks (`run`, `runBackground`, `runMain`, the test workers) and the `Dockerfile` for the image. The native jar's launcher starts the JVM once more with it where it is missing (**Packaging** under **Build & Test Commands**). A JVM started any other way (a test run from an IDE, the thin jars by hand) needs it in its own environment, and a start without it logs a WARN naming it.
  - **A second reference** (`retain`). ONNX Runtime's shutdown hook releases the environment as a stop begins, while `Altitude.cleanup()` still embeds what the import queue accepted, and a pass on a released environment fails or takes the JVM down. The native environment counts its references, so `retain` takes one more and never gives it back. The API offers no way to, so it calls `OrtEnvironment`'s private `createHandle` by reflection, with `OnnxRuntime.ortApiHandle` and `nativeHandle`; if an ONNX Runtime version renames them, the embedders fail to open, and so the start, naming the version. After an ONNX Runtime upgrade, run `OnnxEnvironmentTests` (its shutdown hook test runs a child JVM) and `make smoke-docker` (its stop mid-import right after a start).
  - The face models are not involved: YuNet and ArcFace run in OpenCV's DNN module.
- **Lifecycle.** `Altitude` takes `newSceneEmbedder` (`OnnxSceneEmbedder` by default, `SwitchableSceneEmbedder` in tests: **Scene models in tests**). It builds `sceneEmbedder` before the services, so a model that fails to open fails the start and never an import. An import without embeddings would fall back to the hash silently. `Altitude.cleanup` closes the embedder after the import's drain, whose threads run the sessions. A drain that ran out leaves those threads embedding, and `OrtSession.close` frees a session at once, under a pass still running on it (a SIGSEGV in ONNX Runtime's library). So `OnnxSceneEmbedder` guards its sessions as `OnnxDescribeEmbedder` guards its tower: an image's passes hold a read lock, `close` the write lock, so it waits for the images under way, and every image after it is refused with `SceneEmbedderClosedException`. That is no failed pass: `AssetService.measureImage` throws it on, the stage drops the asset, and the file fails as "Interrupted by a restart" (`PipelineUtils.dropReason`), where an image stored with no embedding would stay so for good.
- **Fits.** Each model fits the image by its own `SceneFit`. DINOv2 uses `CenterCrop`: the short side scaled to 224, then the center square. This transform is the project's own, not the checkpoint's reference one. SigLIP 2 uses `Squash`, as its checkpoint's processor does: the whole image to 256 × 256, aspect not kept, so a wide frame's edges stay in view. `export-models.py` of `renegade-otter/altitude-models` checks the models on these same fits, and the similarity thresholds are calibrated to them. Changing a fit therefore means calibrating again. `SceneEmbedderTests` pins DINOv2's square by its SHA-256.
- A model that cannot prepare the image, or whose pass fails, gives no embedding (WARN), and the other model's embedding stands. A closed embedder is the one refusal (**Lifecycle**, above).
- The models are `SceneModel.file` (**Model files**). Their memory is `SCENE_MODELS_COST`, and the `ImportParallelism` scaladoc has the measurements; `session.disable_prepacking` is deliberately not set.
- **Calibration** on `BurstFrames`: the burst's frames score 0.98 to 1.00 by either model, and the far picture about 0.25 (DINOv2) and 0.58 (SigLIP 2). A half-size copy scores 0.99, so only the size test keeps it out. SigLIP 2 is near-invariant to a mirror (0.99), DINOv2 less so (0.96).

**Description embedding.** SigLIP 2's text tower embeds a description in the space of SigLIP 2's Scene embeddings, so a description compares with a still image by `SceneEmbedding.similarity`. The Describe search uses it (**Describe search**). `util/DescribeEmbedder.scala` holds `DescribeEmbedder` and `OnnxDescribeEmbedder`. `embed` returns `None` only from the test instances' switched-off double. `OnnxDescribeEmbedder` shares `OnnxSessions` with the Scene embedder.

- `OnnxDescribeEmbedder.normalized` collapses whitespace and lowercases, and no prompt goes around the description. The tokenizer tells a tab, a line break and a doubled space from a space. Without the normalization, the same words spaced differently would be different model inputs and different cache keys.
- The model is three model files, exported together and checked against PyTorch: `ModelFile.Siglip2Text`, `Siglip2TokenEmbeddings` and `Siglip2Tokenizer` (**Model files**). The float16 token-embedding table sits outside the graph and is memory-mapped (`TextTower`), because a description reads only 64 of its rows. Inside an fp32 graph the table would take 790 MB of the process's own memory; mapped, its pages are clean and are dropped under memory pressure.
- `SceneModel.SIGLIP2_LOGIT_SCALE` and `SIGLIP2_LOGIT_BIAS` are the checkpoint's constants of the match probability, and the export fails on a checkpoint that holds others. `SceneModel.siglip2Cosine` inverts the formula, and the Describe search's cutoff goes through it.

**The tokenizer.** `util/Siglip2Tokenizer.scala` is the project's own, so the text side needs no native library beside ONNX Runtime. It reproduces the checkpoint's processor (a `GemmaTokenizer`, padded and truncated to `MAX_TOKENS`, 64) after lowercasing. SigLIP 2 was trained on lowercased text, and the reference tokenizer leaves the lowercasing to its caller. The scaladoc lists the steps.

- `lowercase` is Unicode's default conversion. It is `toLowerCase(Locale.ROOT)` except for a capital sigma, whose final form follows Unicode's rule (`isFinalSigma`), not the JDK's.
- The checkpoint ships no SentencePiece scores, only an ordered merge list. The export derives a score per piece and proves that the list is rebuilt from those scores in `Candidate`'s order. A change to that order on either side breaks parity with the reference. The export also fails when the reference tokenizer stops having the shape the Scala one assumes (`check_tokenizer_shape`).

**Loading a description's model.** Nothing loads at startup. `Altitude` takes `newDescribeEmbedder` and builds `describeEmbedder` at no cost, and an import never loads it.

- The first description loads the tokenizer, a `lazy val` that the next description retries if loading fails. It then opens the text tower under the write lock of a `ReentrantReadWriteLock`, exactly once. Every pass holds the read lock. So `close()` (from `Altitude.cleanup`) waits for the passes under way. After it, the embedder refuses every description with an `IllegalStateException`, a cached one included.
- The model files are in place before the start (**Model files**). A file that fails to load therefore fails each description, never the start.
- The last `CACHE_SIZE` (256) embeddings are cached by the normalized text. Two threads asking for one new description both run the tower, and the first embedding stored is kept.
- The costs (about 570 MB resident from the first description on, about 91 ms a pass) are in the class's scaladoc. `ImportParallelism` does not budget them.
- **Tests.** `Siglip2TokenizerTests` and `DescribeEmbedderTests` (unit) hold the tokenizer and the embedder to the reference, against golden files in `test/resources/siglip2/`. The files are tracked. After a change to the descriptions in `scripts/siglip2-golden.py` or to the checkpoint, regenerate them with `uv run scripts/siglip2-golden.py`. The suites read the model files through `TestModelFiles` (**Build & Test Commands**). `StartupTests` covers the wiring.

**Assignment.** `SequenceService.assign(asset)` runs inside the completion transaction. Assets are assigned one at a time per repository, in upload order, so a burst's earlier uploads are already completed candidates.

- **Locking.** An eligible asset first takes `AssetDao.lockSequences()`, as `CurationService.resolve` and `reopen` do. This makes a repository's Sequence writers take turns: on PostgreSQL through an advisory transaction lock per repository, on SQLite through the single write connection. Row locks cannot do it, for two reasons:
  - A write transaction is `READ COMMITTED`, so a frame still completing is in no row that a resolve's `FOR UPDATE` finds until it commits.
  - Each writer picks the rows it locks by a read made before its locks (an assignment's matches, a resolve's Picks), which another writer's changes would make stale.
- The library operations take no `lockSequences`, so each writer locks every row it writes in one pass in ID order, as they do (**Lock order**): an assignment re-reads its matches locked, with every member of their Sequences when they merge (`AssetDao.lockSequenceFrames`); a resolve locks its Picks' Sequences with the frames it recycles (`lockLiveFrames`); a reopen takes the tree's turn and then locks its Picks with the frames it restores (`lockCompleted`). Tests: `SequenceServiceTests` (a recycle of the candidates, and of a member outside the window, during an assignment) and `CurationServiceTests` (a recycle during a resolve, a move during a reopen), each on PostgreSQL.
- **Authority.** `SequenceRule` (`core/util`, pure) decides. Both candidates statements prefilter in SQL with derived copies of the rule. A change to the rule is made in both places.
- **Two kinds of frame.** Both are still images in triage with a hash, and the two kinds never share a Sequence.
  - `isDated`: the capture time comes from the camera's own clock (`CameraClockSources`). The file-name rung counts, because the gap test needs whole seconds and a name gives them. No camera model is needed, since a frame saved out of a messaging app names none.
  - `isUndated`: there is no capture time at all.
  - A time from another clock, such as a container's or a GPS timestamp, makes an image neither kind. Such an image cannot be spaced from a burst's frames and its time was not stripped, so it never joins a Sequence.
- **`matches`** is symmetric.
  - Two dated frames must be within `sequence.max_gap_ms` and on the same camera: both name the same `publicMetadata.deviceModel`, or neither names one. So an original and its metadata-stripped copy are never a burst.
  - Two undated frames match whatever camera either names. A frame stripped of its time is stripped of its camera too.
  - Both kinds also need the same `width` and `height` and `lookAlike`. Under `lookAlike`, any Scene model whose embedding both frames carry is enough when its cosine clears that model's threshold. The hashes decide (`sequence.max_hash_distance`) only when no model embedded both. A pair that a model compared is never rescued by its hashes.
- **Why `matches` works that way.**
  - The hash at any usable distance rejects a reframed or zoomed shot, which the embedding holds under.
  - SigLIP 2's cosines crowd toward 1, so each model needs its own threshold.
  - A portrait and a landscape frame of one scene can embed alike, so the size test stays.
  - Either model's likeness is enough, so a burst one model misses is caught by the other.
- `assign` reads its four Settings from one snapshot per asset.
- **Dated candidates** come from `AssetDao.getSequenceCandidates` (`sequenceCandidatesStatement`).
  - It reads triaged frames within the window, in the trash too, since a recycled frame keeps its Sequence.
  - It lists every calendar day of the window through `dayOf` and probes `is_recycled IN (FALSE, TRUE)`, so that `asset_triage_date_taken` answers it.
  - The read takes no row locks: the matches are re-read locked, as the undated ones are.
- **Undated candidates** come from `AssetDao.getUndatedSequenceMatches(asset, limit)(keep)` (`undatedSequenceCandidatesStatement`).
  - It reads the triaged frames with no capture time at the asset's size, newest imports first, up to the cap. `asset_triage_undated` answers it on both engines, so an import never reads the rest of triage.
  - The rows stream through `BaseDao.collectBySqlQuery` and are kept only when `SequenceRule.matches` holds, so at most the matches' embeddings are held.
  - The read takes no row locks.
- **The locked re-read** (`AssetDao.lockSequenceFrames`, both kinds): only the matches still in triage once locked go on. So a candidate that a concurrent move sorts is left out, and the asset is never stamped alone.
- **The cap** is `Altitude.undatedSequenceCandidates`: `Const.Sequence.UNDATED_CANDIDATES_PER_CORE` (5,000) times the core count, logged at INFO and passed to `SequenceService`'s constructor (tests build their own). A candidate costs about 6 KB to read, and undated frames have no time window. So without the cap, an import's cost would grow with all of triage. A read that hits the cap logs at DEBUG.
- **Joining.**
  - With no match, there is no Sequence: a lone image is never one.
  - When no match has a Sequence, the asset and the matches get a new `BaseDao.genId`.
  - When the matches share one Sequence, the asset joins it.
  - When they are in several, the Sequences merge, since a burst is transitive. `countSequenceMembers` picks the survivor: the most members, then the earliest first capture, then the ID. An empty count starts a new ID rather than failing the import. `repointSequences` moves the other Sequences' members (INFO), all locked by the re-read; a member marked for purging is left as it is.
  - `setSequence` writes only rows still in triage.

| Operation | Effect on membership |
|---|---|
| Move out of triage (`moveAssetsToFolder`, also out of the trash into a folder) | Writes `sequence_id` NULL with the triage flag. A sorted asset never carries a Sequence. |
| Recycle from triage | None. The asset keeps its triage flag and Sequence and stays a candidate. A frame of its burst imported meanwhile joins it, and a restore brings the pair together. |
| Restore | None. |
| Curation's resolve (also Keep all) | Decided per Sequence of the Picks. When the set holds every frame of the Sequence still out of the trash (`lockLiveFrames`, locked in ID order with the frames it recycles), its Picks leave it (`clearSequence`). Otherwise they stay. Recycled frames keep it. A cleared Pick stays a candidate of `assign`. |
| Curation's reopen | Restores the recycled frames (a duplicate stays in the trash with its Sequence) and stamps the Picks back through `setSequence`, so a Pick moved into a folder since stays sorted. |
| Purge, discard of a dropped import, repository delete | Nothing beyond the row's delete. |

The four `sequence.*` Settings are Live and open `SettingGroup.Triage`: `sequence.max_gap_ms` (60000), `sequence.dinov2.min_similarity` (0.80), `sequence.siglip2.min_similarity` (0.90, measured on INRIA Holidays: [docs/curation-batch-detection.md](../docs/curation-batch-detection.md), Working thresholds) and `sequence.max_hash_distance` (10). Both similarity thresholds are always in force, so lowering either one groups more freely. The defaults are starting points to calibrate on real files.

Tests:
- `ImageMeasurementTests` and `SceneEmbedderTests` (unit) assert orderings, never exact values.
- `SequenceRuleTests` (unit) cover each condition both ways.
- `SequenceServiceTests` (both engines) run on `BurstFrames`, which `CurationServiceTests` shares. They seed camera metadata, import through `importNamed` and `importUndated`, cover concurrent moves (`contend`), and check both candidates plans (`SearchPlans.lookupPlanOf`: `asset_triage_date_taken`, `asset_triage_undated`).
- `TestContext.persistAsset` clears any Sequence an import gives a fixture: random images are undated and of one size, so with the Scene models on they would pair. A test that wants Sequences stamps them with `setAssetSequence` (**Fixtures**).
- Not covered: face detection on a grayscale decode. The measurement handles a one-channel `Mat`, but `FaceDetectionService` converts the aligned crop with `BGR2GRAY`, which throws on one, and no fixture is grayscale.

**Curation** (the glossary's Curation set, Pick, Bundle, Contender and Too close to call; the modal is **Curation** in `views/AGENTS.md`) adds no table. The queue and the sets are read from `asset.sequence_id`, and nothing the rule decides is stored. `CurationService` reads each set in one read transaction. Every Curation statement of `AssetDao` takes an `owner`, which is `AssetRules.curatedOwner`: under Curate own without Curate all, an account sees only its own frames (**Accounts and access**).

- `queue()` lists the Sequences with at least `Const.Curation.MIN_FRAMES` (2) live frames, counted over those frames alone. It is ordered by `first_captured_at IS NULL, first_captured_at, sequence_id`. The explicit NULL test is needed because SQLite and PostgreSQL sort NULL at opposite ends; with it, undated Sequences come last on both. The cover is the first live frame in capture order, so a cover is never a recycled frame.
- `countQueue()` drops the cover, since the toolbar reads it after every asset mutation. The queue, its count and a Sequence's frames all read through `asset_sequence`, so their cost scales with the rows that carry a Sequence, not with the library.
- `sequenceSet(sequenceId)` reads a window: the first `Const.Curation.MAX_SEQUENCE_FRAMES` (100) frames in capture order. Sequences chain transitively, so a static time-lapse can be one Sequence of thousands of frames. `getSequenceFrames` sorts and cuts in SQL, in the same order as `CurationRule.captureOrder`; keep the two in step. A full window sets `CurationSet.heldBack`.
- A window holds part of a Sequence, as a selection can. `resolve` decides by the whole membership, so a window's Picks stay in the Sequence and Keep all changes nothing.
- `selectionSet(assetIds)` keeps the IDs that pass `Asset.isStillImage`, the one spelling of that test, and are completed and not recycled. Either set is `None` under two frames.
- `setSizeOf` (the Detail panel's link) and `curatableFrameCounts` (the grouped grid's Curate buttons) count a Sequence's whole live size, past the window.
- A set's read adds each frame's Faces (`PersonService.getFacesOfAssets`, without hidden and bad-match people), its album and Location membership, and its Histogram, then hands the `CurationFrame`s and one Settings snapshot to the rule.

**The rule.** `CurationRule.assess` (`core/util`, pure; the models are `models/CurationSet.scala`) runs whenever a set is read, so a changed threshold applies from the next read. Every list it returns is in capture order: a frame with no capture time last, ties broken by import time, then ID.

| Bundle | Holds a frame when |
|---|---|
| **Poor faces** | One of its Faces' quality is at least `curation.face_quality_gap` below the same Person's best in the other frames. Or, among the frames of its Sequence, a Person found in at least half of them has no Face in it. |
| **Blurry** | A Person it shares with another frame at a similar size (box areas within 2×) has Face sharpness under `curation.blur_ratio` of that Person's best at that size. A frame with no such Person, in a Sequence, is compared on `asset.sharpness` with its Sequence's sharpest other frame, by the same ratio. A frame with neither is never Blurry. |
| **Too dark** | `crushed_shadows` ≥ `curation.crushed_fraction`, or `luminance` < `curation.dark_luminance`. Or, in a Sequence, it is on the dark side of `ImageMeasurement.TARGET_LUMINANCE`, at least `curation.luminance_gap` farther from it than the Sequence's frame nearest it. |
| **Too bright** | `clipped_highlights` ≥ `curation.clipped_fraction`, or `luminance` > `curation.bright_luminance`. Or, in a Sequence, the same gap on the bright side. |

- **Compare only what is comparable.** Across different scenes, sharpness and exposure mostly reflect content, so the Sequence clauses compare only frames of one Sequence. The same-Person tests apply anywhere in the set. Face sharpness and Face quality never compare across Persons. A Person's best is taken from the other frames, since a Person twice in one frame (`twins.png`) is nothing a Pick can tell apart.
- A frame sits under its most serious problem, in table order (`BundleKind`). Its other problems are chips. A `CurationReason` says what is wrong, by how much, and compared to what, and `htmx/curation_set` words it.
- An absolute Too dark or Too bright that holds for every frame cannot be fixed by picking, so it becomes a `CurationNotice` on the set, not a Bundle. An unmeasured frame stops the notice. A notice states each test at its mildest value, so its words hold for every frame.
- **The rule never reads `image_quality`, and the view never shows it.** The rule's only suggestion is a sole Contender (`soleContender`). A set with no Bundle is Too close to call.
- A frame with no metrics is a Contender with a note, and its Faces still count for the others.
- `CurationSet` derives the view's layout (`railFrames`, `openingFrames`, `faceRows`).

The seven `curation.*` thresholds (`blur_ratio` 0.5, `face_quality_gap` 2.0, `clipped_fraction` 0.05, `crushed_fraction` 0.05, `dark_luminance` 0.15, `bright_luminance` 0.75, `luminance_gap` 0.1) are Live Settings of `SettingGroup.Triage`, after the `sequence.*` ones. They are calibrated on real files, so the defaults are starting points.

**A set's outcome.** `resolve(keepIds, recycleIds)` and `reopen(keepIds, recycleIds, sequenceOf)` are the two writes. Each runs as one transaction that first takes `lockSequences` (**Assignment**) and changes membership as the table above says.

- **Refusals.** Both raise `IllegalOperationException` on an empty `keepIds`, or on a `keepIds` that overlaps `recycleIds`. `resolve` also refuses a Pick that is no live asset of the repository, since the set would be recycled with nothing kept. `reopen` also refuses a Sequence given for a frame that is no Pick.
- **Permissions.** Curate own and Curate all apply as **Accounts and access** says (`AssetRules.requireCurate`, `curatedOwner`).
- `resolve` recycles through `LibraryService.recycleAssets`, so the stats count as for any recycle. It answers with each Pick that left its Sequence, which is what `reopen` takes back.
- `reopen` restores through `restoreRecycledAssets`, so it fails as a restore does. An unknown ID is a `NotFoundException` and changes nothing.
- Keep all is `resolve` with nothing to recycle. It dismisses a wrongly grouped Sequence.
- Recycling a Bundle is no call of this service. The client uses the grid's recycle and restore endpoints and reads the set again. A move in the queue's walk never reaches the server.
- Recycling a frame takes it out of its albums and Locations, and a restore does not add it back; the set's footer counts these frames (`inAlbumOrLocation`). Its Faces leave its Person's `num_of_faces`, so an unnamed Person known mostly from a burst can fall under the Matched line.

## Image edits

An asset's **Edit** (the glossary's Edit, Edit panel, Crop tool, Display image and Show original) is every control of the Edit panel at one value, a small JSON object. The server keeps one Edit per asset, replaced by each save; Undo and Redo live in the browser's Edit panel. The original is never written, and the original, its Preview and every import measurement (Image quality, the Histogram, the hash, the Scene embeddings, hence Sequences and the duplicate check) stay the original's; Curation shows the original everywhere, since it judges captures. An Edit adds two **edited images** the server renders: the edited **Preview** (grid, Quick view, map) and the **Display image** (Asset detail). Only a still image outside the trash is editable (`AssetEditService.whyNotEditable`). The Edit's format, geometry, math, validation and renderers are [docs/image-edits.md](../docs/image-edits.md); the browser side is **Edit panel** in `views/AGENTS.md`.

**The Edit.** `models/EditRecipe.scala`, stored as `asset_edit.recipe` and sent as-is by the client. `EditRecipe.parse` (text or `ujson.Value`) is the one way in. An asset is **edited** when its Edit is not the identity (`isIdentity`). The geometry is in the **upright original** (the original turned by its EXIF orientation), as are the Faces' boxes: `AssetService.uprightSize(asset)` swaps the stored size for orientations 5–8, read from the original's metadata (unreadable metadata counts as upright, at WARN; a missing original is `IllegalOperationException`, `ORIGINAL_MISSING`). The client cannot derive it from the stored size, so the server sends it.

**The stored Edit.** `asset_edit` (`models/AssetEdit.scala`). Three counters that must not be confused:

- `edit_version` (`editVersion`): 1 at the first save, +1 per save, never reused; a save names the one it was built on, and `rendered_version` (NULL before the first render) is the one whose images are stored. Not the recipe's `version` key, which is the format's.
- `asset.edit_rev` (`rev` in the state): the revision of the edited images and their URLs' cache key; 0 means none, show the original.
- `last_rev`: the highest revision the asset has used, so none is reused.

An asset never edited has no row and reads as edit version 0 with the identity. The first save inserts the row; the asset's lock, taken first by every save, makes a racing first save wait and then fail as a conflict. Statements are hand-written and scoped to the Library in `dao/jdbc/AssetEditDao.scala`; the engine subclasses only spell "edit version not rendered" (`IS DISTINCT FROM` / `IS NOT`) as the partial index `asset_edit_01` does, so the startup's requeue (`pendingRenders`) uses it. An account's delete leaves the Edits it saved with no author (`ON DELETE SET NULL`).

`AssetEditService` (`Altitude.service.assetEdit`) writes it, each save one transaction built on the edit version the client saw (`base`):

- `save(assetId, base, recipe, account)` normalizes as `parse` does. Equal to the stored Edit: nothing written, the current state answered. Otherwise it stores edit version `base + 1`. A stale `base` is `EditConflictException(state)` carrying the current state; a non-editable asset is `IllegalOperationException` (`EDIT_NOT_STILL`, `EDIT_RECYCLED`).
- The Edit panel saves only on Done, all held changes as one Edit. Revert to original is a save of the identity; the browser's Undo and Redo are further saves.
- The upright size is read before the transaction opens, so reading the original's metadata holds no lock (on SQLite, the one write connection); the save re-checks editability under its locks.
- **One lock order:** a save first share-locks its saver's account (`UserService.lockActor`), whom the Edit's `updated_by_account_id` references, so an account write rewriting the asset takes its turn with it (`AssetEditServiceTests`, on PostgreSQL); then the asset (`AssetDao.lockUnpurged`, `FOR NO KEY UPDATE` on PostgreSQL), then the Edit (`AssetEditDao.getForUpdate`, `FOR UPDATE`). A save, a render's write and a delete of the asset all take the last two in this order, so none waits on another in a cycle (`EditRenderServiceTests`, on PostgreSQL). `FOR NO KEY UPDATE` makes a purge's mark and delete and other saves wait, while the first save's insert (whose foreign key share-locks the asset) does not block on its own lock.
- After commit (`TransactionManager.afterCommit`) the save is queued to render.
- Reads, each an `EditState`: `get` (with the upright size), `status` (without; what the client polls), `editOf(asset)` (Asset detail's; None when never edited). `editOf` re-reads the asset's `edit_rev` and the Edit in one snapshot instead of trusting the caller's `asset`, or a render committing in between pairs a rendered version with the wrong revision.

**Rendering.** `EditRenderService` (`Altitude.service.editRender`) renders on the `edit-render` `QueuedPipeline` (the queue, `stop()`, shutdown order and startup order are **Import Pipeline** and **Library stats and purging**), on its own dispatcher `altitude.edit-render-dispatcher` with `Altitude.editRenderParallelism` threads: a render decodes a whole original in floats, so it is bounded apart from the import.

- `enqueue(assetId)` is debounced per asset (`Const.Edit.RENDER_DEBOUNCE_MS`, each call restarts it), so a run of saves renders once, at the last edit version. A test that renders by hand lengthens `debounce` so the queue never races it.
- One render per asset at a time (a second is queued again): each image is staged under one fixed name.
- `render(assetId)` renders and stages the images outside any transaction, then, with asset and Edit locked, publishes them only if the edit version is the one it read (else `Discarded`, staged files deleted, asset queued again).
- An edited Edit publishes both images under `last_rev + 1` before the commit that sets `edit_rev` to it. The identity, and an Edit whose original is missing or undecodable (`Unrenderable`, not retried at startup), set `edit_rev` to 0 so the asset shows its original; either way the edit version is recorded rendered. The edited images are deleted only after that commit, under the asset's lock and only while `edit_rev` is still 0, so a newer render's images survive.
- A render that throws is retried with doubling delay, up to `EditRenderService.MAX_RETRIES`, then left for the next startup. `renderedOnDispatcher` catches any `Throwable` and always completes the queue's future: a fatal error (an `OutOfMemoryError` on a huge original) must neither hold the queue's slot forever nor reach Pekko's fatal-error handler, which stops the JVM.
- `requeuePendingRenders()` at startup offers every repository's unrendered Edits, with no account. `shutdown()` cancels the delays, `stop()`s the queue and waits up to `pipeline.shutdown_timeout` for renders under way; the rest stays pending for the next startup.

**The renderer.** `util/EditRenderer.scala`, `render(original, recipe, longEdge)`: an 8-bit BGRA `Mat` the caller releases, drawn as **The two renderers** in [docs/image-edits.md](../docs/image-edits.md). The Display image is the result at most `Const.Edit.DISPLAY_LONG_EDGE` on its long edge (never upscaled), WebP at `DISPLAY_WEBP_QUALITY`; the edited Preview is `ImageUtil.makeImageThumbnail` of the same result. Auto-straighten (`AssetEditService.autoStraighten` → `EditRenderer.autoStraightenAngle`, docs **Auto-straighten**) stores nothing and runs on the request's thread in one of `autoStraightenSlots`, a semaphore of `editRenderParallelism` permits separate from the queue, so it never waits behind renders. No free slot is a `BusyException` (503); an undecodable original (`ImageException`) is `IllegalOperationException`, `ORIGINAL_UNREADABLE` (400).

**Parity.** The Edit has two renderers that must draw the same picture: `EditRenderer` and the Edit panel's WebGL2 renderer (`static/js/edit/`). **A change to the geometry or the math is made on both sides, in [docs/image-edits.md](../docs/image-edits.md) and in `test/resources/edit/vectors.json`, in the same change, and both suites pass**; docs **Parity** names the files and suites, what the vectors hold and how to regenerate them.

**Edited images and caching.** One edited image of each kind per asset (`FileStoreService.editedImagePath`: the edited Preview beside the Preview, the Display image under `display/`), replaced whole by each render: staged as `.<name>.tmp` beside it, then renamed over it under the asset's locks; what is staged and not published is deleted (`discardStagedEditedImages`). `deleteEditedImages` deletes the two known paths and their temporary files without listing a directory (on `edit_rev` 0, and in `purgeAssetById`).

- The revision is never reused for an asset, so each render's images get new URLs, which the content route caches for good (**Serving** under **Video**).
- Every asset read carries `asset.edit_rev` (`Asset.editRev`), so a search page needs no extra query. `Util.previewUrl(asset)` is the one Preview URL of the grid and Quick view (`?v=<editRev>` when above 0); Curation's templates keep `Util.contentUrl`, the original's. Map cells carry `MapCell.editRev` (`SearchQueries.mapCells`) for the pin's URL.
- `ContentViewController` serves `preview` with `v` as the edited Preview (without, the original's) and `display` only with `v`. Through `AssetEditService.editedImage`: `v` equal to `edit_rev` is the stored image; below it, an uncached (`no-store`) 302 to the current `v` that keeps a signed URL's `exp` and `sig` (they sign the path alone); above it, or 0, an uncached 404, since a later render may store other bytes there. No cache may ever keep current bytes under a revision that named others.
- A render publishes before its commit, so the current `v` may briefly serve the newer images (harmless); a failed commit leaves them so until the retry.
- A Guest's request reads the asset to refuse one Browse does not show (`visibleOnly`), as for the original.

**Routes.** `routes/api/EditController.scala` (`/api/edit/r/:repoId/asset/:assetId`), every route `@requireLogin() @requirePermission(Permission.EditImages)` in `answeringJson`: an unknown or other Library's asset is a 404; a refused Edit or body (`EDIT_WHOLE_NUMBER`, `EDIT_RECIPE_REQUIRED`) or a non-editable asset a 400.

| Route | Answer |
|---|---|
| `GET …/asset/:assetId` | The state (`stateJson`), with the upright size |
| `PUT …/asset/:assetId` | Takes `{base, recipe}`: the new state, or a 409 `{error, state}` (`EDIT_CONFLICT`) on a stale `base`, which the client adopts |
| `GET …/asset/:assetId/status` | `{editVersion, renderedVersion, rev}`, polled until the edit version is rendered |
| `GET …/asset/:assetId/auto-straighten?recipe=` | `{angle}`, null when no lines agree; 400 for an undecodable original, 503 `{error}` when every slot is taken |

Asset detail's fragment and JSON (`AssetActionController.showAssetDetailModal`) carry `edit` (`EditController.stateJson`) when the asset has one, `editable` (holds Edit images and `whyNotEditable` is empty) and, for a holder of Edit images, `editRefusal` (the Edit toggle's title); the fragment also carries the measurement's clipping levels and box for the Edit panel's Clipping blink. ## Models

- A model (`core/models/`) extends `BaseModel`; most are case classes whose companion carries a `JsonCodec` reader/writer and a `Conversion[ujson.Value, _]`, as `Folder.scala` does. `JsonCodec` writes snake_case keys.
- DAOs build models from rows (`makeModel` for a hand-written read, its typed twin `toModel` for a ScalaSql one; the two must agree), so services and DAOs exchange models, not JSON. A JSON API of another shape (camelCase, a derived field such as the folder tree's `isRoot`) builds its `ujson.Obj` by hand in the controller.
- `FolderService.getTree` assembles the tree, recursive `numOfAssets` included, in memory from one folder read and one grouped count (`SearchQueries.folderCounts`, answered from the capture-day index alone); `FolderController` only serializes it.
- `BaseDao.updateById` / `updateByQuery` take an untyped `Map[String, Any]`, bound by `Columns.literal`: scalars, plus an `Option` for a nullable column in a `SET` (`None` renders `NULL`). Never put `None` in a `Query`: its predicate (`DynamicFilter`, shared by `deleteByQuery`) would render `= NULL`, which never matches.

## Names

Every name the app keeps unique is compared under its **name key** (`CONTEXT.md`), and only `altitude.core.util.NameKey.of(name)` computes it. The key folds letter case in any script ("Straße" and "STRASSE" are one name) and canonical and compatibility Unicode forms (macOS decomposed accents, a full-width "Ａlbum"), but not accents ("Émile" and "Emile" are two names). It is the same on both engines and under any JVM default locale; `NameKey`'s scaladoc gives the formula and why each step is there. A name is stored and shown as `NameKey.normalized(name)`: NFC, compatibility forms kept.

The keyed names, each under a unique index on its key:

- Instance-wide: an account's email address and username (`account.email_key` under `account_01`, `account.username_key` under `account_02`; **Accounts and access**) and a Library's (`repository_01`; **Libraries**).
- Within a repository: a folder's among its siblings (`folder_02`), an album's (`album_01`), a Location's or Category's in one shared pool (`location_01`), a metadata field's (`metadata_field_02`; `UserMetadataService.addField` also checks before its insert), and a live Person's (`person.name_for_sort` under `person_01`, through `PersonService.nameKey`; `docs/faces.md`).
- Metadata values: two values of one field on one asset are one value when their keys are equal (`UserMetadataValue.checksum` hashes the key and is the value's equality). A value is stored in NFC, and a keyword's `metadata_parameter` row holds its key, which the metadata filter compares (`SearchQueries.valueMatch`), so a keyword matches in any case or Unicode form.

Each model derives its `nameKey`. The DAO's insert and every rename write it beside the name, and the folder, album, Location and metadata field lists order by it. The browser mirrors the fold in `static/js/common/name-key.js`: `nameKey` for the Change combobox's exact match against existing Persons, and `partialMatchKey` (every final sigma read as a plain one, since the key gives a word-final sigma its final form) for substring filters. The server stays the authority.

**Length.** The services run `Validators.validName(name, field, maxLength, minLength)` on every add and rename; `PersonService.validName` wraps it with the reserved-name check, and `Repository.validName` counts the same way (**Libraries**). It counts code points after NFC, since NFC can lengthen a name, and refuses a key over `NameKey.MAX_KEY_BYTES` (`NAME_KEY_TOO_LONG`), which keeps every key within PostgreSQL's btree row limit. Its `ValidationException` message is also the name field's error, in the request validator's texts. The limits are `Api.Constraints` (`MAX_*_NAME_LENGTH`, `MIN_NAME_LENGTH`). A dialog's request validator and the browser's `maxlength` check the name as typed; the folder, album and Location dialogs also show the service's refusal as the field error.

The rule for a new named thing: store `NameKey.normalized(name)` through `Validators.validName`, keep `NameKey.of(name)` in a `name_key TEXT NOT NULL` column under a unique index (`TEXT` on both engines, since a fold can lengthen a name: "ß" becomes "ss"), and let the index's violation surface as a `DuplicateException` (`BaseService.add` and `updateById` turn it into one). Fold nowhere else: not in SQL (no `lower()` and no collation for name equality: SQLite's `lower()` folds ASCII only, PostgreSQL's follows the database collation), and not with `toLowerCase` in Scala.

## Albums

An `Album` is a flat, repository-scoped list of pointers to assets, unique under its name key (`album_01`; see **Names**). Membership is `album_asset`: no model, written only through `AlbumDao`, an asset in any number of albums, unknown / foreign / recycled asset IDs dropped on add, adds idempotent.

- An add share-locks the assets first, in ID order (`AssetDao.shareLockLive`), so a recycle meanwhile either waits and then drops the new member, or is waited for and the asset is left out: the album's count matches its grid. It inserts with `ON CONFLICT DO NOTHING`, in asset ID order, so a concurrent add of the same asset (a double submit) waits on `album_asset_01` and skips the row, and two adds of the same assets wait on each other in one order however each reads the assets; the count is of the rows that were new (`AlbumServiceTests`, red on PostgreSQL without each). On SQLite the share lock is skipped: the one write connection already holds off a recycle.

- Nothing album-related writes an asset: add, remove, rename and delete (a hard delete; memberships cascade) change membership and album rows only.
- `LibraryService.recycleAssets` drops recycled assets from every album in its transaction (folder deletion too). Restoring does not re-add; purging cascades.
- Only `AlbumDao.getAll` computes `Album.numOfAssets`; other reads leave it 0, `AlbumService.getAlbumsOfAsset` (the Detail panel, via `album_asset_02`) included.
- Reads and writes by album ID are repository-scoped (**DAO / Service Layer**): another repository's album is a `NotFoundException`.
- The batch ops' Add to album dialog (`AlbumActionController.htmxAddAssets`) adds the selection to an album, or creates one in the same transaction (`AlbumService.addAssetsToNewAlbum`; a taken name writes nothing).
- Search within an album: the `albumId` parameter, `SearchQuery.albumIds` (**Search results and date grouping**).

## Search results and date grouping

Two search paths share one definition of "what matches": `LibraryService.search` (full `Asset` records for the ungrouped grid) and `LibraryService.searchGrouped` (the grouped grid). Both resolve the scope through `SearchService.withResolvedScope`, afresh on every request and every page: the root folder is no folder filter (triaged assets have no folder), any other folder is itself plus its current descendants, and Search text is resolved against the repository's names (**Text search**). Every predicate is built once, in `SearchQueries.matching` (`core/dao/sql/search/`), a typed ScalaSql relation in which every filter is a semi-join on `asset.id`, so a search reads `FROM asset` alone with no duplicate rows. Every statement over it is a hand-written `WITH` shell built through `SearchQueries.statement`, which heads it with the Search text's CTEs and then the description's (**Sorted or grouped**), so no shell can leave them out and no count can disagree with its rows. The shells are hand-written because `MATERIALIZED`, the guarded `LIMIT CASE` on a trailing slice and SQLite's planner hint cannot be typed queries; each fragment carries its own bind values. Two counts read the same relation: `LibraryService.count`, exact (`PersonService.merge`'s recount, `triageSummary` and the Triage routes; **Triage summary, scope dialogs and Quick view**), and `LibraryService.cappedCount`, the map layout's total.

**Pages and totals.**

- A page is continued by cursor only, never by page number or `OFFSET`: the narrow candidate slice starts after the cursor's anchor (`afterBySort`, with an inclusive bound so an index seeks to it) and reads `rpp + 1` rows to detect continuation; only the page is joined back to `asset`. A page costs the same however deep it is, and `rpp` must be at least 1 (`IllegalArgumentException`), so no search reads an unbounded set of full rows.
- Rows a sort puts last for lack of a value (SQLite's legacy NULL import times, descending) are read in a second, guarded slice (`candidatesCte`), since a range never reaches NULL.
- Sorted by capture time, a flat page reads the day-ordered slices of a day-grouped page (`dayCandidates`), because day then time is the order of `asset_search_date_taken`, which neither engine reads in order for the time alone; the cursor carries the day.
- A first page carries a **capped count**, `SELECT count(*) FROM (<matching ids> LIMIT cap + 1)` with `SearchQuery.totalCap` (`Const.Search.TOTAL_CAP`, 10,000); one past the cap means more. A first page of `SearchQuery.withoutTotal` (Quick view, which counts exactly) has none. `includes/search_results` renders `data-results-total` (at most the cap) and `data-results-total-capped`.
- `totalCap`, `textProbeLimit` and `describeExactLimit` are tuning carried on the query for tests; none is part of the cursor fingerprint.
- `noLocationFilter` (a Triage subset, `util/TriageSubset`) is also the "No location" group's predicate. The bounding-box filter (`util/BoundingBox`; `west > east` crosses the antimeridian) matches an asset by its own point or, without one, by the pin of any Location it is in: the rule the map plots by (**Map**). `bboxFilter`'s scaladoc says why it is a union of two index-bounded ID sets.

**People match and date ranges.**

- `SearchQuery.peopleMatch` (`util/PeopleMatch`, `All` by default): `Any` is one semi-join over the set, `All` one semi-join per person, AND-ed in ID order so one search renders one statement.
- `takenRange` and `importedRange` are `util/DateRange`s of whole days, both ends included, either open. A Date Taken range (`takenFilter`) compares `SearchDialect.day(original_created_at)`, the exact expression `asset_search_date_taken` is built on, so it is a seek; its days are the camera's wall-clock days, and an asset with no capture time is in no range, even an open-ended one.
- A Date Imported range (`importedFilter`) is half-open on `created_at` itself, with no day expression, from the start of the first day in the server's zone to the start of the day after the last: a seek in `asset_search_created`. The zone is the JVM's (`ZoneId.systemDefault`), read as `matching` is built, the one input of `SearchQueries` that is not an argument. The bounds bind as the engine stores an import time (`timestamptz`; UTC `SqliteOverrides.DATETIME_FORMATTER` text, which orders as instants because every stored value is canonical). The scaladoc covers the 31 December 9999 end and legacy NULLs.
- Each of the two search indexes carries the other's date, so a page sorted by one date within a range on the other tests the range on the index, never the table. The triage indexes carry no second date.
- `SearchQuery.copyWith` keeps the match and both ranges, so the resolved copies still carry them.

`SearchQuery.grouping` (`SearchGrouping` of `GroupBy.DateTaken` with a direction, `GroupBy.Location` or `GroupBy.Sequence`) makes a query grouped; `SearchDao.searchGrouped` dispatches to one of three statements sharing one shell. `SearchQueries.grouped` emits **one statement** per page: a materialized narrow `candidates` slice (`LIMIT rpp + 1`), the `page`, `day_counts` (one correlated count per distinct day on the page), the page joined to `asset`, and the capped total on a first page. Under a scored sort (Relevance, or a Describe search's similarity) it first materializes `scored` (`ScoredRow`) so the score is computed once, and the slices, cursor comparison and order read it. The order is day, sort, ID (`orderWithinGroup`), with the newest capture time before the ID under a scored sort. The `SearchDialect`s supply the day expression (`col::date`, `date(col)`: it must match the index expression character for character), `textMatch`, null placement, the `SortValue` mapper and, on SQLite, a unary `+` on a secondary sort term that is not the grouping's date, so the planner keeps the day index. `GroupedSearchResult.continuesGroup` says the first group continues the previous page's last.

**Group by Location** (`SearchQueries.groupedByLocation`) is the same shell over two relations:

- `located` joins `matching` to `location_asset`, `location` and a left-joined category: **one row per asset × Location**. An asset in two Locations appears under both, so group counts can sum past the total, which counts assets. `unlocated` is always the trailing "No location" group, counted only on the pages that reach it.
- Groups are in the sidebar's **Path order** (**Locations**), spelled here as the category's name key and the Location's joined by U+0001 (`PATH_SEPARATOR`, below every printable character, so the composite orders as the pair and cannot collide with a top-level name), or the Location's key alone; then the Location ID, the sort, the asset ID. The direction is fixed: `groupDirection` with `groupBy=location` is a 400.
- A cursor in a Location slices `located` and lets `unlocated` fill the page only once `located` runs out (the guarded `LIMIT CASE`).
- `SearchGroupKey` is `Day(date)`, `Location(id, pathKey, name, categoryName)` (all `None` for the trailing group) or `Sequence`.

**Group by Sequence** (`SearchQueries.groupedBySequence`) is that shell over `sequenced` and `unsequenced`, the trailing "No sequence" group:

- Groups are in Curation's queue order, fixed: the first capture of the group's *matching* frames (oldest first, none last), then the Sequence ID. The first capture is a window over the matching frames, so a search showing some of a Sequence's frames orders and counts its group by those.
- `SearchGroupKey.Sequence(id, firstCapturedAt)` maps onto the cursor's `key` and `groupId`, so `SearchCursor` keeps its shape. A Sequence is told by its ID before its first capture (`afterSequence`, `SearchGroupKey.continues`), because the first capture moves when the frame that set it leaves. Another Sequence can therefore overtake it on the next page, and it opens again with a second header.
- `SearchResultsController.parseGrouping` makes `sequence` outside the Triage view no grouping, not a 400: only a frame in triage carries a Sequence, and grouping survives a change of view. The fragment names no grouping while `HX-Replace-Url` and the search store keep the request's, so a return to Triage groups by Sequence again.

**Text search** (`q`, the Search text; the terms are in the root `CONTEXT.md`):

- `util/SearchWords.of` is the one word-splitting rule, for the stored Search document, every name read at query time and the typed text, so the three cannot disagree. The camelCase hump is its only case-dependent boundary, so all three read `SearchWords.variants`, which adds the reading without humps: `mcdonald` finds `McDonald` and the reverse. `variants` memoizes 50,000 texts in an LRU map.
- It lower-cases letter by letter, with no context: each code point becomes the lower case of its capital, so a letter with two lower-case forms is one (ς and σ, which `String.toLowerCase` writes for a capital sigma ending a word; µ and μ; ſ and s; the Greek symbol forms ϐ ϑ ϕ ϖ ϰ ϱ ϵ; ı and i). FTS5 folds some of them and PostgreSQL's `simple` configuration none, so without it "ΟΔΟΣ" and "οδοσ" would be two words on PostgreSQL. The fold need not match an engine's own, since every document, name and typed text goes through `SearchWords` (`SearchWordsTests`; `SearchServiceTests` on both engines).
- `util/SearchText.parse` returns an `Option[SearchExpression]` and never fails; its scaladoc has the grammar. Terms past `SearchText.MAX_TERMS` (16) are dropped. Text with no term left is `None` everywhere: no filter, no Relevance, not refused in the trash.

A term can match in six **Search sources** (`util/ResolvedSearchText.scala`, `SearchSource`), each with the Relevance a match there is worth:

| Source | Matches assets | Relevance |
|---|---|---|
| Person: named, not hidden, not merged away (`is_deleted`), not a bad match | with a Face of that Person | 5 |
| Location | in that Location | 4 |
| Category | in any Location of that Category | 3 |
| Folder, not recycled, not the root | in that folder or any folder below it | 2 |
| Album | in that album | 2 |
| Search document: file name and user metadata values | whose document has the term | 1 |

Only the last is stored. The **Search document** is one `search_document` row per asset whose `body` is the words of the file name and of every user metadata value, each in all its variants, so the engines index words the application already split.

- Names of people, Locations, Categories, folders and albums are never copied into a document, so a rename, merge, hide, move, delete or membership change shows in the next search with nothing to reindex.
- `SearchDao.writeDocument` (JDBC DAO, one upsert for both engines) runs from `indexAsset`, `reindexAsset` and `addMetadataValue`, always inside the service transaction that changes the asset (the import's index flows, `UserMetadataService`'s edits, `AssetService.rename`). It rewrites only a changed body, which on SQLite also spares the FTS entry. Recycling does not touch it; purging deletes it by cascade.
- Every field type's values are in the document, but only `FACETED_FIELD_TYPES` (`KEYWORD`, `NUMBER`, `BOOL`) get `metadata_parameter` rows (`addParameters`), the only thing the metadata filters read: a `TEXT` or `DATETIME` value is found by its words, never by a filter. A keyword is filtered under its name key (**Names**).
- PostgreSQL indexes a generated `tsv` (`to_tsvector('simple', body)`, no stemming, no stop words) under GIN; SQLite has `search_document_fts`, an FTS5 external-content table kept in step by triggers and keyed by a declared `id` because `VACUUM` may renumber an implicit rowid. `tsv`, SQLite's `id` and the FTS table appear only as raw fragments in the dialects.

`SearchService.resolveText` reads the name sources in one read-only transaction (`SearchDao.searchNames`), matches each term against each name in memory (`SearchTerm.isIn`: the document's rule, confined to one reading of one name), probes, and returns a `ResolvedSearchText`. A Category's hits become its Locations and a folder's expand to its descendants, so each source is a plain ID filter. `SearchQuery` keeps `text` as typed with `resolvedText` beside it, and `matching` refuses unresolved text (`requireResolvedText`) rather than searching the documents alone.

A term's **sources** (`SearchQueries.TextSource`: the name sources it resolved IDs in, then always its document) are relations of asset IDs; a folder is the asset's own `folder_id`, tested two-valued (`inFolders`: false, never NULL, for a triaged asset, which has none), so an excluded folder name keeps the assets in no folder. `textFilter` ORs a term's sources, ORs a group's alternatives and ANDs the groups. A per-request **probe** in the same transaction picks one of two paths:

- `SearchDao.probeText` (`SearchQueries.textProbe`) is one statement with a branch per positive group: the `UNION ALL` of its sources, `limit + 1` rows (`Const.Search.TEXT_PROBE_LIMIT`, 5,000), each source read from the index that leads with its ID and carries the asset. A group within the limit is complete, and `ResolvedSearchText.candidates` is the intersection of the complete groups' hits: `None` means broad, and an empty set answers with nothing without reading the library (`matchesNothing`).
- **Selective path** (candidates present): `matching` filters `asset.id` by the candidate set; every other group, exclusion and Relevance source is an `EXISTS` probe on the asset's row through an index that leads with `asset_id`.
- **Broad path** (no candidates): each source of each term is a `MATERIALIZED` CTE at the head of the statement, built once however the shell renders `matching`. A group of one excluded term is an anti-join (`SearchDialect.excludes`: `NOT EXISTS` on PostgreSQL, `NOT IN` on SQLite, each the shape its planner handles well).

The text sources and the people, album, Location and folder-scope filters bind each ID set as one parameter (`Columns.isInSet`, **DAO / Service Layer**). `textMatch` builds its query string from `SearchWords` output only, one bind per term with its readings OR-ed. The body is one string, so a phrase can match across the boundary between the file name and a value, two values, or two readings of one value.

**Relevance** (`sort=relevance`, `SearchSort.Relevance`) is the one sort that is not an asset column. `SearchQueries.relevance` renders it, only when it is the sort, from the filter's own term sources (`textSources`): per group a `CASE` over the non-excluded sources, highest score first, so a term counts as its best source and `OR` alternatives count once; the groups add up. Exclusions score nothing. The order is Relevance descending, capture time `DESC NULLS LAST`, ID. `SearchQuery` throws for the Relevance sort without usable text, and `SearchResultsController` answers that request with a 400 first. The map layout has no sort.

Paging is by cursor only. `SearchCursor` is an opaque, versioned Base64URL token holding the last image's group key and `groupId`, sort value (and `s2`, the capture time, under a scored sort), ID, and a fingerprint of the search as requested (`SearchCursor.scopeFingerprint`). The fingerprint takes the folder as given, the Search text as typed and a date range as its days, never what they resolve to, since those are resolved afresh on every page; the page size is not in it. A mismatch is a `SearchCursorException`, a 400. So is a cursor whose values its search could not have written, as a token edited by hand keeps its fingerprint: every statement is built through `statement`, which first checks the sort value against the kind the engine reads the sort's values as (`SearchDialect.readsAs`), and under a scored sort the capture time beside it (`SearchQueries.requireCursorFits`), and a group key is read through `cursorKey` (a day, a Sequence's first capture), so neither reaches a statement as anything but a bound value of its column's kind. A cursor supplies a position only, never access or SQL. Results are live: a cursor continues from values, so deleting its anchor or inserting before it neither skips nor repeats images, and the counts describe the current matching set. A Describe search's cursor has no group, its sort value is the cosine distance (`SortValue.Real`, spelled as the double's own text so it reads back exactly), and its fingerprint is `describeFingerprint`'s.

**Describe search** (`describe`). A description, the words that say what a photo shows ("woman in a park"), finds the still images that look like it. It is one of a search's filters: the other Search filters (the Search text, a folder, people, Locations, the two date ranges, `triaged=true`) decide which assets are ranked, as an intersection, and never where they stand, Relevance included; with none it ranks the repository view. In its own order, similarity, it is one ranked list whose weaker matches are its end; under another sort, or grouped, it is two parts (**Sorted or grouped**).

- `SearchRequestParser.descriptionOf` reads `describe` into `Scope.description`, trimmed, beside the filters and no part of the query. It refuses, as a 400, a blank description, one over `Const.Search.MAX_DESCRIPTION_LENGTH` (300, as a form counts), the trash, and by name `albumId`, `subset`, `bbox` and `layout=map`.
- That refusal is generic: what a description takes is what `descriptionOf` blanks in a `Params.copy`, and any other set field of `Params` is refused under its `productElementNames` name. A field `Params` gains is therefore refused beside a description until it is blanked there. The parser deliberately names no ID-shaped `Api.Field` value for this, which `RouteTableTests` would count as a body field of every route that calls `parse`. `Params.layout` exists for this rule alone; only the results route hands it in.
- Only the results route and the panel's form hand a description in. With no sort named, the results route defaults to `SearchSort.Similarity` (`sort=similarity`) with a description, Relevance with Search text alone, the newest import otherwise; `sort=similarity` without a description is a 400. Ungrouped, `SearchService.describe` gets the query with the sort unless it is similarity, which a query never names; grouped, `describeGrouped` gets the sort (similarity included) and the grouping.
- A described search is always a filtered search (`isFiltered`); its title and empty-result text are under **Results title** in `views/AGENTS.md`. `includes/search_results` reads off the filters whether there is a description (`isDescribed`), then offers the Similarity sort and no Map segment, so nothing on the page sends what the route refuses. The total is exact and never capped. The browser side is **Search parameters** in `views/AGENTS.md`.
- `SearchService.describe` requires a page size, no grouping and no similarity sort in the query. It checks the cursor against `SearchCursor.describeFingerprint` (marked as a description's, so a cursor of the same filters without the description, or the reverse, is refused), reads the three Settings from one snapshot (`rankingBy`) and embeds the description (`app.describeEmbedder`, cached) before the transaction, since a pass of the text tower holds no connection. Inside `txManager.withVectorSearch(limit)` (**A vector search of a limit**) it resolves the scope and reads the page in one snapshot.
- The Settings end the results whatever the filters: `search.describe.min_probability` (0.00009, converted to the least cosine by `SceneModel.siglip2Cosine`) and `search.describe.max_results` (1,000, bounded by `Const.Search.TOTAL_CAP` so the exact total never passes what a first page counts to), the nearest of what the filters match, so a narrow filter can leave few results or none. `search.describe.weaker_match_ratio` ends nothing (**Weaker matches**). An embedder that embeds nothing (a test instance with the model off) finds nothing.
- Each page is logged at DEBUG with its description escaped (`Util.printable`): the one log line that holds the description.

`SearchDao.describe(query, ranking)` takes a `DescribeRanking` and reads one statement, `SearchQueries.described`, built through `statement` like every other: `ranked (id, distance) AS MATERIALIZED`, the `rpp + 1` rows after the cursor in `(distance, id)` order, those rows joined to `asset` with the bulky metadata JSON as NULL (`BulkyMetadata.AsNull`), the weaker line and count, and the total on a counting page.

- The ranked rows are the one part the engines write differently: `SearchDialect.ranked(matching, ranking)` returns `RankedRows`, exactly or, when the ranking has `throughIndex`, through a vector index. The engine's DAO decides (`SearchDao.rankingFor`); `SearchQueries.rankedCtes` renders the rows for `described` and for a part alike.
- The ranked rows are the `matching` relation itself, ordered and limited by the vector search, so there is no join back to the matches and a Describe search cannot disagree with its filters' search.
- `AssetRow` maps neither a Scene embedding nor SQLite's rowid; the dialects name them through `SearchQueries.assetColumn`. An asset with no embedding (a Video, an animated image, a still image the model could not embed) is never ranked. Every page ranks again, so results are live.
- **PostgreSQL** (`PostgresSearchDialect`, `postgres.SearchDao`) picks a shape per page (`ranksExactly`): it counts the matches that carry an embedding (`SearchQueries.embeddedCount`, capped one past `describeExactLimit`, in the page's transaction), ranks at most the limit exactly and more through the index, and logs the choice at DEBUG. A description with no filter is counted too, since the index holds every repository's embeddings and a small Library beside a large one would otherwise walk the whole index. `Const.Search.DESCRIBE_EXACT_LIMIT` (75,000) is an estimate, not a measurement: at a million embedded assets a whole-index scan costs about 14 µs a visited row, an index search filling 1,000 results from filters leaving `n` assets visits about `1,000 × 1,000,000 ÷ n` rows over a 0.2 s base, and exact ranking costs about 5 µs an embedding, crossing near 75,000 at about 0.4 s. The count's own cost is unmeasured.
  - **Exact** (`rankedExactly`): each distance in an `OFFSET 0` subselect so it is computed once, then cutoff, order and limit. It orders by the `vector` column, not the `halfvec` cast, so the planner cannot use `asset_describe`.
  - **Index** (`rankedByIndex`): candidates from `asset_describe`, an HNSW index over `siglip2_embedding::halfvec(768)` (the column stays `vector(768)`). The inner select is `matching` ordered by the same cast with `LIMIT limit`, so the filters apply as the scan walks and the iterative scan of `withVectorSearch` continues until enough rows pass. It takes each candidate's exact full-precision distance, and the cutoff is in the outer select, because inside it a description with nothing near enough would send the index hunting for rows that are not there. The search is approximate and can miss rows outright (`docs/test-coverage.md`, **Describe search**, the recall gap).

  Both give each row its exact full-precision distance, and the page orders them the same way (by the similarity, then capture time, then ID; `orderWithinGroup`), so a cursor from one shape continues on the other when the count crosses the limit between pages.
- **SQLite** (`SqliteSearchDialect`, `sqlite.SearchDao`) has one shape and chooses nothing: a `scanned` CTE over `vector_full_scan('asset', 'siglip2_embedding', ?)` (sqlite-vector's exact scan of every repository's embeddings, the vector bound as raw float32) joined to `matching` by rowid. SQLite flattens the CTE, so the scan drives whatever the filters. The column is registered on each connection as it opens (**Connections and transactions**).

**Weaker matches.** The match threshold ends a Describe search far down a ranking whose tail looks little like the description, so the results say where that tail begins.

- A result is a **weaker match** (`CONTEXT.md`) when its cosine is under `search.describe.weaker_match_ratio` (0.75) of the best match's. The line is a fraction of the best match, not a fixed cosine, because each description's cosines are on their own scale (a short one scores low throughout); the measurement is in `docs/curation-batch-detection.md` (**A description's weaker matches**).
- `described` reads the line off the whole ranking (`weaker_line`), so it is the same on every page whatever the cursor. `SearchQueries.IS_WEAKER` is the one SQL comparison with the line, and `jdbc.SearchDao.weakerMatches` repeats it in Scala, so a row is on the same side in the count and on the page; keep the two in step.
- A page names `WeakerMatches(index, count)` at its first row under the line only when the row before (on the page, or the cursor's) is above it, so exactly one page names them. A line that is not positive is no line: a ratio of 0 is the Setting's way of asking for none. The best match is never weaker.
- `htmx/results_grid` renders `includes/weaker_matches_header` before that row's cell (**Group headers** in `views/AGENTS.md`). Every page ranks again, so if the best match changes between pages the header can appear twice or not at all.

**Sorted or grouped.** Under a sort other than similarity, or under a grouping, the search is read in two parts (`DescribedPart`): `Nearer`, the matches above the line, then `Weaker`, each a search of its own sorted and grouped as requested, the second under the weaker matches' header.

- `SearchQuery.described` carries a `Described(ranking, part)`, set by `SearchService`, which makes the description one more filter of `matching`: `asset.id IN (SELECT id FROM described)`. `statement` heads such a statement with `describedCtes` after the text's: the ranking of the query's own filters (`rankedCtes` over `query.undescribed`), then `described (id, similarity) AS MATERIALIZED` for the part. So every statement over a search (flat, the three grouped pages, their counts) works among a part unchanged.
- Similarity is a scored sort like Relevance (`SearchSort.isScored`): a grouped statement materializes `scored` from `described` (`scoredCte`). An ungrouped search is never sorted by similarity this way: that is `described`'s own order.
- `SearchService.describedInParts` runs inside `withVectorSearch(limit)`, resolving the query and picking the ranking shape (`rankingFor`) once for every statement of the page. A cursor continues one part, named by its fingerprint (`describeFingerprint(..., part)`, over a `scopeFingerprint` that holds the sort and grouping); a cursor of any other search matches neither part and is refused.
- A `Nearer` page with more is that part's alone, and a first page adds the weaker count to its total. A page that ends `Nearer` goes on with `Weaker` from its start, read as a first page so it is counted, and names where it begins (`SearchResult.weaker` by asset, `GroupedSearchResult.weaker` by group). Each part's rows are grouped apart (`GroupedSearchResult.groupsOf`), so a group with matches in both parts is two groups, each counting its own part.
- A page with no room left still reads one weaker row to learn whether there is one, and its cursor is then `Nearer`'s last row, which the next page continues into `Weaker`. `continuesGroup` holds only within the cursor's part, so the first weaker group always has a header.

Measured once, a description alone (before its filters and the shape-choosing count), on the machine of `ImportParallelism`'s figures, over random unit vectors, warm, default Settings, 50 to a page: PostgreSQL over 1,000,000 embedded assets answers any page in 205 to 265 ms, about half of it the index scan; SQLite over 100,000 in 167 ms, about 1.7 µs per embedding whatever the limit; a new description adds about 90 ms of text tower; a result limit of 10,000 takes 1.4 s on PostgreSQL. Nothing with filters, and not the two-part pages, is measured on either engine (`docs/test-coverage.md`).

Tests: `SearchRequestParserTests`, `SearchQueryModelTests` (the fingerprints), `DescribeEmbedderTests`, `DescribeSearchTests` (both engines, Scene and Describe models on), `SearchResultsControllerTests` and `SearchPanelControllerTests`; what each covers is in `docs/test-coverage.md` (**Describe search**). The controller tests import nothing: the server embeds with the real text tower, and the fixtures are file-less assets with embeddings at chosen cosines (`lookingLike`, `TestContext.atCosine`).

`routes/SearchRequestParser` is the shared parameter-to-scope parser for the HTML search, the map cells/bounds endpoints, the Triage routes' counts and the panel's form. A route builds one `SearchRequestParser.Params` by name and hands it on whole (`parse(params)`, `SearchResultsController.browserViewUrl`), so no two same-typed values can swap. `parse` returns a `Scope` (people and Locations as lists in request order) that each controller turns into a `SearchQuery` with its own sort, grouping and paging. A refusal is a plain-text 400 in HTML search and the panel, a JSON 400 from the map endpoints.

- The view sets the flags: `view=triage` is the triaged assets not recycled (`SearchQuery.TRIAGE_VIEW`; a recycled triage asset keeps `is_triaged`), `view=trashbin` the recycled assets not marked for purging, any other view the repository view (neither recycled nor triaged).
- `triaged=true` adds the triaged assets to the repository view (`false` equals absent); in the trash it tells the assets recycled from triage from the rest; `view=triage&triaged=false` is refused. It is a column filter in `SearchQuery.params`, so it is part of the fingerprint.
- The scope has Search text only when `q` has a usable term; text with `view=trashbin` is refused. `bbox` is the grid's and the crowded-pin panel's filter only; the map never reads it (**Map**). `subset` is taken in every view, though only Triage offers it.

**Advanced search parameters.**

- `personId` and `locationId` name one ID or several, comma-separated (`SearchRequestParser.idsOf`: each once, in order, an empty segment no ID, as the browser store's `idsOf` reads them), at most `SearchRequestParser.MAX_IDS` (10) each. The folder and the album stay one ID. Several Locations match any; several people all, or any with `peopleMatch=any`.
- The four dates are ISO days read by `SearchRequestParser.ISO_DAY` (four-digit year, strict calendar), because `LocalDate.parse` would also read a signed five-digit year, whose instants SQLite's text misorders.
- An album or a subset beside what only the panel combines (a date range, several people or Locations, or more than one of the Search text, a folder, a person and a Location) is refused; the parser counts any folder, the root included, having no repository at hand. The trash refuses a date range and several people or Locations.
- An ID that names nothing in the repository is no error and matches nothing. `SearchResultsController` and both map routes take the five parameters; `TriageController`'s scope dialog and Quick view take none.

**The results title of a filtered search.** A search is a **filtered search** (`CONTEXT.md`, `SearchResultsController.isFiltered`) when it has a description, a date range, two people or more, two Locations or more, or more than one of the Search text, a folder, a person and a Location, the root folder counting as no folder. Its title is a chip per filter (**Results title** in `views/AGENTS.md`), named through `SearchService.filterNames` on a first page only. Its IDs that name nothing in the repository have no chip and are no 404. Any other search names one scope at most, read by ID on every page, and one that is not the repository's is a 404 that names nothing of it.

`layout` is separate from `view`: `grid` (default) or `map`. With `layout=map`, grouping and paging are ignored, and `bbox` as **Map** says; `LibraryService.cappedCount` gives the total, `mapBounds` the initial bounds, and `includes/search_results` renders `htmx/map_view` without `#assets`, its Group menu disabled. The fragment's `data-results-*` attributes carry the scope the client reads, among them the Search text matched (`data-results-q`) and the grouping the server used. `HX-Replace-Url` is a projection of the request (`browserViewUrl`), without the grouping on the map. The browser side is **Map view** in `views/AGENTS.md`.

`GET /htmx/search/r/:repoId` is HTML only: a JSON request (`Accept` or the legacy `Content-Type: application/json`) is a 400 with a `{"error": ...}` body. The detail modal walks the rendered grid (**Detail navigation** in `views/AGENTS.md`).

- An options fragment is at most `Const.Search.MAX_FILTER_OPTIONS` (50) `role="option"` elements. `SearchService.offered` matches over the same name candidates the Search text resolves against, so the options and the text cannot disagree about a name. The people route reads `PersonService.getListedSearchable`, whose query spells `searchablePeople`'s four flags; `SearchServiceTests` holds the two to one answer.
- `q` is parsed as Search text, and an option is offered when its own name has every group (`SearchTerm.isIn`); a match is never in the path, so text naming a Category or an ancestor folder offers nothing below it. No usable term offers every name.
- Options are ordered by name key (`NameKey.of`), a folder's path segment by segment. The first 50 are kept in a heap in one pass (`firstOf`), so an empty `q` sorts none of a large tree. Names are matched in memory on every request, so the browser never holds the tree and a rename shows in the next request.
- The panel parses its parameters as a search of its view does, so the same refusals are plain-text 400s. `SearchService.filterNames` names what is left, each by ID and never from the name candidates. A person is any live one, hidden or unnamed included, since the People tab can scope a search to them. An ID that names nothing there (gone, another repository's, merged away, a bad match, a Category as a Location, the root folder, a recycled folder) gets no chip and no input and is never a 404, so the panel shows what is left of a bookmarked search.
- Tests: `SearchRequestParserTests`, `SearchServiceTests` (both engines), `SearchPanelControllerTests`, `SearchResultsControllerTests`, `MapControllerTests` and `RouteTableTests`; coverage in `docs/test-coverage.md` (**Advanced search panel**).

Date storage behind this:

- `original_created_at` is the camera's wall-clock time with no zone (PostgreSQL `TIMESTAMP WITHOUT TIME ZONE`; SQLite `yyyy-MM-dd HH:mm:ss` text, a fraction only when there is one), parsed and bound as a `LocalDateTime` with no instant conversion, so its day never depends on the JVM or server zone. With no capture time it is NULL and the asset is in the "No date" group.
- `CaptureDateResolver` adds EXIF's `Sub-Sec Time Original`/`Digitized` to the date beside it and keeps an XMP date's own fraction, to the microsecond, so burst frames within one second keep their order. Every other rung is whole seconds, and an unset clock stays a sentinel whatever subsecond it carries.
- The file name is the last rung (`filename`), read only when no metadata rung is plausible: five shapes in `CaptureDateResolver.nameShapes` (compact camera, Pixel, dashed timestamp with optional `AM`/`PM`, Apple's export, Facebook's epoch). Each regex is anchored at the start of the name and needs a boundary after the seconds, so an incidental digit run never reads as a time. A name gives whole seconds only. A name with a date and no time resolves nothing, since a midnight time would put a day's frames into one Sequence. Every shape goes through `WallClockParser.parse`'s strict calendar check and the plausibility rules, so a plausible metadata date always wins.
- `created_at` is bound explicitly in UTC by `AssetDao.add`, truncated to the microsecond so both engines store one value, never by the engine default.
- `asset_search_date_taken` is `(repository_id, is_recycled, is_pipeline_processed, <day expression>, <raw timestamp>)` with carried columns: the day gives seeks, per-day counts and range bounds; the raw timestamp makes a same-field grouping and sort read in index order; the carried columns keep text, folder, day and Date Imported tests off the table.
- Nulls sort where each engine puts them (`SearchDialect.nullsFirst`, which the cursor comparison must agree with). No `NULLS LAST`, which would forfeit index-ordered reads; the one exception is the Relevance sort's capture-time tiebreaker, which no index orders anyway.
- For a schema change, see **Schema migrations**.

The search's indexes are in both `all.sql` files, each with a comment naming the read it serves; read them before adding a filter or a sort, and keep the two files in step. Rules they encode that the comments do not spell out:

- The triage indexes (`asset_triage_created`, `asset_triage_date_taken`, `WHERE is_triaged`) let the triage view, `PersonDao.getTriagedAssetCounts` and `AssetDao.getSequenceCandidates` follow the size of the triage set, not the library.
- The membership tables are indexed in both directions, each index holding both columns, so a probe from either side reads its index alone; `face_02` carries `asset_id` for the same reason.
- `asset_01` is unique on (`repository_id, checksum`) over the live assets only: one live copy of a content per repository, any number in the recycle bin. Checksums are `CHAR(64)` lowercase hex and IDs `CHAR(36)`, both `COLLATE "C"` on PostgreSQL so they compare byte-wise as on SQLite. The account and person name-key indexes are under **Names** and **Accounts and access**.
- SQLite uses a partial index for a bound flag only when the flag is bound as a number, as ScalaSql binds booleans. `SqliteOverrides.nativeBool` binds `"1"`/`"0"` text, so a hand-written JDBC statement that should read a partial index writes the flag as a literal.
- PostgreSQL's `asset` has `toast_tuple_target = 128`, so its `jsonb` metadata lives out of line and the heap row a search reads stays narrow; SQLite's `asset` declares its large columns last, in the order of **Sequences and Image quality** (a cost rule), so reading any other column skips their overflow pages.
- `SearchPlans` (test trait) reads a statement's plan over a seeded, analyzed library, rolled back afterwards, for the suites that check which index a search reads; `indexOnlyPlanOf` says whether an index alone answers it.

Coordinates: `latitude` / `longitude` on `asset` are WGS84 decimal degrees, nullable, parsed on import only, in `ExtractMetadataFlow` through `util/GeoLocationResolver`, which like `CaptureDateResolver` reads only persisted inputs, so a later backfill needs no file. The `N`/`S`/`E`/`W` ref tag decides the hemisphere whenever present, because the stored degrees-minutes-seconds description drops the sign of a value between -1 and 0 (London's longitude). Unparseable or out-of-range values and 0/0 resolve to nothing. There is no editing and no backfill of existing rows. The partial index `asset_geo` serves the map's bounding-box reads from the index alone; `SearchMapTests` checks on both engines that a cells statement reads it (on PostgreSQL over a few thousand analyzed rows, rolled back and the table analyzed again, since the schema is shared by the suites that follow). The `location` and `location_asset` tables are under **Locations**.

## Locations

A `Location` row (`models/Location.scala`, table `location`) is, by `LocationKind`, a **Category** (a named container, one level deep, no pin, no assets) or a **Location** (a WGS84 pin, optionally under a Category).

- Both kinds share one name pool per repository under the name key (`location_01`; see **Names**); a clash is a `DuplicateException`.
- The model constructor and the schema CHECKs enforce each kind's shape. `LocationService` enforces the rest (`IllegalOperationException`): a parent must be a Category, only a Location moves, a Category holds no assets.
- Membership is `location_asset`, the `album_asset` shape (see **Albums**), including the recycle, restore and purge behaviour (`LibraryService.recycleAssets`). Adds are idempotent and drop unknown, foreign and recycled asset IDs, so the returned count can be below the request's; they lock and insert as an album's add does (`LocationServiceTests`).
- **Path order** (`LocationDao.getAll`): Categories and top-level Locations by name key, each Category directly followed by its Locations. The explicit category-first sort key keeps a Location "Alba" from sorting before its Category "Italy". Only `getAll` computes `numOfAssets`; `getLocationsOfAsset` (Detail panel) uses the same order.
- Delete is hard. A Category's Locations move to the top level first, in the same transaction (`moveChildrenToRoot`); `category_id` has no cascade on purpose, so a delete that skips the move fails instead of orphaning.
- Every mutation looks the row up through the inherited `BaseService.getById`, scoped by `BaseDao.repositoryScoped`, so a foreign ID is a `NotFoundException` and changes nothing.

Search filters and **Group by Location** are under **Search results and date grouping**; the map's queries under **Map**.

`LocationController` (JSON): `/api/location/r/:repoId/list` in path order, and `PUT`/`DELETE .../assets` with `{locationId, assetIds: [...]}`. A malformed payload or Category target is a 400, a foreign Location a 404.

`LocationActionController` owns the tab, the six dialogs and their submits:

- Add to location sends `assetIds` comma-separated and answers `{"added": n}` through `dialogSuccessResponse`, so the dialog reports what the server applied, not the selection size.
- Field, duplicate-name and target errors re-render the form (`dialogFormValidationResponse`). Coordinates come from the map pin as strings, or as JSON numbers; a missing or out-of-range one is a single `PIN_REQUIRED` error. An empty Category means the top level.
- An invalid hidden `id` is a plain-text 400, a foreign one a 404.

The UI is under **Locations** and **Location pin editor** in `views/AGENTS.md`.

## Map

The map never receives a result set: a repository can hold millions of assets, so the browser asks for a viewport and gets aggregates. Each aggregate is one statement in `SearchQueries` over a `points` CTE of the search's **plotted points** (`plottedPoints`; `CONTEXT.md` **Plotted point**): an asset with its own coordinates is plotted there only; one without is plotted at the pin of *each* Location it is in. The CTE is a `UNION ALL` of two typed relations over `matching`, so the map carries every filter the grid does. The `bbox` filter (`bboxFilter`) implements the same rule separately; keep the two in step.

- `mapCells`: points in the box go to square cells by `floor(coordinate / cellDegrees)` (`floor` is built into both engines); one window pass per cell gives the count, the centroid and a rank by newest capture time (nulls last on both engines, through a `CASE`) then ID. The rank-one asset **represents** the cell, so its thumbnail is stable across pans. `SearchService.cellDegrees(zoom)` is `360 / 2^zoom / 4` (a quarter tile), zoom clamped to 0..20; the client's crowded-pin logic relies on the same rule (`views/AGENTS.md` **Map view**).
- `mapLocations`: the Locations pinned in the box that hold a matching asset, with that count. The matches are read once into a materialized `matched`, restricted to members of the repository's Locations in the box (`membersOfLocationsIn`, which the bounding-box filter reads too), so it scales with those memberships, not the library or the instance. The count agrees with the grid scoped to the Location.
- `mapBounds`: the extent and count of every plotted point, unclipped, for fitting the map; `None` when nothing is plotted. Points on both sides of the antimeridian span the whole longitude range.

`LibraryService.mapCells` / `mapBounds` resolve the scope like `search` and read in one read-only transaction.

`GeocoderService` backs the place-name search of the Add Location dialog. The server proxies it so the browser never talks to the geocoder and the identifying `User-Agent` the Nominatim policy requires is set in one place. The `map.geocoder.enabled` Setting, read on every search, is **off by default** because every query goes to a third party; off, `search` throws `IllegalOperationException`. `map.geocoder.url` is any Nominatim-compatible endpoint. The basemap is the `map.tile.url` / `map.tile.attribution` Settings (readers under **Settings**).

`MapController` (`/api/map/r/:repoId/`, all `@requireLogin()`; `geocode` also requires `Permission.Organize`):

- `cells` and `bounds` accept the client's search parameters verbatim (`cask.QueryParams`) and ignore the grid-only ones (`sort`, `layout`, grouping, paging) and `bbox`, as the search route's map layout does (`SearchResultsController`, where `bbox` stays in the URL as the crowded-pin panel's scope), so the map behind an open crowded-pin panel plots the whole search; `subset` still narrows it. A scope `SearchRequestParser.parse` refuses is a JSON 400 with its message (**Search results and date grouping**); a Guest's refused view is a JSON 403 (`refusedView`, **Accounts and access**); a `QueryTimeoutException` is a JSON 503.
- `viewport=s,w,n,e` is the map's own clipping box, passed separately to the service and never an asset filter: a visible Location counts every matching member even when that member's own GPS point is outside the viewport.
- `geocode` is a JSON 404 when the geocoder is off and a JSON 502 on a `GeocoderException` (unreachable, non-200, or not a list).

**SQL explain log** (`transactions/SqlExplainer.scala`, `transactions/ExplainingConnection.scala`). A dev aid: `dev.sql_explain=true` in `application-dev.conf` (an `Environment.devSwitch`) makes `TransactionManager.connection` wrap each connection in a proxy that offers the explainer each new query shape (`SqlExplainer.shapeKey`) just before it first runs. Off, a transaction runs on the pooled connection itself; no DAO knows about it. Plans go to `sql-debug.log` in `Environment.ROOT_PATH` (git-ignored, emptied at server start), with the originating DAO line, its caller and a runnable form of the SQL.

- Only *prepared* statements starting with `SELECT`, `WITH`, `INSERT`, `UPDATE` or `DELETE` are explained. Anything run through `createStatement` is not, including statements with no bind values, which ScalaSql (an update) and commons-dbutils' `QueryRunner` send that way (`SELECT nextval(...)`, an unfiltered count).
- The explain runs on the statement's own connection with its binds. PostgreSQL: `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` for a read, which runs it one extra time; `EXPLAIN (SETTINGS)`, never executed, for anything containing `INSERT`, `UPDATE` or `DELETE`; both inside a rolled-back savepoint, so a failed explain cannot abort the transaction. SQLite: `EXPLAIN QUERY PLAN`. A failed explain is logged in place of the plan and never reaches the request.

## Schema migrations

`Altitude.schemaVersion` is the current version. The `Altitude` constructor runs `migrationService.migrate()` in every environment, after the DAOs and before `settings.load()`. A fresh database (version 0, which a missing `system` table also means) runs `migrations/<engine>/all.sql` once and is stamped with the current version. `MigrationService` rethrows any other failure to read the version, so a locked or refused read never passes for a fresh database and never gets `all.sql` run over it.

- **Nothing is dropped.** `all.sql` creates into the schema as it finds it (PostgreSQL's current schema, the first of the search path that exists), and first refuses a database that is no empty one (`MigrationService.requireEmpty`), whose tables then stay as they are: a schema to create into that holds a table (another application's database, or an Altitude one whose `system` table is gone; an extension's own relations, such as `pg_stat_statements`' views, do not count, nor on SQLite SQLite's own tables and sqlite-vector's `_sqliteai_vector`, which loading the extension creates), and on PostgreSQL a search path that names no schema that exists, or that leads past a schema holding a `system` table, which the error names. A database is emptied by whoever means to (`make clear-db`, `TestDatabase.wipe`), never by a start.
- **One transaction per script.** A script runs in one transaction with its version's code and its stamp (DDL is transactional on both engines, FTS5 tables and triggers included), so a failure or a stop leaves the version before it, never a schema its stored version does not describe. Both `all.sql` files seed version 0, so the stamp in the script's transaction is what gives a fresh database its version. Every `<version>.sql` an upgrade needs is read before the first runs, and a missing one fails naming the script and both versions, with nothing changed.
- Tests: `StartupTests`: on both engines another application's table, a script whose stamp fails, the stamp of a fresh database, a missing `<version>.sql` and one missing after a present one; on PostgreSQL an extension's views, a search path to no schema and one past Altitude's (a transaction manager of the test's own, whose connections set `search_path`).

The test bundles migrate a wiped schema (`TestDatabase.reset`, **Test Structure**).

DO NOT add new migrations or bump the version number. The per-version path (`migrations/<engine>/<version>.sql`) has no files and gets none. Every schema change goes into both `all.sql` files (Postgres and SQLite) as the original table and index definitions of a fresh schema, never as an ALTER of an earlier definition; `schemaVersion` stays 2, and a database is recreated from scratch.

## Config & Environments

The environment is `dev`, `test` or `prod` (`Environment.CURRENT`, from `Environment.resolve`): the `altitude.env` system property, then the `ALTITUDE_ENV` variable, then prod. An empty value counts as unset. A value that names no environment stops the start, naming the accepted spellings (`Environment.ACCEPTED`), so a typo never runs as another environment; the variable is checked even where the property wins. `ENV` is not read: it is a POSIX shell's own variable. The `Makefile` sets `ALTITUDE_ENV` on every target that starts the server or the tests, and the image passes `-Daltitude.env=prod`.

Config resolution order, the first winning:
- **dev** and **prod** (`Altitude.loadConfig`): the `ALTITUDE_` environment variables → the environment's config file → `reference.conf` (defaults in `altitude/resources/`), layered and then resolved together.
  - The file (`Altitude.configFile`): dev reads `application-dev.conf` in the working directory. Prod reads the file `ALTITUDE_CONFIG` names (a relative path is under the jar's folder; a file that does not exist fails the start), else `application.conf` in the jar's folder (`Environment.ROOT_PATH`), never the working directory's. With no file there the defaults apply, and an INFO line says so. The jar is `Environment.codeLocation`, which `NativeLibraries` reads too: its code source's URL through `Path.of(url.toURI)` (`Environment.pathOf`), never `java.io.File(URI)`, which refuses a jar on a Windows share (`file://server/share/...`) for its authority. A file that does not parse fails the start.
  - The variables: `environment.conf`, a resource of `key=${?ALTITUDE_...}` lines and nothing else, gives a key its variable's value. Only the keys whose variable is set are layered over the file, and a variable set to an empty value sets an empty value, never an unset one. Where an empty value would pass for a setting, the start refuses it, naming the variable: the host (to the JDK an empty host is the loopback address, so a container would answer its own health check and nobody else), the port, the Data directory (which would be the jar's own folder) and, on PostgreSQL, the password. The other keys refuse an empty value by their type or their own check; the Models directory alone takes it, as its default. `ALTITUDE_ENV`, `ALTITUDE_CONFIG` and the two logging variables set no key and count as unset when empty. A key gets a variable by a line there and the variable's name in the key's comment in `reference.conf`.
  - `loadConfig` takes the variables as a parameter (the process's own by default, `Environment.variables`) and reads no other environment, so a test passes its own, and a substitution in a config file resolves against the config's keys and the `ALTITUDE_` variables alone: `${HOME}` there fails the start.
  - `make clear-db` (`tools/ClearDb.scala`) reads through `loadConfig` with no variables: it drops the database and empties the Libraries' folder that `application-dev.conf` names, never those a shell's `ALTITUDE_DB_*` or `ALTITUDE_DATA_DIR` name, and only as dev (`ClearDbTests`). So it does not clear a dev server that was started with such variables.
- **test**: system env overrides → every `reference.conf` on the test classpath, the main one first, so a key both files set keeps the main value (the test file's `db.engine` included: controller tests run on SQLite). Test values that must differ go in `Altitude.testConfig`, which `TestModelFiles` reads too: the data directory under the test directory, the test database URL and credentials, and the bundle's engine. A test run reads no config file and, of the `ALTITUDE_` variables, `ALTITUDE_MODELS_DIR` alone, through `reference.conf`.

The config files hold only what shapes the process at startup: `server.*`, `fs.data.dir`, `storage.engine.default`, `db.engine`, `db.sqlite.*`, `db.postgres.*`, `db.pool.leak_detection_threshold`, `face.debug.enabled`, `import.parallelism.max`, `models.dir`, `dev.*` and the test `test.dir`. Everything an Admin tunes is a Setting (see **Settings**); a leftover key for one in `application.conf` is ignored. `import.parallelism.max` is the exception: it caps a Setting on purpose, for a machine where no Admin tunes anything. Trap: a leftover `import.parallelism=N` puts a number where HOCON needs an object to hold `.max`, so unless the cap follows it in the same file, or its variable sets it, the number replaces the object and hides the cap; `ImportParallelism.configuredCap` then applies no cap and logs a WARN.

| `ALTITUDE_IMPORT_PARALLELISM_MAX` | `import.parallelism.max`. |
| `ALTITUDE_LOG_FORMAT`, `ALTITUDE_LOG_LEVEL` | No config key: **Logging**, below. |

- Not the server's: `ALTITUDE_PLATFORM` is the build's (**Packaging** under **Build & Test Commands**), `ALTITUDE_SOURCE_DIR` the test module's (**Transaction boundaries**), and `ALTITUDE_PUBLISH_PORT` `compose.yaml`'s own, the host port, which never reaches the container. `ORT_DISABLE_TELEMETRY` is ONNX Runtime's (**Scene embedding**), and `TZ` sets the JVM's zone, in which Date Imported's day falls.
- On SQLite the start logs a WARN when the database folder's file store is not a local disk's own: a network share, a host folder shared into a container or a mount through FUSE (`Altitude.sqliteDiskWarning`: `nfs`, `nfs4`, `cifs`, `smb3`, `9p`, `virtiofs`, `fakeowner` and any `fuse` type, so `fuseblk`, a local NTFS or exFAT disk through FUSE, too), since WAL needs a local disk's own file system. `fakeowner` is the type of a host folder under Docker Desktop for Mac with VirtioFS, listed without having been seen on a Mac. The check only warns.
- Tests: `EnvironmentTests`, `StartupConfigTests` (unit).

**Logging.** There are three logback files, and which one a JVM logs by is decided outside the application.

- `altitude/resources/logback.xml` is the prod configuration, the one logback finds when nothing names another, so the image and a jar need no flag. It logs to the console alone, through one of two appenders: `text` (the date and time in ISO 8601 with the zone's offset, the request ID and the account's ID in brackets, no colours and no caller data) or `json` (logback's `JsonEncoder`, one object a line: `timestamp`, `level`, `threadName`, `loggerName`, `mdc`, `formattedMessage`, `throwable`). No logger has a level of its own, so a request's START and END lines show at DEBUG alone.
- `ALTITUDE_LOG_FORMAT` (`text` or `json`, default `text`) names the root's appender and `ALTITUDE_LOG_LEVEL` (`TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR` or `OFF`, default `INFO`) its level. Each is read from a system property of its name, then the environment, trimmed and in either case, an empty one unset. They are no config keys and cannot become ones: logback configures itself at the first logger, before any config is read.
- `logback.xml` reads them through two `PropertyDefiner`s (`LogSettings.scala`), which answer the default for an unknown value, since logback itself would give an unknown format no appender and an unknown level DEBUG. `App`'s start then fails on it (`LogSettings.requireValid`), in every environment, and the refusal is logged as any failed start's is. `LogSettings` and its definers run inside logback's own start, so they neither log nor touch an object that does (`Environment`).
- The logger `altitude.core.LogSettings.unselected` in `logback.xml`, at OFF, refers to both appenders. Without it logback warns of the appender the root does not use, and one warning makes it print its whole status ahead of the first line of every start. A new appender is added to it.
- `logback-dev.xml` is the dev configuration: colours, caller data, the application at INFO and the request lines. Nothing finds it by its name: `forkArgs` in `build.mill` passes `-Dlogback.configurationFile=logback-dev.xml` to what Mill starts (`run`, `runBackground`, `runMain`), and Mill writes the same arguments into the start script of `./mill altitude.assembly`'s jar, which is no supported artifact. The supported jars, the platform jars (`platformJar`) and the image's thin jars (`dist`), carry no start script and no flag: they are started by `java` and log by `logback.xml`. A dev start outside Mill logs by `logback.xml` unless it passes the flag. The two variables change nothing in it.
- Tests log by `altitude/test/resources/logback-test.xml`, which the test module's `forkArgs` name and which silences the application.
- Every refusal of the start (a logging variable, the environment, the config file, the port, the PostgreSQL password) is one ERROR line of `App.main`, in whichever format the log has, and ends the process with status 1 (**Startup** in **Library stats and purging**).
- Tests: `LogSettingsTests` (unit) reads the real files.

**Model files.** The models are files outside the repository and the build; `util/ModelFiles.scala` pins them and puts them in place.
- **Pins are the trust anchor.** `ModelFile`, an enum of the seven, pins each file's name, URL, size and SHA-256. Six are assets of release `ModelFile.TAG` of `renegade-otter/altitude-models` (its README gives each file's checkpoint and licence; its `export-models.py` makes them). ArcFace comes from `maze/faceX` on Hugging Face at `ModelFile.FACEX_REVISION`, the revision the face code was tuned with, since its non-commercial licence forbids re-hosting. A new set is a new release tag plus new pins, never a changed release. `TAG` and `FACEX_REVISION` are `inline val`s because the enum cases build their URLs while the companion initializes.
- **Where.** A set lives in `<models.dir>/<tag>/`, so sets never mix and an older set's directory is left alone. An empty `models.dir` (the default) is `models/` in the per-user cache (`UserCache.folder`: `$XDG_CACHE_HOME/altitude/models` when that is absolute, else `~/.cache/altitude/models`; the native jar's `natives/` is beside it), shared by the dev server, every test bundle, every worktree and a second instance. `ALTITUDE_MODELS_DIR` sets it, for a container's volume (`/models` in the image); its substitution is in `reference.conf` as well as `environment.conf`, since the tests read `reference.conf` alone. `~` or a leading `~/` is the home directory; any other relative path is under `Environment.ROOT_PATH`. With no absolute home directory (`user.home` is `?` for a user with no passwd entry, as in some containers), `ModelFiles.root` fails the start rather than caching under the working directory.
- **At startup.** `Altitude.models` (`ModelFiles.ensure`) runs in the constructor (its place: **Architecture Overview**), and the start waits for it, so nothing runs without its model; a failed download leaves no non-daemon thread to keep the process up. A file counts as in place when it has its pinned size; the SHA-256 is checked only on download, so a start never hashes the 1.6 GB.
- **Download.** `ModelDownloader`'s scaladoc and comments hold the mechanics and their reasons. In short: a process lock plus a file lock on `<models.dir>/.lock` (`LockFile.locked`, which `NativeLibraries` shares), so instances and test bundles starting at once download once; a resumable `<file>.part`, verified against its pin and moved atomically, so a crash never leaves a short file under the real name; a body bounded by the pin, so a CDN or proxy cannot fill the disk; retries for passing host trouble. Progress logs at INFO.
- **Failure.** Any file that cannot be put in place fails the start with `ModelFilesException`, never a bare `IOException`. Its message lists each missing file (name, size, SHA-256, URL) and the directory to put it in, which is how an instance with no route to the internet gets them.
- **Readers** take their paths from `ModelFiles.path`, never from the classpath: `OnnxSceneEmbedder`, `OnnxDescribeEmbedder` and `FaceDetectionService`. No classpath resource is extracted to a file at runtime: the native jar's libraries are unpacked by `NativeLibraries` (**Packaging**).
- **Tests.** `ModelDownloaderTests` runs against local HTTP servers, never the network. What the test bundles need of the files is under **Build & Test Commands**.

Development-only keys live in `application-dev.conf`. One rule covers them: `Environment.devSwitch` (flags) and `Environment.devSetting` (text) honour a key only in the dev environment and ignore it, with a WARN, anywhere else. They are read once at startup, and `make watch` does not watch `application-dev.conf`: a change takes effect at the next restart, which a change to a watched source brings.
- `dev.user` (a username or an email address) and `dev.password` skip login during frontend work. `UserService.getDevUser` runs bcrypt only until the password first succeeds, then builds the claims from the database on every request (`claimsOf`), so account changes show at once. A failed dev login is not retried for 30 seconds, so it costs one bcrypt check and one audit event, not one per request. An agent's browser check sets the two keys and comments them out after (**Do** in `views/AGENTS.md`).
- `dev.sql_explain=true` logs each new query's plan to `sql-debug.log` (see **SQL explain log**).
- `dev.restart_pipeline=true` restarts a pipeline queue whose stream fails (see **Import Pipeline**).

`Environment.isDev` gates anything that exists in dev only. Two things do:
- The **style guide**: `App.allRoutes` registers `StyleGuideController` only in dev, so its routes are 404s elsewhere, and `includes/nav.scala.html` shows its button under the same check. The page scans the source tree on every request (`StyleGuideScan.scan`, a pure function in `core/util`); `GET /style-guide/scan.json` serves the same scan to the design tweaks panel. Its sample dialogs validate like real ones and persist nothing.
- The **design tweaks panel**: the vendored tokentweak package configured by `static/js/design-tweaks.js`. Its two script tags in `includes/header_common`, under the same check, are commented out, so no page loads it until they are restored.

Controller tests reach the dev routes through a test-only `cask.Main` (`DevApp` in `StyleGuideControllerTests`) and assert that a non-dev app answers them 404 and renders neither the button nor the panel script. The page and the panel are described under **Style guide** and **Design tweaks** in `views/AGENTS.md`.

## Settings

A **Setting** (`CONTEXT.md`) is a system-wide tunable with a default that an Admin edits on the Settings screen. Its one home is the `setting` table (`name`, `value`, `default_value`), seeded in both `all.sql` files; a leftover config key for a Setting is ignored. The registry (name, group, label, help, `SettingType`, `SettingKind`, engine, cross rules) is the companion of `models/Settings.scala`.

- A **Live setting** is used from the next operation that reads it; the one **Restart setting**, `import.parallelism`, from the next server start, capped by `import.parallelism.max` in the server config.
- The Settings with `engine = postgres` (`face.recognition.hnsw_ef_search`, `db.postgres.read_statement_timeout`) are neither shown nor saved on SQLite, and their cross rules are not judged.
- A Setting is stored and shown as the text that was saved, so a `Decimal` must be a plain decimal (`SettingType.PLAIN_DECIMAL`). Other forms a JVM reads as a finite number (an exponent, hexadecimal, a type suffix) fail as "Must be a plain decimal, with no exponent", not "Must be a number". Hence the Describe match threshold's default is `0.00009` everywhere, never the JVM's `9.0E-5`.
- `Settings.validate(values, engine)` returns the error of every failing field. A cross rule is judged only when both its fields pass their own rules and its field applies to the engine.

`SettingsService` (`Altitude.settings`) holds the values as one immutable typed snapshot (`Settings`), replaced whole on every `load()` and `save()`, so a reader never sees a half-written set. Loads and saves are `synchronized`; readers never wait.

- It is constructed empty, before the transaction manager, and loaded after the migration; until then `currentIfLoaded` is `None` and `current` and `atStartup` throw.
- `atStartup` is the first load's snapshot, the running value of a Restart setting; `pendingRestart` lists those whose saved value differs from it.
- `save(values)` trims and merges over the current set (a Setting not submitted keeps its value), and validates. Any failure throws `ValidationException` naming every failing field and writes nothing. Otherwise it writes only the changed rows in one transaction, logs each change at INFO with old and new value, and swaps the snapshot. A value spelled differently (`0.850` for `0.85`) is not a change, for the write and for the restart notice alike.
- `load()` fails on a missing or invalid row and only WARNs on a row the registry does not know, so a retired Setting does not block startup.

A reader takes its value from `app.settings.current` when it needs it, never in a constructor, and from one snapshot per operation (one `extractFaces`, one Video, one Curation set, one Describe page). A class built without `app` takes a getter: `() => Settings` (`VideoService`, `GeocoderService`), or `() => Option[Settings]` for `TransactionManager`, which sets the read statement timeout and `hnsw.ef_search` per transaction only once loaded. No DAO holds a Setting: the caller passes the values in (`FaceDao.searchClosestFaceMatches`). `Altitude.importParallelism` reads `atStartup` once, before the actor system is built. An import in flight picks up a changed Live setting at its next stage. The face quality thresholds never re-tier Faces already stored.

The screen is `GET /settings/r/:repoId` (`SettingsController`) and its form's save, `POST /htmx/settings/r/:repoId` (`SettingsFormController`, whose `form` also renders the form for the page), both `@requireLogin() @requireAdmin()` (a User or a Guest gets the gate's 403: **Permissions on routes**).

- The form posts JSON (`hx-json-enc`). The controller reads only the applicable Settings; it stringifies a JSON boolean or number (a number in plain notation, `plainText`: `0.00002`, never `2.0E-5`), reports any other JSON type as `INCORRECT_VALUE_TYPE`, and takes an absent checkbox as `false`.
- A failed validation is `dialogFormValidationResponse` with the form over the submitted values and the errors beside their fields; a success answers the saved form.
- `form` passes `Altitude.importParallelismResolution` as a note on `import.parallelism`, so the screen always shows what is running and why.
- Markup, Reset, the restart notice, the save event and the Admin-only nav link (why `NavController` requires login): see **Settings screen** in `views/AGENTS.md`.

Mill is run as `./mill` (`mill.bat` on Windows), its own bootstrap script, which downloads the version `build.mill`'s header names; the `Makefile` calls it, never an installed `mill`. `.gitattributes` pins `mill` and every `*.sh` to LF and `mill.bat` to CRLF, whatever the clone's `core.autocrlf`: the `Dockerfile` copies `mill` into a Linux build stage as it is checked out, where a CRLF shebang line fails the build. A new script run inside an image, or by `sh` or `bash`, that is no `*.sh` gets a line there. Every target that starts the server or the tests sets `ALTITUDE_ENV` (**Config & Environments**): a `./mill altitude.run` by hand runs as prod without it.

> **Run `make test` only when the `altitude-core-postgres-test` container is up.** Otherwise use `make test-local` or one bundle.
> **Do not run tests if only the frontend was changed** (Twirl templates, CSS, JS, HTML); verify it in the browser. The one exception is a module that `scripts/test-js/` imports (the DOM-free modules of `static/js/edit/`, `common/content-urls.js`, `common/histogram.js`, `stores/search-params.js` with `constants.js`): run `make test-js`, which takes seconds.

The stylesheet (its rules: **Do** in `views/AGENTS.md`) is a build output: `cssBundle` in `build.mill` inlines `static/css/app.css`'s `@import`s into `assets/app.<hash>.css`, and `assetManifest` compiles its URL in as `Assets.appCss`. `StaticController` serves only that name under `/assets/`, and everything else (vendored CSS, fonts, JS modules) under `/static/` (their caching: **Request Lifecycle**). So a CSS edit needs a recompile and a restart (`make watch` does both); `./mill altitude.resources` refreshes JS but leaves the running server linking the old CSS name, which answers 404.

**Packaging.** Compile, run and test take the build machine's native libraries (`detectPlatform()` in `build.mill`, which fails on an Intel Mac: ONNX Runtime ships no natives for one, and Altitude runs there in Docker). The build compiles for Java 21 (`-release 21` for scalac, `--release 21` for javac), the floor the jar runs on, so an API newer than that fails the compile whatever JDK builds.

- **The native jars.** `./mill altitude.platformJar` → `platformJar.dest/altitude-<version>-<platform>.jar`, the fat jar of `ALTITUDE_PLATFORM`, started with `java -jar` (no start script is prepended). `make dist-jars` runs it for each of the four platforms on this one machine and copies each jar to `out/dist-jars/`, since each run replaces the task's folder. Started with no flag a jar runs as prod and logs by `logback.xml`.
  - Its inputs: the launcher's class, `distLib`'s `altitude.jar` and `lib/` in the classpath's order, the platform's bytedeco classifier jars as they are (javacpp loads from `org/bytedeco/<preset>/<platform>/` and unpacks into its own cache), and `platformNatives`: ONNX Runtime's folder of the platform (`ai/onnxruntime/native/<folder>/`, no `.dSYM`), sqlite-jdbc's one library and sqlite-vector's one build, each under the path its loader looks on the classpath. The task fails when an entry is another platform's bytedeco folder or a native library outside those paths.
  - `mill.javalib.Assembly` merges them by `platformJarRules`: `reference.conf` and the `META-INF/services/` files concatenated (`java.sql.Driver` names both drivers), and so are the licence and notice files that many jars hold under one name (`META-INF/LICENSE*`, `META-INF/NOTICE*`, and `LICENSE*` and `NOTICE*` at the root), since an Apache-licensed jar's `NOTICE` must travel with its code; the inputs' manifests, signatures, `INDEX.LIST` and `module-info.class` dropped, the first of any other name winning. The jar is then written again in name order with one fixed entry time, so the same inputs give the same bytes.
  - Its manifest: `Main-Class: altitude.launcher.Launcher`, `Altitude-Platform`, `Altitude-Build` (the first 16 hex digits of a SHA-256 over the native entries' names, lengths and bytes in name order: the same natives give the same value), `Implementation-Version`, `Enable-Native-Access: ALL-UNNAMED` (Java 22 and later load the natives without a warning; it applies to a `java -jar` start alone) and `Multi-Release: true` (the classes some dependencies hold for newer Java versions load as from their own jars).
  - **Its natives at runtime** (`NativeLibraries`, early in the start, after the logging check). ONNX Runtime's, sqlite-jdbc's and sqlite-vector's libraries are unpacked once, flat, into `natives/<Altitude-Build>-<Altitude-Platform>/` in the per-user cache (`UserCache.folder`: `$XDG_CACHE_HOME/altitude`, else `~/.cache/altitude`), beside the models' default folder whatever `models.dir` says, and the start sets `onnxruntime.native.path`, `org.sqlite.lib.path` with `org.sqlite.lib.name`, and `altitude.native.dir` to the folder. Left to themselves, ONNX Runtime and sqlite-jdbc copy theirs into the temp folder at every start (about 30 MB), which a killed run leaves there and which on Windows, where a loaded library cannot be deleted, even a clean stop leaves; ONNX Runtime still makes an empty `onnxruntime-java*` folder there, which the JVM's exit removes. Under the lock file `natives/.lock` (`LockFile.locked`, as the model files have it) a start removes the `.part` files a killed unpack left, writes each library whose file is missing or not its entry's length to a `.part` and moves it to its name, so a name always holds a whole library and a library in place is never written again; then it touches its folder and removes the folders of other builds untouched for 30 days. A running instance keeps its folder fresh on either engine: `Altitude` schedules `NativeLibraries.touchInUse` every day on the actor system's scheduler (`TOUCH_EVERY`), only where the start unpacked, and `cleanup()` cancels it. Without it a long-running instance's folder could be pruned under it: on SQLite each connection a pool replaces loads sqlite-vector from it, and on Windows a prune deletes what no process holds open and leaves a partial folder. A property that is set already is kept, and with all of them set, as the image's `jvm-options` set them, nothing is unpacked, touched or pruned, and the cache is never looked up: the image's root filesystem is read-only and its home folder may not be writable. Outside a jar whose manifest names a build and a platform (Mill's `run`, the tests, any jar but a platform jar), it does nothing. A folder that cannot be written fails the start, naming it. javacpp's libraries are javacpp's, unpacked into its own cache (`~/.javacpp/cache`). Tests: `NativeLibrariesTests` (unit), over jars written for each test.
  - **The launcher** (`launcher/src/altitude/launcher/Launcher.java`, the root `launcher` Mill module) is one Java class compiled with `--release 8` and nothing on its classpath, so any Java from 8 on runs it before a class of the application loads. A Java older than 21 is told what to install; a jar of another platform than `os.name`/`os.arch`'s names the jar to download, or Docker for an Intel Mac, Windows on ARM (or the x64 jar on an x64 Java, emulated) and any system with no build; each exits with status 1. Those come from the JVM, not the machine: an Intel Java on Apple Silicon (Rosetta) reports an Intel Mac, so that refusal also says to install an arm64 Java, first of all when the jar is `macosx-arm64`, and a 32-bit Java is told to install a 64-bit one if the machine is 64-bit. Run from a classes folder it has no `Altitude-Platform`, and checks the Java version alone. With `ORT_DISABLE_TELEMETRY=1` it calls `altitude.core.App.main` by reflection (the `altitude.launcher.main` property names another class, for its tests). Without it, it starts the same JVM once more: `java.home`'s `java`, the runtime's input arguments, `-jar` and the jar when started from it (else `-cp` and `java.class.path`), the same arguments, the variable added and `JDK_JAVA_OPTIONS`, `JAVA_TOOL_OPTIONS` and `_JAVA_OPTIONS` removed (their options are among the input arguments already), input and output inherited; it exits with that JVM's status, and with 143 when it is stopped. Every input argument goes to both JVMs, so where they start something meant for one process (an agent: `-javaagent:`, `-agentlib:`, `-agentpath:`; a debugger's port, `jdwp`; a JMX port; a flight recording, `-XX:StartFlightRecording`), it first says that setting `ORT_DISABLE_TELEMETRY=1` skips the second JVM (`relaunchHint`). Its shutdown hook, registered before the second JVM starts, passes a stop on (`Process.destroy`, a SIGTERM on Linux and macOS) and waits for the second JVM's drain; on Windows, where `destroy` kills, it only waits, since a console's Ctrl-C reaches both. The hook and the start hold one lock, and the hook sets a flag under it: a stop before the start starts no second JVM, and one during the start reaches the second JVM once it has started, so none is left running. Tests: `LauncherTests` (unit), with `LauncherStub` in place of the application.
  - **The smoke test.** `make smoke-jar` (`scripts/smoke-jar.sh`, whose header lists what it needs and its `JAR`, `JAVA`, `ALTITUDE_MODELS_DIR`, `START_TIMEOUT`, `STOP_TIMEOUT` and `KEEP` variables) copies this machine's platform jar (or `JAR`, or its argument) into a scratch folder and starts it with `java -jar` from another, as a person would: a scratch home folder (`HOME` and `-Duser.home`, since Java takes `user.home` from the account and javacpp caches under it), user cache (`XDG_CACHE_HOME`) and temp folder (`TMPDIR`, `TMP`, `TEMP` and `-Djava.io.tmpdir`), the models folder named, a free port, no other `ALTITUDE_` variable and no `ORT_DISABLE_TELEMETRY`, so the launcher's second JVM is part of what it tests. It runs Setup, imports photos with faces and a video, stops the jar, starts it again and stops it once more, and checks that the server listens on loopback addresses alone (the start's line, and every socket listening on the port by `ss` or `netstat`), that the launcher runs it in a second JVM and no JVM of the jar is left once the launcher ends (`pgrep`, and on Windows the process table through PowerShell), that a SIGTERM to the launcher drains the server before the launcher ends with status 143, that `data/` is beside the jar and nothing else is written there or where it was started, that the temp folder is empty after a stop, that the natives are in `natives/<Altitude-Build>-<platform>/` of the scratch cache and the cache holds nothing else (no models, no ONNX Runtime device ID), that the scratch home folder holds javacpp's cache alone and the caller's own home, cache and temp folders gain nothing of Altitude's, and that the second start writes no library and loads from the same folder. It runs on Linux, macOS and Git Bash on Windows. On Windows no signal from outside the console asks a JVM to drain, so its stop is `taskkill /F /T`, the drain and exit-status checks are skipped there, and the temp folder may keep ONNX Runtime's empty `onnxruntime-java*` folder, which a JVM's own exit removes. Run it after a change to `platformJar`, the launcher, `NativeLibraries` or the start.
- **The dist tasks** write what the image's `/app` holds, under `out/altitude/`: thin jars and one platform's natives in a folder, so a start unpacks nothing and the image's root filesystem is read-only.
  - `./mill altitude.distLib` → `distLib.dest/`: `lib/` (the dependency jars, without bytedeco's classifier jars, and with ONNX Runtime's and sqlite-jdbc's rewritten without their natives) and `altitude.jar` (without `sqlite-vector/`). They are the same bytes for every platform and every run (one fixed time on every jar entry), so an image for two architectures compiles once and a rebuilt image reuses the layer of a jar that did not change. The task fails when a jar in `lib/` still holds a native library: a new dependency that bundles natives is added to `nativesInJars`, and `distNative` extracts its libraries.
  - `./mill altitude.distNative` → `distNative.dest/`: `native/`, one flat folder of the target platform's libraries (bytedeco's, ONNX Runtime's, sqlite-jdbc's, sqlite-vector's, and the links javacpp makes when it unpacks, which the libraries are loaded through), and `jvm-options`, the flags that make each load from `/app/native`, the folder's fixed place in the image: `java.library.path`, javacpp's `cacheLibraries=false` and `canCreateSymbolicLink=false`, `onnxruntime.native.path`, `org.sqlite.lib.path` and `org.sqlite.lib.name`, `altitude.native.dir`.
  - `./mill altitude.dist` → `dist.dest/`: both.
- **`ALTITUDE_PLATFORM`** (`linux-x86_64`, `linux-arm64`, `macosx-arm64` or `windows-x86_64`) names the platform `distNative` and `platformJar` package. Unset or empty it is the build machine's, and any other value fails the build, naming the four. It is a `Task.Input`, so the Mill daemon reads each call's value, and nothing `compile` depends on reads it: a switch recompiles nothing.
- **The image.** `make docker` (`docker buildx build --load`: the `Dockerfile`'s cache mounts need BuildKit) builds `altitude:local` for this machine's architecture; with `DOCKER_PLATFORM` it builds the other one's, which needs QEMU for the runtime stage's one `RUN`.
  - The `lib` and `native` stages run on the build machine's architecture and copy the build's inputs by name (`mill`, `build.mill` and `altitude/`; the `native` stage `altitude/resources/sqlite-vector` alone). A build input added outside `altitude/` needs a `COPY` there. `.dockerignore` keeps the tests, the documents, local config and data out of the context.
  - The runtime stage is `eclipse-temurin:21-jre-noble` with the four packages bytedeco's OpenCV and FFmpeg link (GTK 2, ALSA, XCB), without which OpenCV does not load. It runs as UID 1000, which owns the empty `/data`, `/data/db` and `/models`, so a named volume mounted on one is writable. `/app` and all it holds are root's: the user the server runs as, UID 1000 or compose's `user:`, reads them and cannot write them, so nothing run inside the server (a media decoder is the exposed part) can replace a jar or a library, or add one to `lib/*`, for the next start to run, with or without a read-only root filesystem. No `COPY` into `/app` takes `--chown`.
  - It sets `ALTITUDE_HOST=0.0.0.0`, `ALTITUDE_DATA_DIR=/data`, `ALTITUDE_MODELS_DIR=/models`, `LD_LIBRARY_PATH=/app/native` (bytedeco's libraries name each other with no path) and `ORT_DISABLE_TELEMETRY=1`, and passes `-Daltitude.env=prod`, `-XX:+ExitOnOutOfMemoryError`, `-XX:+ErrorFileToStderr`, and `-Djava.io.tmpdir=/tmp/altitude` with `-Daltitude.tmpdir.own=true`. A config file is `/app/application.conf`, beside the jar.
  - The temp folder is where Undertow spools a multipart body and Tika and ImageIO what they read. A run that is killed, crashes or exits on an `OutOfMemoryError` leaves its files there, and `/tmp` is a volume that outlives the run, so every start makes `/tmp/altitude` and empties it (`TempFolder`; a symbolic link is removed, never followed, and the folder is left writable by any user, for a later run under another `user:`). It is a folder under `/tmp` and not `/tmp` itself because the JVM keeps files of its own there whatever its temp folder is (`hsperfdata_<user>`), which a start must not remove from under itself. Tests: `TempFolderTests`, `AppStartTests`, and `make smoke-docker`.
  - Its `HEALTHCHECK` asks `/api/health` on `${ALTITUDE_PORT:-8080}`, with a 15-minute start period for the first start's model download.
- **Compose.** `compose.yaml` (project `altitude-app`) runs the image: the `data` and `models` volumes, `/tmp` as an anonymous volume (the one other place the server can write: Tika and ImageIO spool large files there, in `/tmp/altitude`; compose keeps the volume when it recreates the container, which is why a start empties that folder), a read-only root filesystem, every capability dropped (`cap_drop: [ALL]`) and `no-new-privileges` (the server is an ordinary user's process on a port above 1024 and needs none), `stop_grace_period: 120s` (**Shutdown** in **Library stats and purging**), and PostgreSQL under the `postgres` profile.
  - It passes the variables `.env.example` lists. A variable passed empty is an empty value to Altitude (**Config & Environments**), so each one passed always has a default, but for the PostgreSQL password, whose empty value fails the start on purpose; the two logging variables and the import cap are passed only when set.
  - It does not pass `ALTITUDE_PORT`: the container's port stays 8080, which the health check and the published port (`ALTITUDE_PUBLISH_PORT`) both rely on. A `server.port` in a mounted config file is seen by neither.
  - A setting a person may change under Docker is added in four places: `environment.conf`, `compose.yaml`, `.env.example` and `README-DOCKER.md`.
  - `compose.dev.yaml` and `compose.test.yaml` (project `altitude`) are the dev and test PostgreSQL containers of `make db`, and no part of `compose.yaml`'s project.
- **The smoke test.** `make smoke-docker` (`scripts/smoke-docker.sh`, whose header lists what it needs and its `IMAGE`, `MODELS_DIR`, `START_TIMEOUT` and `KEEP` variables) runs `altitude:local` as the caller's user on a read-only root filesystem with no capability and no new privileges, as `compose.yaml` does, in a container and volumes of its own: Setup, an import of photos with faces and of a video, a stop in the middle of a second import that must drain, nothing unpacked at runtime, native libraries of the image's own architecture alone, and an `/app` that is root's and that the user cannot write. Run it after a change to the `Dockerfile`, the dist tasks or the shutdown, and after an ONNX Runtime upgrade.

Tests read the model files from the dev server's Models directory (see **Model files**), so a machine downloads them once for both. Every test instance ensures the whole set; the unit suites that run a model without an instance use `TestModelFiles.models`, same directory. A machine's first test run therefore starts with a ~1.6 GB download, logged at INFO (`logback-test.xml` lets the downloader's loggers through) so it does not look hung; bundles started together share it through the lock file. Which models a test instance opens: **Scene models in tests**.

Parallel runs (`make test`, `test-local`, `test-focused`) give each bundle its own worker JVM and sandbox (`out/altitude/test/testOnly.dest/worker-N/sandbox`), so each has its own relative `test-data` and only the PostgreSQL bundle touches the test database. Per-worker output is in `worker-N.log` and the merged report in `test-report.xml`, both in `testOnly.dest/`. Wall time is the slowest bundle's: about 4 minutes for `make test`, 3 for `make test-local`.

To focus a test, tag it: `test("my wip test", Focused) { ... }`.

Tag `Slow` a test that seeds a library's worth of rows (`SearchPlans.atScale`), runs a model many times over, or binds tens of thousands of IDs: `test("...", Slow)` with `org.scalatest.tagobjects.Slow` (the per-test tag; `org.scalatest.tags.Slow` tags only a whole `FunSuite`). Every target but `make test-with-slow` and `test-focused*` skips them (`SKIP_SLOW` in the `Makefile`), so a focused `Slow` test still runs: to check a `Slow` test you changed, focus it, since `make test-with-slow` runs only when the user asks for it.

## Test Structure

Integration tests extend `IntegrationTestCore`, controller tests `ControllerTestCore`; fixtures are `TestContext`'s. A bundle's database keeps every test's accounts and Libraries:

- `IntegrationTestCore.beforeEach` marks the instance not set up, in the database and in memory, so a Setup test is not refused for an earlier test's Setup; turns every account's new-Library switch off (a Library created grants each account whose switch is on), persists a fresh repository and a context account (a User with no grant), and gives the test's thread every Permission, as an Admin's request has. A test of a rule that reads Permissions narrows them around its calls (`RequestContext.permissions.withValue`, as `AssetPermissionTests` does).
- A Library name is unique instance-wide (`repository_01`), so `persistRepository` numbers its names across the JVM (`TestContext.nextRepositoryName()`) and a test naming its own Library makes the name unique (a random suffix, as `RepositoryServiceTests` does).
- `persistRepository()` takes no owner and grants nobody access (`TestContext.grant` does, every Permission by default). It records no last active Library: a login lands through `landingRepositoryOf`, and a test of the landing records one itself.
- A test login with an email needs its "@" (`makeUser` gives one), or it is looked up as a username.

Controller tests run against SQLite through a real HTTP server (port 8081) whose instance, `App.altitude`, is a second `Altitude` over the suite instance's file. So `ControllerTestCore.beforeEach` resets the database (`SqliteSuiteBundle.setup()`) and reloads the server's Settings (`App.altitude.settings.load()`). Fixtures are built through the suite's instance, never over HTTP, with every Permission; the server's requests read theirs from the login token. `login()` grants a User every Permission (a Guest none) in the context's first Library when it holds no grant there; a test that wants fewer grants them first or uses `loginAs(accountType, permissions)`, whose caller states all Permissions for an Admin and none for a Guest.

Tests run against both engines via `SqliteSuiteBundle` / `PostgresSuiteBundle` without code changes; every test instance, `StartupTests`' second one included, is built by `TestAltitudeApp.build(dbEngine)`, and `TestDatabase.reset` (wipe, migrate, load the Settings) runs in the bundles' `beforeAll` and `ControllerTestCore.beforeEach`. Other helpers:

- A fixture's dates go through `TestContext.setAssetDates`, which writes each engine's storage form.
- `IntegrationTestCore.contend(first, second)` holds the first transaction open until the second waits on it, for the tests of concurrent writers. `refuse(event, table, rowId)` (a trigger refusing one row's write) and `breakFileStore` / `restoreFileStore` are for the tests of a failure inside a stage.
- `TestContext.letWatchedFilesRest()` lets the next scan read every Watch folder file without waiting out its rest.
- What a test reads of the Import record or a Watch folder beyond what the app reads belongs in `TestContext`, not a service (`imports`, `importFiles`, `watchFolderMemory`, `isWatchFolderWorking`, which a test waits out before it asserts). `isWatchFolderWorking` reads `WatchFolderService`'s in-memory `scanning` and `inFlight` fields by reflection, by name.
- `IntegrationTestCore.withSetting(name, value)(f)` saves its default back afterwards, so other suites see the seeds (`SettingsServiceTests` restores them in `afterEach`). Unit tests build a snapshot with `TestSettings(overrides)` over `TestSettings.seeds`, which `SettingsServiceTests` asserts against the seeded rows.
- `NominatimStub` is the geocoder tests' local endpoint.

**Scene models in tests.** `TestAltitudeApp.build` gives the test instances `SwitchableSceneEmbedder` and `SwitchableDescribeEmbedder` (`ModelSwitch`), off by default: a fixture import carries no Scene embedding, so frames pair by the hash alone and no model pass runs (about 0.75 s an image), and a description has no embedding. A suite whose subject is the embeddings turns a model on for all its tests (`override def usesSceneModels = true` / `usesDescribeModel = true`: `SequenceServiceTests`, and `DescribeSearchTests` for both) or for one test (`withSceneModels { ... }` / `withDescribeModel { ... }`).

- The Scene double opens the real models on the first `turnOn`, on the test's thread, so a model that fails to open fails the suite or test with its own error rather than an import thread's WARN, and a JVM that never turns it on never loads them (about 1.2 GB). It caches the answers by the SHA-256 of the pixels, so the `BurstFrames` imported test after test are embedded once.
- The controller server's instance builds the real ONNX embedders, as production does, so the controller tests of the Describe search need no switch: their fixtures are assets with no file given embeddings at chosen cosines to the server's embedding of the description (`SearchResultsControllerTests.lookingLike`).
- For the unit suites that run a model without an instance, see **Build & Test Commands**.

**Fixtures.** `TestContext.persistAsset` imports a random image through the whole pipeline: a file, a Preview, face detection, Image quality and a hash (it clears the Sequence the import may give it, see **Sequences and Image quality**). `TestContext.insertAsset(asset)` persists, indexes and completes an asset without the pipeline: no file, Preview, faces, Image quality, hash or Scene embeddings, and no Sequence until a test stamps one (`setAssetSequence`). Bulk fixtures whose tests read none of those use `insertAsset` (`CurationServiceTests.longSequence`, `CurationActionControllerTests.frame`, `StatsServiceTests.importedAsset`); a test that reads a file, a Preview or a measurement it does not set uses `persistAsset`.

## Key Files to Know

Only files whose name does not say what they hold. Paths are under `altitude/src/altitude/core/` unless they start with `altitude/` or `scripts/`.

| File | Why |
|---|---|
| `App.scala` | The entry point and every route's registration; its `main` builds the HTTP server |
